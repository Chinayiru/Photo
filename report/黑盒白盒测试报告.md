## 1. 结论摘要

一共确认 **12 项缺陷**：1 项**严重**（跨站读取整库，已在真实生产实例上复现）、5 项**中/中低**（其中 F4 会造成磁盘与数据库长期不一致，F2+F6 会累计导致全站上传被锁死）、6 项**低**。核心问题分三类：

1. **安全边界被自己打开**：CORS 对任意 Origin 回显（`enable_cors()` 默认 `"*"`），叠加 `/panel/**` 只用「来源 IP 是否回环」把关、且全服务无 Host 校验 —— 三者合起来构成一条**从任意网页到整库读取**的完整链路。
2. **未校验的外部数值直达底层库**：`declared_taken_at` 未设边界，`1e300` 能穿过上传全流程，在 `datetime.fromtimestamp()` 处抛 `OverflowError`，把一个上传会话永久卡在 `open`。
3. **`UNIQUE(root_id, rel_path)` 没有 `WHERE missing=0` 部分索引**：已删除行的墓碑占着路径，把照片移动到一个「曾经有同名文件」的目录会 500，并且此时**文件已经搬走、数据库还指向旧路径**。

## 2. F1（严重）CORS 回显任意来源 + `/panel` 只认回环 + 无 Host 校验

### 2.1 三个缺陷单体

**（a）CORS 默认 `*` 且回显调用方**

`backend/app/server.py:156` 以无参形式调用：

```python
router.enable_cors()
```

`backend/app/core/dispatch.py:177` 的默认值是 `allow_origin: str = "*"`，而 `_apply_cors`（`dispatch.py:348-359`）在 `"*"` 时**把请求里的 `Origin` 原样回显**：

```python
def _apply_cors(self, ctx: Ctx, reply: Reply) -> None:
    origin = ctx.headers.get("origin")
    reply.headers["Access-Control-Allow-Origin"] = self._cors["origin"]
    ...
    if origin:
        # 带凭据的请求不能用 "*"，必须回显来源。
        reply.headers["Access-Control-Allow-Origin"] = (
            self._cors["origin"] if self._cors["origin"] != "*" else origin)
        reply.headers["Vary"] = "Origin"
```

实测（8803 实例，未认证）：

```
GET /api/system/ping  Origin=https://evil.example.com   -> [200] ACAO='https://evil.example.com'
GET /api/system/ping  Origin=null                       -> [200] ACAO='null'
GET /api/system/ping  Origin=http://127.0.0.1:9999      -> [200] ACAO='http://127.0.0.1:9999'
```

任意 Origin（包括 `null`、任意端口、任意域名）都被逐字回显，**不存在白名单**。

**（b）`/panel/**` 的唯一边界是「来源 IP 是回环」**

`backend/app/auth.py` 的 `auth_middleware` 对 `/panel` 前缀只做 `is_loopback(ctx)` 判断，没有 token、没有本地会话：

```python
ip = (ctx.client_ip or "").strip().lower()
if ip.startswith("::ffff:"):
    ip = ip[7:]
return ip in ("127.0.0.1", "::1", "localhost", "")
```

这意味着**在运行 PhotoBridge 的那台电脑上打开的任何网页**，其请求的来源 IP 就是 `127.0.0.1` —— 对服务端而言与用户自己点面板完全无法区分。

**（c）全服务没有 Host 校验**

`grep -rn "trusted_host\|TrustedHost\|allowed_hosts" backend/app` 只命中绑定地址与状态展示，**没有任何 Host 头校验**。因此 DNS rebinding 也能成立。

### 2.2 组合成完整攻击链（实测通过）

用一个「网页能发出的请求」逐级验证（8803 实例，`delete_to_recycle_bin=true`，与用户真实配置一致）：

```
POST /panel/pair-code   Origin: https://evil.example.com   Host: evil.example.com:8803
  -> [201]  ACAO='https://evil.example.com'   body: {"code":"809862", ...}

POST /api/pair          Content-Type: text/plain;charset=UTF-8   body: {"code":"809862"}
  -> [201]  client_token=<64 字符>, set-cookie: pb_token=...; Max-Age=7776000

GET /api/timeline        Authorization: Bearer <token>   Origin: https://evil.example.com
  -> [200]  ACAO 回显，照片列表可读
GET /api/items/{id}/raw  -> [200]  真实照片字节可读
```

关键点在于**第一步**：攻击者不需要用户输入任何配对码 —— 它自己从 `/panel/pair-code` 现取了一个。取到码之后 `/api/pair` 就不需要任何凭据了。

`ctx.json()`（`backend/app/core/ctx.py:299-312`）**不检查 Content-Type**，只要求 body 是 JSON 对象。所以配对、移动、重命名、删除这些纯 JSON 接口，都能用 `text/plain` 这个「CORS 简单请求」的内容类型发出去，**绕过预检**。

### 2.3 边界（不夸大）

**预检确实不通过**，这是浏览器侧唯一的实质屏障：

```
OPTIONS /api/pair   -> [405]  access-control-allow-methods: None
OPTIONS /api/timeline、/api/items/delete、/panel/pair-code、/api/uploads/init -> 全部 [405]
```

所以：
- ✅ 可跨源：GET/HEAD/POST，无自定义头，body 为 `text/plain` 等简单类型 —— 即**读列表、读原图、配对、移动、重命名、删除**。
- ❌ 不可跨源：需要 `Authorization` 头或 `application/json` 的请求（会被预检拦住）。

但攻击者**不需要**带 token：它自己刚 mint 了一个。所以「`Authorization` 触发预检」这条防线在 F1 的链路里形同不存在。

补充两个诚实的限定：
1. 上述链路是用 HTTP 客户端按浏览器的实际报文逐字构造并验证的，**没有**在真实浏览器里跑端到端页面。
2. 较新版本 Chrome 的 Private Network Access（PNA）可能对「公网页面 → 本地回环」追加自己的预检；Firefox / Safari / 旧版 Chrome 无此限制。这不是本服务提供的防护，不能计入安全设计。

### 2.4 生产实例上同样成立

在用户的真实运行实例上（`dist\PhotoBridge\PhotoBridge.exe`，监听 `0.0.0.0:8787`，真实库 `D:\Photos`）只做只读探测：

```
GET /api/system/ping   Origin=evil -> [200] ACAO='https://evil.example.com'
GET /panel/devices     Host=evil.example.com:8787 -> [200] ACAO='https://evil.example.com'
     body: {"device_id":"40d30eceecdf4e11","device_name":"YiRu","items":[]}
OPTIONS /api/pair      -> [405] ACAO='https://evil.example.com'
```

即：**真实生产实例上，任意网页都能读到配对面板，并据此换取 90 天有效期的 token。** 探测期间 mint 出的配对码已通过再调一次 `/panel/pair-code` 作废（`revoke_all_codes`），未留下可用凭据。

### 2.5 与自身文档的冲突（这是「回归」而非「设计取舍」）

`docs/06-安全设计文档.md` 明确禁止，实现却反着来：

- `:3349` 「④恶意站点无法设置 `Authorization` 头（自定义头触发 CORS 预检，**而本服务不返回宽松 CORS 头**）」—— 实测本服务**确实**返回宽松 CORS 头。
- `:3367` 「一期**不存在跨源请求，也不需要 CORS 白名单**」—— 代码却默认开着 `"*"`。
- `:3824` 「### 规则 15：CORS 绝不用 `*`」，`:3835` 「检查：grep `allow_origins=["\*"]` → 必须为空」。
- `docs/07-测试计划与用例.md:2344` `TC-LINT-SEC-016`（P0）：`grep -rn 'allow_origins=\["\*"\]' backend/ cloud/` 期望**无结果**。

这条 lint 规则**因为写法而空过**：代码里没有 `allow_origins=["*"]` 这个字面量，只有 `enable_cors(allow_origin: str = "*")` 的关键字默认值。**规则被语法绕过，不是被遵守。**

**一个必须说清楚的细节**：`/panel/**` 的来源限制**确实按文档实现了**。`docs/04-接口设计文档.md:4116-4120` 曾把「同网任何设备都能调 `/panel/pair-code`」列为已知安全设计缺失并给出对策（「必须校验 `request.client.host ∈ {127.0.0.1, ::1}`」），代码里 `is_loopback` 逐字实现了这个对策。

所以 F1 的性质比「漏做」更严重：**按文档做对了的防护，被 CORS 配置从侧面架空。** 文档做风险分析时假设「同网设备」是威胁源，没料到威胁源是**运行 PhotoBridge 那台电脑上的浏览器** —— 而那个连接的 `client_ip` 恰恰是 `127.0.0.1`，`is_loopback` 必然放行。

更关键的是唯一相关的测试**把这个 bug 写成了期望行为**：

```python
# backend/tests/test_core.py:504-510
def test_cors_echoes_origin_when_present(router: Router) -> None:
    """带凭据的请求不能用 "*"，必须回显来源。"""
    router.enable_cors()
    r = run(router.dispatch(Ctx("GET", "/api/system/ping",
                                headers={"Origin": "http://localhost:5173"})))
    assert r.headers["Access-Control-Allow-Origin"] == "http://localhost:5173"
```

注释本身说的是对的话（带凭据不能用 `*`），但正确做法是**白名单 + `Vary: Origin`**，而不是「谁来就回显谁」。所以 888 条测试全绿，**恰恰因为测试断言了错误行为**。

### 2.6 修复建议

1. **默认关闭 CORS**：`enable_cors()` 的默认值改为「不启用」，或改为显式白名单（本项目一期是同源，`docs/06:3367` 自己也这么说）。`server.py:156` 无参调用应删除。
2. **加 Host 校验**：只接受 `127.0.0.1`/`localhost`/本机实际 LAN IP + 配置端口的 Host 头，其余 421/404。这是防 DNS rebinding 的唯一有效手段。
3. **`/panel/**` 不能只靠 IP**：应改为「回环 IP **且** 携带面板专用一次性令牌（托盘打开浏览器时注入）」，或干脆只监听 Unix socket / 只接受带 `Origin: null` 的 `file://` 页面。
4. **`ctx.json()` 校验 Content-Type**（至少拒绝 `text/plain` 解析 JSON），把「简单请求」这条路堵掉。
5. **补一条真正有效的 lint**：`grep -rn 'enable_cors' backend/` 必须只出现「显式白名单」形式；并把 `test_cors_echoes_origin_when_present` 改成「非白名单 Origin **不**回显」。

## 3. F2（中）`declared_taken_at` 无边界 → 归档 500 + 会话永久卡死

### 3.1 事实链

`handlers/uploads.py:233` 的 `_opt_float` 只做「能不能解析成 float」，**没有任何范围检查**：

```python
def _opt_float(v): ...   # 接受 int/float/数字串；1e300、1e400(→inf)、NaN 全部通过
```

该值被原样写进 `media.taken_at` / `upload_sessions.taken_at`，直到归档时才在 `archive.py:74` 炸掉：

```python
dt = datetime.fromtimestamp(taken_at)   # OverflowError: timestamp out of range for platform time_t
```

实测：

```
init  declared_taken_at=1e300  -> [201]  upload_id=5d01e853960440f4aee283a07a761d73
patch                          -> [206]
complete                       -> [500] E3001 internal_error, detail=null
session now: status='open' complete=True received=85/85
orphan .part files left in .photobridge_tmp: 1
```

日志栈：

```
File "D:\Photos\backend\app\archive.py", line 74, in archive_dir
    dt = datetime.fromtimestamp(taken_at)
OverflowError: timestamp out of range for platform time_t
  <- uploads.py:789 _place_sync
  <- uploads.py:869
  <- uploads.py:883 loop.run_until_complete(coro)
  <- archive.py:327 dir_rel = "/".join(p for p in (prefix, archive_dir(taken_at)) if p)
```

### 3.2 为什么这一条的破坏力超出一个 500

1. **会话永久卡在 `open`**：`complete` 失败但状态没回滚，`received==total` 且 `complete:true`，可每次重试仍然 500。用户看不到任何可操作提示。
2. **占死并发额度**：`MAX_OPEN_SESSIONS = 3`（`uploads.py:70`，检查点 `:438`）。卡 3 个就**全站上传被拒**：

   ```
   -> [429] E4002 同时上传的任务太多，请等前面的传完
   ```
   `purge_expired`（`uploads.py:141`）只清理超过 24 小时过期的会话，所以这个自锁会持续一天。
3. **临时文件泄漏**：`.part` 留在库里，只有 `abort_session` 才清。
4. **前端不会兜底**：见 F6 —— 上传失败不会 `abort`，所以现实里「失败三次 → 再也传不上去」很容易发生。

### 3.3 修复建议

1. `_opt_float` 加范围：`declared_taken_at` 落在 `[1970-01-01, now+1天]`（或 `[0, 4e9]`）之外直接 400 E1001；拒绝 `inf`/`nan`（`math.isfinite`）。
2. `archive.archive_dir` / `archive_name` / `candidate_names` 三处 `fromtimestamp` 统一包一层，越界回退到 `time.time()` 并记 warn —— 归档时间戳错一次不该让整次上传失败。
3. `complete_session` 用 `try/finally` 保证异常时把状态置为 `failed` 并 `unlink` 临时文件，不要留 `open`。
4. 把 `MAX_OPEN_SESSIONS` 的检查从「计数」改为「计数 + 自动回收超过 N 分钟无进展的 open 会话」。

## 4. F3（中）索引器不校验魔术字节

上传路径有 `check_magic()`（`uploads.py`，`MAGIC_HEAD_BYTES=32`），**索引器没有**。`indexer.py:118 should_index(name, root)` 只判 `_is_excluded_file` 与扩展名：

```python
def should_index(name: str, root: RootConfig) -> bool:
    ...
    return _ext_of(name) in root.include_exts
```

实测：往库里直接写 51 字节 HTML，命名 `planted_final.jpg`，触发 `POST /api/index/rescan`：

```
search -> [200] 1 hit(s)
GET /api/items/127/raw -> [200] ct='image/jpeg' nosniff='nosniff' len=51
body=b'<html><body><script>alert(1)</script></body></html>'
```

同样字节走**上传**接口则被正确拒绝：

```
complete -> [400] E1017 文件内容与扩展名不符（声明 .jpg，实际 无法识别）
```

**同一个文件，走 A 路被拒、走 B 路被收录并以 `image/jpeg` 端出。** 触发 B 路的现实途径很多：SMB 拷入、U 盘、其他程序写入，以及**本程序自己的 `/api/items/rename`**（只校验扩展名，不重读内容 —— 上面 F10 的 RTL 例子就是这么落盘的）。

风险等级没有更高，是因为 `X-Content-Type-Options: nosniff` 恒定下发（`dispatch.py:277`），浏览器不会把 `<html>` 当 HTML 执行；前端也没有任何 `v-html`/`innerHTML`（`grep` 干净，`ViewerView.vue` 只用 `<img :src>`）。**但「内容类型说谎」本身仍是缺陷**：用户会看到一张永远打不开的图，而 detail 接口报告它 `kind='image'`、`w=null h=null`，无从判断原因。

**修复建议**：索引时对前 32 字节做 `sniff_kind`，与扩展名不符则不入库（或入库但标 `corrupt` 并在列表里显示为「非图片」）。成本极低 —— 只读 32 字节，不增加全量哈希开销。

## 5. F4（中）墓碑行占路径：移动/重命名 500 + 磁盘与 DB 长期不一致

### 5.1 根因

`backend/app/db.py:86`：

```
UNIQUE(root_id, rel_path)
```

**没有 `WHERE missing = 0` 的部分索引**。已删除的照片只被 `UPDATE media SET missing = 1`（`browse.py:813`）打上标记，行**留在表里继续占用 `(root_id, rel_path)`**。

移动接口在文件已经搬走之后，才做一次裸 `UPDATE`（`browse.py:1141`）：

```python
db.execute(
    "UPDATE media SET rel_path = ?, file_name = ? WHERE id = ?",
    (dst_rel, name, mid),
)
```

这一句在 `try` 之外（`try` 覆盖到 `:1136`），没有 `IntegrityError` 处理（对照索引器 `indexer.py:608`、`:642` 都有 `ON CONFLICT` / `except IntegrityError`）。于是撞上墓碑就抛 `sqlite3.IntegrityError: UNIQUE constraint failed: media.root_id, media.rel_path`。

更值得注意的是 `browse.py:1102-1109` 挑选候选名时**明确加了** `missing = 0`：

```python
taken = {r["file_name"] for r in db.query(
    "SELECT file_name FROM media WHERE root_id = ? AND rel_path LIKE ? AND missing = 0", ...)}
```

也就是说：**代码在两处对「墓碑算不算占位」给出了相反的答案。** 选名时不把已删除的行当占位，写库时唯一索引又把它们当占位。

### 5.2 实测（决定性复现）

```
A id=128 at 'tombfinal/2026/2026-10/20261017_125436.png'
move -> [200] to='tombfinal_flat/20261017_125436.png'
delete -> [200] {"deleted":1,"failed":[]}     # 墓碑留在 tombfinal_flat/20261017_125436.png
B id=129 上传时直接用墓碑的同名文件
move B -> [500] E3001 internal_error, detail=null, retryable=true

rows:
  id=128 missing=1 rel_path='tombfinal_flat/20261017_125436.png'  on_disk=True
  id=129 missing=0 rel_path='tombfinal_src/2026/2026-10/20261017_125436.png'  on_disk=False
```

注意最后两行：**`id=129`（用户以为移动成功的那张照片）的数据库路径指向一个不存在的文件，而真实文件正躺在墓碑的路径上。** 由于 `browse.py:1125` 是「先搬文件再改库」，`UPDATE` 失败时文件已经搬完 —— 磁盘和数据库就此分叉。下一次扫描会把 129 标成 `missing`，用户会以为「照片丢了」。同时 `id=128` 这条墓碑的 `on_disk=True`，扫描会把它「复活」并赋一个新 id，缩略图缓存也随之错位。

### 5.3 修复建议

1. **改部分唯一索引**：`CREATE UNIQUE INDEX ... ON media(root_id, rel_path) WHERE missing = 0`。这是最小改动，与 `browse.py:1106` 已有的语义一致，也与 `idx_media_sha` 用 `WHERE sha256 IS NOT NULL` 的既有风格一致。需要写迁移（并处理历史数据里可能已存在的重复 `missing=1` 行）。
2. **或者**删除时直接删行（`docs/04 §4.4.1` 本来就是这么要求的，见 F9）。
3. **把 `UPDATE` 包进异常处理**：撞唯一约束时回滚文件（`os.replace` 反向搬回）并返回 `failed[{code:"E3012"}]`，不要 500、不要留分叉。
4. 补回归测试：**「移动到曾删除过同名文件的目录」**。现有 888 条测试没有覆盖这个组合（`test_move_rename.py` 只覆盖磁盘冲突与库内冲突，不覆盖墓碑）。

## 6. F5（中低）已删除照片的缩略图继续以 1 年 `immutable` 端出

`get_thumb` 在 `browse.py:242` 的查询里**取了** `missing`，但只用来「决定要不要生成」，不决定「要不要给」。缩略图文件本身从不随删除清理（全仓 `grep thumb_path` 无任何 unlink/drop）。

实测（真实照片 media 62）：

```
BEFORE delete: thumb -> [200] etag="w320-1792174943603084-3143"
                       cache-control='private, max-age=31536000, immutable'  188B
delete        -> [200] {"deleted":1,"failed":[]}
AFTER  delete: thumb -> [200] etag="w320-1792174943603084-3143"
                       cache-control='private, max-age=31536000, immutable'  188B
conditional GET -> [304]      # 已删除的照片被浏览器缓存钉住一年
raw            -> [404]       # 这一条是正确的
```

对比之下 `get_raw` 在 `browse.py:471` 有 `if row["missing"]: raise NotFound`，是对的。同一行数据，两个接口给出相反答案。

需要说明的是：`handlers/common.py:113-120` 明确记录「`missing=1` 返回 200 + `missing:true` 是**有意**的」（让手机显示「照片已不在」占位符，以便与「记录不存在」区分）。所以问题不是「返回 200」，而是：

1. 返回的是**真实图片**而非占位符；
2. 带着 `max-age=31536000, immutable` —— 删除后一年内手机上还是那张图；
3. 缩略图缓存文件永不清理（审计实例实测：`missing=0` 存活行 59 条、总行 130 条，而 `data/thumbs` 下有 205 个文件 —— 删除的行把缩略图留在了磁盘上）。

**修复建议**：`missing=1` 时直接返回 `placeholder_webp` 且 `Cache-Control: no-store`（占位符可以随手重算，不需要缓存）；或删除时同步 `thumb_path(...).unlink(missing_ok=True)`；并在 `data/thumbs` 上加一个「孤儿清理」到维护脚本。

## 7. F6（中）前端上传失败从不 abort 会话

`frontend/src/stores/upload.ts:213-227` 的 catch 分支：

```ts
} catch (e) {
    ...
    task.status = "FAILED";
    task.error = err?.friendly ?? (e instanceof Error ? e.message : "上传失败");
    ...
}
```

只在本地把状态标成 `FAILED`，**没有** `DELETE /api/uploads/{id}`。`api.del`只出现在显式的取消路径（`upload.ts:357`，`cancelTask`）。

后果：任何一次失败（网络抖动、服务端 500、F2 那种归档异常）都会在服务端留下一个 `open` 会话。`MAX_OPEN_SESSIONS=3`，所以**连续三次失败之后，用户再也传不上任何东西**，且错误提示是 `429 E4002 同时上传的任务太多，请等前面的传完` —— 而实际上前面并没有任务在传。

**修复建议**：`FAILED` 分支里补一次 `api.del`（失败可忽略）；或在 init 时记录会话并在 `retryTask` 里复用 —— 现有 `_reconcile_offset` 已经能处理续传，关键是别让废弃会话一直占额度。

## 8. F7–F12（低）其余缺陷

### F7 未知 `root_id` → 500

```
root_id='nope'         -> [500] E3001 detail=None
root_id='../library'   -> [500] E3001 detail=None
root_id='LIBRARY'      -> [500] E3001 detail=None
```

根因：`config.py:350` 抛 `ConfigError`，而 `errors.py` 的 `to_app_error()` **没有任何 `ConfigError` 映射**，于是落到兜底 E3001。调用点：`uploads.py:372`（init）、`:127`、`:224`。
修复：`to_app_error` 增加 `ConfigError → E1004/E1001(400/404)`；或 init 里先 `has_root(root_id)` 再取。

### F8 `media_id` 超出 int64 → 500

```
GET /api/items/9223372036854775807   -> [404] E1004   （正确）
GET /api/items/9223372036854775808   -> [500] E3001
GET /api/items/99999999999999999999  -> [500] E3001
```

`core/ctx.py:314 param_int` 只做 `int(raw)`（Python 任意精度，永远成功），值再绑进 SQLite 才抛 `OverflowError: Python int too large to convert to SQLite INTEGER`。它自己的注释写着「失败抛 400（而不是 500）」，但漏了溢出这一档。
修复：`int(raw)` 后加 `-2**63 <= v <= 2**63-1` 判断。

### F9 删除接口响应与 `docs/04 §4.4.1` 不一致

```
实测:  POST /api/items/delete -> {"deleted":1,"failed":[]}
docs/04 §4.4.1 承诺: deleted:[ids], already_missing:[], not_found:[], failed:[{id,code,message}], db_removed:N
                     语义: 「文件进回收站 + DB 行删除（不是标记 missing）」
```

实现是「标记 `missing=1`」，且 `deleted` 是整数而非数组，另三个字段缺失。**前端与实现一致**（`frontend/src/api/types.ts:321-323` 声明 `deleted: number`），所以错的是**文档**。这也正是 F4 墓碑问题的来源 —— 如果按文档删行，唯一索引冲突就根本不存在。
修复：二选一，但必须让 docs/04 与实现一致；推荐按文档删行（可顺带消掉 F4）。

### F10 重命名接受 RTL override 文件名

```
POST /api/items/rename {"new_name": "x\u202eegap.png"} -> [200]
  -> to='手机上传/2026/2026-10/x‮egap.png'   on_disk=True
```

`U+202E`（RIGHT-TO-LEFT OVERRIDE）会让文件名在资源管理器/相册里显示成反序，可用于伪装（例如让 `.png` 看起来是别的类型）。同一接口对 `CON.png`（`[400] E1009`，`detail="CON.png"`）和 NUL（`[400] E1009`，`detail="\u0000"`）的拒绝是正确的，说明校验链存在、只是没覆盖 bidi 控制字符。
修复：在 `sandbox` 的字符校验里拒绝 `Cf` 类格式字符（至少 `U+202A–U+202E`、`U+2066–U+2069`）。

### F11 `is_loopback` 把空 IP 当回环

```python
return ip in ("127.0.0.1", "::1", "localhost", "")   # auth.py:568-579
```

空串（以及 `None` → `("" or "").strip()`）返回 `True`。当前 HTTP 适配器 `local_http.py:74` 会写 `request.client.host or ""`，正常情况不会为空；但任何未来的传输层（隧道适配器、测试桩、Unix socket、某些 ASGI 部署）只要留空 `client_ip`，就**直接获得 `/panel/**` 的访问权**。这是 F1 的纵深防御底座，建议改成显式 `if not ip: return False`。

### F12 「根」参数命名不一致，错误字段被静默忽略

`rescan` / `timeline` / `folders` / `search` 用 `root`（`browse.py:1318`、`:116`、`:553`、`:656`），**且校验是正确的**：

```
POST /api/index/rescan {"root":"nope"}    -> [400] E1001 未知的 root：nope
POST /api/index/rescan {"root":"library"} -> [202] {"started":true,"root":"library",...}
GET  /api/timeline?root=nope              -> [400]
```

但上传接口同时接受 `root` 和 `root_id`（`uploads.py:71`），而 `rescan` 只认 `root` —— 传 `root_id` 会被**静默忽略**并退化成「扫全部」：

```
POST /api/index/rescan {"root_id":"nope"} -> [202] {"started":true,"root":null,...}
```

对一个「指定根」的请求返回「扫全部」的 202，属于会误导调用方的静默降级。修复：统一参数名，或对未知字段返回 400。

## 14. 一句话总结

这套代码在**「单个函数做对」这件事上完成度很高** —— 沙箱七步校验、分片协议的 14 种畸形输入、配对锁定、原子归档、错误脱敏，这些都是硬功夫，而且注释里写清了每处是为了防哪个真实事故。

但它失败在**「函数之间的接缝」**：
- CORS 在中间件里做对了一半（知道带凭据不能 `*`），却在 `server.py` 里被无参调用打开了 `*`；
- 唯一索引在选名时把墓碑当「不占位」，在写库时又当「占位」；
- 上传路径校验魔术字节，索引路径不校验；
- 前端知道失败要标 `FAILED`，却不知道还要 `abort` 服务端会话。

**所以 888 条测试全绿是可以理解的，而且这正是它最值得警惕的地方** —— 唯一直接相关的测试（`test_core.py:504`）把 CORS 回显断言成了期望行为，`TC-LINT-SEC-016` 这条本该拦住它的规则因为写法差异空过。测试覆盖的是「每个零件符合设计」，没有覆盖「零件组合起来是否符合安全目标」。
