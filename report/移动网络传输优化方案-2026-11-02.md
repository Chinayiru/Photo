# 远程相册移动网络传输优化方案

日期：2026-11-02  
状态：方案归档，尚未实施；未进行真实移动网络性能测试。  
依据：当前仓库只读代码检查，以及用户本轮补充。仓库实现不等于线上正在运行的版本。

## 1. 结论与已确认边界

建议优先实施：**取消自动原图传输 → 修正上传超时 → 小分片与低并发对比 → 减少后台竞争 → 接入已有秒传 → 核查缓存与预览尺寸**。

现有 WebP、分片续传、原子落盘和流式中继不重做。服务器确认为 Windows Server，因此不采用 Linux sysctl 启用 BBR 的方案；上传前有损压缩也不采用。

用户回复“保留”，本方案据此按**保留原始照片及其元数据**处理：原文件上传、保存、下载保持字节一致；缩略图和预览图可以作为本地派生副本减量，但不替换原文件。

### 1.1 硬约束

1. 阿里云 ECS 维持 2 核、2 GiB、公网带宽 1 Mbps，不升级、不扩容带宽。
2. 照片及其派生媒体仅保存在本地电脑，云端只中继，不持久化媒体字节。
3. 不引入额外付费 CDN 或对象存储。
4. 保留断点续传、绝不覆盖、原子落盘、服务端内容校验。
5. 保留原始照片及其元数据，不默认转码或清理原文件。
6. 每项优化给出可执行的验证判据；没有实测的数据不写成实测收益。

云端零媒体存储允许流式转发必需的有界瞬时内存缓冲，不允许媒体临时文件、完整媒体缓存或请求体日志落盘。移除所有内存缓冲和背压并不是本方案目标。

### 1.2 当前确认情况

| 项目 | 状态 | 对方案的影响 |
|---|---|---|
| ECS 操作系统 | 用户确认 Windows Server | Linux BBR/sysctl 方案不采用，不为提速重装系统 |
| 线上是否使用仓库 Caddy 配置 | 未知 | 先核实进程、服务、配置路径和版本，不直接修改模板 |
| 手机实际 HTTP 版本 | 未知 | HTTP/1.1、HTTP/2、HTTP/3 的收益均待测 |
| 两段链路各自瓶颈 | 未知 | 分别观察手机↔云、云↔本地的耗时和队列 |
| 30 秒超时是否已造成失败 | 用户认为可能；尚无日志证实 | 列为 P0 排查，不断言已证实故障 |
| 分片与并发最佳组合 | 未知 | 以 256 KiB、并发 1 为候选起点，必须与当前基线比较 |
| 手机浏览器能力与后台恢复 | 未知 | 使用实际目标手机验证，不能假设所有浏览器相同 |
| 原照片与元数据 | 按用户“保留”回复处理 | 原文件不压缩、不剥离元数据 |
| AVIF 收益、HTTP 协议收益、跨页面恢复 | 未知 | 保持为后续验证项 |

1 Mbps 按十进制换算是 125 kB/s，约 122 KiB/s；有效媒体吞吐还受协议开销、链路与竞争影响。后文文件大小统一使用 KiB/MiB，测试速率统一记录 KiB/s。

上传和下载都会经过 ECS 公网出口：上传为云端→本地，下载为云端→手机；同时发生时会竞争出口带宽。不能仅按手机上下行方向判断是否互相影响。

## 3. 逐项优化结论

下文“采用”均指建议未来实施，并不表示已修改或已部署。各项均无本轮实测数据。

### 3.1 源头减量：三类请求严格隔离

- **结论：采用，P0。** 时间线只请求缩略图；查看器使用缩略图占位及预览图；原图只由“下载原图”触发。
- **变更位置：** `frontend/src/stores/viewer.ts:schedulePrefetchRaw/rawSrcFor/downloadRaw`；`frontend/src/views/ViewerView.vue:useRaw/rawSrc`；`frontend/src/components/PhotoCell.vue:src`。
- **关键变更：** 去掉自动原图预取、捏合放大取原图以及预览失败自动取原图的路径；原图下载仍提供原始文件。
- **收益与判据：** 浏览、滑动、放大、预览失败及空闲停留的原图请求数均为 0；每避免一张 4 MiB 原图，在 80 KiB/s 下可释放约 51 秒传输容量，属于计算示例。
- **风险：** 查看器放大细节受预览尺寸限制，原始细节仍可通过明确下载获得。
- **约束影响：** 不改变续传、绝不覆盖、原子落盘和云端零媒体存储。

### 3.2 源头减量：WebP、尺寸档位与 AVIF

- **结论：保留已有 WebP；尺寸策略和 AVIF 需验证。** 不为凑 Q80 将现有 Q78 调高，也不预设 AVIF 再降 40–50%。
- **变更位置：** `backend/app/thumbs.py:generate_thumb/thumb_path`；`backend/app/handlers/browse.py:get_preview`；`frontend/src/stores/viewer.ts:previewSize`。
- **关键变更：** 根据实际图片显示区域、DPR 和省流策略评估现有档位；AVIF 仅在本地电脑生成，浏览器不支持则使用 WebP。缓存版本区分格式、尺寸和编码参数。
- **收益与判据：** 分开比较“同尺寸换格式”和“同格式换尺寸”；AVIF 可设样本体积中位数至少减少 20% 为候选门槛，同时视觉抽查通过、冷生成与热缓存端到端耗时无明显退化。
- **风险：** 编码开销、解码耗时和色彩变化可能抵消体积收益，编码器质量数字不能直接横向比较。
- **约束影响：** 只改本地派生副本，原图与元数据不动；派生文件继续原子生成，云端不缓存媒体。

### 3.3 源头减量：上传前 Canvas/WebWorker 有损压缩

- **结论：不采用。** 按用户保留原照片及元数据的要求，上传不改变原始字节。
- **变更位置：** 无；不新增上传转码步骤。
- **关键变更：** 维持原文件上传；后续即使浏览器支持 WebP 编码，也不据此自动开启压缩。
- **收益与判据：** 不计压缩减量收益；验证上传前后文件 SHA-256 一致，并抽查元数据保留。
- **风险：** 有损压缩会改变归档内容，可能损失 HDR、色彩、动画、拍摄信息等。
- **约束影响：** 四项安全约束及原文件完整性均保持。

### 3.4 源头减量：元数据剥离

- **结论：派生预览保留现状并抽查；原文件不采用剥离。**
- **变更位置：** `backend/app/thumbs.py:generate_thumb/_apply_orientation`。
- **关键变更：** 检查派生图 GPS、EXIF、IPTC、XMP 残留；正确处理方向与颜色后再清理非必要信息，不能盲目删除 ICC。原文件上传、落盘和下载均不处理元数据。
- **收益与判据：** 记录实际减少字节；方向与颜色正确、原文件哈希一致；已经清除的 EXIF 不重复计收益。
- **风险：** 错误清理方向或色彩信息可能导致旋转错误、偏色。
- **约束影响：** 仅涉及本地派生图，不改变原文件和四项安全约束。

### 3.5 传输层：BBR

- **结论：本次不采用 Linux BBR/sysctl 方案。** 当前 ECS 已确认为 Windows Server。
- **变更位置：** 无；不执行 sysctl，不重装系统。
- **关键变更：** 暂不调整拥塞控制；如未来单独评估 Windows 网络栈，须先核实系统版本与支持能力。
- **收益与判据：** 本次不计任何 BBR 收益，不承诺 10–30% 提速。
- **风险：** 不能把 Linux 配置或收益假设直接套用 Windows，也不能将 TCP 算法与 QUIC 混为一谈。
- **约束影响：** 无影响。

### 3.6 传输层：HTTP/2 与 HTTP/1.1

- **结论：需验证，P2。** 不采用“超过 512 KB 一律回退 HTTP/1.1”的通用规则。
- **变更位置：** 待确认的线上反代配置；仓库参考 `cloud/Caddyfile`、`cloud/Caddyfile.windows-domain`；若最终需要独立上传入口，再涉及 `frontend/src/api/uploader.ts:uploadChunk`。
- **关键变更：** 先查实际进程、配置、TLS 终止点和手机实际协商协议，再做上传与下载独立 A/B。保持现有入口作为回退。
- **收益与判据：** 分别记录上传吞吐及失败率、多缩略图首屏耗时、预览 P95；不能只凭下载变快认定成功。
- **风险：** fetch/XHR 不能直接指定 HTTP/1.1，同一连接通常不能按 URL 路径选择 ALPN；独立入口需要额外处理鉴权与跨域。
- **约束影响：** 保留流式转发、鉴权、上传状态接口和四项安全约束。

### 3.7 传输层：QUIC/HTTP/3 与 0-RTT

- **结论：需验证，P3；状态变更请求不采用 0-RTT。**
- **变更位置：** 待确认的实际反代、UDP 443、安全组和防火墙配置；仓库 `cloud/docker-compose.yml:caddy.ports` 已有 UDP 443 映射，但不能据此推断 Windows 线上已启用。
- **关键变更：** 优先核实现有代理是否支持，再测试实际协商、弱网与切网，保留 HTTP/2 回退；不为此先替换整个隧道。
- **收益与判据：** 比较真实移动网络下恢复耗时、失败率、预览 P95、上传吞吐及服务器资源占用，收益应超过测试波动。
- **风险：** HTTP/3 仅影响覆盖到的链路，云到本地 WebSocket/TCP 仍可能存在队头阻塞；0-RTT 具有重放风险。
- **约束影响：** 上传、完成提交、删除等状态变更不使用可重放早期数据；四项安全约束不变。

### 3.8 分片与续传：分片配置、自适应

- **结论：采用，先固定候选对比，再引入自适应，P0/P1。**
- **变更位置：** `backend/app/config.py:上传配置`；`backend/app/uploads.py:_chunk_size/_append_chunk_locked`；`frontend/src/stores/upload.ts:doUpload`。
- **关键变更：** 增加明确的字节或 KiB 配置，候选初值 256 KiB；当前 `_chunk_size` 会执行 `int(mb)`，不能用 0.5 MiB 配置直接期待 512 KiB。自适应使用服务端确认后的分片耗时，目标约 4–8 秒，并受会话上限约束。
- **收益与判据：** 对比 128/256/512/1024/2048 KiB 的有效吞吐、重复字节、超时率、恢复耗时；256 KiB 在 40 KiB/s 下约 6.4 秒，2 MiB 约 51 秒，均为计算示例。
- **风险：** 小分片增加往返与 fsync 成本，重试同一片时不得改变内容与范围，不能只用 XHR 发出进度估算端到端速率。
- **约束影响：** 保留服务端 offset 权威、顺序追加、会话锁、fsync、最终校验和原子提交；保持旧会话兼容，云端不落媒体。

### 3.9 分片与并发：低并发与可见图片调度

- **结论：采用，P1。** 云端通路并发 1 为候选默认，实测证明有益再升到 2。
- **变更位置：** `frontend/src/stores/upload.ts:concurrency/schedule`；`frontend/src/components/PhotoGrid.vue:setupObserver`；`frontend/src/components/PhotoCell.vue:图片加载`。
- **关键变更：** 不因网络 API 缺失就默认并发 3；保持每个文件顺序上传；下载优先可见图片，不额外扩大并发。
- **收益与判据：** 比较并发 1/2/3 的总吞吐、首个完成时间、超时与重试；单流没有稳定优势时按实测选择。
- **风险：** HTTP/2 的同域连接数限制不等于低请求并发，`loading="lazy"` 不保证仅加载视口内图片。
- **约束影响：** 只改调度，不改四项安全约束。

### 3.10 分片与续传：失败片重试、状态确认

- **结论：保留并补齐验证，不重写续传，P1。**
- **变更位置：** `frontend/src/api/uploader.ts:uploadChunkWithRetry`；`frontend/src/stores/upload.ts:doUpload/retryTask`；`backend/app/uploads.py:_reconcile_offset`。
- **关键变更：** 对超时或应答丢失，优先查询服务端 offset，避免已落盘分片重复传输；保留有限重试、抖动退避和重试次数边界。
- **收益与判据：** 测试片中断网、落盘后应答丢失、切网、隧道重连；恢复后最终哈希一致，不重传已确认前缀，报告重复字节比例。
- **风险：** 页面内暂停继续不代表刷新或关闭后也能恢复，跨页面必须另测任务状态与文件重新取得。
- **约束影响：** 以本地真实落盘进度为准，保留绝不覆盖、原子提交、云端零媒体存储。

### 3.11 中继：流式转发与有界缓冲

- **结论：采用现状，核查线上，不重做。**
- **变更位置：** `cloud/relay/forward.py:Forwarder._relay/_stream_response`；`cloud/relay/tunnel.py:_pump_body`；`shared/mux.py:队列与信用流控`；实际反代配置。
- **关键变更：** 确认没有整文件缓冲、媒体临时文件或请求体日志；保留必要的有界队列与背压。
- **收益与判据：** 大文件持续流动，内存不随文件总大小线性增长，云端无媒体字节落盘；若现状通过，不计新增收益。
- **风险：** 不应为减少缓冲而移除流控，防止内存膨胀和共享隧道阻塞。
- **约束影响：** 符合云端零媒体存储；本地收齐一个有界分片后落盘是既有上传设计，保持不变。

### 3.12 中继：连接复用、保活和控制帧

- **结论：保留，必要时按证据微调。**
- **变更位置：** `backend/app/tunnel.py:_connect_once/_heartbeat_loop`；`cloud/relay/tunnel.py:_heartbeat_loop`；`shared/mux.py:信用回补`；实际反代配置。
- **关键变更：** 核查持久隧道、HTTP 连接复用及满带宽时心跳、CREDIT、取消帧的及时性；不盲目提高心跳频率。
- **收益与判据：** 长时间上传及浏览无拥堵引发的异常重连，记录握手耗时与重连次数。
- **风险：** 过密心跳增加耗电，过宽超时延迟故障发现。
- **约束影响：** 保留鉴权、取消和续传机制，四项约束不变。

### 3.13 用户感知：关闭原图预取、收紧后台预取

- **结论：采用，P0。** 与三类请求隔离配套实施，收益不重复累加。
- **变更位置：** `frontend/src/stores/viewer.ts:prefetchWorthIt/schedulePrefetchRaw/prefetchRaw/close`；`frontend/src/components/PhotoGrid.vue:setupObserver`。
- **关键变更：** 不自动预取原图，即使 Wi-Fi 也遵守明确点击才传原图；切图、关闭时撤销在途及已排队工作。评估缩减当前提前 1200px 的分页触发范围，并单独限制图片请求。
- **收益与判据：** 空闲停留不出现原图请求，关闭后不启动延迟原图任务，记录会话总下载字节及取消后额外字节。
- **风险：** `effectiveType="4g"` 不是 Wi-Fi 判断，CPU 空闲也不是网络空闲。
- **约束影响：** 不改变四项安全约束。

### 3.14 用户感知：小文件优先与上传期间后台让路

- **结论：采用，P1。**
- **变更位置：** `frontend/src/stores/upload.ts:schedule`；`frontend/src/views/TimelineView.vue:媒体变化监听/refresh`；`frontend/src/components/PhotoGrid.vue:setupObserver`。
- **关键变更：** 未开始任务优先小文件，加入等待时间权重防止大文件饥饿；上传期间暂停非必要预取和自动列表重载，结束后合并刷新。
- **收益与判据：** 对比首个、前五个完成时间以及后台传输字节；主要改善等待感受，不承诺提高管道吞吐。
- **风险：** 保留 SSE、心跳、完成确认、用户主动操作和本地索引处理，不能为让路丢弃状态更新。
- **约束影响：** 不改变上传文件字节和落盘流程，四项约束保留。

### 3.15 补充 P0：响应头、传输及总超时配合

- **结论：采用修正方案，线上是否已因此失败仍需验证。**
- **变更位置：** `cloud/relay/forward.py:Forwarder._relay/_total_timeout`；`cloud/relay/tunnel.py:forward_request`；`shared/protocol.py:HEAD_TIMEOUT/TOTAL_TIMEOUT`；`frontend/src/api/uploader.ts:uploadChunk`；`backend/app/handlers/uploads.py:patch_upload`。
- **关键变更：** 区分请求体持续传输阶段、传完后处理响应阶段、无进展超时和有界总时限；同时检查共享隧道的计时路径，避免只调整一层。结合小分片验证，不把全局超时一律关闭。
- **收益与判据：** 30 秒响应头等待与 2 MiB 慢速分片存在冲突；正常持续有进展的分片不应被提前取消，停滞请求仍及时释放。记录 504/取消与耗时分布，不能仅凭推算认定线上故障。
- **风险：** 原图下载当前也有 1800 秒总时限，大文件在 1 Mbps 下可能超过该时限，须同时验证有界长时传输及 Range 恢复。
- **约束影响：** 不提前返回成功、不省略 fsync 或校验，继续保持四项安全约束。

### 3.16 补充 P1：前端接入已有 SHA-256 秒传

- **结论：采用，复用既有后端能力。**
- **变更位置：** `frontend/src/stores/upload.ts:doUpload`；拟新增分块哈希 Worker；`backend/app/uploads.py:init_upload/find_duplicate`。
- **关键变更：** 在 Worker 中分块计算原文件 SHA-256，提交给已有 init 接口；按队列逐个准备，不等待所有选中文件先算完。
- **收益与判据：** 对已建立哈希且仍存在的重复文件，第二次上传不发送媒体分片；记录哈希耗时、命中率及减少字节。首次上传无减量，已有索引缺哈希时不能假设命中。
- **风险：** 控制手机内存、耗电和主线程卡顿，不用文件名或大小代替内容哈希。
- **约束影响：** 保留服务端权限检查、存在性检查、内容校验及安全提交，原文件和元数据不变。

### 3.17 补充 P1：已有浏览器缓存的命中与失效

- **结论：采用核查，复用现有缓存机制。**
- **变更位置：** `backend/app/handlers/browse.py:_file_thumb_reply/get_preview`；`frontend/src/api/client.ts:thumbUrl/previewUrl`。
- **关键变更：** 保留版本 URL、私有缓存及 ETag；避免无意义 URL 变化，编码策略变化时正确更新版本。
- **收益与判据：** 同版本重复查看应命中缓存或仅条件请求，单列首次与重复查看媒体字节，缓存命中不得记作网络吞吐提升。
- **风险：** 不绕过鉴权，不长期缓存占位图，不忽略照片变更后的缓存失效。
- **约束影响：** 仅浏览器与本地派生缓存，云端不保存媒体，四项约束保留。

## 4. 测试设计与记录要求

### 4.1 先确认线上实际运行路径

此处是后续检查计划，本次没有连接服务器或修改服务。

1. 在 Windows Server 核实实际服务、进程、启动参数、监听端口、反代配置路径和版本。
2. 查明手机入口是否经过 Caddy、其他代理或第三方隧道，分别标注 TLS 终止点与云到本地的通路。
3. 在真实手机访问中记录实际协商协议；代理具备 HTTP/3 能力或响应包含公告，不代表本次请求已使用 HTTP/3。
4. 对齐前端、云端和本地的请求耗时、响应状态、offset 进展与隧道重连记录。日志只记录必要指标，不记录照片内容、凭据或媒体请求体。
5. 先收集已有失败记录，核实是否在约 30 秒发生响应头超时。

### 4.2 真实移动网络基线

- 使用真实 4G/5G，确认手机没有走 Wi-Fi 或局域网直连；本机回环结果仅能用于功能检查，不能作为性能验收。
- 固定手机、浏览器版本、运营商、位置和样本；分别覆盖正常信号与弱信号，记录测试时间和网络状态。
- 同一阶段只改变一个因素，交错执行 A/B，避免把时段网络差异当收益。
- 每组常规传输至少重复 10 次；记录样本量、P50、P95、失败次数。少量样本的尾延迟仅作初步判断，不能宣称统计可靠。
- 冷浏览器缓存、热浏览器缓存、本地派生图首次生成及已生成状态分别统计。
- 上传和下载先单独测试，再增加同时上传与浏览的竞争场景。

### 4.3 指标口径

| 指标 | 计算或观测口径 | 注意事项 |
|---|---|---|
| 上传有效吞吐（KiB/s） | 本地确认新增的唯一媒体字节 / 上传阶段耗时 / 1024 | 计入重试与退避，不能用浏览器已发出字节代替落盘确认 |
| 下载有效吞吐（KiB/s） | 实际完成接收的媒体字节 / 传输阶段耗时 / 1024 | 缓存结果单列，失败传输单列 |
| 上传端到端耗时 | 选择或开始任务至本地最终提交确认 | 哈希、排队、传输、提交耗时分别记录 |
| 首屏缩略图耗时 | 进入时间线至固定首屏全部可见图片显示 | 固定图片数量与布局，报告 P50/P95 |
| 预览图耗时 | 点击图片至目标预览完成显示 | 包括请求、必要生成、解码与显示 |
| 断点续传成功率 | 恢复且最终哈希一致次数 / 故障注入次数 | 按故障类型分组，不混成一个无解释百分比 |
| 重试字节比例 | 应用层重复发送的媒体字节 / 唯一媒体字节 | 与 TCP 重传率分开；未取得 TCP 统计则注明未知 |
| 会话传输总量 | 一轮固定浏览/上传操作的媒体与后台请求字节 | 便于识别预取浪费和重复刷新 |
| 云端资源与存储 | 进程内存趋势、CPU、队列、文件系统写入情况 | 不随媒体总大小无限增长，不出现媒体落盘 |

## 5. 实施顺序与回退原则

1. **基线：** 核实线上运行路径、版本和协议，收集真实移动网络数据。
2. **P0：** 关闭自动原图；处理上传响应头计时风险；验证小分片、并发 1 候选。
3. **P1：** 分片/并发矩阵、小文件优先、后台让路、接入已有秒传、缓存核查。
4. **P1/P2：** 在稳定候选上评估分片自适应、预览尺寸策略。
5. **P2：** HTTP/2 上传与下载独立 A/B；必要时验证 HTTP/1.1 上传入口。
6. **P3：** 有明确收益再引入 AVIF 或 HTTP/3。

每项独立开关或配置，保存基线，出现数据一致性、恢复成功率或稳定性退化即回退。涉及参数变化时，已有上传会话继续沿用兼容语义；不删除未完成临时文件，不强迫用户重传完整文件。

## 7. 未采用项及原因

| 未采用项 | 原因 |
|---|---|
| 上传前默认或自动有损压缩 | 用户要求保留原照片及元数据 |
| 原文件 EXIF/IPTC 等剥离 | 改变原始归档内容；只允许派生图处理 |
| Windows Server 执行 Linux BBR/sysctl 方案 | 系统不适用；不为此重装系统 |
| 重做 WebP、分片续传、原子落盘、流式中继 | 已具备，优先修补缺口与验证 |
| 提高 Q78 至 Q80 并宣称减量 | 不能保证减量，可能增加体积 |
| 文件超过 512 KB 一律关闭 HTTP/2 | 不是普遍规则，必须针对实际部署验证 |
| 自动原图预取、放大自动请求原图 | 与原图明确点击才传输的目标冲突 |
| 根据 Wi-Fi、4G 标签或 CPU 空闲判断带宽富余 | 不能代表 1 Mbps 中继出口是否繁忙 |
| 取消所有缓冲、背压、超时或暂停所有 SSE | 损害稳定性、资源控制和状态可靠性 |
| 上传与提交等状态变更使用 0-RTT | 存在重放风险，不作为本次提速手段 |
| 盲目增加并发或替换整个隧道架构 | 暂无证据表明收益足以抵消复杂度 |
| 扩带宽、升级服务器、付费 CDN/对象存储、云端媒体缓存 | 违反任务硬约束 |

本文件仅形成方案与验收清单；所有测试值仍待取得，任何配置、代码和线上服务变更均尚未执行。
