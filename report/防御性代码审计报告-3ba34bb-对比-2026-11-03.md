## 3. 降级为「策略决策」的（2 项）

### 3.1 面板（原 D3-2 / D5-2）

我原写「面板接口零令牌，边界只剩回环」。复核指出：默认关闭 + 共享中间件三层门控 + handler 再判回环。我逐行核对后确认：

- `backend/app/config.py:179` `panel_http` 默认 **false**；
- `backend/app/auth.py:1054-1066`：`panel_http` 未开 → 整条 prefix `404`（连回环也拒）；开了才判 `is_loopback`；
- `backend/app/auth.py:1034`：Host 校验在**所有分支之前**（注释写明"攻击链第一步是读 `/panel/pair-code`"）；
- `backend/app/handlers/auth.py:283/305/344`：handler 内再判一次回环；
- `transports/local_http.py:230`：面板开启时禁止通配绑定（我实测 8880 实例 `exit 2`）。

且 `auth.py` 的注释显示**"只判回环"这个更弱的版本曾经存在并被评为漏洞**（恶意本地网页可现取配对码换 90 天令牌），现已被"默认整条关闭"取代。

→ **判定：不是「鉴权缺失」，而是「显式启用的本机调试接口，信任边界＝回环 + 本机进程」**。我撤回"必须排第二"的排序；保留一句提示：一旦用户打开 `panel_http`，同机任意进程即可签发配对码，这属于该配置的威胁模型，应在文档里写死（复核 B-02 的表述我采纳）。

### 3.2 CORS link-local（原 D4-5）

- 事实双方一致：`is_lan_origin()` 对 RFC1918、IPv4 link-local、IPv6 ULA、IPv6 link-local 都返回 `True`（我的 `probe4` 与复核 §6.1 独立得到同结论）。
- 我原把它写成「DNS rebinding 面/SSRF 风险」——**定性错误**：浏览器不会以 `Origin: http://169.254.169.254` 发起页面级请求，这与服务端 SSRF 无关。
- 我**保留一条意见**（不作为缺陷）：`169.254.0.0/16` 在浏览器 Origin 语义下没有合法来源页，放行它**零收益**；建议在「地址族策略表」里把它显式排除，而不是"顺手允许"。这属策略收敛，不是漏洞修复。

## 4. 修法分歧：沙箱（原 D4-1）

- **风险成立**：我复核确认 `sandbox.resolve()` 返回的是 `Path`（`sandbox.py:137`），调用方 `common.py:529` 在执行器里**再按路径 open**；我原 `probe2.json` 记录的 `actual=b'LOOT'` 是真实的（本轮未重跑该 junction 替换，仅核对了产物与链路）。
- **我接受复核对修法的否决**：Windows 下 `os.open(O_NOFOLLOW)` 只约束最终段，不能阻止**祖先目录**被替换；`fstat` 后对原字符串 `realpath()` 比较，等于拿"可变路径"当基准，仍可被换。正确做法是「打开后以**已固定的根**对新句柄的真实对象路径做归属判定，并把 seek/read 都放在同一句柄上」（复核 B-01 的 5 步拆分）。
- **我接受「读写分开设计」**：`archive.reserve/place`、移动、改名、回收站删除各自的父目录竞态不能用读取句柄方案覆盖。原报告把"TOCTOU"写成一个整体待修项，粒度太粗。
- **我补一条更硬的证据（§6）**：这不是"没人想到"，而是"文档说已经做了"。

## 6. 我补充的新证据：文档宣称的 TOCTOU 缓解不存在

复核提到「`docs/06:1145` 给出 `open_read()` 示例，而 `sandbox.py` 并无该入口」。我把这一条做成可核对的事实：

```powershell
Select-String -Path backend\app\sandbox.py -Pattern 'open_read|open_write|safe_replace|O_NOFOLLOW|fstat'
# → 无任何匹配

Select-String -Path "docs\06-安全设计文档.md" -Pattern 'open_read'
# docs/06:193    from app.sandbox import resolve, open_read, open_write, safe_delete, safe_replace
# docs/06:196    with open_read(root_cfg, rel_path) as f:   # 校验 + 打开，TOCTOU 安全
# docs/06:1099   真正的打开必须走 open_read / open_write，它们会复核边界以消除 TOCTOU
# docs/06:1145   def open_read(root_cfg: dict, rel_path: str):
```

- `docs/06:1099` 的原文是**断言式的**：「真正的打开必须走 `open_read` / `open_write`，它们会复核边界以消除 TOCTOU」。而 `sandbox.py` 里没有任何一个这样的函数，`backend/app/handlers/common.py` 的 `iter_file()` 也没有"打开后归属复核"。
- `docs/06:1232`、`:1383` 又记录"接受 Windows 路径复核的残余竞态"。
- 这两处**互相矛盾**：一处说"用 open_read 消除"，一处说"接受残余风险"。实际情况是后者（没有 open_read）。

→ 建议在风险登记册里补一条：**ISSUE：`docs/06` 描述的 `open_read/open_write/safe_replace` 未实现，TOCTOU 残余风险按 `:1232`/`:1383` 接受；任何"已用 open_read 消除"的表述需撤回。** 这比"实现存在窗口"更值得记录——因为后人读文档会以为缺口已经堵上。

## 8. 本轮我实际跑的校验（只读，2 个脚本）

```powershell
# 断言计数（AST，三根目录）
.\.venv\Scripts\python.exe build\_def_audit\_assert_count.py
# → 13 处（与复核一致）

# bidi 真实码点：沙箱 vs 清洗函数 vs strip_bidi
.\.venv\Scripts\python.exe build\_def_audit\_bidi_check.py
# sandbox.read -> SandboxError: E1009 bidi_control
# download_filename repr: 'photo\u202egnp.exe'   contains U+202E: True
# strip_bidi repr: 'photognp.exe'                contains: False
```

结论三条：
1. **复核第 43 行正确**：带真实 U+202E 的名字进 `sandbox.resolve(..., "read")` 直接 `E1009 path_denied/bidi_control`，所以"磁盘上已有 bidi 名文件会被直接读到"这条链不成立；**下载名缺口只能经 `?name=` 参数触发**，与复核 A-01 描述一致。
2. **缺口本身成立**：`download_filename()` 原样保留 U+202E（`filename*` 里出现 `%E2%80%AE`）。
3. **修法代价极低**：`strip_bidi()` 一行即净，且 `strip_bidi` 只清 `BIDI_CONTROLS` 集合（不误删全部格式字符），与复核"保留边界"的要求一致。
