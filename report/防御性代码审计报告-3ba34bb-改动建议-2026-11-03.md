## 二、可以独立落地的修改

### A-01 下载名接入现有双向字符净化

- 位置：`backend/app/handlers/common.py:551`、`backend/app/handlers/browse.py:676`、`backend/app/sandbox.py:252`。
- 代码依据：`download_filename()` 只去除路径分隔符、常见 Windows 非法字符、CR/LF/TAB；`filename_disposition()` 在 `common.py:579` 将其编码进 `filename*`。
- 已确认入口：有权访问某正常媒体的请求 `GET /api/items/{id}/raw?download=1&name=...`，`name` 在 `browse.py:678` 直接进入下载名清洗函数。不需要磁盘上存在带 bidi 的文件名。
- 本轮复测：输入 `"photo" + chr(0x202E) + "gnp.exe"`，返回值保留 U+202E，头字段含 `filename*=UTF-8''photo%E2%80%AEgnp.exe`。
- 改动：在 `download_filename()` 中调用 `sandbox.strip_bidi()`，继续执行现有清洗、空值回退和长度限制；响应头的 ASCII 回退与 UTF-8 名称均使用清洗结果。
- 保留边界：`strip_bidi()` 去除的是既有 `BIDI_CONTROLS` 集合，不能据此声称清除了所有零宽字符；不要无差别删除全部 Unicode 格式字符。
- 验收：覆盖真实 U+202E、方向隔离字符、全部被剥离后的空名、正常中文名、CRLF、路径分隔符；用正常临时媒体发下载请求并检查头；浏览器另验保存名展示。
- 影响定性：附件显示名欺骗及展示一致性问题。现有证据不支持“任意文件下载”“下载即执行”或“可执行文件伪装已在浏览器实测成功”。

原报告声称“已有 bidi 文件名不会被沙箱拦住”也不准确：本轮直接调用 `sandbox.resolve(root, 带真实U+202E的名称, "read")` 得到 `SandboxError: E1009 path_denied`。应改用上述 `name` 参数链描述已确认缺口。

### A-02 播放票改准确说明，保留可复用语义

- 位置：`backend/app/streamticket.py:1`、`:53`、`:65`。
- 决策依据：`docs/04-接口设计文档.md:3441` 至该表结尾规定正常鉴权换票、单条目绑定、300 秒有效；没有首次消费即失效的要求。`streamticket.py:57` 也明确解释票不携带 `client_id` 的设计。
- 改动：首行“一次性入口凭证”改为“短期、单条目、有效期内可复用的播放凭证”；同时修正“播完就废”等容易被理解成完成播放即撤销的描述。
- 不采用：首次请求后删除票或写入已消费表。视频播放、拖动进度、重试会对同一 URL 发起多次 Range 请求，这样修改会破坏播放流程。
- 验收：同票同条目在有效期内连续读取及 seek 成功；其他条目、过期票、篡改签名、空票拒绝；票不能作为其他 API 的通行凭证。
- 另行决策：若要求踢出或撤销后旧票立即失效，需要设计带会话标识的新版本票，并在每次验证时查询撤销状态。仅把 `client_id` 写进签名、却不校验独立会话或撤销状态，不能阻止持票转发。

### A-03 提高审计索引降级的可观测性

- 位置：`backend/app/audit.py:244`、`:253`、`:254`。
- 代码依据：索引表 INSERT 失败被捕获后只输出 DEBUG；文件主记录已先经 `:235` 写入，`_append_file()` 在 `:272` 执行 fsync。
- 改动：首次或持续失败时输出限频 WARNING，记录失败次数，恢复后输出一次恢复提示。日志只保留动作、失败类别等必要信息，避免输出令牌、媒体字节或将内部错误直接返回客户端。
- 保留：文件先写并确认落盘，再尝试表索引；表失败不让已完成的上传、删除变成接口失败。
- 验收：模拟索引表不可写，确认请求不因索引故障失败、文件记录仍存在、生产日志级别能看见降级；连续故障不刷屏；恢复后可观察到恢复状态。
- 定性：运维可观测性增强，不应写成已确认丢失全部审计记录。

### A-04 清理未接线的尺寸辅助函数

- 位置：`backend/app/handlers/browse.py:286`；真实校验在 `backend/app/handlers/common.py:618`。
- 证据：本轮 AST 扫描 `backend/app/`、`cloud/relay/`、`shared/`、`backend/tests/`、`scripts/`，找到一个 `_size_allowed()` 定义，未找到该名称的直接调用。
- 改动：确认没有动态引用后删除该辅助；尺寸白名单继续由 `parse_size()` 负责，不增加另一套判断。
- 验收：合法 320/1600 返回对应尺寸；非法整数或非整数保持契约错误；缺省或空值保持 `allowed[0]`，不能把空值误写成必定拒绝。
- 定性：死代码清理，不是尺寸防御被绕过。

## 三、需要先定边界的修改

### B-01 沙箱读取改为同一句柄验证与使用，写入操作另行设计

**风险成立，但原报告给出的修法不能直接执行。**

- 当前调用链：`browse.py:658 sandbox.resolve()` → `:663 stat_size(src)` → `:688 range_file_reply()` → `common.py:529` 在执行器中再次按路径打开 → `:538` 读取。
- 沙箱行为：`sandbox.py:134` 检查各段重解析点，`:135` 验证根内路径，然后 `:137` 返回 `Path`；返回的不是已打开文件或固定目录句柄。
- 原实测材料：`build/_def_audit/out/probe2.json` 的 TOCTOU 条目保存了 `actual = b'LOOT'`、`escaped = true`。本轮核对了该产物和源码，未重新执行 junction 替换探针，也未把它升级为 HTTP 远程利用证明。
- 必要前提：攻击者或另一个本地写入者能在检查后替换库内目录。仅可提交远程路径参数，尚不足以完成这条利用链。

既有决策必须同时写清：`docs/06-安全设计文档.md:1232`、`:1383` 已接受 Windows 路径复核不能完全消除竞态的残余风险。因此它不是新发现的、完全未评估的公网攻击面。另一方面，文档 `:1145` 给出了 `open_read()` 和打开后复核的示例，而当前 `sandbox.py` 并无该入口，实际 `common.iter_file()` 也没有打开后归属复核。应区分“文档接受残余风险”和“示例中的缓解步骤当前是否实现”，不能声称现有实现已经把窗口缩到某个毫秒数。

建议拆为以下工作：

1. **先收窄读取路径**：由沙箱或专门的安全 IO 模块提供“校验并打开”的入口；Windows 使用文件句柄取得实际打开对象路径，再以已固定的可信根进行规范化归属判断。所有验证必须在返回媒体字节之前完成，失败即关闭句柄。
2. **元数据与内容使用同一对象**：从该句柄取大小和需要的文件元数据，后续 seek/read 继续使用同一句柄。不要校验一个句柄、随后又把路径交给 `open()` 或 `FileResponse`。
3. **明确重解析点保证**：`FILE_FLAG_OPEN_REPARSE_POINT` 或 POSIX `O_NOFOLLOW` 不能单凭一个最终段标志阻止祖先目录跳转。若要求“整条路径绝不经过重解析点”，还要设计目录句柄固定、逐段打开及相应共享访问策略；仅核对最终对象在根内，只能证明最终对象归属。
4. **单列修改类操作**：`archive.reserve/place`、移动、改名、回收站删除需要各自处理父目录替换和目标竞态。读取句柄方案不能宣称解决 `os.replace()`、路径式回收站调用的全部风险；保留独占占名、不覆盖和回收站约束。
5. **生命周期**：处理客户端断开、协程取消、零字节、206/304/416 和验证失败时的句柄关闭；不增加无界后台任务。

不采用原报告的简化修法：在 Windows 直接套 `os.open(O_NOFOLLOW)`，或 `fstat()` 后再对原字符串 `realpath()`，都不足以证明打开的对象属于可信根。`st_ino/st_dev` 相等也必须有可信、无竞态的比较对象，不能单独作为归属证明。

验收应先做可控的“校验后、打开前”替换，再覆盖“打开后”替换；确认库外哨兵从不作为响应体输出，允许安全拒绝或继续读取已验证的库内句柄。使用独立临时根、库外哨兵和明确同步屏障；清理时只移除本次创建的链接对象，不能递归跟随 junction 清理目标。对读取、改名、移动、删除、落盘分别出具结果，不合并成一个“TOCTOU 已修复”。

### B-02 面板维持默认关闭，额外认证按调试入口设计

- 正确位置：三个 handler 在 `backend/app/handlers/auth.py:275`、`:303`、`:333`，原报告所写 `handlers/panel.py` 不存在。
- 默认关闭：`backend/app/config.py:179`。
- 共享入口检查：`backend/app/auth.py:1034` 做 Host 校验；`:1058` 检查面板开关；`:1061` 检查回环。
- 通路检查：`auth.py:926` 对非 LAN 的 `Ctx.via` 返回 false，不能通过云端声明一个回环 IP 获得面板权限。
- handler 二次回环检查：`handlers/auth.py:283`、`:305`、`:344`。
- 启动门控：`config.py:1072`、`:1096` 拒绝面板开启时的非回环监听。
- 决策依据：`docs/06-安全设计文档.md:4266`、`:4273`；`docs/11-风险登记册与决策记录.md:1515` 的 ISSUE-018。

因此，应将原报告“面板鉴权只在传输层”“默认零认证暴露”的结论改成：**显式启用的本机调试接口，以回环和本地进程信任为边界；同机进程能否调用属于该配置的威胁模型。** 回环不代表用户身份，但当前已有防线也不能被省略。

若要支持开启 HTTP 面板后的额外身份隔离，再设计独立 Bearer 凭证及其轮换、受保护存储，并保留默认关闭、Host、来源和回环检查。原方案中的“启动时打印 token”不适合 `packaging/photobridge.spec:151 console=False`。

普通 TCP HTTP 无法直接得到调用进程 SID；若目标是 Windows 不同用户隔离，可评估带 ACL 和对端身份验证的命名管道。文件中的 token、签名密钥和数据库也需匹配的目录 ACL。同一用户权限的恶意进程通常能读取同一用户的凭证文件，额外 token 不能被宣传为防住同用户本地恶意软件。

### B-03 CORS 明确地址与 Origin 策略，避免以 SSRF 理由删 link-local

- 位置：`cloud/relay/cors.py:116`、`:149`、`:151`。
- 事实：`is_lan_origin()` 接受私有、回环和链路本地地址；本轮确认 IPv4 link-local、IPv6 ULA 和 IPv6 link-local 都返回 true。
- 原因：模块说明 `cors.py:12`、`:21` 已解释 DHCP 局域网页面切换到云端的跨源需求，不能将其与电脑端默认关闭 CORS 混为同一条配置策略。
- 判定：允许 `Origin: http://169.254.169.254` 不会让服务端访问元数据地址，不是 SSRF。现有证据也未证明攻击页面因此取得配对令牌或读到受保护媒体。
- 改动前先定：回环、RFC1918、IPv6 ULA、IPv4/IPv6 link-local、组网使用的 CGNAT 段分别应否自动允许；非私有自定义域名是否只走显式白名单。
- 可做的边界收紧：Origin 解析限定 HTTP/HTTPS 并检查端口合法性，避免依赖 `ipaddress.is_private` 的含义推断产品支持范围；这属于输入规范与策略明确化，不应写成已确认数据泄露。
- 验收：按拍板后的地址表参数化；合法 LAN 切云仍工作，公网恶意域、后缀欺骗、`null`、畸形 Origin 不回显；预检不进隧道，保留不发送 `Access-Control-Allow-Credentials` 的现有约束。

### B-04 保留 fsync；有性能数字后再调整执行方式

- 位置：`backend/app/audit.py:218`、`:269`、`:272`。
- 决策依据：`docs/11-风险登记册与决策记录.md:2362` 的 T-017：文件主记录、只追加、先 fsync，表为索引。
- 不采用：删除 fsync、只写表、fire-and-forget 后直接返回业务成功，或为避免阻塞把队列改成无上限。
- 有条件的方案：先测审计耗时和事件循环延迟；达到问题判据后，使用有界执行器或单写者队列，并等待持久化确认，维持顺序、失败语义和退出 drain。
- 验收：并发业务不交错记录；成功持久化确认后强杀仍可读到记录；磁盘故障有日志；队列满有明确策略。本轮没有性能测量，不判定它已造成性能故障。

## 四、不建议随报告直接修改的防线

1. **不要删绑定启动检查。** `Config.__init__()` 从 `config.py:386` 起只合并配置、解析数据目录，不验证绑定。真正的启动闸门在 `transports/local_http.py:230`；本轮构造不安全配置成功、随后 `check_bind_safety()` 返回 false，已验证两者不同职责。
2. **不要直接翻转默认开关。** `config.py:167 allow_lan=True` 与 `:247 allow_delete=True` 不是匿名放行。默认回环、配对、根权限和回收站限制应整体判断。若需要更严格产品预设，另写迁移及首次运行方案。
3. **不要因为“都是 Host”就合并两端策略。** 后端与 relay 的允许对象不同；若将来共享，只提取确实相同的解析规则，不把部署策略一并搬走。
4. **不要机械替换所有 assert。** 原报告列举的九处是内部不变量，不是请求鉴权。跨 `backend/app`、`cloud/relay`、`shared` 的 AST 实际找到 13 处：原九处、`shared/mux.py:1018` 的一个运行路径不变量，以及 `shared/protocol.py:428`、`:429`、`:437` 的三个直接运行自检。统计应区分生产路径和自检，不能把“9 处”写成全仓总数；是否改显式异常按调用契约逐处判断。
5. **三个 `_client_ip()` 壳不算重复安全策略。** `cloud/relay/auth.py:284`、`forward.py:919`、`pairing.py:632` 都调用同一个 `netutil.client_ip()`。清理仅影响维护，不应列为防御缺陷修复。

## 七、实施顺序与拆分建议

1. **先修报告和判据。** 更正错误位置、面板默认行为、播放票语义、bidi 输入和覆盖口径；使探针失败能真实返回非零，去掉真实数据库依赖。否则修复验收仍会“恒绿”。
2. **做三个独立小改动。** 下载名净化；播放票注释与契约说明；审计索引失败的限频告警。每项补对应回归，不混入默认配置变更。
3. **另立沙箱安全 IO 变更。** 先确认 Windows 句柄和威胁模型，再实现读取闭环；修改类操作单独验收。若实际部署允许不可信程序改动媒体目录，此项应提升到小改动之前处理。
4. **最后清理。** 删除 `_size_allowed()`，按需要简化 `_client_ip()` 壳；不批量替换内部断言，不以“去冗余”为理由删除启动门控、fsync 或逐段沙箱检查。
