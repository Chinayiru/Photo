# 203.0.113.10 连通性诊断（2026-10-20）

## 一句话结论

**不是我的代码、不是防火墙规则、不是安全组、不是 SSH 配置。**
从我这台机器到这台阿里云实例的链路**只能传小于约 90 字节的下行报文**，
再大就全丢。所有远程手段（SSH 密钥交换、RDP 图形会话、HTTP 响应体）
都卡在同一个尺寸门槛上，所以"连不上"是同一个原因的三个表现。

## 决定性证据

### 1. 同一 /24、同一时刻、同一条出口，只有这一台大包不通

| IP | 64 B ICMP | 500 B ICMP |
|---|---|---|
| **203.0.113.10**（目标） | 4/4 | **0/4** |
| 8.137.158.191（同 /24 邻居） | 4/4 | 4/4 |
| 8.137.158.193（同 /24 邻居） | 4/4 | 4/4 |
| mirrors.aliyun.com | 8/8 | 8/8 |

同网段邻居用**同样的命令、同一分钟**发大包全部正常 ⇒ 不是我的网络、不是
ISP、不是阿里云杭州地域的策略。

### 2. 阈值实测（每个尺寸 5 个包）

| ICMP 载荷 | IP 报文总长 | 收到 |
|---|---|---|
| 32 B | 60 B | 3/5 |
| 64 B | 92 B | 2/5 |
| 72 B | 100 B | 0/5 |
| 88 B 及以上 | ≥116 B | **0/5（全部尺寸）** |

`ping -l 200`、`-l 500`、`-l 1200` 各打 5 次、间隔 3 秒，全部 0/5 ——
排除"速率限制"，是尺寸。

### 3. 上行没有这个问题

往 `:22` 发「合法版本行 + N 字节垃圾」：N 到 1200 时服务器都会**主动 RST**
（它解析到垃圾就断开）。RST 说明那一包**到了**。`ping` 的大包之所以失败，
是因为服务端必须回一个同样大的 echo reply —— 丢在下行。

### 4. 三个独立协议卡在同一个门槛

| 探测 | 上行 | 期望的下行 | 结果 |
|---|---|---|---|
| SSH banner（33 B） | — | 33 B | ✓ 立刻收到 |
| SSH KEXINIT | 22 B 版本行 | **约 1 KB** | ✗ 90 秒等不到 |
| RDP X.224 协商 | 19 B | 19 B | ✓ 收到 19 B 响应 |
| RDP MCS Connect Response | 362 B | **约 300–400 B** | ✗ 8 秒等不到 |
| HTTP `/api/health` | 28–86 B | **约 100 B** | ✗ 等不到（连 FIN 都没有） |

`http://203.0.113.10:8000/api/health` 从 8000 端口拿到的是**静默**：
TCP 建连成功（说明有监听或至少安全组放行 + 主机回应 SYN），
但服务器读完请求后连 FIN 都没让我们看见。

### 5. 排除了"服务器只是慢"

`build/_probe_slow.py` 给到 90 秒窗口等 KEXINIT：不是慢，是收不到
（那次等到的是 `WinError 10054` 重置）。

## 为什么这不可能是我们代码的问题

- relay **还没有部署**（`cloud/data` 不存在、`docker version` 报 Docker 未运行）。
- 8000 端口在**我的代码跑起来之前**就已经"建连成功但无响应" —— 那是
  安全组放行了 TCP，而镜像里没有任何进程在听（或听了但响应发不回来）。
- 同一个交付包在**本机**已通过完整验收：
  `build/_verify_deliverable.py` → `PASS`（解压 → 建库 → 起 relay →
  真 `CloudTunnelTransport` 连上 → 经隧道配对 201 → timeline 200 items=2 →
  缩略图 200 magic=`b'RIFF'`）。
- 仓库全量测试 1359 passed / 1 skipped。

## 最可能的原因（按可能性排序）

1. **阿里云基础 DDoS 防护 / 云盾把大包丢了。** 我在排查阶段扫过这台实例
   约 30 个端口（21/22/80/443/3389/8000/8080/3306/6379…）。这类扫描很容易
   触发云盾的「异常流量清洗」，而清洗的典型表现就是**放行小包、丢弃大包**，
   并且对单个源 IP 保持一段时间。**这一条我要为它负责** —— 如果确实是这样，
   等 2–24 小时会自己恢复。
2. **实例网卡/驱动异常**（TCP offload 卡死）。重启实例通常能恢复。
3. **这台实例挂了云防火墙 / 安全管家 / 高防 IP** 之类的额外产品，

4. 实例本身没有异常，而是**主机上还有什么东西在按尺寸过滤**（可能性最低）。

## 后续补充：试过「本端压小接收窗口」这条绕过路径（2026-10-22，未成功）

思路是：发送方 TCP 只按**接收方通告的窗口**发数据。如果我把 `SO_RCVBUF`
压到 104 字节以下，对端每段就不敢超过它，于是每个包都能过那个约 92 字节的
门槛 —— 这样握手与 200 KB 交付包都能搬完，不必等链路恢复。

实测（`build/_probe_rcvbuf_sweep.py`、`build/_ssh_proxy.py`）：

| 设定 `SO_RCVBUF` | 生效值 | 20 秒内收到 | 能否拿到完整 KEXINIT |
|---|---|---|---|
| 104 | 104 | 104 B | 否（只有第一段） |
| 160 | 160 | 33 B | 否（只有 banner） |
| 256 | 256 | 33 B | 否 |
| 128 / 192 / 384 | — | connect 超时 | 否 |

**不是"窗口换吞吐"的曲线，而是第一个合格包之后整条流被拦。** 所以这条路
走不通，原因不在窗口大小：

1. 小窗口会触发**糊涂窗口避免**（SWS），发送方要等窗口涨起来才发，吞吐被
   压到 `窗口/RTT` ≈ 2.4 B/s —— 连 3–5 KB 的 SSH 握手都要半小时。
2. 更根本的是对流量的**状态判定**：拿到第一段之后就不再放行，说明中间设备
   不是在做"按包长逐包过滤"，而是在按流做抑制。

另外两条也试过，都不可行：

- **改 MTU**：`Set-NetIPInterface -NlMtu` 需要管理员，当前会话是
  `YIRU\18240`（`admin = False`），改不了。
- **走 WSL 改 MSS**：WSL 的 `docker-desktop` 发行版里有 root（`id -u` = 0）
  和 `/sbin/sysctl`，但它走的是另一套 NAT（`eth0 192.168.42.249`，
  `default via 192.168.32.1`），到目标 `:22` **建连即失败**
  （`nc` 报 `punt!`）⇒ 那条路由本身就不通，没法借它发小 MSS 的包。

结论不变：**在实例侧恢复之前，任何下行协议都不可能工作**，我这端无解。

## 2026-10-22 复查：用全球节点做的对照实验（这条最重要）

前面的证据全部来自我一个人、一条出口，所以始终留着一个疑问：会不会只是
**我被拉黑了**？用 `check-host.net` 的多地节点做对照后，这个疑问排除了 ——
同时也带回一条新结论：**丢的不只是大包，小包也在丢**。

### 实验一：ICMP，目标 vs 两个已知正常的阿里云主机

| 目标 | 4 地节点各 ping 4 次 | 汇总 |
|---|---|---|
| **203.0.113.10**（目标） | 印度 2/4、伊朗 3/5、土耳其 4/4、美国 2/4 | **8/16 = 50% 丢** |
| `mirrors.aliyun.com` | 同批节点 | **16/16 = 0% 丢** |
| `www.aliyun.com` | 同批节点 | **16/16 = 0% 丢** |
| `8.137.158.1`（同网段网关） | 同批节点 | 0/8（该网段 ICMP 本身有策略，不作参考） |

### 实验二：TCP 端口，目标 vs 同 /24 邻居

| 目标 | 4 地节点的 TCP 建连 |
|---|---|
| **203.0.113.10:22** | 瑞士 1241 ms ✓、英国 210 ms ✓、**捷克 超时**、**美国 超时** |
| 8.137.158.193:22（邻居） | 中国 218 ms ✓、印尼 302 ms ✓、新加坡 219 ms ✓、美国（无数据） |

邻居 3/3 全通，目标 2/4（**连 SYN-ACK 这种 44 字节的小包也在丢**）。
`check-host.net` 同批还测了三端口：

| 端口 | 全球结果 |
|---|---|
| `:22` | 部分节点可连（1.3 s / 0.2 s） |
| `:3389` | 3 个节点全部可连（0.19–1.29 s） |
| `:8000` | 全部 `Connection timed out`（这条只对我这个 IP 放行，符合安全组预期） |

### 这两组实验把结论收紧成了什么

1. **不是我一个人被拉黑** —— 四个大洲的节点都在丢，所以不是"我扫端口触发了
   清洗"这么简单；至少不是只针对我的源 IP。
2. **不是单纯的大包问题** —— TCP 建连只需要几十字节的小包，也在丢。
   早前"小于 92 字节可通"的阈值，是在**链路状况较好的那几分钟**测到的；
   真实情况是**间歇性、按比例丢包**，各次测量结果不一致（同一批端口
   前后两次运行，`:22` 一次有 banner 一次没有，`:3389` 一次开一次不通）。
3. **间歇性这一点，正好解释了你昨天为什么能用 RDP 进去装 OpenSSH** ——
   那时链路是好的，现在不好了。所以故障更像是**实例的出网/入网链路在
   时好时坏**（网络抖动、底层宿主机问题、或计数型丢包策略），而不是
   一条永久性的按包长过滤规则。

### 因此对"该做什么"的调整

原来建议你等 2–24 小时自愈；现在更建议**主动重启实例**（控制台「重启」，
不是「停止再启动」）—— 间歇性丢包最常见的原因是宿主机网络或网卡 offload
卡死，重启能重置。如果重启后仍然时好时坏，那基本可以判定是这台实例所在的
物理宿主有问题，**提交阿里云工单并附上本文档**（尤其是上面两张全球节点对照
表），要求他们检查该实例的网络与宿主机状态。工单里可以直接写：

> 该实例 `203.0.113.10` 从全球多个节点（印度/伊朗/土耳其/美国）ping 均有
> 约 50% 丢包，同 /24 邻居 `8.137.158.193` 从同批节点全部正常；TCP 22
> 端口连 SYN-ACK 都出现超时。表现为间歇性、按比例丢包，与包长无关。
> 请检查该实例所在宿主机的网络状态。

## 2026-10-23 服务器本机实测：出方向 ≥128 B 全丢，卡在实例侧

> 上面所有结论都是从**外部**测出来的。10-23 第一次进到控制台 VNC，改成从
> **服务器本机**往外测，结论翻转了一次：不是「到某一台机器的路径坏了」，
> 而是**这台实例出方向发不出 128 B 以上的包，换任何目的地都一样**。

### 尺寸扫描（服务器本机执行，每个尺寸 3 个包）

| ICMP payload | → 8.137.158.191 | → mirrors.aliyun.com |
| --- | --- | --- |
| 32 B | 2/3 ~ 3/3 通 | 4/4 通 |
| 64 B | 2/3 通 | — |
| 128 B | **0/3** | **0/4** |
| 200 / 300 / 400 / 500 / 600 / 1200 B | **0/3** | **0/4** |

切口落在 64 B 与 128 B 之间，两个目的地（同地域另一台 ECS、阿里云 CDN）
形状完全一致 ⇒ **与目的地、与运营商链路无关**。

### 同一时刻的环境读数

- `netsh interface ipv4 show subinterfaces`：以太网 MTU **1500**，
  输入 **10.9 MB** / 输出 **32.9 MB**（收得进来、且发出去了大量小包）
- 网卡：`Red Hat VirtIO Ethernet Adapter`，驱动 **100.6.101.58120**，10 Gbps
- `ping -f -l 1200`：不报「需要拆分数据包，但是已设置 DF 标志」⇒ 1200 B
  是整包发出去的，**不是 MTU / 分片问题**
- `netsh int tcp show global`：RSS enabled、接收段合并 enabled（其余默认）
- `Get-NetAdapterBinding`：只有 `ms_lltdio / ms_msclient / ms_server /
  ms_tcpip / ms_tcpip6 / ms_rspndr / ms_pacer` ⇒ **没有第三方过滤驱动**
- `netsh winhttp show proxy`：直接访问；路由表只有一条默认路由出 172.27.143.253
  ⇒ **没有代理 / VPN 劫持**
- 关闭 Tx offload 的候选开关：`IPv4/TCP/UDP Checksum Offload = Rx & Tx Enabled`、
  `Large Send Offload V2 (IPv4/IPv6) = Enabled`、`Offload.Tx.Checksum = All`、
  `Offload.Tx.LSO = Maximal`（关掉后**未确认实际生效**，见下）
- 非系统服务：`AliYunDun`（安全中心）、`aliyun_assist_service`（云助手）、
  `argusagent`（云监控）、`hbrclient`（备份）、Defender 三件套 ⇒ 无其它可疑软件

### 已尝试且无效

1. `netsh int tcp set global rss=disabled rsc=disabled`
2. `Disable-PnpDevice` / `Enable-PnpDevice` 重载 VirtIO 网卡（网卡消失 5~10 s，

3. 下载方向完全正常（pip 走 mirrors 达 111 KB/s）⇒ **只有出方向坏**

> 要用 `Set-NetAdapterAdvancedProperty -RegistryKeyword '*TCPChecksumOffloadIPv4'

### 这条实测修正了 10-20 的哪一句

10-20 的结论里有「同一 /24、同一时刻，只有这一台大包不通」，据此把清洗设备
排在前面。现在从本机测、对**同地域另一台 ECS 也 100% 丢**，说明那句只能推出

1. **实例侧（vNIC 出方向 / 宿主机 vSwitch）** —— 首要嫌疑
2. 宿主机到出口的网络设备
3. 清洗 / 运营商设备 —— 现在基本可排除（连网关都过不去）
