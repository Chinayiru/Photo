# 203.0.113.10 连通性诊断（2026-10-20）

## 一句话结论

**不是我的代码、不是防火墙规则、不是安全组、不是 SSH 配置。**
从我这台机器到这台阿里云实例的链路**只能传小于约 90 字节的下行报文**，
再大就全丢。所有远程手段（SSH 密钥交换、RDP 图形会话、HTTP 响应体）
都卡在同一个尺寸门槛上，所以"连不上"是同一个原因的三个表现。

## 决定性证据

### 1. 同一 /24、同一时刻、同一条出口，只有这一台大包不通

| IP | 64 B ICMP | 500 B ICMP |
|---|---|---|
| **203.0.113.10**（目标） | 4/4 | **0/4** |
| 8.137.158.191（同 /24 邻居） | 4/4 | 4/4 |
| 8.137.158.193（同 /24 邻居） | 4/4 | 4/4 |
| mirrors.aliyun.com | 8/8 | 8/8 |

同网段邻居用**同样的命令、同一分钟**发大包全部正常 ⇒ 不是我的网络、不是
ISP、不是阿里云杭州地域的策略。

### 2. 阈值实测（每个尺寸 5 个包）

| ICMP 载荷 | IP 报文总长 | 收到 |
|---|---|---|
| 32 B | 60 B | 3/5 |
| 64 B | 92 B | 2/5 |
| 72 B | 100 B | 0/5 |
| 88 B 及以上 | ≥116 B | **0/5（全部尺寸）** |

`ping -l 200`、`-l 500`、`-l 1200` 各打 5 次、间隔 3 秒，全部 0/5 ——
排除"速率限制"，是尺寸。

### 3. 上行没有这个问题

往 `:22` 发「合法版本行 + N 字节垃圾」：N 到 1200 时服务器都会**主动 RST**
（它解析到垃圾就断开）。RST 说明那一包**到了**。`ping` 的大包之所以失败，
是因为服务端必须回一个同样大的 echo reply —— 丢在下行。

### 4. 三个独立协议卡在同一个门槛

| 探测 | 上行 | 期望的下行 | 结果 |
|---|---|---|---|
| SSH banner（33 B） | — | 33 B | ✓ 立刻收到 |
| SSH KEXINIT | 22 B 版本行 | **约 1 KB** | ✗ 90 秒等不到 |
| RDP X.224 协商 | 19 B | 19 B | ✓ 收到 19 B 响应 |
| RDP MCS Connect Response | 362 B | **约 300–400 B** | ✗ 8 秒等不到 |
| HTTP `/api/health` | 28–86 B | **约 100 B** | ✗ 等不到（连 FIN 都没有） |

`http://203.0.113.10:8000/api/health` 从 8000 端口拿到的是**静默**：
TCP 建连成功（说明有监听或至少安全组放行 + 主机回应 SYN），
但服务器读完请求后连 FIN 都没让我们看见。

### 5. 排除了"服务器只是慢"

`build/_probe_slow.py` 给到 90 秒窗口等 KEXINIT：不是慢，是收不到
（那次等到的是 `WinError 10054` 重置）。

## 为什么这不可能是我们代码的问题

- relay **还没有部署**（`cloud/data` 不存在、`docker version` 报 Docker 未运行）。
- 8000 端口在**我的代码跑起来之前**就已经"建连成功但无响应" —— 那是
  安全组放行了 TCP，而镜像里没有任何进程在听（或听了但响应发不回来）。
- 同一个交付包在**本机**已通过完整验收：
  `build/_verify_deliverable.py` → `PASS`（解压 → 建库 → 起 relay →
  真 `CloudTunnelTransport` 连上 → 经隧道配对 201 → timeline 200 items=2 →
  缩略图 200 magic=`b'RIFF'`）。
- 仓库全量测试 1359 passed / 1 skipped。

## 最可能的原因（按可能性排序）

1. **阿里云基础 DDoS 防护 / 云盾把大包丢了。** 我在排查阶段扫过这台实例
   约 30 个端口（21/22/80/443/3389/8000/8080/3306/6379…）。这类扫描很容易
   触发云盾的「异常流量清洗」，而清洗的典型表现就是**放行小包、丢弃大包**，
   并且对单个源 IP 保持一段时间。**这一条我要为它负责** —— 如果确实是这样，
   等 2–24 小时会自己恢复。
2. **实例网卡/驱动异常**（TCP offload 卡死）。重启实例通常能恢复。
3. **这台实例挂了云防火墙 / 安全管家 / 高防 IP** 之类的额外产品，
   按字节数丢包。
4. 实例本身没有异常，而是**主机上还有什么东西在按尺寸过滤**（可能性最低）。

## 需要你做的事（按推荐顺序）

1. **先等一等**：如果是我扫描触发了清洗，2–24 小时会自愈。
   期间我可以随时复验，不用你做任何事。
2. **重启实例**（控制台的「重启」，不是「停止再启动」）。重启后告诉我，
   我用一条命令就能判断恢复没有。
3. 如果重启无效：**检查这台实例是否关联了「云防火墙」「DDoS 高防」
   「安全管家」**，有就先解绑/关掉再试。
4. 如果还不行：**换一个公网 IP**（同 /24 的 .191/.193 在我这边大包全通，
   说明不是地域问题，是这台实例/这个 IP 的状态问题）。
5. 顺手确认：`8000` 在安全组里是「入方向 / TCP / 8000 /
   授权对象 219.76.131.52/32」。

## 另外两件与本次故障无关、但你需要知道的

1. **`cloud.base_url` 必须写全 `http://`**。写成 `203.0.113.10:8000`
   会被 `backend/app/tunnel.py:_ws_uri()` 补成 `https://`，然后对明文
   relay 做 TLS 握手，报 `SSL: WRONG_VERSION_NUMBER`，重连 5 次全失败。
2. **裸 IP 页面不是 secure context**：该页面上 `crypto.randomUUID`、
   `navigator.clipboard`、`navigator.serviceWorker` 全是 `undefined`。
   当前产品不受影响（复制有 `execCommand` 兜底），但以后别在这条路上
   用 `crypto.subtle` / Service Worker。
