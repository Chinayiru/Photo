本轮新确认 **3 项缺陷 + 1 项修复不彻底 + 1 项文档漂移 + 2 项待裁决/契约内行为**：

1. **F13（中）断线续传的状态查询接口不是只读的**：`GET /api/uploads/{id}` 对**已完成**的会话返回 `offset=0, complete=false`，并且**把数据库里的 `received` 改回 0**。客户端如果因为 `complete` 响应丢包而重试，会看到"0 字节、未完成"，按 0 重传 → 被服务端以 `409 E1012 上传已结束` 拒绝 → 界面显示"上传失败"，**而照片其实早已入库**。这是本轮唯一一个"日常路径上会被用户看到"的新缺陷。
2. **F14（中）写入口不认"扫描排除目录"**：`POST /api/items/move` 的目标目录、`POST /api/uploads/init` 的 `target_dir` 都可以指向 `data` / `node_modules` / `#recycle` / `.photobridge_tmp`。实测四个目标全部 200/201 成功落盘，照片**先出现在时间线、下一次 rescan 后变成"已丢失"并从界面消失**，且此后 `move`/`rename` 一律 `E1004 照片不存在` —— 只能手工去磁盘上搬回来。
3. **F5 修复不彻底（中低）**：上轮"已删除照片缩略图仍带 1 年 `immutable`"只修了 `/thumb`，**`/preview` 没修**。实测删除后 1600px 预览图仍以**完全相同的字节**、同一 ETag、`private, max-age=31536000, immutable` 端出，带 `If-None-Match` 还能拿到 304。
4. **F18（中低）** 上传会话**从不续期**：`docs/04:3405` 要求"每次成功分片都把 `expires_at` 刷新为 `now + 24h`"，实现里 `append_chunk` 只 `UPDATE upload_sessions SET received = ?`（`uploads.py:753-755`），`expires_at` 自 `init` 之后一动不动。实测传完一半，DB 里 `expires_at` 与 `init` 返回值**秒级完全相同**。后果：一个 2 GB 视频在弱网下传过 24 小时（或用户暂停一天再继续）就会撞上"上传会话已过期"，前端拿到 `409 E1012` 且 `retryable=false` → `releaseSession` → **从 0 重传**，而这恰恰是文档写这段续期的原因（"否则白传"）。这个缺陷与 F13 一起构成"长上传不可靠"的完整故事。
5. **F19（低/文档向）** 上传三个接口的响应字段与 `docs/04` §4.3.1–4.3.3 不一致，详见 §4.8。
6. **F15（待裁决）** `GET /api/system/info` 明文返回本机绝对路径（`roots[].path`、`host_app.autostart.expected`）。但**接口文档 §4.1.1 的字段表明确列了 `path`**，`frontend/src/api/types.ts` 也声明它必需 —— 文档与实现一致，属"契约内的信息暴露面"，不是实现偏离，故列为**需要产品裁决**的项而非缺陷。
7. **F16（低）** `GET /api/search?q=%00` 用一个 NUL 字符就能退化成"全表扫描并返回全部"，绕过"至少一个筛选条件"的守卫。机理是 SQLite 的 `LIKE` 在 NUL 处截断模式串，不是注入。
8. **F17（非缺陷）** `timeline/search` 的 `limit=0`、`-1` 被静默钳到 1。`docs/04` 行 299 记载的行为就是"钳制到 `[1,500]`、不报错"，**契约如此**。

## 3. 上轮 F1–F12 复核：全部已修

> 每条都给出"源码判定行 + 现网实测"，不以测试通过作为修复证据。

### F1（严重）CORS 回显 + `/panel` 只认回环 + 无 Host 校验 —— 三层全部改掉

- **CORS**：`backend/app/core/dispatch.py:183` 的签名是 `def enable_cors(self, *, allow_origins: Iterable[str] | str = (), ...)` —— 默认空元组 = **不启用**；`dispatch.py:392` `_apply_cors` 只给白名单命中的源写头，且回的是**配置里的字符串**而不是请求的 `Origin`。`server.py:163` `router.enable_cors(allow_origins=origins)`，`server.py:161-162` 留了注释："★ 不要写成 `enable_cors()`：那曾经等于谁来都回显"。
  - 实测：`POST /api/pair` 带 `Origin: http://evil.example` / `null` / `http://127.0.0.1:9999` 全部 201 且**无 `Access-Control-Allow-Origin`、无 `Vary`**；预检 `OPTIONS` 无任何 `access-control-*` 头。
- **`/panel`**：`backend/app/auth.py:887-912`，`PANEL_PATHS=("/panel",)`；`server.panel_http` 默认 false（`config.py:148`）时**整条前缀直接 404，连回环也拒**；开启后仍要求 `is_loopback(ctx)`，否则 404 —— **故意不是 403**，避免告诉扫描者"这个路径存在"。`config.py:774-778` 还禁止 `panel_http=true` 时监听 `0.0.0.0`。
  - 实测：实例 A（未开 panel）上 `/panel/pair-code|devices|audit` 全 404；实例 B 回环访问 200/201。
- **Host 校验**：新增 `backend/app/netguard.py`（181 行）：`host_of()` / `allowed_hosts()` / `is_host_allowed()` / `check_host()`；`DEFAULT_TRUSTED_HOSTS={127.0.0.1, localhost, ::1, [::1]}` + `local_ipv4_addresses()` 枚举的真实网卡 + `socket.gethostname()`/`getfqdn()`；端口不参与比对；`trusted_hosts` 写 `["*"]` 才跳过。`auth.py:880` 在**所有分支之前**调用，命中则 `raise NotFound(path)`。
  - 实测：`Host: evil.example` → **404**（带 token 也是 404）；`127.0.0.1:8811`、`localhost:8811`、`192.0.2.10:8811`、`[::1]:8811`、`LOCALHOST:8811`、裸 `127.0.0.1` → 200。
  - 设计取舍（**不是缺陷，但要知道**）：空 Host 放行。理由写在 `netguard.py:31-45`：浏览器发出的每个请求必带 Host（RFC 7230 §5.4），能省 Host 的客户端随手就能写成 `127.0.0.1`，这层校验对它无价值；而 `Ctx` 也由隧道适配器、内部 dispatch、测试夹具构造，那里没有 Host 概念。同文件还记了一条教训："第一版写成空 Host = 拒绝，全量测试炸出 80 个失败 —— 那不是测试写得不好，是这个语义本身错了"。
  - 同一处观察到 `Host: 127.0.0.1:8811.evil.com` → **200**（`host_of` 按第一个冒号切，得到 `127.0.0.1`）。浏览器不会发出这种 Host，纯手写客户端不受影响，**不构成 DNS rebinding 绕过**（rebinding 场景下 Host 是 `evil.example`，已被拦），仅记录。

### F2（中）`declared_taken_at` 无边界 —— 已加双重校验

`backend/app/handlers/uploads.py:235-267` 的 `_opt_float`：先 `math.isfinite(ts)`（挡 `inf`/`nan`），再判 `archive.MIN_ARCHIVE_TS / MAX_ARCHIVE_TS`。注释完整记了原缺陷链条（`1e300` → `datetime.fromtimestamp()` 抛 `OverflowError` → 不在 `EXC_MAP` 里 → 500 → 会话永久 `open` → 攒满 3 个后全站上传被拒一天），以及为什么**不静默夹取**（"客户端显式声明了一个 3000 年后的拍摄时间，多半是它自己的 bug，静默改成'现在'会把照片归到错误的年份目录里"）。

实测：`1e300` / `-1e300` / `99999999999999` → 400「时间戳超出合理范围（1980 年至 3000 年之间）」；`inf` / `"nan"` → 400「时间戳格式不正确」。**无 500，无死会话**。

### 4.1 F13（中）`GET /api/uploads/{id}` 不是只读查询：它会把已完成会话的进度改回 0

**现象**（`H:\.pb_audit\bb_f13flow.py`）

```
② PATCH 全量            → 206  {"offset":9992, ..., "complete":true}
③ complete             → 201  media_id=53 rel='retry/2026/2026-10/20261020_101202.jpg'
④ GET /api/uploads/{id} → 200  {"status":"completed","offset":0,"received":0,
                                "complete":false,"total_size":9992,"media_id":null}
⑤ 按 offset=0 重传      → 409  E1012 "上传已结束"
```

同一时刻 DB 里的 `received` 已被写成 0（探针直接查 `upload_sessions`：`(10000,10000,'completed')` → GET 一次后变 `(0,10000,'completed')`）。**未完成**会话的 GET 是幂等的（连续两次都返回 `offset=1000`，不写坏）。

**根因**（白盒）

- `backend/app/handlers/uploads.py:139`：`received = uploads._reconcile_offset(st.db, sess)`。
- `backend/app/uploads.py:636-659` `_reconcile_offset`：以**磁盘上 `.part` 文件大小**为准（`os.path.getsize(temp)`）；`complete` 成功后 `.part` 已被 `_unlink_temp()` 删除 → `actual=0` → `actual != sess["received"]` → `uploads.py:658` `UPDATE upload_sessions SET received = ?` 写回 0。
- `handlers/uploads.py:148` 再用这个 0 算 `"complete": received >= total_size` → `false`。

日志里能直接看到这条 WARNING（`H:\.pb_audit\bb2\data\logs\agent.log`）：

```
WARNING [backend.app.uploads] 会话 7a5e3e50920f4306951ed2546a12b9f3 的 offset 与磁盘不一致（DB=9992 磁盘=0），以磁盘为准
```

**影响**

`frontend/src/stores/upload.ts:298-310` 的续传分支：

```ts
const st = await api.get<UploadStatusResponse>(`/api/uploads/${task.uploadId}`, ...);
if (st.complete) { task.offset = st.total_size; } else { task.offset = st.offset; }
```

因为 `complete=false`，`task.offset` 被设成 0，接着从 0 重发第一片 → 409 `E1012`（`retryable=false`，`errors.py:49`）→ 任务标 `FAILED`，界面弹"上传已结束，请重新开始"，**而照片已经在库里了**。用户唯一出路是再点一次重试（此时 `uploadId` 已被 `releaseSession` 清空，会重新 `init` 并命中内容去重 → 显示"已存在"）。

触发条件不是"服务端崩了"，而是**客户端没收到 complete 的响应**（切后台被杀、弱网丢包、超时）—— 手机相册上传里这是常态。

**契约偏离**

`docs/04-接口设计文档.md:3507` 定义 `offset` = "**已接收字节数**（客户端从此处继续）"；行 3511 `status` 含 `completed`；行 3516 `media_id` 在 `status='completed'` 时给出。实测响应的 `media_id` 是 `null`（`get_upload` 根本没返回这个字段），也与文档不符。

**顺带确认的两个相邻行为（都正确，不要改坏）**

- 对**已完成**会话调 `DELETE` → `409 E1012`「上传已完成，无法取消」（`H:\.pb_audit\bb_f13abort.py`），不会删掉已归档的照片。
- 对已完成会话重复 `complete` → `200 already_completed:true`，幂等（`uploads.py:801-811`）。

**修复方向（三选一，推荐 ①）**

1. `_reconcile_offset` 在 `sess["status"] != "open"` 时直接 `return int(sess["received"])`，不读磁盘、不写库 —— 已完成会话的进度就是 `total_size`；同时 `get_upload` 补 `media_id` / `dedup` / `final_rel` 字段。
2. 保底做法：`get_upload` 里 `if sess["status"] == "completed": received = int(sess["total_size"])`，仍让 `_reconcile_offset` 管 open 会话。
3. 把 `_reconcile_offset` 的 `UPDATE` 挪到"只有 `status='open'` 才写"，至少先止血（GET 保持只读）。

同时建议给 `test_api_contract.py` 的 `test_upload_status_and_complete_match_types` 补一条"complete 之后再 GET"的断言 —— 现有用例只在 complete **之前**取过一次 GET（`test_api_contract.py:414`），所以 1353 条全绿也发现不了它。

### 4.7 F18（中低）上传会话从不续期：24 小时是"从 init 起算"的绝对期限

```
DB    -> status=expired received=1003（已收的 1003 字节被弃）
```

**影响链**：`frontend/src/stores/upload.ts:236` `if (!(err?.retryable ?? false)) void releaseSession(task);` —— `E1012` 的 `retryable` 是 `false`（`errors.py`），所以 `releaseSession` 清掉 `task.uploadId`，用户点"重试"走 `init` **从 0 开始**，已传的 1003 字节（真实场景可能是 1.8 GB）白费。这正是文档 3405 行想避免的场景。

**为什么定"中低"而不是"中"**：24 小时窗口对"当天传完"的常规场景够用；触发需要**跨天续传**（暂停过夜、或云带宽下 2 GB 传超过一天）。但一旦触发，损失的是**全部已传字节**，且用户没有任何提示说"你必须在 24 小时内传完"。

**修复方向**：在 `_append_chunk_locked` 的那条 UPDATE 里一起刷新：

```python
ttl = float(cfg.upload["session_ttl_hours"]) * 3600.0
new_exp = max(float(sess["created_at"]) + ttl, time.time() + ttl)
db.execute(
    "UPDATE upload_sessions SET received = ?, expires_at = ? WHERE id = ?",
    (new_offset, new_exp, upload_id),
)
```

`docs/04:3321` 已经把这个行为写进 PATCH 的响应字段说明（"每次成功分片都会刷新"），所以改实现即可，文档不用动。顺带：`PATCH` 的响应里应带上 `expires_at`（文档 §4.3.2 字段表列了它，实现没返回 —— 见 F19），否则客户端无从知道自己的会话被续到什么时候。

### 4.8 F19（低，文档向）上传三接口的响应字段与 `docs/04` 不一致

把三个接口的**真实**响应键与文档字段表逐项对比（实测抓取，`H:\.pb_audit\bb_dedup2.py`）：

- `percent` 在**整个后端**里 `grep` 不到（`backend/app/**.py` 无一处 `percent`），文档却在 §4.3.2 与 §4.3.3 都列了它并给了公式，还写了理由"前端进度条直接用，免二次计算"。前端 `upload.ts:500-511` 确实自己算了 `percent` —— 所以**文档描述的是一个从未实现的字段**。

### 5.2 上传链路

- 完整链路：`init 201 → PATCH 206 → complete 201`，返回 `{media_id, rel_path:"手机上传/2026/2026-10/20261020_092658.jpg", dedup:false, sha256}`；重复 `complete` → **200 `already_completed:true`**（幂等，`uploads.py:801-811`）。
- 断点续传：传一半后 GET 返回 `offset=320207`，按该 offset 续传成功 → 206 `complete:true`；`complete` 得 `dedup:true`（同内容秒传）。
- 乱序分片：先发 `bytes 500-999/1000` → **416 `E1011`「分片顺序异常，期望 0，收到 500」**；整片重复 → 206 `duplicate:true` 且 offset 不变；部分重叠 `400-899` → 416；补齐 `500-999` → 206 `complete:true`。`X-Upload-Offset` 头在 416/409 上都带（`uploads.py:721,826`），前端 `uploader.ts:145-158` 据此重新对齐。
- `Content-Range` 8 种畸形写法全部 400 `E1010`：`bytes 0-999/999`、`bytes 5-4/1000`、`bytes 0-999/0`、`bytes=0-999/1000`（等号写法）、`bytes 0-9999999999/1000`、`bytes -1-10/1000`、`bytes 0-999/abc`、超 `chunk_size+1024` 的分片。
- `init` 校验：`size=0/-5` → 400；`size=10^18` → 413 `E1006`；`a.exe` → 400 `E1017`；`.jpg`（无主名）→ 400 `E1017`「不支持的扩展名：无扩展名」；`a.jpg:stream`（NTFS 数据流）→ 400 `E1017`；名字 300 字符 → 400「文件名过长」；未知 root / `../../etc` → 400「媒体目录不存在」；缺 name → 400「缺少文件名」。
- **两段式文件名校验（设计如此，不是漏洞）**：`../escape.jpg`、`..\escape2.jpg`、`CON.jpg`、`a\x01b.jpg`、`a\u202egnp.jpg`、200 字符名在 `init` 阶段**全部 201 放行**（只存进 `declared_name`），`complete` 归档时全部落成 `手机上传/2026/2026-10/<时间戳>.jpg` —— **服务端丢弃用户提供的名字**，库根外 `H:\.pb_audit\bb2\escape.jpg` / `escape2.jpg` 均不存在，DB 里 `rel_path` 也是干净路径。真正的沙箱过滤在 `archive.place()` + `sandbox.resolve`，RLO/穿越/设备名全部无害化。
- 伪装文件（F3）：`PATCH` 206 后 `complete` 400 `E1017`，且会话转 `aborted`、临时文件被删（`uploads.py:834-846`）—— 注释解释了为什么与 sha256 不符的处理相反（"伪装文件的字节再传一万遍也还是 exe"）。

### 5.3 缓存与条件请求

- thumb/preview 成功：`private, max-age=31536000, immutable` + `Vary: Authorization` + ETag（`w320-<mtime>-<size>` / `p1600-...`）。
- raw：`private, max-age=0`，无 ETag；`Range: bytes=0-9` → **206** + `Content-Range: bytes 0-9/3378` + `Accept-Ranges: bytes`；越界 → 416；`HEAD` → 200、`Content-Length` 正确、体 0 字节。
- `If-None-Match`：原值 → 304；大写前缀 `"W320-..."` → 200（前缀大小写敏感）；弱校验 `W/"w320-..."` → 304；去引号裸值 → 304；截断串 → 304（前缀匹配）；`"nonsense"` → 200。比 RFC 7232 宽松（应精确强比较或弱比较），**但方向是"少给 304"之外的"多给 304"** —— 由于 ETag 由 `mtime+size` 构成、同 id 内容不会变，**多给 304 不会导致错误内容**；不记为缺陷，但若将来 ETag 引入更弱的口径需要重新审视。
- 304 响应不带 `Cache-Control`（合法，RFC 7232 §4.1 允许沿用已缓存表示的响应头）。
- `If-Modified-Since` 被忽略（服务端不发 `Last-Modified`），恒 200 —— 合法，因为 ETag 是唯一判据。
- SSE `/api/events`：200、`text/event-stream; charset=utf-8`、`no-store`、`X-Accel-Buffering: no`、`Connection: keep-alive`（`handlers/events.py` 注释说明三个头在 `?once=1` 分支也必须设，否则 hello 帧会被缓存）。

### 5.4 删除 / 移动 / 重命名

- 删除契约：`{deleted, failed[]}`；`ids` 非数组/空数组/含字符串/超 200 项 → 400「一次最多删除 200 项」/「ids 必须是非空数组」/「ids 必须是整数数组」。

1. **`db.py:86` 仍是表级 `UNIQUE(root_id, rel_path)`**。F4 修在应用层（`_update_rel_path` 捕获 `IntegrityError` → 删墓碑 → 重试），任何**未来新增的裸 UPDATE** 都会重新踩坑。建议迁移成 `CREATE UNIQUE INDEX ... WHERE missing = 0`（SQLite 支持部分索引），但要注意 `SCHEMA_VERSION` 升级与旧库迁移路径（`db.py:424` `migrate()`）。

### 10.2 为什么单独立一个 `E1019`，而不复用 `E1009` 或 `E1004`

前端弹给用户的是 `user_hint`（`client.ts:66`、`ViewerView.vue:322`），不是 `message`：

| 若复用 | 用户会看到 | 实际该做的事 |
|---|---|---|
| `E1009` | 「路径不合法」 | 文件还在磁盘上，去把它搬到别的目录 |
| `E1004` | 「内容不存在或已被删除」 | 同上 —— 用户会以为照片被删了 |

两句都把用户带往错误方向。`E1019` 的 `user_hint` 直接写「照片在一个不会被扫描的文件夹里，
请在电脑上把它移到别的目录」，这是一句**可执行**的话。已登记进 `docs/04` §5.2 错误码表。

> ⚠️ 顺带修掉一处**让这个文案白写**的缺陷：`frontend/src/stores/viewer.ts:moveCurrent()`
> 原来 `if (!item) return null;` —— 而 `moved` 为空有三种原因（有意跳过、**真的失败**、
> 响应本身空），失败被 `ViewerView.vue:311` 当成「照片已经在这个目录里了」。
> 也就是说后端把话说清楚了，前端却把它译成一句与事实相反的话。现在 `failed[0]` 会被
> 抛成 `ApiError`。

### 10.3 新建回归文件 `backend/tests/test_audit_20261020.py`（20 条）

一条缺陷对应至少一条**会红**的用例，另有 5 条**反向对照**（正常路径不能被一起挡掉）。
首轮跑出 **8 条失败**，其中 **6 条是用例本身写错**（最典型的三类）：

1. **`_ctx()` 不支持 `headers=`** —— 于是 F5 那两条"已删除照片还能不能拿 304"的用例
   根本没把 `If-None-Match` 送进去，"304 不会发"与"缓存头是否 `no-store`"两件事
   一起变成了恒真断言。**这是本报告 §5.3 已经写过的教训的复发**。
2. **`_state()` 没注入 `indexer`** —— 生产里 `AppState.indexer` 非空，`media_id` 正是
   索引器写回来的。装置缺它时 `media_id` 恒为 `None`，那条断言变成了在验装置缺失。
3. **断言写错了字段** —— `E1019` 的 `message` 是 `ErrorSpec.message`（稳定英文标识符
   `file_in_excluded_dir`），人话在 `detail` / `user_hint`；`/api/search` 的响应跟
   `/api/timeline` 同形，**没有 `hits` 字段**。两处都写成了"在错误的字段里找子串"。

另有 2 条失败是**装置容量**：`MAX_OPEN_SESSIONS = 3` 是并发会话上限（不是文件名数），
反向对照用例连开 4 个会话拿到的是 `E4002 too_many_uploads`，看起来像"这个名字被拒了"。
