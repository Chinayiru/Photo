## 1. 文档信息与安全目标

### 1.1 本文档回答什么

本文档回答三个问题，**只回答这三个**：

1. **怎么防越界**——一个被攻破的手机端，能不能删掉电脑上任意文件？
2. **怎么防越权**——A 手机的令牌，能不能看 B 手机的照片？
3. **怎么防数据丢失**——上传会不会覆盖已有照片？断网会不会留下半截文件？

不回答的问题（各归其位）：接口字段 → [04-接口设计文档](04-接口设计文档.md)；表结构 → [05-数据库设计文档](05-数据库设计文档.md)；具体算法与状态机 → [03-详细设计说明书](03-详细设计说明书.md)；怎么部署加固 → [08-部署与运维手册](08-部署与运维手册.md)。

### 1.2 安全目标（按优先级排序）

| 优先级 | 目标 | 判定标准 | 失败后果 |
|---|---|---|---|
| **G1** | **照片不丢** | 任何操作序列下，`D:\Photos` 已有文件的内容不被覆盖、不被静默删除 | 不可逆的用户数据损失 |
| **G2** | **不越界** | 任何 API 输入都不能让进程读写库目录之外的路径 | 整台电脑沦陷（可删任意文件、可写启动项） |
| **G3** | **不越权** | 未持有有效 `client_token` 的请求拿不到任何媒体字节 | 照片（含 GPS）泄露给局域网内任意设备 |
| **G4** | **云上无媒体** | 云端磁盘、内存、日志中不存在任何照片字节 | 隐私底线被突破，架构核心承诺失效 |
| **G5** | **可追溯** | 所有写操作（删除/移动/上传）在 `audit.log` 有不可抵赖的记录 | 出事无法定位，也无法追责 |
| **G6** | **可用性** | 恶意输入不能让 Agent 崩溃或让 1 核 1 GB 的 VPS OOM | 服务不可用，需人工重启 |

### 1.3 安全范围

**在范围内**：

- 电脑端 Agent：`sandbox.py` / `uploads.py` / `archive.py` / `indexer.py` / `thumbs.py` / `local_server.py` / `tunnel.py`
- 云 Relay：`main.py` / `auth.py` / `devices.py` / `pairing.py` / `tunnel.py` / `protocol.py`
- 手机端 PWA：`frontend/src/**`
- 部署配置：Caddy/Nginx TLS、防火墙、systemd/Docker

**明确不在范围内**：

- 电脑本机已被物理接触且已取得管理员权限（本方案假设**操作系统本身可信**；沙箱只防"应用层越界"，不防"本机管理员"）
- 用户主动把 `client_token` 截图发到公网
- 云服务商（RackNerd/阿里云）在宿主机层面读取内存——这是 IaaS 的固有限制，只能靠二期 E2E 缓解
- 用户自己的账号密码弱口令（单用户系统，密码策略由用户自己负责，但 §4.6 给出建议）

### 1.4 安全设计原则（本项目采用的四条）

| 原则 | 在本项目的落地 |
|---|---|
| **单点收口** | 所有文件访问必须经过 `sandbox.resolve()`，**不存在第二条通往文件系统的路** |
| **默认拒绝** | 白名单而非黑名单：扩展名白名单、魔术字节白名单、路径段白名单、client 操作白名单 |
| **失败安全** | 校验失败一律拒绝并记审计日志，绝不"降级放行"；缩略图生成失败不影响原图 |
| **零信任输入** | 来自隧道的 `path`、`query`、`headers` 全部视为攻击者可控，因为云可能已被入侵 |

> **关键认知**：云端是**不可信边界**。设计文档 §8.3 已明确"云终止 TLS，云理论上能看到明文"。
> 因此电脑端 Agent 必须假设"从隧道收到的每一个字节都可能是攻击者伪造的"，
> 不能因为"请求来自我的云服务器"就降低校验强度。**这一条决定了 §3 沙箱的全部强度。**

## 2. 威胁模型

### 2.1 资产清单

| 编号 | 资产 | 位置 | 敏感度 | 泄露影响 | 丢失/损坏影响 |
|---|---|---|---|---|---|
| **A1** | 照片文件本体 | `D:\Photos`（24 GB，4952 个文件） | **极高** | 私密照片外泄 | **不可逆损失** |
| **A2** | EXIF 元数据（**含 GPS 经纬度**） | 嵌入 A1 | **极高** | 可还原家庭住址、日常轨迹 | 元数据丢失，照片仍在 |
| **A3** | 账号凭证（邮箱 + 密码哈希） | 云端 `cloud.db` | 高 | 账号被接管 → 全部设备 | 无法登录 |
| **A4** | `agent_token`（电脑↔云长期令牌） | 云端 DB + 电脑配置 | **极高** | 可伪造电脑接入云 → 直通照片库 | 电脑失联，需重新注册 |
| **A5** | `client_token`（手机↔云） | 云端 DB（存 hash）+ 手机浏览器存储 | 高 | 单台手机被冒充 | 需重新配对 |
| **A6** | 配对码（6 位数字） | 云端 `pair_codes` + 电脑托盘显示 | 中 | 攻击者绑上一台恶意手机 | 配对失败，重新生成 |
| **A7** | 审计日志 `audit.log` | 电脑 `data/audit.log` | 中 | 暴露操作历史与文件名 | 无法追溯 |
| **A8** | **电脑本身**（文件系统、启动项、注册表） | 用户主机 | **极高** | 整机沦陷，可植入持久化后门 | 需重装系统 |
| **A9** | 索引数据库 `photobridge.db` | 电脑 `data/` | 中 | 暴露完整文件清单、GPS、相机型号 | 重建即可（重新索引） |
| **A10** | 云端流量计数 `traffic` 表 | 云端 `cloud.db` | 低 | 暴露使用习惯 | 无影响 |

**敏感度最高的两项是 A1（照片）和 A8（电脑本身）**。A8 的风险来自 A1 的写权限——设计文档 §8.4 已确认开启"删除/移动/上传进相册"，这意味着**一旦沙箱被绕过，攻击面不是"读照片"，而是"删任意文件"**。这就是 §3 必须做到"极其详细"的原因。

### 2.2 威胁主体（谁可能攻击）

| 编号 | 威胁主体 | 能力假设 | 动机 |
|---|---|---|---|
| **T1** | 外部攻击者（互联网） | 能扫描端口、发任意 HTTP 请求、爆破 | 拿照片、拿肉鸡 |
| **T2** | **云服务器被入侵** | 完全控制云进程与 DB，能伪造任意隧道帧 | 横向打穿到电脑 |
| **T3** | 云服务商偷看 | 能读 VPS 内存与磁盘 | 商业画像、批量采集 |
| **T4** | **手机丢失/被盗** | 持有已配对的浏览器存储 | 直接看照片 |
| **T5** | 局域网内其他设备 | 能 ARP 欺骗、嗅探明文 HTTP、扫 8787 端口 | 看照片、拿令牌 |
| **T6** | 恶意文件（图片炸弹/畸形 EXIF） | 能上传构造的图片 | DoS、内存耗尽、解析器 RCE |
| **T7** | 路径穿越攻击者 | 能构造任意 `path` 参数 | 越界读写任意文件 |
| **T8** | 越权访问者 | 持有合法但低权限的令牌 | 访问他人设备 |
| **T9** | 重放攻击者 | 能录制并重发合法请求 | 绕过一次性校验 |
| **T10** | 中间人（MITM） | 能劫持网络流量（公共 Wi-Fi、恶意热点） | 窃取令牌与照片 |
| **T11** | 供应链攻击者 | 能投毒 PyPI/npm 依赖 | 在 Agent 里植入后门 |

### 2.3 威胁 → 对策矩阵

**可能性评级**：低（需要罕见条件）／中（常规条件下可能）／高（不需要特殊条件）。
**影响评级**：低／中／高／**致命**（照片不可逆丢失或整机沦陷）。

| # | 威胁 | 影响 | 可能性 | 现有对策 | 残余风险 | 一期是否接受 |
|---|---|---|---|---|---|---|
| 1 | 外部攻击者扫到 8787 直连端口 | 致命（可读全部照片） | **中** | ①云端中继为默认通路，直连仅同网；②`client_token` 校验；③启动时检测公网 IP 并拒绝绑定 | 绑 `0.0.0.0` 时同网任何设备可达；直连为**明文 HTTP**，令牌可被同网嗅探 | ⚠️ **部分接受**，见 §6.7（**必须改默认绑定**） |
| 2 | 云服务器被入侵（T2） | 致命 | 中 | ①云端零媒体存储；②云上仅有账号/设备/计数；③隧道帧仍受电脑端沙箱校验 | 攻击者可伪造任意隧道帧 → 但沙箱挡住越界；可读明文照片（TLS 在此终止） | ✅ **接受**（一期），二期 E2E 消除 |
| 3 | 云服务商偷看（T3） | 高（照片+GPS 泄露） | 低（自建 VPS） | 无技术对策；云端不落盘 | 内存中可见明文照片与 EXIF GPS | ✅ **接受**（一期），二期 E2E 消除 |
| 4 | 手机丢失（T4） | 高 | 中 | ①设备级 `client_token`，可在云端单独撤销；②撤销后立即失效；③Service Worker 缓存需清理 | 丢失到撤销之间的窗口内可看全部照片；离线缓存可能残留 | ✅ **接受**，靠"快速撤销"缓解 |

| 6 | 路径穿越（T7） | 致命 | 中 | §3 七步沙箱，逐段校验 + realpath 边界断言 + 重解析点拒绝 | TOCTOU（校验与打开之间的竞态）需靠"打开时复核"消除 | ✅ **接受**（已缓解到低） |

| 9 | 越权访问（T8） | 高 | 中 | 每个 `/d/{device_id}/**` 请求都校验 `client.device_id == path.device_id` | 云被入侵时可绕过；但电脑端仍会复核 | ✅ **接受** |

| 13 | 供应链投毒（T11） | 致命 | 低 | ①`requirements.txt` 带 hash 锁定；②`pnpm-lock.yaml`；③最小依赖 | 传递依赖的传递依赖无法完全审计 | ✅ **接受**，靠审计与最小化缓解 |

| 17 | 云端磁盘写满（日志膨胀） | 中 | 中 | 日志轮转 + 只记元数据不记字节 | 无 | ✅ **接受** |

### 2.4 一期明确接受的风险及理由

以下风险**在一期被显式接受**，并记录到 [11-风险登记册与决策记录](11-风险登记册与决策记录.md)：

**R-1：云端 TLS 终止导致云可见明文（对应威胁 2、3）**

- **接受理由**：①云是用户自建 VPS，不是第三方网盘；②云端零媒体落盘，风险窗口仅限内存中的转发瞬间；③设计文档 §15.2 已论证——一期最大风险是"隧道多路复用 + 流控 + 断点续传这套架构能不能跑通"，叠加密钥协商会把调试难度翻倍，而收益在当前场景下很低；④协议已预留 `flags` 位与 `enc` 字段，二期填充实现即可，不改协议结构。
- **残余风险**：4199/4915（**85.4%**）的照片带 GPS IFD（实测数据），云端可见完整位置轨迹。
- **复评触发条件**：①改用第三方云服务商；②新增多用户；③照片涉及他人隐私。

**R-2：局域网直连为明文 HTTP（对应威胁 1、5、11）**

- **接受理由**：直连只在手机与电脑同处一个受信 Wi-Fi 时启用；家用网络的可信度足够；直连带来 10~50 倍速度提升且不消耗云带宽。
- **残余风险**：同一 Wi-Fi 下的其他设备（室友、访客、被入侵的智能家居）可嗅探令牌与照片。
- **缓解措施**：见 §6.7，**必须实施**（默认绑 `127.0.0.1`、显式开启、绑具体私网网卡、检测公网 IP）。
- **复评触发条件**：用户经常在不可信 Wi-Fi（酒店/咖啡厅）下使用直连。

**R-3：6 位配对码的数学强度有限（对应威胁 12）**

- **接受理由**：配对码必须"人类可读可输入"，6 位是体验与安全的折中；且配对需要先通过账号登录（单账号系统），攻击者得先有密码。
- **残余风险**：见 §4.5 的定量分析。
- **缓解措施**：按账号/设备全局锁定（而非按 code 锁定）+ 未认证请求限流。

**R-4：假设电脑本机可信（对应威胁 21）**

- **接受理由**：本方案的沙箱是**应用层沙箱**，防的是"通过 API 越界"，不是"本机管理员作恶"。任何用户态程序都无法防御同机管理员。
- **残余风险**：本机其他恶意软件可读 `config.json` 中的 `agent_token`，可直接读库目录。
- **复评触发条件**：电脑上运行了来源不明的软件。

**R-5：一期不做 E2E 加密**

- **接受理由**：见 R-1 与设计文档 §15.2。
- **实施约束**：**协议必须从一期就预留字段**（帧头 `flags` 位、`REQ_HEAD.enc`），否则二期要改协议。

## 3. 路径沙箱设计（安全核心）

> `backend/app/sandbox.py` 是**整个项目最重要的一个文件**。
> 它一旦有漏洞，G1（照片不丢）和 G2（不越界）同时失效。
> 本节按"为什么需要 → 唯一入口约定 → 七步逐条详述 → Windows 攻击面全清单 → 参考实现 → 恶意用例表"展开。

### 3.1 为什么必须有沙箱

**先看没有沙箱时会发生什么。** 设计文档 §8.4 确认开启写权限，Agent 的运行身份是**用户自己的账号**，该账号对 `E:\` 盘和 `C:\Users\alice\` 有**完全控制权**。如果接口实现是这样的：

```python
# ❌ 错误写法：把客户端给的 name 直接拼进路径
target = os.path.join(UPLOAD_DIR, req.name)
# req.name = "..\\..\\..\\Users\\18240\\AppData\\Roaming\\Microsoft\\Windows\\Start Menu\\Programs\\Startup\\evil.bat"
```

攻击者只要在 `name` 里写上面那一串，一次上传请求就能在**开机启动项**里落一个可执行文件。下次开机即持久化。

**更糟的是删除接口**：设计文档允许删除。如果删除走的是拼接路径，`POST /api/items/delete {"path": "..\\..\\..\\"}` 的后果不需要再解释。

**结论**：单一根库 + 写权限 = **一旦穿越就能删任意文件**。沙箱不是"锦上添花的安全加固"，它是**写权限能被允许的唯一前提**。设计文档 §8.4 的四条硬约束里，第 1 条"所有文件操作必须过沙箱"是其余三条的地基。

### 3.2 沙箱的唯一入口约定

**硬规则**：`backend/app/` 下的**任何模块**，只有 `sandbox.py` 允许出现 `open()` / `Path.read_*` / `Path.write_*` / `shutil.*` / `os.remove` / `os.rename` / `os.replace` 等直接文件系统调用。其余模块必须调用：

```python
from app.sandbox import resolve, open_read, open_write, safe_delete, safe_replace

p = resolve(root_cfg, rel_path, need="read")     # 只做校验与规范化，不打开文件
with open_read(root_cfg, rel_path) as f:         # 校验 + 打开，TOCTOU 安全
    ...
```

**用 lint 强制**：见 §10 的编码规范检查脚本 `scripts/check_sandbox.py`，扫描 `backend/app/**`，命中禁用 API 且文件不在白名单中的一律失败。

### 3.3 七步校验逐条详述

设计文档 §8.1 给出了七步骨架。下面**逐条展开**：检查什么、为什么、绕过方式、代码骨架。

---

#### 第 1 步：拒绝绝对路径、盘符、UNC、前导分隔符

**检查什么**

| 形态 | 示例 | 判定 |
|---|---|---|
| 前导正斜杠 | `/etc/passwd`、`/Windows/System32` | 拒绝 |
| 前导反斜杠 | `\Windows\System32` | 拒绝 |
| UNC 路径 | `\\server\share\a.jpg` | 拒绝 |
| 长路径前缀 | `\\?\C:\Windows` | 拒绝 |
| 设备命名空间 | `\\.\C:`、`\\.\PhysicalDrive0`、`\\?\GLOBALROOT\Device\...` | 拒绝 |
| 盘符绝对 | `C:\Windows\win.ini` | 拒绝 |
| 盘符相对 | `C:..\..\secret.txt` | 拒绝 |
| 前导空格 | ` C:\Windows`、`  ok.jpg` | 拒绝 |

**为什么**

`os.path.join(root, "C:\\Windows")` 在 **Windows 上会丢弃 root**，直接返回 `C:\Windows`——因为 Windows 的 `join` 遇到带盘符的第二个参数时整体替换。所以"用 join 拼路径"这个看起来安全的写法，在 Windows 上是**漏洞**。

**绕过方式（攻击者视角）**

1. `..\` 穿越（第 2 步处理）
2. `C:` 盘符替换（本步处理）—— Windows 独有，POSIX 背景的开发者最容易漏
3. `\\?\` 长路径前缀：**绕过 MAX_PATH 检查**，同时**绕过 Win32 规范化**——`\\?\C:\Windows\..\Windows` 中的 `..` 不会被 Win32 层消解，直接交给文件系统
4. `\\.\` 设备命名空间：`\\.\C:` 直接拿卷句柄；`\\.\PhysicalDrive0` 拿裸盘
5. `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\...` 读卷影副本，**绕过文件锁与权限**
6. 混合分隔符：`/\/\/`、`\/\/`
7. 前导空格：` C:\Windows`（实测 `os.path.abspath` **不会**去掉空格）

**实测确认**（本机 Windows，Python 3.13 + Pillow 12.3.0）：

```
Path(r'\\?\C:\Windows').resolve()        -> '\\?\C:\Windows'          ← 未拒绝！
Path(r'\\.\C:').resolve()                -> '\\.\C:'                  ← 未拒绝！
Path(r'\\.\PhysicalDrive0').resolve()    -> '\\.\PhysicalDrive0'      ← 未拒绝！
Path(r'\\?\GLOBALROOT\Device\...').resolve() -> OSError [WinError 6] 句柄无效
os.path.abspath('NUL')                   -> '\\.\NUL'                  ← 被自动转成设备路径
```

**关键发现**：`Path.resolve()` **不会**拒绝设备命名空间，它把 `\\?\C:\Windows` **原样返回**。所以**必须在拼路径之前**用字符串前缀检查拦下，不能指望 `resolve()` 帮你。

**代码骨架**

```python
_DRIVE_RE = re.compile(r"^[A-Za-z]:")

def _step1_reject_absolute(rel: str) -> None:
    if rel.startswith(("\\\\", "//")):
        raise SandboxError("E_PATH_ABSOLUTE", "UNC 或设备命名空间")
    if rel.startswith(("\\", "/")):
        raise SandboxError("E_PATH_ABSOLUTE", "前导分隔符")
    if _DRIVE_RE.match(rel):
        raise SandboxError("E_PATH_ABSOLUTE", "带盘符")
    if rel != rel.lstrip(" \u00a0"):          # 前导空白
        raise SandboxError("E_PATH_INVALID", "前导空白")
```

---

#### 第 2 步：拒绝 `..` 段、空段、`.` 段、NTFS 数据流 `:`、保留设备名

**检查什么**（按段拆分后逐段检查）

| 检查 | 拒绝示例 | 理由 |
|---|---|---|
| `..` 段 | `../a.jpg`、`a/../../b.jpg` | 经典穿越 |
| 空段 | `a//b.jpg` | 规避正则的常见手法 |
| `.` 段 | `./a.jpg`、`a/./b.jpg` | 同上；规范化本身有歧义 |
| `:` | `a.jpg:hidden`、`a.jpg:$DATA`、`a.jpg::$INDEX_ALLOCATION` | **NTFS 备用数据流（ADS）** |
| 保留名 | `CON`、`CON.jpg`、`NUL`、`AUX.txt`、`COM1.jpg`、`LPT9`、`nul.tar.gz` | Windows 设备名 |
| 尾随点/空格 | `a.jpg.`、`a.jpg `、`a.jpg...`、`a.jpg\t` | Windows 静默去除 |
| 非法字符 | `<>:"|?*` 与 `\x00`-`\x1f` | 文件系统不允许，且常被用作注入 |
| `~` | `PROGRA~1` | 8.3 短名，见 §3.4.1 |
| 单段 > 255 | 300 个 `a` + `.jpg` | 文件系统上限 |
| 总长 > 240 | 三层各 100 字符 | 见 §3.4.9 |

**为什么**

- **空段与 `.` 段**：攻击者用 `a//../../b` 或 `a/./../../b` 试图让只匹配 `..` 的正则失效。实测：`sub//ok.jpg` 在朴素实现下被 Windows 当作 `sub/ok.jpg` **正常通过**。**本项目的策略是"空段与 `.` 段一律拒绝"**，而不是规范化掉——拒绝比规范化安全，因为规范化本身有歧义。
- **ADS（NTFS 备用数据流）**：**Windows 最容易被忽略的严重攻击面**。`file.jpg:hidden.exe` 是**一个文件的两个流**：主文件 `file.jpg` 显示 1 字节，备用流 `hidden.exe` 可装**任意可执行内容**。实测确认：

  ```
  创建 ADS 成功: ok.jpg:ads
    主文件大小 = 1
    目录列表:  ok.jpg              1 字节
              ok.jpg:ads:$DATA    11 字节     ← 只有 dir /r 才看得到
  os.path.exists("ok.jpg:hidden") -> False      ← 存在性检查也失效
  ```

  **攻击场景**：上传 `evil.exe:a.jpg`，扩展名检查看到 `.jpg` 通过，落盘后是 `evil.exe` 的一个名为 `a.jpg` 的备用流。**任何 `:` 必须无条件拒绝。**
- **保留设备名**：`CON`、`PRN`、`AUX`、`NUL`、`COM1`-`COM9`、`LPT1`-`LPT9` 在 Windows 上是**设备**不是文件。关键陷阱：**`CON.jpg` 也是设备**！Windows 会忽略保留名后的扩展名。实测 `os.path.abspath('NUL')` 返回 `\\.\NUL`，证明系统层面确实特殊处理。正确做法是取**第一个点之前的部分**再比较：`s.split(".")[0].upper() in RESERVED`，这样 `CON`、`CON.jpg`、`CON.tar.gz`、`nul.txt` 全部命中。
- **尾随点与空格**：Win32 层会**静默去掉**文件名末尾的点和空格。实测：`exists('ok.jpg.')` 返回 **True**（即被当成 `ok.jpg`）；`exists('ok.jpg ')` 返回 **True**；但 `exists('  ok.jpg')` 返回 False（前导空格保留）。**这会造成"校验的文件名"与"实际落盘的文件名"不一致**——攻击者构造 `a.jpg.` 与 `a.jpg` 指向同一文件，绕过"不覆盖已有文件"检查：先查 `a.jpg.` 不存在（其实 `a.jpg` 存在），再写入，**覆盖成功**。因此尾随点/空格必须在段级直接拒绝，**不允许"自动去除"**。

**绕过方式**

1. 大小写混写保留名：`con`、`Con.JpG` → 必须 `.upper()` 后比较
2. 保留名 + 多级扩展名：`CON.tar.gz` → 必须只取第一个点之前
3. ADS 变体：`a.jpg::$DATA`、`a.jpg:stream:$DATA`、`a.jpg:stream:stream2` → **任何 `:` 一律拒绝**
4. 尾随点/空格组合：`a.jpg .`、`a.jpg. `、`a.jpg ...`
5. Unicode 空白：`a.jpg\u00a0`（不换行空格）—— 实测**通过了朴素实现**（Windows 不会去掉 `\u00a0`，但会去掉 `\u0020`）。检查必须同时覆盖 `\u0020`、`\u00a0`、`\t`。
6. 编码绕过：URL 编码 `%2e%2e`、`%00`、双重编码 `%252e` —— **实测朴素实现全部放行**（因为 `%` 是合法字符）。必须在**路由层**先做 URL 解码，沙箱只处理解码后的字符串，同时**拒绝含 `%` 的段**作为纵深防御。

**代码骨架**

```python
WIN_RESERVED = {"CON", "PRN", "AUX", "NUL",
                *(f"COM{i}" for i in range(1, 10)),
                *(f"LPT{i}" for i in range(1, 10))}
ILLEGAL_CHARS = set('<>:"|?*%') | {chr(c) for c in range(0x20)} | {"\x7f", "~"}
MAX_SEG_LEN = 255

def _step2_validate_segments(rel: str) -> list[str]:
    norm = rel.replace("\\", "/")
    if norm.endswith("/"):
        norm = norm.rstrip("/")            # 允许单个尾随分隔符（目录语义）
    clean: list[str] = []
    for s in norm.split("/"):
        if s in ("", "."):
            raise SandboxError("E_PATH_SEGMENT", "空段或 . 段")
        if s == "..":
            raise SandboxError("E_PATH_TRAVERSAL", ".. 穿越")
        if ":" in s:
            raise SandboxError("E_PATH_ADS", "NTFS 数据流或盘符")
        if set(s) & ILLEGAL_CHARS:
            raise SandboxError("E_PATH_CHAR", "非法字符")
        if len(s) > MAX_SEG_LEN:
            raise SandboxError("E_PATH_TOO_LONG", "单段超长")
        if s != s.rstrip(" \u00a0.\t"):
            raise SandboxError("E_PATH_TRAILING", "尾随点或空白")
        if s != s.lstrip(" \u00a0"):
            raise SandboxError("E_PATH_TRAILING", "前导空白")
        if s.split(".")[0].upper() in WIN_RESERVED:
            raise SandboxError("E_PATH_RESERVED", "Windows 保留设备名")
        clean.append(s)
    if not clean:
        raise SandboxError("E_PATH_INVALID", "无有效路径段")
    return clean
```

> **注意**：把 `%` 与 `~` 加入 `ILLEGAL_CHARS` 是**纵深防御**。正常相对路径不需要它们；放行 `%` 会让 `%2e%2e`、`%00` 有可乘之机；放行 `~` 会打开 8.3 短名（§3.4.1）。实测确认库中 **0 个文件**含 `~` 或 `%`。

---

#### 第 3 步：拒绝单段 > 255 与非法字符

已在第 2 步合并实现。**单独强调一点**：段长度限制用**字符数**而非字节数，因为 NTFS 的限制是 255 个 UTF-16 码元。中文目录名（如 `全部备份`）是 4 个字符，按字节算是 12 字节——**用字节数判断会误拒**，用字符数判断才正确。

同时必须检查**总长度**：见 §3.4.9。

---

#### 第 4 步：`p = (root / rel).resolve(strict=False)`

**检查什么**：把相对路径拼到根上，然后做**规范化 + 重解析点消解**。

**为什么用 `strict=False`**：写操作的目标文件可能**尚不存在**（上传新文件），`strict=True` 会抛 `FileNotFoundError`。但 `strict=False` 有陷阱：它**不检查路径是否存在**，因此也不检查中间段是否是重解析点（Windows 上 `Path.resolve` 只对存在的部分做消解）。

**绕过方式与对策**

- 中间目录不存在 → `Path.resolve` 原样返回，不消解。**对策**：用 `os.path.realpath` 而非 `Path.resolve`。
- 攻击者先建 junction 再穿越 → 见第 5 步。

**代码骨架**

```python
def _step4_realpath(root: Path, clean: list[str]) -> tuple[Path, Path]:
    root_real = Path(os.path.realpath(root))
    cand = root_real.joinpath(*clean)
    real = Path(os.path.realpath(cand))       # 消解已存在的 junction / symlink 前缀
    return cand, real
```

> **实测对照**：`Path.resolve(strict=False)` 与 `os.path.realpath` 在 junction 场景下结果**一致**（都正确消解 `realpath(junc/ok.jpg)` → `...\root\sub\ok.jpg`），但 `realpath` 对"末尾段不存在但前缀是 junction"更可靠。本项目统一用 `os.path.realpath`。

---

#### 第 5 步：逐段检查 symlink / junction / mount point / reparse point

**检查什么**：从根开始逐段向下走，任何一段如果是**重解析点（reparse point）**，一律拒绝。

**为什么必须拒绝而不是"消解后放行"**

消解后放行是常见做法（`realpath` 后判断是否在根内），但本项目**选择更严格的拒绝策略**，理由：

1. **消解后放行有 TOCTOU 窗口**。实测演示：

   ```
   mklink /J link sub          → Path(link/ok.jpg).resolve() = ...\root\sub\ok.jpg    在 root 内 ✓
   rmdir link
   mklink /J link ..\outside   → Path(link/ok.jpg).resolve() = ...\outside\ok.jpg     在 root 外 ✗
   ```

   同一个 `rel_path`，在**两次调用之间**结果从"安全"变成"越界"。攻击者只要能在这两个时刻之间替换 junction（例如通过另一个 API 的并发请求），就能打穿。
2. **库目录里合法地不应该有重解析点**。用户的照片库是普通文件夹树。出现 junction 只有两种可能：①攻击者建的；②用户自己做了目录映射（此时应显式配置为另一个 root，而不是藏在库内部）。**两种情况都应拒绝并报警**，而不是静默跟随。

**Windows 上怎么检测重解析点**（本步的技术难点）

`os.path.islink()` 在 Windows 上**只对符号链接返回 True，对 junction 返回 False**。实测：

```
mklink /J junc sub  → os.path.islink(junc) = False                 ← 漏检！
                    → os.lstat(junc).st_file_attributes = 0x410
                      0x400 位命中 = True                          ← 正确
```

**正确的检测方法**是检查 `st_file_attributes` 的 `FILE_ATTRIBUTE_REPARSE_POINT (0x400)` 位：

```python
FILE_ATTRIBUTE_REPARSE_POINT = 0x400

def _is_reparse_point(p: Path) -> bool:
    """检测 symlink / junction / mount point / OneDrive 占位符等一切重解析点。"""
    try:
        st = os.lstat(p)
    except OSError:
        return False                       # 不存在 → 不是重解析点
    if stat.S_ISLNK(st.st_mode):
        return True                        # POSIX 风格符号链接
    return bool(getattr(st, "st_file_attributes", 0) & FILE_ATTRIBUTE_REPARSE_POINT)
```

覆盖的重解析点类型：

| 类型 | 创建方式 | `islink` | `0x400` 位 |
|---|---|---|---|
| 符号链接（文件/目录） | `mklink` / `New-Item -ItemType SymbolicLink` | ✅ True | ✅ True |
| **目录联接（junction）** | `mklink /J` | ❌ **False** | ✅ True |
| 卷挂载点 | `mountvol` | ❌ False | ✅ True |
| OneDrive/云占位符 | OneDrive 文件按需 | ❌ False | ✅ True |
| AppExecLink | Microsoft Store 应用 | ❌ False | ✅ True |
| WSL 互操作链接 | `\\wsl$\` | — | ✅ True |

**绕过方式**

1. **只用 `islink` 检查** → junction 漏检（实测确认）。**这是最容易犯的错。**
2. **只做一次 `realpath` 边界断言** → TOCTOU 打穿（见上）。
3. **以为"Windows 上创建符号链接需要管理员权限，所以没事"** → junction **不需要管理员权限**。实测 `mklink /J` 返回 **rc=0（成功）**，而 `mklink`（符号链接）返回 **rc=1「你没有足够的权限执行此操作」**。**攻击者最可能用的是 junction，不是符号链接。**
4. **硬链接**：`mklink /H` 创建硬链接，`st_file_attributes` **不含** 0x400 位（硬链接不是重解析点）。硬链接只能指向同卷文件，**无法跨卷**。风险：攻击者在库内建一个指向库外同卷文件的硬链接，边界断言会通过（路径确实在库内），但内容来自库外。**缓解**：库在 `E:`，用户敏感数据多在 `C:`，跨卷不可达；剩余风险接受，但审计应记录 `st_nlink > 1` 的异常文件（见 §6.6）。
5. **大小写差异**：`mklink /J LINK sub` 后用 `link/ok.jpg` 访问，Windows 大小写不敏感，仍命中。

**代码骨架**

```python
def _step5_reject_reparse(root_real: Path, clean: list[str]) -> None:
    cur = root_real
    for seg in clean:
        cur = cur / seg
        if _is_reparse_point(cur):
            audit_security("reparse_rejected", str(cur))
            raise SandboxError("E_PATH_REPARSE", f"路径段是重解析点：{seg}")
```

> **注意顺序**：本步必须在 `realpath` **之前**对**原始段**做检查（因为 `realpath` 会把 junction 消解掉，消解后就再也看不到它是重解析点了）。同时在第 6 步之后再检查一次**解析后的路径**，形成"检查 → 解析 → 再检查"的双保险（见 §3.5）。

---

#### 第 6 步：断言 p 位于 realpath(root) 之内（**大小写不敏感**）

**检查什么**：解析后的绝对路径必须落在根目录之内。

**为什么必须大小写不敏感 + 不能用前缀比较**

Windows 文件系统大小写不敏感（NTFS 默认）。实测：

```
os.path.exists('OK.JPG')  ->  True        ← 大写也能命中 ok.jpg
os.path.commonpath([r'E:\Software\相册\a', r'e:\software\相册']) -> 'E:\Software\相册'
```

两种错误写法都要防：

```python
# ❌ 错误写法 1：前缀比较，被 "相册-备份" 绕过（字符串确实以 "相册" 开头）
if not str(real).startswith(str(root_real)):
    raise ...

# ❌ 错误写法 2：大小写敏感，SOFTWARE vs software 场景误拒
if not str(real).startswith(str(root_real)):
    raise ...

# ✅ 正确写法：normcase + commonpath（同时解决大小写与前缀歧义）
if os.path.normcase(os.path.commonpath([str(real), str(root_real)])) != \
   os.path.normcase(str(root_real)):
    raise SandboxError("E_PATH_ESCAPE", "解析后越出根")
```

**为什么 `commonpath` 能防前缀歧义**：实测 `os.path.commonpath([r'E:\a\b', r'E:\a\bc'])` 返回 **`E:\a`**（不是 `E:\a\b`），所以 `E:\a\bc` 会被正确判定为越界。而 `startswith` 会误判为"在 `E:\a\b` 内"。

**额外注意**：`commonpath` 在**跨盘符**时抛 `ValueError`（`E:` vs `C:`）。必须捕获并转为"拒绝"：

```python
try:
    common = os.path.commonpath([str(real), str(root_real)])
except ValueError:                       # 不同盘符
    raise SandboxError("E_PATH_ESCAPE", "跨盘符")
```

**绕过方式**

1. 前缀歧义（`相册` vs `相册-备份`）→ 用 `commonpath`
2. 大小写差异（`SOFTWARE` vs `software`）→ 用 `normcase`
3. 跨盘符 → 捕获 `ValueError`
4. 短文件名（8.3）：`PROGRA~1` 是 `Program Files` 的 8.3 名。`Path.resolve` **不展开**短名（实测原样返回），边界断言会把它当根内的普通名字 → **放行**。**对策**：第 2 步拒绝含 `~` 的段（首选；实测库中 0 个文件含 `~`）。若必须支持，用 `GetLongPathNameW` 展开后再断言。
5. Unicode 归一化：见 §3.4.8。

---

#### 第 7 步：权限模型（`need` 与 root mode）

**检查什么**

| root mode | `need='read'` | `need='write'` | 说明 |
|---|---|---|---|
| `readonly` | ✅ 允许 | ❌ 拒绝 | 只读库（如外部备份盘） |
| `upload` | ✅ 允许 | ✅ 允许（仅追加） | 可上传新文件，不可删除/移动/改名 |
| `readwrite` | ✅ 允许 | ✅ 允许 | 完整权限（设计文档 §8.4 的选择） |

**为什么**

设计文档 §8.4 允许删除/移动/改名。但"允许删除"和"允许覆盖"是**两件事**：即使 mode 是 `readwrite`，**上传路径也绝不能覆盖已有文件**（G1 的核心）。因此权限检查之后还有一层**操作级检查**（见 §6.5）：

- `need='write'` + 操作是"新建" → 要求目标**不存在**，否则改名加序号
- `need='write'` + 操作是"删除" → 要求目标**存在**，且走 `send2trash`
- `need='write'` + 操作是"移动" → 要求**源存在、目标不存在**

**代码骨架**

```python
_WRITE_MODES = {MODE_UPLOAD, MODE_READWRITE}

def _step7_check_mode(root_cfg: dict, need: str) -> None:
    mode = root_cfg.get("mode", MODE_READONLY)
    if mode not in VALID_MODES:
        raise SandboxError("E_ROOT_MODE", f"未知 root mode: {mode}")
    if need == "read":
        return                                   # 三种 mode 都允许读
    if need == "write" and mode not in _WRITE_MODES:
        raise SandboxError("E_ROOT_READONLY", f"root {root_cfg.get('id')} 为只读")
```

**绕过方式**

1. `need` 参数从请求里来 → **必须由服务端代码硬编码**，绝不能由客户端指定。
2. root 配置被篡改（`config.json` 可写）→ 本机可信假设（R-4）。
3. 上传目标目录落在 `readonly` root 内但通过 `target_dir` 参数指向另一个 root → **对策**：`target_dir` 必须解析为 `(root_id, rel_path)` 二元组，不允许只给路径。

### 3.4 Windows 特有攻击面（重点）

> 本节每一条都经过**本机 Windows 11 + Python 3.13 实测**。实测结果用 `实测：` 标注。
> 这些是 POSIX 背景的开发者**几乎必然踩中**的坑——Linux 上安全的代码在 Windows 上不安全。

#### 3.4.1 短文件名（8.3 格式，如 `PROGRA~1`）

**原理**：为兼容 DOS，NTFS 可为每个长名文件生成一个 8.3 别名。`Program Files` 的别名是 `PROGRA~1`。

**危害**：绕过基于"名字"的黑名单。攻击者传 `PROGRA~1/evil.jpg`，字符串检查看不到 `Program Files`。

**实测**：

```
Windows 11 的 C: 卷 dir /x 未列出任何 8.3 短名   → 该卷 8dot3name 默认禁用
fsutil 8dot3name query C:                        → 权限被拒（无法确认全局状态）
Path.resolve('PROGRA~1')                          → 原样返回，不展开
```

**结论与对策**：Windows 11 默认禁用 8.3 生成，**风险低于预期**，但**不能依赖这个默认值**（用户可手动开启 `fsutil 8dot3name set 0`，老卷可能保留）。

- **首选对策**：第 2 步把 `~` 加入非法字符集。实测真实库中 **0 个文件**含 `~`，无副作用。
- **备选对策**（若未来必须支持）：用 `GetLongPathNameW` 展开后再做边界断言。

#### 3.4.2 NTFS 备用数据流（ADS，`file.jpg:hidden.exe`）

**原理**：NTFS 文件可以有多条数据流。`file.jpg:hidden.exe` 表示"文件 `file.jpg` 的名为 `hidden.exe` 的备用流"。默认流是 `:$DATA`。

**危害**（最严重的 Windows 特有攻击面）：

1. **扩展名检查失效**：`evil.exe:a.jpg` 的扩展名看起来是 `.jpg`，通过白名单。
2. **存在性检查失效**：实测 `os.path.exists("ok.jpg:hidden")` → **False**，即使该流存在。
3. **目录列表看不到**：实测 `dir` 只显示主文件 `ok.jpg`（1 字节），必须 `dir /r` 才显示 `ok.jpg:ads:$DATA`（11 字节）。
4. **内容可任意**：实测成功写入 11 字节到 `ok.jpg:ads`，主文件大小不变。
5. **`Zone.Identifier` 是合法 ADS**：从网上下载的文件会带 `file.jpg:Zone.Identifier`。这证明 ADS 在正常使用中确实存在，不能靠"不会有 ADS"来假设。

**实测**：

```
创建 ADS 成功: ok.jpg:ads
  主文件大小 = 1 字节
  dir 列表:  ok.jpg               1 字节
  dir /r:    ok.jpg:ads:$DATA    11 字节
os.path.exists("ok.jpg:hidden") -> False
Path.resolve('ok.jpg:hidden')   -> 原样返回（不报错）
```

**对策**：**第 2 步遇到任何 `:` 无条件拒绝**。不区分是盘符还是 ADS——含 `:` 的相对路径段永远非法。

#### 3.4.3 设备名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`-`COM9`、`LPT1`-`LPT9`，以及带扩展名的 `CON.jpg`）

**原理**：这些名字在 Windows 上指向**字符设备**，不是文件。

**关键陷阱**：**扩展名会被忽略**。`CON.jpg`、`CON.tar.gz`、`nul.txt` 全部是设备。

**实测**：

```
Path.resolve('CON')     -> 原样返回，不报错
Path.resolve('CON.jpg') -> 原样返回，不报错        ← 扩展名不救你
Path.resolve('nul.txt') -> 原样返回
os.path.abspath('NUL')  -> '\\.\NUL'                ← 被自动转成设备路径！
```

最后一行是**决定性证据**：Python 的 `abspath` 主动把 `NUL` 转成了设备命名空间 `\\.\NUL`，说明系统层面确实特殊处理。

**危害**：写 `CON` 会写到控制台；写 `NUL` 会静默丢弃（**上传接口返回 200 但文件不存在**，用户体验上是"照片凭空消失"）；读 `COM1` 可能阻塞。

**对策**：

```python
WIN_RESERVED = {"CON", "PRN", "AUX", "NUL",
                *(f"COM{i}" for i in range(1, 10)),
                *(f"LPT{i}" for i in range(1, 10))}
...
if s.split(".")[0].upper() in WIN_RESERVED:      # 只取第一个点之前
    raise SandboxError("E_PATH_RESERVED", ...)
```

`split(".")[0]` 保证 `CON`、`CON.jpg`、`CON.tar.gz`、`nul.txt` 全部命中。`.upper()` 保证 `con`、`Con.JpG` 命中。

**实测覆盖**：`CON`、`CON.jpg`、`sub/NUL`、`AUX.txt`、`COM1.jpg`、`LPT9`、`com1.JPG`、`nul.tar.gz` **8 条全部 DENY [E_PATH_RESERVED]**。

#### 3.4.4 尾随点与空格（Windows 会静默去掉）

**原理**：Win32 API 在把路径交给文件系统前，会去掉**文件名末尾**的点和空格。

**危害**：**"校验的名字"与"实际落盘的名字"不一致**，直接击穿"绝不覆盖"保证。

**攻击场景**（这是本项目最阴险的绕过）：

```
1. 库中已有 photo.jpg
2. 攻击者上传名为 "photo.jpg." 的文件
3. 沙箱检查"photo.jpg. 是否存在" → 不存在 → 判定为"新建"，允许写入
4. Win32 去掉尾随点 → 实际写入 photo.jpg
5. 原照片被覆盖，不可逆丢失
```

**实测**：

```
os.path.exists('ok.jpg.')    -> True       ← 尾随点被吃掉，指向 ok.jpg
os.path.exists('ok.jpg ')    -> True       ← 尾随空格被吃掉
os.path.exists('ok.jpg...')  -> True
os.path.exists('  ok.jpg')   -> False      ← 前导空格【不】被去掉
os.path.normpath('ok.jpg.')  -> 'ok.jpg.'  ← Python 的 normpath 不去除！
```

**关键**：`os.path.normpath` **不会**去除尾随点/空格——只有 Win32 文件 API 会。所以**不能靠 normpath 规范化，必须显式拒绝**。

**Unicode 空白的陷阱**：实测 `sub/ok\u00a0.jpg`（NBSP）**通过了**朴素实现。NBSP 不会被 Win32 去掉，但它看起来与空格无异，可用于绕过"肉眼检查"。**对策**：检查集合包含 `" "`、`"\u00a0"`、`"\t"`。

**对策**：

```python
if s != s.rstrip(" \u00a0.\t"):
    raise SandboxError("E_PATH_TRAILING", "尾随点或空白")
if s != s.lstrip(" \u00a0"):
    raise SandboxError("E_PATH_TRAILING", "前导空白")
```

**实测覆盖**：`sub/ok.jpg.`、`sub/ok.jpg `、`sub/ok.jpg...`、`sub/ `、`....//....//secret.txt` **全部 DENY**。

#### 3.4.5 UNC 路径（`\\server\share`、`\\?\C:\`、`\\.\`）

**原理**：以两个反斜杠（或两个正斜杠）开头的是 UNC（网络共享）或设备命名空间。

**危害等级**：

| 形态 | 危害 | 实测结果 |
|---|---|---|
| `\\server\share\a.jpg` | 读/写网络共享；可指向攻击者控制的 SMB 服务器（**NTLM 凭据泄露**） | `Path.resolve` → `'\\server\share\a.jpg'` 原样返回 |
| `\\localhost\C$\Windows` | 本机管理共享，等同本地绝对路径 | → `'\\localhost\C$\\'` |
| `\\?\C:\Windows` | **绕过 MAX_PATH**，且**绕过 Win32 规范化**（`..` 不被消解） | → `'\\?\C:\Windows'` **未拒绝！** |
| `\\?\UNC\server\share` | 长路径形式的 UNC | → 原样 |
| `\\.\C:` | 卷句柄 | → `'\\.\C:'` |
| `\\.\PhysicalDrive0` | **裸磁盘句柄**，可读写整个物理磁盘 | → 原样 |
| `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\` | **卷影副本**，可读历史文件、绕过文件锁 | → `OSError [WinError 6] 句柄无效` |

**决定性实测**：

```
Path(r'\\?\C:\Windows').resolve()             -> '\\?\C:\Windows'      ← 未拒绝！
Path(r'\\.\C:').resolve()                     -> '\\.\C:'              ← 未拒绝！
Path(r'\\.\PhysicalDrive0').resolve()         -> '\\.\PhysicalDrive0'  ← 未拒绝！
Path(r'\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\Windows').resolve()
                                              -> OSError [WinError 6] 句柄无效
```

**结论**：**`Path.resolve()` 不会拒绝设备命名空间**。`\\?\` 和 `\\.\` 必须用**字符串前缀**在拼路径之前拦下。指望 `resolve()` 兜底是错的。

另外实测确认 `\\?\` 前缀能绕过路径长度限制：

```
open('a'*200 + '.txt', 'w')             → 成功（未加前缀时 300 字符失败）
open('\\\\?\\' + 'b'*200 + '.txt', 'w') → 成功
```

**对策**：第 1 步 `rel.startswith(("\\\\", "//"))` 一律拒绝。实测覆盖 11 条 UNC/设备路径，全部 DENY [E_PATH_ABSOLUTE]。

#### 3.4.6 大小写不敏感导致的绕过

**原理**：NTFS 默认大小写不敏感。`OK.JPG` 与 `ok.jpg` 是**同一个文件**。

**危害**：

1. **判重失效**：`sha256` 判重之外若还用"文件名判重"，`OK.JPG` 会绕过 `ok.jpg` 的检查 → **覆盖**。
2. **边界断言失效**：`E:\Software\相册` 与 `e:\software\相册` 是同一个目录。若断言写成大小写敏感的 `startswith`，会误拒合法路径；若断言方向搞反，会误放越界路径。
3. **保留名绕过**：`con`、`Con`、`CON` 都要拦（已由 `.upper()` 解决）。

**实测**：

```
os.path.exists('OK.JPG')  -> True     ← 大写命中 ok.jpg
os.path.commonpath([r'E:\Software\相册\a', r'e:\software\相册'])
                          -> 'E:\Software\相册'    ← commonpath 自己处理了大小写
```

**对策**：边界断言必须用 `os.path.normcase` + `os.path.commonpath`（见第 6 步）。**不要**自己写 `str.lower()` 比较——`normcase` 还会处理分隔符方向。

#### 3.4.7 符号链接、目录联接（junction）、挂载点、重解析点

**原理**：这四类都是 **NTFS 重解析点（reparse point）**——一个"跳转"标记。

**危害**：攻击者在库内建一个指向库外的链接，之后所有"在库内"的路径实际都落在库外。

**实测（这是本节最重要的实测）**：

```
mklink /J junc sub                        → rc=0  【成功】不需要管理员权限！
mklink link sub（符号链接）                → rc=1  「你没有足够的权限执行此操作」
os.path.islink(junc)                      → False   ← 【漏检！】
os.lstat(junc).st_file_attributes         → 0x410
  0x410 & 0x400 (FILE_ATTRIBUTE_REPARSE_POINT) → True   ← 【正确检测】
os.path.realpath(junc/ok.jpg)             → ...\root\sub\ok.jpg   ← 正确消解
```

**三条关键结论**：

1. **junction 不需要管理员权限**（rc=0），符号链接需要（rc=1）。所以**攻击者会用 junction**。认为"Windows 建链接要管理员"是错的。
2. **`os.path.islink()` 对 junction 返回 False**。只用 `islink` 检查 = **完全漏检**。这是最容易犯的错。
3. **必须检查 `st_file_attributes & 0x400`**。

**TOCTOU 实证（为什么不能"消解后放行"）**：

```
mklink /J link sub
  Path(link/ok.jpg).resolve()  -> ...\root\sub\ok.jpg       在 root 内 ✓

rmdir link; mklink /J link ..\outside
  Path(link/ok.jpg).resolve()  -> ...\outside\ok.jpg        在 root 外 ✗
```

**同一个 `rel_path`，两次调用之间结果从"安全"变成"越界"。** 攻击者只需在检查与使用之间替换 junction（例如通过另一个 API 的并发请求）即可打穿。

**对策（本项目的选择：一律拒绝）**：

```python
FILE_ATTRIBUTE_REPARSE_POINT = 0x400

def _is_reparse_point(p: Path) -> bool:
    try:
        st = os.lstat(p)
    except OSError:
        return False
    if stat.S_ISLNK(st.st_mode):
        return True
    return bool(getattr(st, "st_file_attributes", 0) & FILE_ATTRIBUTE_REPARSE_POINT)
```

覆盖的完整重解析点清单：

| 类型 | 创建方式 | `islink()` | `0x400` 位 | 需管理员 |
|---|---|---|---|---|
| 文件符号链接 | `mklink` | ✅ | ✅ | ✅ 是 |
| 目录符号链接 | `mklink /D` | ✅ | ✅ | ✅ 是 |
| **目录联接 junction** | `mklink /J` | ❌ **False** | ✅ **True** | ❌ **否** |
| 卷挂载点 | `mountvol` | ❌ | ✅ | ✅ 是 |
| OneDrive 按需文件 | OneDrive | ❌ | ✅ | — |
| AppExecLink | Microsoft Store | ❌ | ✅ | — |
| WSL 互操作链接 | `\\wsl$\` | — | ✅ | — |
| **硬链接** | `mklink /H` | ❌ | ❌ **无此位** | ❌ 否 |

**硬链接的残余风险**：硬链接**不是**重解析点，`0x400` 位为 0，因此上面的检测**拦不住它**。但硬链接**只能指向同一卷**的文件。本项目库在 `E:`，用户敏感数据多在 `C:`，**跨卷不可达**。残余风险：

- 库内文件被建硬链接 → 修改一处影响另一处。缓解：审计时记录 `st_nlink > 1` 的异常文件。
- 攻击者把库外同卷文件硬链接进库内 → 需要先能在 `E:` 盘写文件（已越界），鸡生蛋问题。**接受**。

**实测覆盖**：`esc/d/evil.jpg`（根内 junction 指向根外）、`deep/j/d/evil.jpg`（嵌套 junction）→ 均 **DENY [E_PATH_ESCAPE]**。

#### 3.4.8 中文与 Unicode 归一化（全角字符、NFC/NFD）

**原理**：同一个"看起来一样"的字符可能有多种 Unicode 表示。

| 类型 | 例子 | 说明 |
|---|---|---|
| 全角/半角 | `ｋ`（U+FF4B）vs `k`（U+006B） | 中文输入法常见 |
| NFC vs NFD | `é` = U+00E9（预组合）vs `e`+U+0301（组合） | macOS 用 NFD，Windows 用 NFC |
| 双向控制符 | U+202E (RLO) | 让文件名**显示**顺序反转 |
| 零宽字符 | U+200B/U+200C/U+FEFF | 不可见 |
| NBSP | U+00A0 | 看起来像空格 |

**危害**：

1. **判重失效**：`photo.jpg` 与 `photo.jpg`（NFD 形式）在 macOS 上是同一个文件，在 Windows 上可能是两个。
2. **视觉欺骗**：`evil\u202eojpg.txt` 显示为 `evil...gpj.txt`，让人以为是 `.jpg`。
3. **绕过黑名单**：`％`（全角百分号 U+FF05）不等同于 `%`（U+0025），若黑名单只写 `%` 则被绕过。

**实测**：

```
os.path.exists('oｋ.jpg')       -> False    ← 全角 k 确实是不同的文件
sub/ok\u202e.jpg                 -> ALLOW   ← 【朴素实现放行 RLO 控制符】
sub/ok\u00a0.jpg                 -> ALLOW   ← 【朴素实现放行 NBSP】
sub/Oｋ.jpg                      -> ALLOW   ← 全角 k 通过（是不同文件名，非漏洞）
```

**对策**：

1. **NFKC 归一化后检查**：`unicodedata.normalize("NFKC", s)` 把全角转半角、把兼容字符统一。**注意**：归一化只用于**检查**，落盘用原串还是归一化串必须固定（本项目选择**落盘也用 NFKC 归一化串**，保证"同一张照片只有一种名字"）。
2. **拒绝危险控制字符**：`unicodedata.category(ch) in ("Cf", "Cc", "Cs", "Co", "Cn")` → 拒绝（覆盖 RLO、零宽、NUL、代理对、私有区）。
3. **白名单化字符集**比黑名单更可靠：允许中日韩文字、拉丁字母、数字、`-_. ()[]` 与常用中文标点，其余拒绝。
4. **明确拒绝 NUL 字节**：实测 `sub/ok.jpg\x00.txt` → DENY [E_PATH_INVALID]（因为 `\x00` 在 0x00-0x1f 范围内，已被非法字符集覆盖）。

**实测数据支撑**：真实库中**全角字符 0 个、含 `~` 0 个、含 `%` 0 个**，所以严格白名单**不会误伤任何真实数据**。

#### 3.4.9 超长路径（>260 字符，`\\?\` 前缀）

**原理**：Win32 传统 API 的路径上限是 `MAX_PATH = 260`。加 `\\?\` 前缀可绕过，上限变成约 32767。

**实测**：

```
20 层 × 20 字符深目录  os.makedirs          -> FileNotFoundError [WinError 3] 系统找不到指定的路径
300 字符文件名         open(...,'w')        -> FileNotFoundError [Errno 2] 找不到文件
'\\\\?\\' + 200 字符   open(...,'w')        -> 成功
```

**危害**：

1. **`\\?\` 前缀绕过长度检查**（实测成功），同时绕过 Win32 规范化（`..` 不消解）→ 已在第 1 步拦下。
2. **深目录导致写入失败**：`makedirs` 抛 `WinError 3`，若未捕获会让上传接口 500。
3. **总长 300+ 的路径通过了朴素实现**（实测：三层各 100 字符 → ALLOW）→ **必须补总长上限检查**。

**对策**：

```python
MAX_PATH_TOTAL = 240        # 留 20 字符余量给临时后缀与 .part

def _check_total_len(root: Path, clean: list[str]) -> None:
    total = len(str(root)) + sum(len(s) + 1 for s in clean)
    if total > MAX_PATH_TOTAL + 20:
        raise SandboxError("E_PATH_TOO_LONG", f"总长 {total} 超过上限")
```

**为什么是 240 而不是 260**：上传流程需要写 `xxx.jpg.part` 或 `xxx.tmp` 后缀，删除进回收站时 Windows 会加 `$R`/`$I` 前缀，缩略图缓存会加哈希后缀。留 20 字符余量避免"主路径合法但衍生路径超限"。

**中文的影响**：中文目录名按**字符数**算，`全部备份` 是 4 个字符（不是 12 字节）。**用字符数而非字节数**，否则会误拒中文路径。实测库中最长路径远小于 240 字符，无风险。

### 3.5 完整参考实现（`backend/app/sandbox.py`）

以下代码**可直接使用**。已通过 64 条用例实测（含 30 条恶意路径），实测结果见 §3.6。

```python
"""路径沙箱：所有文件系统访问的唯一入口。

设计原则：
  1. 默认拒绝 —— 白名单而非黑名单，无法确认安全即拒绝
  2. 单点收口 —— 全项目只有本模块允许直接调用 open/os/shutil
  3. 失败安全 —— 校验失败抛 SandboxError，绝不降级放行
  4. 零信任输入 —— 来自隧道的路径视为攻击者可控

七步校验（顺序不可调换）：
  1. 拒绝绝对路径/盘符/UNC/设备命名空间/前导分隔符
  2. 拒绝 .. 段、空段、. 段、':'（ADS）、Windows 保留设备名、尾随点/空白、非法字符
  3. 拒绝单段 > 255 字符、总长 > MAX_PATH_TOTAL
  4. p = os.path.realpath(root / rel)     消解重解析点
  5. 逐段检查 symlink/junction/reparse point，命中即拒绝（不做"消解后放行"）
  6. 断言 realpath 结果位于 realpath(root) 之内（normcase + commonpath）
  7. 权限模型：need 与 root mode 匹配
"""
from __future__ import annotations

import os
import re
import stat
import unicodedata
from dataclasses import dataclass
from pathlib import Path

from .config import MODE_READONLY, MODE_READWRITE, MODE_UPLOAD, VALID_MODES

# ---------------------------------------------------------------- 常量

FILE_ATTRIBUTE_REPARSE_POINT = 0x400

WIN_RESERVED = {
    "CON", "PRN", "AUX", "NUL",
    *(f"COM{i}" for i in range(1, 10)),
    *(f"LPT{i}" for i in range(1, 10)),
}

_ILLEGAL_CHARS = set('<>:"|?*%\\') | {chr(c) for c in range(0x20)} | {"\x7f", "~"}
_TRAILING_WS = " \u00a0\t"
_DRIVE_RE = re.compile(r"^[A-Za-z]:")
MAX_SEG_LEN = 255
MAX_PATH_TOTAL = 240

_WRITE_MODES = {MODE_UPLOAD, MODE_READWRITE}


class SandboxError(Exception):
    """沙箱校验失败。code 用于测试断言与客户端提示。"""

    def __init__(self, code: str, message: str = "") -> None:
        super().__init__(f"{code}: {message}" if message else code)
        self.code = code
        self.message = message


@dataclass(frozen=True)
class ResolvedPath:
    root_id: str
    root: Path        # realpath 后的根
    real: Path        # realpath 后的目标绝对路径
    rel: str          # 规范化后的相对路径（正斜杠分隔）


# ---------------------------------------------------------------- 内部工具

def _is_reparse_point(p: Path) -> bool:
    """检测 symlink / junction / mount point / OneDrive 占位符等一切重解析点。

    注意：os.path.islink() 对 Windows 目录联接（junction）返回 False，
    必须检查 st_file_attributes 的 FILE_ATTRIBUTE_REPARSE_POINT 位。
    """
    try:
        st = os.lstat(p)
    except OSError:
        return False                       # 不存在 → 不是重解析点
    if stat.S_ISLNK(st.st_mode):
        return True
    return bool(getattr(st, "st_file_attributes", 0) & FILE_ATTRIBUTE_REPARSE_POINT)


def _normalize_segment(s: str) -> str:
    """NFKC 归一化（全角→半角、兼容字符统一），用于检查与落盘。"""
    return unicodedata.normalize("NFKC", s)


def _has_control_char(s: str) -> bool:
    """Cf（格式符，含 RLO/零宽）、Cc（控制符）、Cs（代理对）、Co（私有区）、Cn（未分配）。"""
    return any(unicodedata.category(ch) in ("Cf", "Cc", "Cs", "Co", "Cn") for ch in s)


def _audit_security(event: str, detail: str) -> None:
    """安全事件审计。延迟导入避免与 audit.py 循环依赖。"""
    try:
        from .audit import write_audit
        write_audit(action=f"security.{event}", rel_path=None, detail=detail)
    except Exception:
        pass                               # 审计失败绝不影响主流程


# ---------------------------------------------------------------- 七步

def _step1_reject_absolute(rel: str) -> None:
    """第 1 步：拒绝绝对路径、盘符、UNC、设备命名空间、前导分隔符。"""
    if rel.startswith(("\\\\", "//")):
        raise SandboxError("E_PATH_ABSOLUTE", "UNC 或设备命名空间")
    if rel.startswith(("\\", "/")):
        raise SandboxError("E_PATH_ABSOLUTE", "前导分隔符")
    if _DRIVE_RE.match(rel):
        raise SandboxError("E_PATH_ABSOLUTE", "带盘符（Windows 上 os.path.join 会被它整体替换）")
    if rel == "" or rel.strip() == "":
        raise SandboxError("E_PATH_INVALID", "空路径")
    if rel != rel.lstrip(" \u00a0"):
        raise SandboxError("E_PATH_TRAILING", "前导空白")


def _step2_validate_segments(rel: str) -> list[str]:
    """第 2 步：逐段校验，返回规范化后的段列表。"""
    norm = rel.replace("\\", "/")
    if norm.endswith("/"):
        norm = norm.rstrip("/")            # 允许单个尾随分隔符（目录语义）
    clean: list[str] = []
    for raw in norm.split("/"):
        if raw in ("", "."):
            raise SandboxError("E_PATH_SEGMENT", "空段或 . 段（拒绝而非规范化，避免歧义）")
        if raw == "..":
            raise SandboxError("E_PATH_TRAVERSAL", ".. 穿越")
        if _has_control_char(raw):
            raise SandboxError("E_PATH_INVALID", "含控制字符（NUL/RLO/零宽）")

        s = _normalize_segment(raw)        # NFKC：全角→半角

        if ":" in s:
            raise SandboxError("E_PATH_ADS", "NTFS 数据流（ADS）或盘符")
        if set(s) & _ILLEGAL_CHARS:
            raise SandboxError("E_PATH_CHAR", "非法字符")
        if len(s) > MAX_SEG_LEN:
            raise SandboxError("E_PATH_TOO_LONG", "单段超过 255 字符")
        if s != s.rstrip(_TRAILING_WS + "."):
            raise SandboxError("E_PATH_TRAILING", "尾随点或空白（Win32 会静默去除，导致校验名≠落盘名）")
        if s != s.lstrip(_TRAILING_WS):
            raise SandboxError("E_PATH_TRAILING", "前导空白")
        if s.split(".")[0].upper() in WIN_RESERVED:
            raise SandboxError("E_PATH_RESERVED", f"Windows 保留设备名：{s}")
        clean.append(s)
    if not clean:
        raise SandboxError("E_PATH_INVALID", "无有效路径段")
    return clean


def _step3_check_total_len(root: Path, clean: list[str]) -> None:
    """第 3 步：总长上限（留 20 字符余量给 .part / $R$I / 缩略图后缀）。"""
    total = len(str(root)) + sum(len(s) + 1 for s in clean)
    if total > MAX_PATH_TOTAL + 20:
        raise SandboxError("E_PATH_TOO_LONG", f"总长 {total} 超过上限 {MAX_PATH_TOTAL + 20}")


def _step4_realpath(root: Path, clean: list[str]) -> tuple[Path, Path]:
    """第 4 步：拼路径并 realpath 消解。返回 (候选路径, 消解后路径)。"""
    root_real = Path(os.path.realpath(root))
    cand = root_real.joinpath(*clean)
    real = Path(os.path.realpath(cand))    # strict=False：写操作目标可能尚不存在
    return cand, real


def _step5_reject_reparse(root_real: Path, clean: list[str]) -> None:
    """第 5 步：逐段拒绝重解析点。

    必须在 realpath 之前对【原始段】检查：realpath 会把 junction 消解掉，
    消解之后就再也看不到它曾是重解析点。
    """
    cur = root_real
    for seg in clean:
        cur = cur / seg
        if _is_reparse_point(cur):
            _audit_security("reparse_rejected", str(cur))
            raise SandboxError("E_PATH_REPARSE", f"路径段是重解析点（symlink/junction）：{seg}")


def _step6_assert_inside(root_real: Path, real: Path) -> None:
    """第 6 步：边界断言，大小写不敏感 + 防前缀歧义。"""
    try:
        common = os.path.commonpath([str(real), str(root_real)])
    except ValueError:                     # 跨盘符
        _audit_security("escape_rejected", f"{real} 跨盘符")
        raise SandboxError("E_PATH_ESCAPE", "解析后跨盘符")
    if os.path.normcase(common) != os.path.normcase(str(root_real)):
        _audit_security("escape_rejected", str(real))
        raise SandboxError("E_PATH_ESCAPE", "解析后越出根目录")


def _step7_check_mode(root_cfg: dict, need: str) -> None:
    """第 7 步：权限模型。need 必须由服务端硬编码，绝不接受客户端传参。"""
    mode = root_cfg.get("mode", MODE_READONLY)
    if mode not in VALID_MODES:
        raise SandboxError("E_ROOT_MODE", f"未知 root mode：{mode}")
    if need == "read":
        return                             # 三种 mode 都允许读
    if need == "write" and mode not in _WRITE_MODES:
        raise SandboxError("E_ROOT_READONLY", f"root {root_cfg.get('id')} 为只读，不允许写")


# ---------------------------------------------------------------- 公开接口

def resolve(root_cfg: dict, rel_path: str, need: str = "read") -> ResolvedPath:
    """把不可信的相对路径解析为根目录内的绝对路径。

    Args:
        root_cfg: config.roots() 中的一项，至少含 id / path / mode
        rel_path: 客户端提供的相对路径（不可信）
        need:     "read" 或 "write"，由服务端代码硬编码

    Raises:
        SandboxError: 任何一步校验失败

    Returns:
        ResolvedPath（含 root_id / root / real / rel）

    注意：本函数只做校验与解析，不打开文件。
    真正的打开必须走 open_read / open_write，它们会复核边界以消除 TOCTOU。
    """
    if need not in ("read", "write"):
        raise SandboxError("E_ARG", "need 只能是 read 或 write")
    if not isinstance(rel_path, str):
        raise SandboxError("E_ARG", "rel_path 必须是字符串")

    root = Path(root_cfg["path"])
    if not root.is_dir():
        raise SandboxError("E_ROOT_MISSING", f"根目录不存在：{root}")

    _step1_reject_absolute(rel_path)
    clean = _step2_validate_segments(rel_path)
    _step7_check_mode(root_cfg, need)                       # 早失败，省掉后面的 IO

    root_real = Path(os.path.realpath(root))
    _step5_reject_reparse(root_real, clean)                 # 检查原始段
    _step3_check_total_len(root_real, clean)

    cand, real = _step4_realpath(root, clean)
    _step6_assert_inside(root_real, real)

    # 复核：realpath 之后再次确认没有任何一段是重解析点
    # （realpath 已消解，这一步只对【未消解】的路径有意义，因此放在 cand 上）
    _step5_reject_reparse(root_real, [p.name for p in _iter_parents(cand, root_real)])

    return ResolvedPath(
        root_id=root_cfg["id"],
        root=root_real,
        real=real,
        rel="/".join(clean),
    )


def _iter_parents(p: Path, stop: Path):
    """从 stop 的下一层开始逐级返回到 p（含 p），用于复核重解析点。"""
    parts: list[Path] = []
    cur = p
    while True:
        parts.append(cur)
        if cur.parent == cur or cur.parent == stop.parent or cur == stop:
            break
        cur = cur.parent
    return list(reversed(parts))


def open_read(root_cfg: dict, rel_path: str):
    """校验并打开文件用于读取（消除 TOCTOU：打开后复核 inode）。"""
    rp = resolve(root_cfg, rel_path, need="read")
    if not rp.real.is_file():
        raise SandboxError("E_NOT_FOUND", "文件不存在")
    f = open(rp.real, "rb")
    try:
        _recheck_after_open(root_cfg, rp, f)
    except Exception:
        f.close()
        raise
    return f


def open_write(root_cfg: dict, rel_path: str, *, exclusive: bool = True):
    """校验并打开文件用于写入。

    exclusive=True 时使用 "xb" 模式：目标已存在则抛 FileExistsError，
    这是"绝不覆盖已有文件"保证的最后一层（内核级原子）。
    """
    rp = resolve(root_cfg, rel_path, need="write")
    mode = "xb" if exclusive else "wb"
    rp.real.parent.mkdir(parents=True, exist_ok=True)
    f = open(rp.real, mode)
    try:
        _recheck_after_open(root_cfg, rp, f)
    except Exception:
        f.close()
        raise
    return f


def _recheck_after_open(root_cfg: dict, rp: ResolvedPath, f) -> None:
    """打开后复核：确认 fd 指向的真实路径仍在根内。

    这是消除 TOCTOU 的关键——校验用的是路径，而 fd 绑定的是 inode。
    若攻击者在 resolve 与 open 之间替换了目录（junction 攻击），
    这里的 fd 路径会与预期不符。
    """
    try:
        fd_real = Path(os.path.realpath(f"/proc/self/fd/{f.fileno()}"))
    except (OSError, AttributeError, NotImplementedError):
        fd_real = None                     # Windows 无 /proc，退化为路径复核
    if fd_real is None:
        fd_real = Path(os.path.realpath(rp.real))
    try:
        common = os.path.commonpath([str(fd_real), str(rp.root)])
    except ValueError:
        raise SandboxError("E_PATH_ESCAPE", "打开后跨盘符")
    if os.path.normcase(common) != os.path.normcase(str(rp.root)):
        _audit_security("toctou_rejected", str(fd_real))
        raise SandboxError("E_PATH_ESCAPE", "打开后路径越界（疑似 TOCTOU）")


def safe_delete(root_cfg: dict, rel_path: str) -> Path:
    """删除到回收站。禁止 os.unlink / os.remove / shutil.rmtree。"""
    from send2trash import send2trash   # 延迟导入：便于测试与缺失时明确报错

    rp = resolve(root_cfg, rel_path, need="write")
    if not rp.real.exists():
        raise SandboxError("E_NOT_FOUND", "待删除对象不存在")
    if rp.real == rp.root:
        raise SandboxError("E_PATH_ROOT", "不允许删除根目录")
    if _is_reparse_point(rp.real):
        raise SandboxError("E_PATH_REPARSE", "不允许删除重解析点")
    send2trash(str(rp.real))            # 唯一允许的删除方式
    return rp.real


def safe_replace(temp: Path, root_cfg: dict, rel_path: str) -> Path:
    """把临时文件原子地搬到目标位置。

    【重要】os.replace 只在【同卷】内原子。实测跨卷（H: → E:）抛
    OSError [WinError 17] 系统无法将文件移到不同的磁盘驱动器。
    因此本函数要求 temp 与目标同卷；调用方必须先保证这一点
    （见 uploads.py 的 _staging_path：临时文件写在目标同卷的 .staging 目录）。
    """
    rp = resolve(root_cfg, rel_path, need="write")
    if rp.real.exists():
        raise SandboxError("E_EXISTS", "目标已存在，拒绝覆盖")
    if os.path.splitdrive(str(temp))[0].upper() != os.path.splitdrive(str(rp.real))[0].upper():
        raise SandboxError("E_CROSS_VOLUME", "临时文件与目标不同卷，无法原子替换")
    rp.real.parent.mkdir(parents=True, exist_ok=True)
    os.replace(str(temp), str(rp.real))
    return rp.real
```

**关于 `_recheck_after_open` 的诚实说明**：Windows 没有 `/proc/self/fd`，因此复核退化为"再次 realpath 目标路径"。这**不能完全消除 TOCTOU**，只能把窗口从"秒级"压到"毫秒级"。真正的完全消除需要 `CreateFileW` + `FILE_FLAG_OPEN_REPARSE_POINT` + 句柄级 `GetFinalPathNameByHandle`，本项目一期不引入（代价是 `ctypes` 复杂度）。**残余风险已记入 §2.3 第 6 行**，二期若需要可用 `pywin32` 的 `GetFinalPathNameByHandle` 补上。

## 4. 认证与授权设计

### 4.1 三层鉴权

系统有三个信任层级，对应三种凭证：

```
┌──────────────┐   client_token    ┌──────────────┐   agent_token   ┌──────────────┐
│   手机 PWA    │ ───────────────▶ │   云 Relay    │ ──────────────▶ │  电脑 Agent   │
│  (不可信)     │  Authorization:   │  (半可信)     │  Authorization:  │  (可信执行)   │
│              │  Bearer <ct>      │              │  Bearer <at>     │              │
└──────────────┘                   └──────────────┘                  └──────────────┘
        │                                                                     ▲
        └──────────── 局域网直连：同一个 client_token ────────────────────────┘
```

| 层级 | 凭证 | 持有者 | 校验方 | 用途 | 有效期 | 存储 |
|---|---|---|---|---|---|---|
| **L1** | `agent_token` | 电脑 Agent | 云 Relay | 建立 WSS 隧道（`/agent/ws`） | 长期（直到吊销） | 云端 `devices.agent_token`（**待改为 hash**）+ 电脑 `config.json` |
| **L2** | `client_token` | 手机浏览器 | 云 Relay | 访问 `/d/{device_id}/api/**` | 90 天 | 云端 `clients.token_hash`（SHA-256）+ 手机 IndexedDB |
| **L3** | `client_token` | 手机浏览器 | **电脑 Agent** | 局域网直连 `http://<lan-ip>:8787/api/**` | 同 L2 | 同 L2（同一个令牌复用） |

**关键设计：L2 与 L3 用同一个 `client_token`**（设计文档 §8.2）。理由：

1. 手机只需保存一个令牌，切换通路（局域网 ↔ 云端）时**不需要重新鉴权**，用户体验连续。
2. 直连校验在电脑端本地完成——电脑端需要知道 `client_token` 的**校验方式**。由于电脑端不能访问云端 DB，采用**共享密钥派生**方案：

```python
# 配对时云端生成 client_token（随机 32 字节 base64url）
# 云端把 token_hash = sha256(client_token) 存 DB，把 token 本身返回手机
# 电脑端如何校验直连请求？
#   方案：配对成功时云端通过隧道下发 token_hash 给电脑端，电脑端存本地表
#   clients(token_hash, device_id, name, created_at, revoked)
# 直连时电脑端算 sha256(收到的 token) 与本地表比对
```

**方案的安全分析**：

| 项 | 评价 |
|---|---|
| 电脑端只存 hash | ✅ 即使电脑被入侵也拿不到可用令牌 |
| 云端下发 hash 走隧道 | ✅ 隧道是 WSS，且云端本来就持有该 hash |
| 电脑端本地校验无需回云 | ✅ 断网时直连仍可用（符合"局域网优先"目标） |
| 撤销的即时性 | ⚠️ 电脑端表需要同步：云端撤销后必须通过隧道 `NOTIFY` 推送 + 电脑端定期（5 分钟）回拉；**最坏 5 分钟窗口** |

**诚实指出**：设计文档 §8.2 未说明"电脑端如何校验直连令牌"。本文档给出上述方案，并已回写为对 [03-详细设计说明书](03-详细设计说明书.md) 的补充要求。这是**设计文档的一个缺口**，见 §12 的发现清单。

### 4.2 令牌设计

| 属性 | `agent_token` | `client_token` | 配对码 |
|---|---|---|---|
| **长度** | 32 字节随机 | 32 字节随机 | 6 位十进制 |
| **熵** | 256 bit | 256 bit | **19.9 bit**（log2(10^6)） |
| **生成方式** | `secrets.token_urlsafe(32)` | `secrets.token_urlsafe(32)` | `secrets.randbelow(10**6)` 补零 6 位 |
| **字符集** | base64url（`A-Za-z0-9-_`） | 同左 | `0-9` |
| **编码长度** | 43 字符 | 43 字符 | 6 字符 |
| **云端存储** | **必须改为 `sha256`**（当前表是明文 `TEXT`） | `sha256`（`clients.token_hash`） | 明文（短期，5 分钟） |
| **电脑端存储** | `config.json`，**必须收紧 ACL 为仅当前用户** | 本地 `clients` 表存 hash | 不存（托盘内存 + 显示） |
| **手机端存储** | 不适用 | IndexedDB（**不用 localStorage**，见 §8.1） | 不存（一次性使用） |
| **传输方式** | `Authorization: Bearer` Header | 同左 | HTTPS 请求体（POST JSON） |
| **有效期** | 长期，直到吊销 | 90 天（`token_ttl_days: 90`） | **5 分钟** |
| **轮换** | 手动（托盘"重新注册"） | 到期自动失效，需重新配对；支持主动轮换 | 每次配对生成新码，旧码立即失效 |
| **吊销** | 云端 `devices.revoked=1` | 云端 `clients.revoked=1` + 隧道 `NOTIFY` 通知电脑端 | 天然一次性 |

**为什么用 `secrets` 而不是 `random`**：`random` 是 Mersenne Twister，**可预测**。`secrets` 使用 `os.urandom`（CSPRNG）。这是硬规则（§10）。

**为什么 base64url 43 字符**：`token_urlsafe(32)` 产生 43 字符（32 字节 → 44 字符含 padding，去 padding 后 43）。**不要截断**——截断会降低熵。

**为什么存 hash 不存明文**：

| 存储方式 | 云端 DB 泄露后果 |
|---|---|
| 明文 `agent_token` | 攻击者直接冒充电脑接入云 → **直通照片库** |
| `sha256(agent_token)` | 攻击者无法反推 → **无法冒充** |

**为什么用 SHA-256 而不是 bcrypt/argon2**：令牌是 256 bit 随机值，不是低熵口令。彩虹表和字典攻击对 256 bit 随机值无效。**bcrypt 的价值在于"慢"以抵抗暴力猜测，而 256 bit 随机值不需要**（猜测空间是 2^256）。用 SHA-256 是正确且高效的选择。

**但配对码必须用慢哈希或限流**——见 §4.5。

**令牌传输的三条硬规则**：

1. **必须走 Header，绝不走 URL**。理由：URL 会被记录在①反向代理访问日志（Caddy/Nginx `access.log`）②浏览器历史 ③`Referer` 头 ④云服务商的流量日志。Header 通常不被记录。
2. **绝不进日志**：所有日志调用必须过脱敏函数（§7.6）。
3. **绝不硬编码**：`grep -r "sk_\|token.*=.*['\"][A-Za-z0-9_-]{20,}" backend/ cloud/` 必须为空（§10 检查项）。

### 4.3 配对流程与安全分析

**流程**（设计文档 §8.2）：

```
[电脑] 托盘点"添加手机" 
   → 生成 6 位配对码 code = secrets.randbelow(10**6) 补零
   → POST /api/devices/{id}/pair  {code, device_id}  （走隧道，带 agent_token）
   → 云端 INSERT INTO pair_codes(code, device_id, expires_at=now+5min, tries=0)
   → 电脑托盘显示：配对码 483920 + 二维码（内含 device_id）

[手机] 已登录（email + password）→ 扫码或手输 6 位码
   → POST /api/devices/{id}/pair  {code}
   → 云端校验：
       ① code 存在？              否 → 401 {"error":"pair_code_invalid"}
       ② expires_at > now？        否 → 401 {"error":"pair_code_expired"}
       ③ tries < 5？               否 → 429 {"error":"pair_code_locked", retry_after:600}
       ④ 该账号是否已绑定此 device_id？否 → 允许（单账号多设备）
       ⑤ 通过 → DELETE FROM pair_codes WHERE code=?（一次性，防重放）
              → 生成 client_token = secrets.token_urlsafe(32)
              → INSERT clients(device_id, name, token_hash=sha256(ct), ...)
              → 通过隧道 NOTIFY 把 token_hash 下发电脑端
              → 返回 {"client_token": ct, "device_id": ..., "expires_at": ...}

[手机] 把 client_token 存 IndexedDB，开始使用
```

**配对码的数学强度分析（必须算清楚）**

- 空间大小：`10^6 = 1,000,000`，熵 = `log2(10^6) ≈ 19.93 bit`
- 单次请求命中概率：`p = 1 / 10^6 = 10^-6`

**场景 A：无限重试（理论最坏情况）**

若没有任何限流，攻击者以 1000 req/s 爆破（云端限流前）：

```
平均需要尝试次数 = 10^6 / 2 = 500,000 次
耗时 = 500,000 / 1000 = 500 秒 ≈ 8.3 分钟
```

**结论：8.3 分钟就能爆破成功。** 这**完全不可接受**——配对码的有效期是 5 分钟，但攻击者可以在**任何时刻**开始爆破，只要用户在爆破期间点了"添加手机"，攻击者就能抢到。实际上攻击者会持续爆破，每次用户配对时都被截胡。

**场景 B：按 code 锁定（设计文档 §8.2 的方案：错 5 次锁 10 分钟）**

问题：**`tries` 计数挂在 `pair_codes` 表的行上，换一个 code 就重置**。攻击者攻击的正是"用户当前正在显示的那个 code"，而锁定发生在该行上。分析：

```
用户在 T 时刻显示 code C
攻击者在 T 后立即开始尝试
  尝试 1-5 次 → tries 达到 5 → 锁定 10 分钟
  但 code C 的有效期只有 5 分钟 → T+5 时 C 过期
  攻击者的 5 次尝试全部落空（每次命中概率 10^-6）
```

**所以"错 5 次锁 10 分钟"对单个 code 是有效的**：每个 code 只允许 5 次猜测，命中概率 `5 × 10^-6 = 5×10^-6`。

**但存在三个绕过**：

1. **按 code 锁定 → 攻击者遍历所有未过期的 code**。云端同时可能存在多个活跃 code（用户多次点击"添加手机"，或有多个设备在配对）。若同时有 100 个活跃 code，攻击者可以对每个都试 5 次 = 500 次尝试，命中概率升到 `5×10^-4`。
2. **锁定状态是"按 code 记"的，不是"按攻击者记"的**。攻击者可以无限次**创建新会话**去尝试不同的 code，锁定只针对他尝试过的那个 code，不影响他尝试其他 code。
3. **`tries` 在 code 过期后随行删除**——攻击者可以在 code 过期瞬间重新开始。

**场景 C：本项目建议的方案（按账号 + 按 IP 双重锁定）**

| 维度 | 限制 | 理由 |
|---|---|---|
| **按 code** | 错 5 次锁定（保留） | 兜底 |
| **按账号** | 任意配对请求错 10 次 → 锁定该账号的**所有**配对 30 分钟 | 攻击者换 code 无效 |
| **按 IP** | 未认证请求 10 次/分钟 | 限制爆破速率 |
| **全局** | 配对请求 60 次/分钟（所有 IP 合计） | 防分布式爆破 |
| **配对码有效期** | 5 分钟（保留） | 缩小窗口 |
| **一次性** | 成功后立即 `DELETE`（保留） | 防重放 |

**加强后的定量分析**：

```
攻击者在 5 分钟窗口内最多尝试次数：
  min(按账号 10 次, 按 IP 10 次/分钟 × 5 分钟 = 50 次, 全局 60 次/分钟 × 5 = 300 次)
  = 10 次

命中概率 = 10 / 10^6 = 10^-5 = 0.001%
```

**结论**：`0.001%` 的配对劫持概率，配合"配对成功后手机端会显示设备名，用户能发现异常"，**可以接受**（R-3）。

**但仍有三个残余风险**：

1. **10^-5 不是 0**。攻击者做 10 万次攻击尝试（每次都要用户恰好在这 5 分钟内配对）理论上会成功一次。**概率极低但非零。**
2. **锁定可被用来 DoS**：攻击者故意错 10 次 → 锁定用户账号的配对功能 30 分钟。用户点"添加手机"会失败。缓解：锁定提示要明确说明"请稍后再试"，且**已配对的手机不受影响**。
3. **单账号系统的前提是"攻击者不知道密码"**。若密码泄露，攻击者根本不需要爆破配对码——直接登录后就能看到所有已配对的设备（`GET /api/devices`）。**所以配对码强度不是系统的瓶颈，账号密码才是。**

**加强建议（按性价比排序）**

| 建议 | 效果 | 成本 | 一期是否采纳 |
|---|---|---|---|
| **① 按账号 + 按 IP 双重锁定**（场景 C） | 概率从 100% 降到 0.001% | 低（改 `pair_codes` 表加索引 + 计数表） | ✅ **必须采纳** |
| **② 配对码改为 8 位** | 概率再降 100 倍（10^-7） | 极低（改一个常量 + UI 显示 8 位） | ✅ **建议采纳**（体验损失很小） |
| **③ 配对码改用字母+数字混合（8 位 base32）** | 熵 40 bit，概率 10^-10 | 低（但手输体验变差，二维码无影响） | ⚠️ 可选 |
| **④ 配对必须同时提供账号密码**（二维码内含一次性 ticket，ticket 与账号绑定） | 攻击者必须先有密码 | 中（改协议） | ⚠️ 二期考虑 |
| **⑤ 配对成功后推送通知**（邮件/App） | 用户能立即发现异常配对 | 中（需邮件服务） | ❌ 一期不做（无邮件基础设施） |

**一期的决定**：采纳 ① + ②，即 **8 位配对码 + 按账号与 IP 双重锁定 + 5 分钟有效 + 错 10 次锁 30 分钟**。理由：改动极小，把风险从"8 分钟可爆破"降到"10^-7 概率"，性价比最高。

| 禁止操作 | 为什么 | 实现方式 |

| **管理其他设备** | 越权 | `/api/devices/**` 只在云端，且校验 `account_id` |
| **读其他 client 的上传会话** | 越权 | `upload_sessions` 表加 `client_id` 列并校验 |
| **绕过沙箱直接写文件** | G1/G2 | lint 强制（§10） |

**实现要点**：

```python
# auth.py —— 每个请求都必须过这个依赖
async def require_client(
    request: Request,
    device_id: str,
    authorization: str = Header(...),
) -> Client:
    token = _parse_bearer(authorization)          # 严格解析，拒绝格式错误
    if not token:
        raise HTTPException(401, {"error": "unauthorized"})
    client = await db.get_client_by_token_hash(sha256(token))
    if client is None:
        raise HTTPException(401, {"error": "unauthorized"})
    if client.revoked:
        raise HTTPException(401, {"error": "token_revoked"})
    if client.expires_at and client.expires_at < now():
        raise HTTPException(401, {"error": "token_expired"})
    if client.device_id != device_id:             # ★ 越权防护的核心
        audit_security("cross_device_attempt", f"{client.device_id} -> {device_id}")
        raise HTTPException(403, {"error": "forbidden"})
    return client
```

**三条实现纪律**：

1. **`device_id` 必须从 URL 路径取，与 token 里的 `device_id` 严格比对**，不能"信任 token 里的 device_id 就忽略 URL"（否则攻击者用 `/d/{别人的id}/...` 会拿到自己设备的响应，造成缓存投毒）。
2. **所有 `/d/{device_id}/api/**` 必须挂这个依赖**。实现方式：FastAPI 的 `APIRouter(dependencies=[Depends(require_client)])`，而不是逐个端点手写（漏一个就是漏洞）。
3. **新增端点时必须同时加权限判断**。§10 的检查脚本扫描 `cloud/relay/main.py`，确认每个 `/d/` 路由都在受保护 router 下。

### 4.5 会话管理与撤销

**令牌过期**：

| 事件 | 行为 |
|---|---|
| `client_token` 到期（90 天） | 云端返回 401 `token_expired`；手机端清除本地令牌并提示重新配对 |
| 到期前 7 天 | 手机端显示"配对即将过期"提示（可选） |
| `agent_token` | 不自动过期（长期），只能手动吊销或重新注册 |

**为什么 `agent_token` 不设过期**：电脑 Agent 需要"开机即连"，若令牌过期则用户必须在电脑前手动重新注册，体验不可接受。安全性靠"吊销"而非"过期"。

**设备撤销后的即时生效**：

```
[用户] 手机点"移除这台设备" 或 电脑托盘点"移除手机"
  → DELETE /api/devices/{id}/clients/{cid}
  → 云端 UPDATE clients SET revoked=1 WHERE id=?
  → 云端通过隧道发 NOTIFY {"event":"client_revoked","client_id":...}
  → 电脑端立即从本地 clients 表删除该 token_hash（直连路径即时失效）
  → 手机端下次请求 → 401 → 清除本地令牌
```

| 路径 | 撤销生效延迟 | 机制 |
|---|---|---|
| 云端中继 | **即时**（下一个请求就 401） | 每次请求查 DB |
| 局域网直连 | **即时**（若隧道在线） | NOTIFY 推送 |
| 局域网直连（**隧道离线时**） | **最长 5 分钟** | 电脑端定期回拉；隧道断了无法推送 |
| Service Worker 已缓存的缩略图 | **最长 24 小时** | 见 §8.4 |

**诚实指出**：隧道离线时"最长 5 分钟"的窗口无法消除（除非直连也强制回云校验，但那就失去了"断网可用"的意义）。**缓解**：手机端在收到 401 后必须**立即清空 Service Worker 缓存**（§8.4）。

**撤销必须级联**：

- 撤销 `device`（电脑）→ 级联撤销该设备下**所有** `clients`
- 撤销 `account` → 级联撤销所有 `devices` 与 `clients`
- 级联必须在一个事务里完成（§7.2）

### 4.6 账号凭证与登录

**单账号系统**（设计文档 §15.1 决策 5：一个邮箱 + 密码，无注册、无找回）。

| 项 | 设计 | 理由 |
|---|---|---|
| 密码哈希 | **Argon2id**（`argon2-cffi`）或 **bcrypt**（cost ≥ 12） | 低熵口令必须用慢哈希 |
| 为什么不用 SHA-256 | SHA-256 每秒可算 10^9 次，8 位口令 1 秒内可破 | 必须用内存硬化哈希 |
| 密码最低长度 | 12 字符 | 单账号系统，密码是唯一防线 |
| 登录限流 | 5 次/分钟/IP + 20 次/小时/账号 | 防爆破 |
| 登录失败锁定 | 错 10 次锁 30 分钟（按账号） | 同 §4.3 |
| 会话 | 登录后签发 **JWT**（短期 1 小时）+ refresh token（30 天） | JWT 无状态，减少 DB 查询 |
| 初始化 | 首次部署时用环境变量 `ADMIN_EMAIL` / `ADMIN_PASSWORD_HASH` 注入 | **绝不硬编码**（§10） |

**重要**：登录后获得的 JWT 与 `client_token` 是**不同的东西**：

- JWT = "我是这个账号" → 能看 `GET /api/devices`、能发起配对、能撤销设备
- `client_token` = "我是这台已配对的手机" → 能看照片

**分离的理由**：JWT 存在手机浏览器内存里（短期、易失），`client_token` 存在 IndexedDB（长期、持久）。若 JWT 泄露，攻击者能管理设备但**不能直接看照片**（还需配对）；若 `client_token` 泄露，攻击者能看照片但**不能管理设备**。**权限分离降低了单点泄露的影响。**

**但必须诚实指出一个风险**：持有 JWT 的攻击者可以**自己发起配对**——他登录后生成一个新配对码，用这个码给自己签发一个 `client_token`，然后看全部照片。**所以 JWT 的安全性等价于账号密码，账号密码是系统的真正根信任。** 这进一步说明"配对码强度不是瓶颈"（§4.3）。

**缓解**：

1. **新配对必须由电脑端确认**：配对码只在电脑托盘显示，攻击者虽然能生成码（若他能登录云），但**他生成的码需要在电脑端确认**——不对，设计文档的流程里，配对码是**电脑生成**、云端存储、手机提交的。攻击者若只控制云（不控制电脑），他无法让电脑生成码。
2. **因此把"生成配对码"的权限从云端移到电脑端是关键设计**（设计文档 §8.2 已如此：托盘生成 → 走隧道上传）。**攻击者持有 JWT 但不能生成配对码**，除非他能通过隧道命令电脑生成——而隧道需要 `agent_token`，JWT 拿不到。
3. **但攻击者可以伪造"配对请求"**吗？流程是：电脑生成 code → 云存 → 手机提交 code。攻击者不知道 code（19.9 bit 随机）。所以他必须爆破——回到 §4.3 的分析。
4. **结论**：**配对码强度确实是重要的**，因为它是"仅有账号密码的攻击者"到"能看照片"之间的唯一屏障。这**加强了 §4.3 采纳 8 位码 + 双重锁定的必要性**。

**修正 §4.3 的结论**：配对码**不是**无关紧要的，它是纵深防御的第二道门。**一期必须采纳 8 位码 + 按账号与 IP 双重锁定。**

## 5. 传输安全

### 5.1 TLS 配置

| 项 | 配置 | 理由 |
|---|---|---|
| **证书来源** | **Let's Encrypt**（Caddy 自动签发与续期） | 免费、自动、被所有安卓浏览器信任 |
| **为什么必须真证书** | 自签证书会导致：①浏览器警告（PWA 无法安装）②Service Worker 需要安全上下文（HTTPS 或 localhost），**自签证书下 SW 注册失败** → 离线缓存、PWA 安装全部失效 | 见设计文档 §6.4 |
| **域名要求** | 必须有真实域名（设计文档 §15.3 遗留项） | Let's Encrypt 不给 IP 签证书 |
| **最低 TLS 版本** | **TLS 1.2**（推荐只开 1.2 + 1.3） | 安卓 7+ 全部支持；TLS 1.0/1.1 已被主流浏览器废弃 |
| **加密套件** | 只允许 AEAD 与 PFS 套件（见下） | 防降级、防离线解密 |
| **HSTS** | `Strict-Transport-Security: max-age=31536000; includeSubDomains` | 防 SSL Strip 降级；**注意：一旦开启，域名在 max-age 内无法用 HTTP 访问**（对个人项目可接受） |
| **OCSP Stapling** | 开启 | 加快握手、提升隐私 |
| **证书续期** | Caddy 自动；监控到期时间并告警 | 证书过期 = 全站不可用 |

**推荐的加密套件**（Caddy 默认即可，以下是显式配置的参考）：

```
TLS 1.3（无需配置套件，协议固定）：
  TLS_AES_128_GCM_SHA256
  TLS_AES_256_GCM_SHA384
  TLS_CHACHA20_POLY1305_SHA256

TLS 1.2（显式指定，全部具备前向保密 + AEAD）：
  TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
  TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
  TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384
  TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
  TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256

明确禁用：
  - 所有 CBC 模式套件（Lucky13 / BEAST 类攻击）
  - 所有 RC4 套件
  - 所有 3DES 套件
  - 所有静态 RSA 密钥交换（无前向保密）
  - TLS 1.0 / 1.1 / SSLv3
  - 压缩（CRIME）
  - 重协商（客户端发起）
```

**Caddyfile 参考**：

```caddy
photo.example.com {
    encode zstd gzip
    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        X-Content-Type-Options "nosniff"
        X-Frame-Options "DENY"
        Referrer-Policy "no-referrer"
        Content-Security-Policy "default-src 'self'; img-src 'self' blob: data:; connect-src 'self' wss://photo.example.com https://photo.example.com http://192.168.0.0/16:8787; script-src 'self'; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'"
        Permissions-Policy "geolocation=(), microphone=(), camera=(self), usb=(), payment=()"
        -Server
    }
    tls {
        protocols tls1.2 tls1.3
        curves x25519 secp256r1
    }
    # 请求体上限（防止一次性大 body 打爆内存）
    request_body {
        max_size 4MB
    }
    reverse_proxy relay:8000 {
        flush_interval -1          # SSE / 流式转发必须立即 flush
        transport http {
            read_timeout 0         # 大文件下载需要长连接
        }
    }
    log {
        output file /var/log/caddy/access.log {
            roll_size 50MiB
            roll_keep 5
        }
        # 关键：日志中不能出现令牌（令牌本就不在 URL 中，这里是纵深防御）

```

**关于 `connect-src` 中的局域网地址**：CSP 必须显式允许局域网直连的 `http://192.168.x.x:8787`，否则浏览器会阻止直连请求。这是**唯一允许的 HTTP 源**，且限私有网段。

**CSP 中的 `'unsafe-inline'`（style-src）说明**：Vue 的 scoped style 与部分 UI 库需要内联样式。**接受此风险**（样式注入的危害远低于脚本注入），但**`script-src` 绝不允许 `'unsafe-inline'` 或 `'unsafe-eval'`**。

### 5.2 隧道安全（WSS）

**为什么用 WSS 而不是 WS**：

1. **防窃听**：`agent_token` 在握手的 `Authorization` header 中传输，明文 WS 会被中间人直接拿走。
2. **防篡改**：明文 WS 下中间人可注入伪造的隧道帧。
3. **防审查/穿越 NAT**：443 端口的 WSS 看起来像普通 HTTPS。

**为什么 `agent_token` 放 Header 而不放 URL**：

```python
# ❌ 错误写法
ws = await websockets.connect(f"wss://photo.example.com/agent/ws?token={agent_token}")
```

| 问题 | 说明 |
|---|---|
| **反代访问日志** | Caddy 的 `access.log` 默认记录完整 URI（含 query string）→ **令牌永久留在服务器磁盘上** |
| **浏览器/客户端历史** | 若用浏览器调试，URL 进历史 |
| **Referer 泄露** | 若该 URL 被嵌入页面，`Referer` 会把令牌带给第三方 |
| **云服务商流量日志** | 部分 IaaS 记录 L7 请求行 |
| **分享截图** | 用户调试时截图会把令牌暴露 |

```python
# ✅ 正确写法
ws = await websockets.connect(
    "wss://photo.example.com/agent/ws",
    extra_headers={"Authorization": f"Bearer {agent_token}"},
    max_size=MAX_FRAME,           # 65536，与服务端一致
    ping_interval=None,           # 用协议自带的 PING/PONG，不用 websockets 的心跳
    open_timeout=10,
)
```

**云端的校验**（必须在**握手阶段**完成，不能等连接建立后再校验）：

```python
async def agent_ws(websocket: WebSocket):
    # ★ 必须在 accept() 之前校验：否则未认证连接会占用资源
    token = _parse_bearer(websocket.headers.get("authorization"))
    if not token:
        await websocket.close(code=4401, reason="unauthorized")   # 未 accept 直接 close
        return
    device = await db.get_device_by_token_hash(sha256(token))     # ★ 存 hash 查
    if device is None or device.revoked:
        await websocket.close(code=4401, reason="unauthorized")
        return
    await websocket.accept()
    ...
```

**WSS 之外的隧道安全措施**：

| 措施 | 说明 |
|---|---|
| **帧大小上限** | `max_frame: 65536`（HELLO_ACK 下发）；超过直接断开，防内存放大攻击 |
| **帧头完整性** | 帧头 5 字节（type + req_id），先读帧头再读 payload，**绝不按声明长度预分配**（防 `Content-Length: 999999999` 类攻击） |
| **req_id 白名单** | 只处理电脑端主动发起或云端正向转发的 req_id；未知 req_id 的响应直接丢弃 |
| **单连接请求数上限** | 单隧道并发 in-flight 请求 ≤ 64，超过返回 503（防 req_id 表膨胀） |
| **空闲超时** | 90 秒无任何帧 → 断开（HELLO_ACK 的 `heartbeat_sec: 25`，3 次未响应即断） |
| **降级路径同样加密** | SSE + POST 长轮询也必须走 HTTPS，`agent_token` 同样走 Header |

### 5.3 云端 TLS 终止的隐私影响（诚实披露）

**这是本项目最重要的隐私披露，必须让用户明确知道。**

**架构事实**：TLS 在云 Relay 处终止（设计文档 §8.3）。云端拿到的是**解密后的明文 HTTP 请求与响应**。

**云端能看到什么**：

| 数据 | 云端是否可见 | 说明 |
|---|---|---|
| **照片原始字节** | ✅ **完全可见** | `/api/items/{id}/raw` 的响应体就是完整照片，云端在转发时**完整经过内存** |
| **缩略图字节** | ✅ 完全可见 | 同上 |
| **EXIF（含 GPS 经纬度）** | ✅ **完全可见** | 缩略图默认已剥离 EXIF（§6.4 实测），但**原图未剥离**，`GET /api/items/{id}` 的 JSON 响应也含 `gps_lat`/`gps_lon` |
| **文件名与路径** | ✅ 可见 | URL 与 JSON 中的 `file_name`、`rel_path` |
| **时间线（拍摄时间）** | ✅ 可见 | `/api/timeline` 响应 |
| **相机型号、镜头、ISO、光圈** | ✅ 可见 | 元数据响应 |
| **`client_token`** | ✅ 可见（Header 明文） | 这也是为什么**云被入侵 = 可冒充手机** |
| **账号密码** | ✅ 可见（登录请求体明文） | **这是最严重的**：用户密码经过云 |
| **上传的文件字节** | ✅ 可见 | 分片上传的每个 chunk |
| **删除/移动操作** | ✅ 可见 | 能知道用户删了哪些照片 |

**量化隐私暴露**：实测库中 **4199/4915 = 85.4%** 的照片带 GPS IFD。若云服务商分析流量，可还原出**完整的家庭住址、工作地点、旅行轨迹**。这是非常敏感的。

**一期的缓解措施**（不能消除，只能降低）：

| 措施 | 效果 |
|---|---|
| 云端**零媒体落盘** | 照片只在内存中经过，不进磁盘、不进日志、不进 CDN 缓存 |
| 日志**只记元数据**（字节数、状态码、耗时），不记 body | 事后无法从日志还原照片 |
| 缩略图/预览**默认剥离 EXIF**（§6.4 实测已天然剥离） | 云端看到的缩略图不含 GPS |
| 使用**自建 VPS**（而非第三方网盘） | 云服务商不是数据接收方；但 VPS 提供商仍可读内存 |
| **流量加密的通道**（用户可选 VPN） | 超出本项目范围 |
| 二期 **E2E 加密** | 彻底消除 |

**明确不做的缓解（及理由）**：

| 方案 | 不做的理由 |
|---|---|
| 在云上做 EXIF 剥离 | 云端不应处理媒体内容——这会把"零存储"变成"零存储但处理"，且实现成本高、易出错 |
| 用第三方 E2E 中继（如 Tailscale/Cloudflare Tunnel） | 超出设计范围；Cloudflare 同样终止 TLS；Tailscale 需要两端装客户端，不符合"手机开网页即用"的目标 |
| 一期就做 E2E | 见 R-5 与设计文档 §15.2 |

### 5.4 E2E 加密的预留设计（二期）

**协议字段预留**（**一期必须实现字段，二期填充逻辑**）：

```python
# protocol.py —— 一期就要定义这些字段，二期不改协议结构

# 帧头：type(1) + flags(1) + req_id(uint32 BE) + payload
#         ▲          ▲
#         │          └── 新增：flags 位
#         └── 现有：帧类型
FLAG_ENCRYPTED = 0x01     # payload 是密文
FLAG_COMPRESSED = 0x02    # payload 已压缩（保留）
FLAG_KEY_ROTATE = 0x04    # 本帧携带密钥轮换信息（保留）

# REQ_HEAD 的 JSON 结构预留 enc 字段
{
  "method": "GET",
  "path": "/api/items/123/raw",
  "headers": {...},
  "enc": null            # 一期恒为 null；二期为 {"alg":"AES-256-GCM","kid":"k1","nonce":"..."}
}
```

**为什么一期就必须预留**：

1. 协议是**云端与电脑端共享**的（`protocol.py`）。二期改协议要同时更新两端并保证版本兼容，成本远高于"一期多两个字段"。
2. 帧头从 5 字节变 6 字节是**破坏性变更**——所有旧客户端都会解析错位。**一期定好 6 字节，二期不动结构。**
3. `flags` 位为 0 时行为与一期完全一致，**零成本**。

**二期的完整方案（X25519 + HKDF-SHA256 + AES-256-GCM）**：

**密钥协商（配对时一次性完成）**：

```
[电脑] 生成长期密钥对 (SK_agent, PK_agent)，SK_agent 存 config.json（权限收紧）
       PK_agent 通过隧道上报云端，云端存 devices.public_key（二期新增列）
       ⚠️ 注意：云端持有 PK_agent 无害（公钥），但不能持有 SK_agent

[手机] 配对时从云端获取 PK_agent
       生成临时密钥对 (SK_client, PK_client)
       shared = X25519(SK_client, PK_agent)                    # ECDH
       session_key = HKDF-SHA256(
           ikm  = shared,
           salt = SHA256(PK_agent || PK_client),               # 绑定双方身份，防未知密钥共享
           info = "photobridge-v1-e2e",
           len  = 32
       )
       把 PK_client 通过云端转给电脑端
       电脑端用 SK_agent 与 PK_client 算出同一个 shared

[双方] 各自派生两把密钥（单向，避免 nonce 冲突）：
       key_c2a = HKDF(session_key, info="client-to-agent", len=32)
       key_a2c = HKDF(session_key, info="agent-to-client", len=32)
```

**加密（每个加密帧）**：

```
nonce = 8 字节单调递增计数器（每方向独立） || 4 字节 0
密文  = AES-256-GCM(key_方向, nonce, plaintext, aad=帧头)     # aad 绑定 req_id 与 flags
```

**重放防护**：

| 机制 | 说明 |
|---|---|
| **单调计数器** | 每方向独立的 64 位计数器，接收方只接受 `counter > last_seen`；重复或回退一律丢弃 |
| **AAD 绑定帧头** | `aad = type \|\| flags \|\| req_id`，篡改 req_id 会导致 GCM 认证失败 |
| **窗口内乱序** | 流控允许多帧乱序到达？**不允许**——隧道是单 TCP 连接，天然有序，所以严格单调可行 |
| **重连后计数器** | 重连时重新协商密钥（新的 X25519 临时对），计数器从 0 开始；旧的 nonce 永不复用 |
| **密钥轮换** | 每 24 小时或每 1 GB 流量后重新协商（`FLAG_KEY_ROTATE`）；AES-GCM 单密钥加密上限 2^32 帧，必须轮换 |

**为什么用 AES-256-GCM 而不是 ChaCha20-Poly1305**：两者都安全。选 GCM 的理由是**硬件加速**（AES-NI 在几乎所有 x86 与 ARMv8 上都有），而电脑端可能是老旧 CPU。手机端（ARMv8+）两者都有硬件支持。**若目标设备无 AES-NI，改用 ChaCha20-Poly1305**。

**为什么 HKDF 的 `info` 要分方向**：若两个方向用同一把密钥，双方的 nonce 计数器从 0 开始会产生**nonce 重用**——AES-GCM 下 nonce 重用是**灾难性的**（可恢复认证密钥，伪造任意消息）。分方向是最简单的避免方式。

**为什么 `salt` 要绑定双方公钥**：防止"未知密钥共享攻击"（Unknown Key-Share）。若不绑定，攻击者可让双方以为自己与对方通信，实际中间人是攻击者。

**二期实现的成本估算**：约 2-3 天（`cryptography` 库 + 双方各 100 行 + 测试）。**主要成本不在密码学，而在调试**——一旦加密出错，症状是"连接建立但所有请求失败"，排查困难。这是设计文档 §15.2 判断"二期上"的核心理由。

### 5.5 一期明确不做 E2E 的理由（汇总）

| 理由 | 说明 |
|---|---|
| **① 一期最大风险不是隐私，是架构能否跑通** | 隧道多路复用 + credit 流控 + 断点续传 + 双通路切换，这四件事任何一件出错都会让项目失败。叠加密钥协商会把调试面翻倍 |
| **② 当前云是自建 VPS，不是第三方网盘** | 威胁模型里"云服务商偷看"的动机与能力都远低于商业网盘 |
| **③ 云端零媒体落盘已经把"存储侧"风险消除** | 剩下的是"转发瞬间的内存可见性"，窗口极小 |
| **④ 协议已预留字段，二期成本可控** | 不改帧结构、不改 API 形状 |
| **⑤ 单用户系统，没有"多租户隔离"的合规压力** | 不涉及等保、GDPR 等要求 |

**但必须做的补偿措施**（一期**必须**全部实施，否则"不做 E2E"就变成了"不设防"）：

1. ✅ 云端零媒体落盘（磁盘、日志、CDN 缓存**全部**不落）
2. ✅ 缩略图与预览默认剥离 EXIF（GPS 不出现在给手机看的图片里）
3. ✅ 全链路 HTTPS + HSTS
4. ✅ 云服务器加固（§7.8）
5. ✅ 协议预留 `flags` 与 `enc` 字段
6. ✅ 本文档 §5.3 的隐私披露写入用户可见的部署文档，让用户**知情**

## 6. 数据安全

### 6.1 上传安全：白名单 + 魔术字节双重校验

**为什么必须双重校验**：扩展名是**用户可控的字符串**，魔术字节是**文件内容**。

**攻击场景**：攻击者把 `payload.exe` 改名为 `photo.jpg` 上传。

- **只查扩展名** → 通过 → 文件落到 `D:\Photos\2024\...\photo.jpg`
- **后果**：①该目录可能被其他软件扫描 ②用户可能双击打开（Windows 会按内容或扩展名执行）③即使不执行，也污染了照片库

**魔术字节表**（本项目支持的格式）：

| 格式 | 扩展名 | 魔术字节（hex） | 偏移 | 备注 |
|---|---|---|---|---|
| JPEG | jpg, jpeg | `FF D8 FF` | 0 | 最常见；`FF D8 FF E0`=JFIF，`FF D8 FF E1`=EXIF |
| PNG | png | `89 50 4E 47 0D 0A 1A 0A` | 0 | 8 字节完整签名 |
| GIF | gif | `47 49 46 38 37 61` 或 `47 49 46 38 39 61` | 0 | `GIF87a` / `GIF89a` |
| WebP | webp | `52 49 46 46` …(4 字节大小)… `57 45 42 50` | 0 / 8 | `RIFF` + `WEBP` |
| BMP | bmp | `42 4D` | 0 | `BM` |
| TIFF | tif, tiff | `49 49 2A 00`（小端）或 `4D 4D 00 2A`（大端） | 0 | |
| AVIF | avif | `.... 66 74 79 70 61 76 69 66` | 4 | ISO-BMFF：`ftyp` + `avif` |
| HEIC | heic, heif | `.... 66 74 79 70 68 65 69 63` | 4 | `ftyp` + `heic`/`heix`/`mif1` |
| MPO | （jpg 的变体） | `FF D8 FF E1` + EXIF 中含 MPF | — | 多图 JPEG，实测库中 72 个 |

**实测数据支撑**：真实库中 `jpg-lx2` 扩展名的 22 个文件，其**真实内容是 PNG**（`Image.open()` 成功识别为 PNG 256×341 RGB）。若只查扩展名，这 22 个会被误认为 jpg；若只查魔术字节，它们会被当作 png 而扩展名是 `jpg-lx2`（不在白名单）。**双重校验 + 白名单排除 `-lx2` 才能正确处理。**

**参考实现**：

```python
# uploads.py

_MAGIC: list[tuple[str, bytes, int]] = [
    ("jpeg", b"\xff\xd8\xff", 0),
    ("png",  b"\x89PNG\r\n\x1a\n", 0),
    ("gif",  b"GIF87a", 0),
    ("gif",  b"GIF89a", 0),
    ("webp", b"RIFF", 0),
    ("bmp",  b"BM", 0),
    ("tiff", b"II*\x00", 0),
    ("tiff", b"MM\x00*", 0),
]
_BMFF_BRANDS = {b"avif", b"avis", b"heic", b"heix", b"hevc", b"hevx", b"mif1", b"msf1"}


def sniff_kind(head: bytes) -> str | None:
    """从文件头 32 字节判定真实类型。返回 kind 或 None（无法识别）。"""
    if len(head) < 12:
        return None
    for kind, magic, off in _MAGIC:
        if head[off:off + len(magic)] == magic:
            if kind == "webp":
                # RIFF....WEBP：必须同时校验偏移 8 处的 WEBP
                if head[8:12] != b"WEBP":
                    return None
            return kind
    # ISO-BMFF：偏移 4 是 "ftyp"，偏移 8 是 brand
    if head[4:8] == b"ftyp" and head[8:12] in _BMFF_BRANDS:
        return "heic" if head[8:12] != b"avif" else "avif"
    return None


_EXT_KIND = {
    ".jpg": "jpeg", ".jpeg": "jpeg", ".jpe": "jpeg",
    ".png": "png", ".gif": "gif", ".webp": "webp", ".bmp": "bmp",
    ".tif": "tiff", ".tiff": "tiff",
    ".avif": "avif", ".heic": "heic", ".heif": "heic",
}


def validate_upload(name: str, head: bytes) -> str:
    """白名单 + 魔术字节双重校验。返回规范化后的扩展名。"""
    ext = os.path.splitext(name)[1].lower()
    if ext not in _EXT_KIND:
        raise UploadError("E_EXT_NOT_ALLOWED", f"扩展名不在白名单：{ext}")

    actual = sniff_kind(head)
    if actual is None:
        raise UploadError("E_MAGIC_UNKNOWN", "无法识别的文件类型（疑似伪装文件）")

    declared = _EXT_KIND[ext]
    # 允许的等价关系（jpeg 与 jpg 同义；heic/heif 同义；tif/tiff 同义）
    equivalent = {
        "jpeg": {"jpeg"}, "png": {"png"}, "gif": {"gif"}, "webp": {"webp"},
        "bmp": {"bmp"}, "tiff": {"tiff"}, "avif": {"avif"}, "heic": {"heic"},
    }
    if actual not in equivalent[declared]:
        audit_security("magic_mismatch", f"name={name} declared={declared} actual={actual}")
        raise UploadError(
            "E_MAGIC_MISMATCH",
            f"扩展名声明为 {declared}，实际内容是 {actual}（拒绝）",
        )
    return ext
```

**注意 `-lx2` 类文件**：`.jpg-lx2` 的 `os.path.splitext` 结果是 `('.jpg-lx2', '')` → `ext = ''` → **不在白名单 → 拒绝**。这是正确行为（这些文件是某 App 的缓存图标，不应进照片库）。**但索引器遇到它们时应静默跳过而非报错**（§6.7）。

### 6.2 图片解码安全（Pillow 解压炸弹防护）

**威胁**：一张 661 字节的 PNG 可以声明自己是 200000×200000 像素（4×10^10 像素）。Pillow 解码时若按其声明分配内存，需要 **120 GB**（4e10 × 3 字节/像素）→ **进程立即 OOM 被杀**。

**实测**（本机 Pillow 12.3.0）：

```
构造：661 字节，IHDR 声明 200000 x 200000
Image.open(f)  → 成功（open 不检查像素数！）
im.load()      → DecompressionBombError:
                 Image size (40000000000 pixels) exceeds limit of 178956970 pixels,
                 could be decompression bomb DOS attack
im.verify()    → 同样抛 DecompressionBombError
```

**关键观察**：

1. **`Image.open()` 不会检查**——只有 `load()` / `verify()` 才会触发。若代码在 `open()` 之后、`load()` 之前读取 `im.size` 并据此分配缓冲区，**就已经中招**。
2. **默认上限是 `MAX_IMAGE_PIXELS × 2`**：Pillow 默认 `MAX_IMAGE_PIXELS = 89478485`（约 8948 万），错误信息中的 `178956970` 正是它的 2 倍。**Pillow 只在超过 2 倍时抛异常，1~2 倍之间只发 `DecompressionBombWarning`。** 这意味着"1.5 倍上限"的图片会被**静默处理**，仍然消耗大量内存。

**本项目的配置**：

```python
# thumbs.py / indexer.py 启动时立即设置（模块导入时执行）
from PIL import Image
Image.MAX_IMAGE_PIXELS = 50_000_000          # 5000 万像素

# ★ 关键：把 warning 升级为 error，消除"1~2 倍静默通过"的窗口
import warnings
warnings.simplefilter("error", Image.DecompressionBombWarning)
```

**为什么选 5000 万**：实测库中最大图是 **8192×5464 ≈ 4477 万像素**（`全部备份\IMG_20241111_171132.jpg` 等，共 **120 个**文件 max 边 ≥ 6000px）。5000 万留有余量，能容纳现有全部照片；同时 5000 万 × 4 字节 = 200 MB，在 1 核 1 GB 的云上不会致命（且缩略图生成在**电脑端**，电脑内存充裕）。

**为什么必须 `simplefilter("error")`**：这是**本次安全评审发现的一个实际缺口**。仅设置 `MAX_IMAGE_PIXELS` 会让 5000 万~1 亿像素的图片通过（只发 warning），而 1 亿像素 × 4 字节 = **400 MB**，若 4 个 worker 并发就是 1.6 GB → **电脑端内存压力**。把 warning 升级为 error 后，任何超过 5000 万像素的图**直接拒绝解码**。

**其他解码安全措施**：

| 措施 | 实现 | 理由 |
|---|---|---|
| **先验头部，后解码** | 用 `Image.open()` 只读 `im.size`（不 `load()`），先判像素数 | 避免"先分配后检查" |
| **逐级降采样** | `im.draft("RGB", (size, size))`（仅 JPEG 有效） | JPEG 的 DCT 缩放让解码时只解 1/8 的数据，实测 76ms/张 |
| **解码超时** | 在 worker 进程中执行，主进程 `join(timeout=30)`，超时则 `terminate()` | 防畸形文件导致解码器死循环 |
| **异常全捕获** | `except Exception`（不是 `except OSError`） | 实测 435 个文件无 EXIF 块、大量文件触发 `Corrupt EXIF data`；Pillow 的异常类型不确定 |
| **拒绝多帧滥用** | 只取第 0 帧（`im.seek(0)`）；MPO/GIF 的帧数上限 100 | 实测有 72 个 MPO（2 帧）与 2 个 GIF；防止"10 万帧 GIF"放大攻击 |
| **HEIC 转换隔离** | `pillow_heif` 在独立子进程/线程中运行 | libheif 是 C 库，崩溃会影响主进程 |
| **临时文件不落库目录** | 解码在内存中完成 | 避免半成品污染库 |

**实测性能基线**（用于设定超时值）：

| 操作 | 实测 | 备注 |
|---|---|---|
| 扫描 4915 张图 + 读元数据 | **12.9 秒**（2.6 ms/张） | 全量索引目标 ≤ 30 秒 |
| 320px 缩略图（含 `draft`） | **76 ms/张**（60 张 4.57 秒） | 单线程；`workers=4` → 100 张约 1.9 秒 |
| 1600px 预览 | **573 ms/张**（60 张 34.37 秒） | **必须懒加载 + 缓存**，不能预生成 |

**超时值设定**：320px 缩略图单张超时 **10 秒**（实测 76ms 的 130 倍余量）；1600px 预览单张超时 **30 秒**（实测 573ms 的 52 倍余量）。超时后标记 `thumb_state='failed'` 并记录原因，**不阻塞队列**。

### 6.3 上传大小限制与流式写入

| 限制 | 值 | 理由 |
|---|---|---|
| 单文件大小 | **2 GB**（设计文档 §1.3）；config 中 `max_file_gb: 32` **建议下调为 2** | 2 GB 是设计目标；32 是 v0.2 遗留值，过大 |
| 分片大小（局域网） | 8 MB | 减少请求数 |
| 分片大小（云端） | 2 MB | 云端内存受限，且 2 MB 便于重传 |
| `init` 请求体 | ≤ 8 KB | 只有 JSON 元数据 |
| `patch` 请求体 | ≤ 分片大小 + 1 KB | **必须严格校验**：`Content-Range` 声明的长度与实际 body 长度一致，否则拒绝 |
| 单 client 并发上传 | **≤ 3**（设计文档 §8.5） | 防带宽独占 |
| 上传会话数上限 | 单 client ≤ 20 个未完成会话 | 防会话表膨胀 |
| 上传会话 TTL | 24 小时（`session_ttl_hours: 24`） | 超时清理临时文件 |

**流式写入**（**绝不整体缓冲**）：

```python
# ❌ 错误写法：整体读进内存
data = await request.body()          # 2 GB 文件 = 2 GB 内存 → OOM
f.write(data)

# ✅ 正确写法：边读边写，内存占用恒定
async def write_chunk(f, request: Request, expected_len: int) -> int:
    written = 0
    async for chunk in request.stream():        # 每次最多 64 KB
        written += len(chunk)
        if written > expected_len:
            raise UploadError("E_CHUNK_TOO_LARGE", "分片超过声明长度")
        f.write(chunk)                          # 直接落盘，不进内存
    if written != expected_len:
        raise UploadError("E_CHUNK_SHORT", f"期望 {expected_len} 实际 {written}")
    return written
```

**云端转发也必须流式**（这是 §7.4 流控的基础）：

```python
# ❌ 错误写法：整体缓冲
body = await agent_response.read()   # 2 GB → 云 OOM
return Response(body)

# ✅ 正确写法：流式转发，每 64 KB flush 一次
async def stream_forward(upstream):
    async for chunk in upstream.aiter_bytes(65536):
        yield chunk                      # StreamingResponse 立即发送
```

### 6.4 EXIF 清洗（给手机看时是否剥离 GPS）

**决策：缩略图与预览默认剥离全部 EXIF；原图保留原样。**

| 资源 | EXIF 处理 | 理由 |
|---|---|---|
| 缩略图 320px | **剥离** | 手机时间线只需要看，不需要元数据；剥离可省流量 |
| 预览 1600px | **剥离** | 同上 |
| **原图 `/raw`** | **保留原样** | 用户下载原图是要"完整备份"，剥离会损坏文件；且原图已经过 TLS 保护 |
| **元数据 JSON**（`/api/items/{id}`） | **保留 GPS** | 用户需要"在地图上查看"功能（设计文档 §6.3）；但**云可见**（§5.3 已披露） |

**实测验证（重要）**：

```
原图 GPS IFD 键 = [1, 2, 3, 4, 5, 6]   （GPSLatitudeRef/Latitude/LongitudeRef/Longitude/...）

convert("RGB") + thumbnail() + save(WEBP, quality=78)
  → 缩略图 getexif() = {}              ← EXIF 已【天然剥离】
  → 16840 字节

若显式传 exif=im.getexif().tobytes()
  → 缩略图 getexif() 含 GPS           ← 【会携带 GPS】
  → 18336 字节（多 1496 字节）
```

**结论**：**缩略图默认就是剥离的**（因为 `convert("RGB")` 创建了新图像，不继承原 EXIF）。**硬规则：生成缩略图/预览时绝不能传 `exif=` 参数。** 这是一条"默认安全、显式才危险"的设计——但必须在代码里加注释与测试防止后人"好心"加上 EXIF。


**为什么原图不剥离**：

1. 用户下载原图是"取回自己的照片"，剥离 EXIF 会让文件与原文件不一致（sha256 变化）→ 破坏"下载的原图就是原图"的保证。
2. 原图走 TLS，且云端零落盘。
3. 若用户要分享（去掉 GPS），应由手机端做（可加"分享时剥离位置"选项）——**这是二期的功能，不是一期**。

### 6.5 绝不覆盖已有文件的保证机制

**这是 G1（照片不丢）的核心保证。** 需要**四层**防护，任何一层单独都不够：

| 层 | 机制 | 防住什么 |
|---|---|---|
| **L1 存在性检查** | 目标路径已存在 → 追加 `_1`、`_2`… | 常规同名冲突 |
| **L2 sha256 判重** | 内容相同 → 丢弃上传，返回已有 `media_id` | 重复上传同一张 |
| **L3 内核级排他** | `open(path, "xb")` — 目标存在则抛 `FileExistsError` | **TOCTOU**：L1 检查与 L2 写入之间的竞态 |
| **L4 原子替换** | 临时文件 + `os.replace`（**同卷**） | 半截文件 |

**L3 为什么必须**：L1 的存在性检查与真正的写入之间有窗口。两个并发请求上传同名文件，都通过 L1 检查，然后都写入 → **一个覆盖另一个**。`"xb"` 模式是**内核原子**的，只有第一个成功。

**L4 的关键发现（严重）**：

**实测**：

```
os.replace(r"H:\...\tmp.bin", r"D:\Photos\dst.bin")
  → OSError [WinError 17] 系统无法将文件移到不同的磁盘驱动器

os.replace(r"H:\...\tmp.bin", r"H:\...\dst.bin")
  → 成功

shutil.move(跨卷)
  → 成功（但是 copy + unlink，【非原子】）
```

**结论：设计文档 §9.2 的"临时区 + `os.replace` 原子落盘"在默认配置下不成立。**

原因：`config.py` 中 `uploads_tmp` 目录由 `config.tmp_dir()` 决定，位于 `APP_ROOT/data/`。而 `APP_ROOT = Path(__file__).resolve().parents[2]`，即 **项目目录所在盘**。**相册库在 `E:`，项目在 `H:`（或部署后在 `C:`）——跨卷。**

**修复方案（三选一）**：

| 方案 | 实现 | 评价 |
|---|---|---|
| **A. 临时文件写到目标同卷** | 在 `D:\Photos\.staging\` 下建临时文件 | ✅ **推荐**：`os.replace` 变为同卷内重命名，原子且快（毫秒级） |
| B. 先复制到目标同卷临时名，再 replace | 两段：跨卷 copy（非原子）+ 同卷 replace（原子） | ⚠️ 可用但有双倍 IO；copy 中断会留垃圾 |
| C. 用 `shutil.move` 接受非原子 | 直接跨卷移动 | ❌ **不采纳**：copy 中断会留下**半截文件**，且名字是最终名 → 违反"不产生半截文件" |

**方案 A 的实现要求**：

```python
# uploads.py
STAGING_DIRNAME = ".staging"

def _staging_path(root_cfg: dict, target_rel: str) -> Path:
    """临时文件必须与目标【同卷】。放在 root 下的 .staging/ 里保证同卷。"""
    root = Path(root_cfg["path"])
    staging = root / STAGING_DIRNAME
    staging.mkdir(parents=True, exist_ok=True)
    # 用 upload_id 做临时名，避免与目标名冲突
    return staging / f"{upload_id}.part"
```

**必须同步的三项配置变更**：

1. `config.py` 的 `roots[0].exclude_dirs` 必须加入 `".staging"`（**否则索引器会去扫描临时文件**）。
2. `.staging` 目录必须被索引器与时间线 API **完全忽略**（不只在 exclude_dirs，还要在 `sandbox` 层显式拒绝 `rel_path` 以 `.staging/` 开头，防止客户端直接访问他人上传中的文件）。
3. 上传会话的 `temp_path` 字段（`upload_sessions` 表）现在指向库内路径——**这意味着"临时区不在库内"的原设计假设失效**，`sandbox` 必须允许写 `.staging/`（通过内部专用 root 或专用 API，不走通用 `resolve`）。

**更简洁的替代方案（推荐给实现者）**：把 `.staging` 放在**每个 root 内**，但在 `sandbox` 中把 `.staging` 加入**段级黑名单**（与 `..`、ADS 同级），只允许 `uploads.py` 通过内部函数 `_internal_staging_open()` 访问。这样既保证同卷，又保证客户端无法通过 API 触达。

**L1/L2 的具体行为**：

```python
def choose_target_name(root_cfg, target_dir: str, name: str) -> str:
    """在 target_dir 下为 name 找一个不冲突的名字。"""
    base, ext = os.path.splitext(name)
    candidate = f"{target_dir}/{name}" if target_dir else name
    if not resolve(root_cfg, candidate).real.exists():
        return candidate
    for i in range(1, 1000):
        candidate = f"{target_dir}/{base}_{i}{ext}" if target_dir else f"{base}_{i}{ext}"
        if not resolve(root_cfg, candidate).real.exists():
            return candidate
    raise UploadError("E_NAME_EXHAUSTED", "同名文件超过 1000 个")
```

**L2 sha256 判重的行为**（设计文档 §9.2）：

```
init 时若客户端提供了 sha256：
  SELECT id FROM media WHERE sha256 = ? AND missing = 0
  命中 → 返回 {"exists": true, "media_id": 12345}，客户端立即"上传完成"
         → 不传输任何字节
         → 【不写入任何文件】
```

**注意**：sha256 判重**只在客户端提供了 sha256 时**才生效（`init` 的 `sha256` 是可选参数）。若不提供，则每次上传都会新建文件（可能产生内容相同的多份文件）。这是**有意的**——强制客户端算 sha256 会让"快速上传"变慢。**但必须在 UI 上体现**（"已存在"提示）。

### 6.6 删除只进回收站

**硬规则**：**代码中不得出现 `os.unlink`、`os.remove`、`shutil.rmtree`。**

**为什么用 send2trash**：

1. 用户的照片是**不可再生的**。误删一张照片的代价远高于"回收站占空间"。
2. Windows 回收站给用户"后悔的机会"——这是**产品责任**，不只是安全措施。
3. 即使是恶意删除请求，也只能删到回收站，**可以恢复**。这直接降低 G1 的风险等级。

**实现约束**：

```python
# ❌ 禁止出现的写法（lint 会失败）
os.unlink(path)
os.remove(path)
shutil.rmtree(path)
path.unlink()
Path(path).unlink()
os.rmdir(path)                     # 空目录删除也禁止（应进回收站）
```

```python
# ✅ 唯一允许的写法
from send2trash import send2trash

def safe_delete(root_cfg: dict, rel_path: str) -> Path:
    rp = resolve(root_cfg, rel_path, need="write")
    if not rp.real.exists():
        raise SandboxError("E_NOT_FOUND", "待删除对象不存在")
    if rp.real == rp.root:
        raise SandboxError("E_PATH_ROOT", "不允许删除根目录")
    if _is_reparse_point(rp.real):
        raise SandboxError("E_PATH_REPARSE", "不允许删除重解析点")
    send2trash(str(rp.real))          # ← 唯一允许的删除
    return rp.real
```

**send2trash 的行为与限制**：

| 项 | 说明 |
|---|---|
| Windows | 调用 `SHFileOperationW` 移入回收站；**需要目标在同一卷**（跨卷会失败） |
| 网络驱动器 / UNC | **不支持**，会抛异常。若 root 是网络路径，删除必须改为"移动到 `.trash/` 子目录" |
| 只读文件 | 会失败，需要先清只读属性（本项目**不做**——失败即报错，不静默改属性） |
| 权限 | 库目录在 `E:` 盘，回收站需有写权限；正常情况有 |
| **`E:` 盘的回收站配额** | 回收站有大小上限，超出后**最旧的文件会被永久删除**。需在文档中告知用户 |

**`send2trash` 未安装的情况**：实测当前环境**未安装 `send2trash`**。必须在 `requirements.txt` 中声明，且 `safe_delete` 中的延迟导入失败时**必须明确报错**，绝不能 fallback 到 `os.remove`：

### 6.7 原子落盘：临时区 + os.replace

**为什么需要原子落盘**：

| 非原子写法的后果 | 场景 |
|---|---|
| **半截文件** | 直接写目标名，写到 800 MB 时断网 → 库里有一个 800 MB 的"照片"，缩略图生成失败，时间线显示破损图 |
| **不可区分** | 半截文件与正常文件同名，用户无法知道哪些是坏的 |
| **覆盖风险** | 若目标是已有文件，写到一半失败 → **原文件已被破坏** |

**原子落盘的正确流程**：

```
1. init      → 分配 upload_id，在 .staging/ 建 {upload_id}.part
2. patch ×N  → 按 offset 写入 .part（幂等：重复 offset 直接跳过）
3. complete  → ①校验总大小 == declared_size
               ②校验 sha256（若客户端提供）
               ③校验魔术字节（读 .part 前 32 字节）
               ④校验像素数（Pillow 读头部，不 load）
               ⑤用 "xb" 模式在目标位置创建【空占位】？
                  ✗ 不需要——os.replace 本身在目标存在时会【覆盖】
                  ✓ 正确做法：先用 resolve 确认目标不存在（L1），
                     再 os.replace（L4）。若两者之间被抢占，
                     os.replace 会覆盖 —— 所以必须用 L3 的 "xb" 保护。
               ⑥os.replace(.part, target)   ← 同卷，原子，毫秒级
               ⑦DELETE upload_session
               ⑧INSERT INTO media
               ⑨生成缩略图（异步，失败不影响原图）
```

**`os.replace` 的原子性保证**：

- **同卷内**：`os.replace` 在 NTFS 上是 `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`，是**原子**的——要么成功，要么目标完全不变。
- **跨卷**：实测抛 `OSError [WinError 17]`，**不会**静默降级为 copy（这是好事，失败比静默非原子好）。

**`os.replace` 与 L3 的配合**（**关键细节，容易做错**）：

`os.replace` 会**覆盖**已存在的目标。因此不能只靠它来保证"不覆盖"。正确顺序：

```python
# ✅ 正确：先用 xb 占位，再 replace
def finalize(upload, root_cfg, target_rel):
    target = resolve(root_cfg, target_rel, need="write").real
    # L1：目标不存在？
    if target.exists():
        target_rel = choose_target_name(...)      # 追加 _1
        target = resolve(root_cfg, target_rel, need="write").real
    # L3：内核级排他占位（若被并发抢占，抛 FileExistsError → 回到 L1 重试）
    try:
        with open(target, "xb"):
            pass                                   # 创建 0 字节占位
    except FileExistsError:
        target_rel = choose_target_name(...)
        target = resolve(root_cfg, target_rel, need="write").real
        with open(target, "xb"):
            pass
    # L4：原子替换占位文件
    os.replace(str(upload.temp_path), str(target))
```

**为什么"占位 + replace"而不是"直接 replace"**：直接 `os.replace` 在目标存在时会**静默覆盖**——L1 的检查到 replace 之间有 TOCTOU 窗口。占位用 `"xb"` 是内核原子的，**唯一能真正防并发覆盖的手段**。

**必须测试的场景**（07 文档覆盖）：

| 场景 | 期望 |
|---|---|
| 上传中途断网，重新 init 同名文件 | 不覆盖；断掉的 `.part` 在 TTL 后被清理 |
| 两个并发请求上传同名文件 | 一个得 `photo.jpg`，一个得 `photo_1.jpg`，**都成功，无覆盖** |
| 上传到 99% 后 complete 校验失败 | 目标位置**没有任何文件**（`.part` 被删），库不受污染 |
| 上传同名但内容不同 | 加 `_1` 后缀，两个文件都在 |
| 上传同名且 sha256 相同 | `exists: true`，**不写任何文件** |
| 临时文件与目标跨卷 | **必须在 init 阶段就失败**，不能等到 complete |

### 6.8 审计日志

**记录什么**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `ts` | TEXT | ISO 8601 本地时间（含时区偏移） |
| `device_name` | TEXT | 电脑名 |
| `client_id` | INTEGER | 哪个 client 发起的（**新增字段**，原设计没有） |
| `client_name` | TEXT | 手机名（便于人读） |
| `action` | TEXT | 见下表 |
| `rel_path` | TEXT | 目标相对路径 |
| `detail` | TEXT | JSON：大小、sha256、错误码、耗时 |
| `prev_hash` | TEXT | **前一条记录的 sha256**（防篡改链，**新增字段**） |
| `hash` | TEXT | 本条记录的 sha256（含 `prev_hash`） |

> ⚠️ **一期实现状态：`prev_hash` / `hash` 两列未落地。**
> 一期实际实现是 `backend/app/audit.py` 的
> `record()` —— 文件（主记录，TAB 五列 + `O_APPEND` + `os.fsync`）
> 加 `audit_log` 表（索引）。哈希链在范围评审时被去掉，
> 因为它的收益（检测篡改）在一期威胁模型下不成立：
> 能改 `data/audit.log` 的攻击者同样能改程序与数据库，
> 哈希链只增加"能检测"的错觉而不增加"能阻止"。
> 本节的加固方案保留为**二期候选**（`docs/11` 有对应条目）。
> 一期真正落实的是本节的其余部分：只追加、不轮转、不自动删除、
> 写入即 `fsync`、以及"三条记录路径行为一致"。
>
> 顺带记录一次真实缺陷：审计写入曾散落在三份互不一致的实现里，
> 实测导致真实库 `audit_log` 表 56 行**全是 `pair`** ——
> `delete` 与 `rescan` 只落了文件、从未进过索引表。

**必须记录的动作**：

| action | 触发 | 是否强制 |
|---|---|---|
| `upload.create` | 上传完成并落盘 | ✅ |
| `upload.dedup` | sha256 命中判重 | ✅ |
| `upload.rename` | 同名冲突加序号 | ✅ |
| `upload.fail` | 校验失败（含魔术字节不符） | ✅ |
| `delete` | 删除（进回收站） | ✅ **强制**（设计文档 §8.4 第 4 条） |
| `move` | 移动/改名 | ✅ **强制** |
| `index.scan_start` / `index.scan_end` | 全量扫描 | ✅ |
| `security.*` | 沙箱拒绝、越权尝试、令牌失败 | ✅ |
| `auth.login_success` / `auth.login_fail` | 登录 | ✅ |
| `pair.success` / `pair.fail` | 配对 | ✅ |
| `client.revoke` | 撤销设备 | ✅ |
| `thumb.fail` | 缩略图生成失败（含原因） | ⚠️ 可选（量大） |
| `thumb.ok` | 缩略图成功 | ❌ **不记**（4952 条噪声） |
| `read.*` | 读照片 | ❌ **不记**（量太大，且会泄露用户浏览行为） |

**明确不记录的内容**：

| 不记 | 理由 |
|---|---|
| **令牌（`agent_token` / `client_token`）** | 日志泄露 = 凭证泄露 |
| **密码** | 同上 |
| **照片字节** | 日志会膨胀到 TB 级 |
| **`sha256` 之外的媒体内容** | 不需要 |
| **用户的浏览行为**（看了哪张图） | 隐私：审计日志本身不应成为监控工具 |
| **请求头全文** | 可能含 `Authorization` |
| **IP 地址** | 家用网络 IP 会变，价值低；且是隐私 |

**防篡改设计**（**设计文档未覆盖，本文档新增**）：

原设计只有"只追加、独立文件"。这**不够**——攻击者若拿到电脑的写权限，可以：
1. 删除包含自己入侵痕迹的日志行
2. 修改日志内容

**加固方案：哈希链**。

```python
def write_audit(action: str, rel_path: str | None, detail: str | None = None,
                client_id: int | None = None) -> None:
    prev = _last_hash()                     # 读最后一条的 hash
    ts = datetime.now().astimezone().isoformat(timespec="seconds")
    body = json.dumps(
        {"ts": ts, "action": action, "rel_path": rel_path,
         "detail": detail, "client_id": client_id, "prev_hash": prev},
        ensure_ascii=False, sort_keys=True, separators=(",", ":"),
    )
    h = hashlib.sha256(body.encode("utf-8")).hexdigest()
    line = json.dumps({**json.loads(body), "hash": h},
                      ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    with open(AUDIT_PATH, "a", encoding="utf-8") as f:   # 追加，永不重写
        f.write(line + "\n")
        f.flush()
        os.fsync(f.fileno())                # 强制落盘
```

**哈希链的效果**：

- 删除任意一行 → 后续所有行的 `prev_hash` 都对不上 → **可检测**
- 修改任意一行 → 该行 `hash` 与内容不符 → **可检测**
- 攻击者要完美篡改，必须重算从篡改点开始的**全部**后续行——成本极高，且需要一个"当前 hash"的外部锚点才能完全防住

**残余限制（诚实说明）**：

- 攻击者若能重写整个文件（从第一行开始重算），哈希链**无法检测**。
- **完整的防篡改需要外部锚点**（如每天把最后一条 `hash` 通过隧道上报云端）。本项目一期**不做**（云端零存储原则，且上报 hash 会引入新的耦合）。
- **一期的实际保证是**："日志被篡改是可检测的，除非攻击者重写全部历史"。对于"电脑被入侵"场景，这已经足够——因为那时照片已经被读走了，审计日志的价值是**事后取证**而非**实时阻止**。

**保留多久**：

| 项 | 策略 |
|---|---|
| 单个文件大小 | 轮转到 10 MB |
| 保留份数 | 5 份（共 50 MB） |
| 保留时长 | 至少 90 天（按量估算：正常使用每天约 20 条 × 200 字节 = 4 KB/天 → 10 MB 可用约 7 年） |
| 轮转方式 | `audit.log` → `audit.log.1` → … → `audit.log.5`（最旧的删除） |
| **轮转时的哈希链** | 轮转后新文件的第一条记录的 `prev_hash` = 上一份最后一条的 `hash`，**链不断** |

**审计日志的访问控制**：

- **绝不通过 API 暴露**（§4.4 黑名单）。理由：攻击者若能读日志，就能知道哪些操作被记录了，从而**精准删除证据**。
- 只在电脑本地用文本编辑器查看。
- 托盘菜单提供"打开日志文件"（本地操作，不经网络）。

### 6.9 电脑端本地服务绑定安全

**风险分析**：`config.py` 的 `DEFAULT_CONFIG` 中 `server.host = "0.0.0.0"`。

**绑 `0.0.0.0` 意味着**：

1. 监听**所有**网络接口，包括公网接口（若电脑直接暴露在公网，或路由器做了端口转发/DMZ）。
2. 局域网内**任何设备**（含访客手机、智能音箱、被入侵的摄像头）都能访问 `http://<电脑IP>:8787`。
3. **直连是明文 HTTP**——同网设备可用 ARP 欺骗嗅探到 `client_token` 与照片内容。

**最坏情况**：用户路由器上恰好做了 `8787 → 电脑` 的端口转发（很多人为游戏/远程桌面做过），则**整个互联网都能访问照片库**，且**明文**。

**设计文档 §8.5 的对策**："本地服务只监听私网，启动时检测并拒绝在公网 IP 上绑定"。但 `config.py` 里写的是 `0.0.0.0`——**配置与设计不一致**。这是本次评审发现的**第三个缺口**。

**缓解措施（必须实施）**：

| 措施 | 实现 | 优先级 |
|---|---|---|
| **M1. 默认绑定改为 `127.0.0.1`** | 改 `DEFAULT_CONFIG["server"]["host"] = "127.0.0.1"`；局域网直连需要用户在托盘**显式开启** | **必须** |
| **M2. 显式开启时才绑私网网卡** | 不绑 `0.0.0.0`，而是枚举网卡，选择 `192.168.*` / `10.*` / `172.16-31.*` 的私网地址，**逐个绑定** | **必须** |
| **M3. 启动时检测公网 IP** | 用 `socket.connect(("8.8.8.8", 80))` 拿本机出口 IP（不实际发包），若该 IP 不是私网地址 → **拒绝启动并托盘告警** | **必须** |
| **M4. 拒绝在公网接口上绑定** | M2 的自然结果：只绑私网地址，公网接口根本不监听 | **必须** |
| **M5. `client_token` 校验** | 所有直连请求（除 `/api/system/ping`）必须带有效令牌 | **必须**（已有设计） |
| **M6. 防火墙规则限专用网络** | 设计文档 §10.2 已要求"防火墙放行 8787 仅专用网络" | 必须 |
| **M7. 直连也启用 HTTPS（自签）** | 可防同网嗅探，但自签证书会导致浏览器警告 + SW 无法注册 | ⚠️ **一期不做**，见下 |
| **M8. 限制直连来源 IP** | 只接受同网段（`192.168.1.0/24`）的请求 | ⚠️ 可选：NAT 环境复杂，易误拒 |
| **M9. 启动时扫描路由器端口转发** | 用 UPnP 查询是否有 `8787` 的转发规则 | ❌ 不做：UPnP 常被禁用，且引入新依赖 |

**M1-M4 的参考实现**：

```python
# local_server.py
import ipaddress
import socket

def _private_bind_hosts() -> list[str]:
    """枚举本机私网 IPv4 地址，用于绑定。绝不返回 0.0.0.0。"""
    hosts: list[str] = []
    try:
        for info in socket.getaddrinfo(socket.gethostname(), None, socket.AF_INET):
            ip = info[4][0]
            try:
                if ipaddress.ip_address(ip).is_private and not ip.startswith("127."):
                    hosts.append(ip)
            except ValueError:
                continue
    except OSError:
        pass
    return sorted(set(hosts))


def _outbound_ip() -> str | None:
    """拿本机出口 IP（不发包，只让内核选路由）。"""
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    try:
        s.connect(("8.8.8.8", 80))       # UDP connect 不发包
        return s.getsockname()[0]
    except OSError:
        return None
    finally:
        s.close()


def assert_not_public() -> None:
    """启动安全检查：若出口 IP 不是私网地址，拒绝绑私网并告警。"""
    ip = _outbound_ip()
    if ip is None:
        log.warning("无法确定出口 IP，跳过公网检查")
        return
    addr = ipaddress.ip_address(ip)
    if not (addr.is_private or addr.is_loopback):
        audit_security("public_ip_detected", ip)
        raise RuntimeError(
            f"检测到公网 IP {ip}。为保护照片安全，拒绝在公网接口上监听 8787。"
            f"请检查路由器是否做了端口转发，或关闭『局域网直连』功能。"
        )


def start_server(cfg: dict) -> None:
    lan_enabled = cfg["server"].get("lan_direct", False)
    if not lan_enabled:
        hosts = ["127.0.0.1"]                 # M1：默认只本机
    else:
        assert_not_public()                    # M3
        hosts = _private_bind_hosts()          # M2：只绑私网网卡
        if not hosts:
            hosts = ["127.0.0.1"]
            log.warning("未找到私网地址，局域网直连不可用")
    # 多网卡需要多个 socket（uvicorn 单 host 限制）或用 SO_REUSEPORT 方案
    ...
```

**M7（直连 HTTPS）为什么一期不做**：

| 理由 | 说明 |
|---|---|
| 自签证书会让浏览器显示"不安全"警告 | 用户每次都要点"继续访问"，体验极差 |
| **Service Worker 无法注册** | SW 需要可信证书或 localhost；自签证书下 SW 注册失败 → **PWA 与离线缓存全部失效** |
| 局域网直连的主要用途是"快速"，加 TLS 握手会增加延迟 | 收益/成本不匹配 |
| 威胁模型里"同网嗅探"已在一期接受（R-2） | 与 §2.4 一致 |

**因此 R-2 的残余风险必须靠 M1-M6 缓解，而不是靠 TLS。** 这是**必须告知用户**的：在不可信 Wi-Fi 下应关闭局域网直连（托盘开关），只用云端中继（走 HTTPS）。

**一个额外的缓解建议（低成本）**：直连时要求 `client_token` + **一个仅在局域网有效的短期票据**（配对时下发，24 小时有效），降低令牌被嗅探后的长期价值。**一期可选**。

## 7. 云端安全

### 7.1 输入校验（Pydantic）

**原则**：**所有** API 参数（路径参数、查询参数、请求体、Header）都必须经过 Pydantic 模型校验。**禁止**直接使用 `request.json()` 或裸 `dict`。

```python
# ❌ 错误写法：无校验
@app.post("/api/uploads/init")
async def init(request: Request):
    body = await request.json()
    size = body["size"]              # KeyError → 500；size 可以是负数或 10^18
    name = body["name"]              # 可以是 100 万字符
```

```python
# ✅ 正确写法：Pydantic 严格校验
class UploadInit(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=False)

    name: Annotated[str, StringConstraints(min_length=1, max_length=255)]
    size: Annotated[int, Field(ge=0, le=2 * 1024**3)]        # 0 ~ 2 GB
    mtime: Annotated[int, Field(ge=0, le=4102444800)]         # 到 2100 年
    sha256: Annotated[str | None, StringConstraints(
        pattern=r"^[0-9a-f]{64}$")] = None
    target_dir: Annotated[str | None, StringConstraints(max_length=512)] = None

    @field_validator("name")
    @classmethod
    def _no_path_in_name(cls, v: str) -> str:
        if "/" in v or "\\" in v:
            raise ValueError("name 不能含路径分隔符")
        return v
```

**关键校验点清单**：

| 参数 | 约束 | 防住什么 |
|---|---|---|
| `name` | 长度 1-255、不含分隔符 | 路径注入、超长名 |
| `size` | 0 ~ 2 GB | 负数、`10^18` 导致磁盘耗尽 |
| `sha256` | 严格 `^[0-9a-f]{64}$` | 注入、超长字符串 |
| `cursor` | base64 或整数，长度 ≤ 64 | 分页注入 |
| `limit` | **1 ~ 200（必须有上限！）** | `limit=10^9` 导致 OOM |
| `q`（搜索） | 长度 ≤ 100，转义 FTS5 特殊字符 | FTS5 查询注入 |
| `root` | 必须是**已知**的 root_id | 越权访问未配置的 root |
| `device_id` | UUID 格式 | 注入 |
| `Content-Range` | 严格 `^bytes (\d+)-(\d+)/(\d+)$` | 分片越界 |
| 请求体总大小 | Caddy `max_size 4MB` + 应用层校验 | 内存耗尽 |

**`limit` 必须有上限**——这是最容易漏的一条。`GET /api/timeline?limit=999999999` 会让服务端尝试构造一个巨大的响应。

**FTS5 查询注入**：SQLite FTS5 的 `MATCH` 有自己的一套语法（`AND`/`OR`/`NEAR`/`"`/`*`）。用户输入 `a" OR ""` 可能造成语法错误或意外匹配。**必须转义**：

```python
def escape_fts5(q: str) -> str:
    """把用户输入包装成 FTS5 的字面量短语，消除语法注入。"""
    return '"' + q.replace('"', '""') + '"'
```

### 7.2 SQL 注入防护

**硬规则：所有 SQL 必须用参数化查询（`?` 占位符）。禁止任何形式的字符串拼接。**

```python
# ❌ 错误写法（六种都禁止）
cur.execute(f"SELECT * FROM media WHERE id = {item_id}")
cur.execute("SELECT * FROM media WHERE id = %s" % item_id)
cur.execute("SELECT * FROM media WHERE id = " + str(item_id))
cur.execute("SELECT * FROM media WHERE rel_path = '" + path + "'")   # 最危险
cur.execute(f"SELECT * FROM media ORDER BY {sort_col}")              # 列名拼接
cur.execute(f"SELECT * FROM {table}")                                # 表名拼接
```

```python
# ✅ 正确写法
cur.execute("SELECT * FROM media WHERE id = ?", (item_id,))
cur.execute("SELECT * FROM media WHERE root_id = ? AND rel_path = ?", (root_id, rel_path))
cur.execute("SELECT * FROM media WHERE sha256 = ? AND missing = 0", (sha256,))

# 列名/表名无法参数化 → 必须用白名单映射，绝不接受客户端字符串
_SORT_COLUMNS = {"taken_at": "taken_at", "size": "size",
                 "file_name": "file_name", "indexed_at": "indexed_at"}

def order_clause(sort: str, desc: bool) -> str:
    col = _SORT_COLUMNS.get(sort)
    if col is None:
        raise HTTPException(400, {"error": "bad_sort"})
    return f"ORDER BY {col} {'DESC' if desc else 'ASC'}"      # col 来自白名单，安全
```

**为什么用 `?` 而不是 `%s`**：`sqlite3` 的占位符是 `?`（或 `:name`）。**注意：`sqlite3` 的参数化只对值有效，对标识符（表名、列名）无效**——所以列名必须走白名单。

**其他 SQL 安全措施**：

| 措施 | 说明 |
|---|---|
| 数据库文件权限 | `cloud.db` 与 `photobridge.db` 设为仅服务用户可读写 |
| 迁移脚本 | 设计文档 §2.4 要求 `migrations/NNN_xxx.sql`；**不允许删库重建**（`00-文档索引与开发流程.md` §3.3 硬约束 5） |
| 事务 | 级联撤销（§4.5）必须在**一个事务**里完成 |
| 不加载第三方 SQLite 扩展 | 减少攻击面 |
| 生产环境关闭 SQL 语句跟踪 | 防止参数值进日志 |

### 7.3 限流与防 DoS

**多层限流**（设计文档 §8.5 + 本文档细化）：

| 层 | 限制 | 作用域 | 超限响应 | 理由 |
|---|---|---|---|---|
| **L1 连接数** | 单 IP 并发连接 ≤ 50；全局 ≤ 500 | Caddy | 连接被拒 | 防连接耗尽 |
| **L2 请求速率** | **单 client 120 req/s** | `client_token` | 429 + `Retry-After` | 正常浏览峰值约 20 req/s（100 张缩略图在 5s 内），120 有 6 倍余量 |
| **L3 上传并发** | **单 client ≤ 3** | `client_token` | 429 | 防带宽独占 |
| **L4 上传速率** | 单 client ≤ 10 MB/s | `client_token` | 降速/429 | 家用宽带上行通常 < 5 MB/s |
| **L5 请求体大小** | `init` ≤ 8 KB；`patch` ≤ 分片大小 + 1 KB；其他 ≤ 1 MB | 路由级 | 413 | 防内存耗尽 |
| **L6 响应体大小** | 无硬限制，但**必须流式** | — | — | 2 GB 原图必须流式 |
| **L7 未认证请求** | 单 IP 10 req/min；全局 60 req/min | IP | 429 | 防登录/配对爆破 |
| **L8 登录** | 单 IP 5 req/min；单账号 20 req/h | IP + 账号 | 429 / 锁定 | §4.6 |
| **L9 配对** | 单 code 5 次；单账号 10 次 → 锁 30 min | code + 账号 | 429 + 锁定 | §4.3 |
| **L10 WebSocket 帧** | 单连接 ≤ 1000 帧/s | 隧道 | 断开 | 防帧洪水 |
| **L11 in-flight 请求** | 单隧道 ≤ 64 | 隧道 | 503 | 防 req_id 表膨胀 |
| **L12 全局带宽** | 见设计文档 §12（月 4.6 GB） | 账号 | 告警 | 成本控制 |

**限流的实现要点**：

```python
class TokenBucket:
    """令牌桶。单机单进程，内存实现足够。"""
    def __init__(self, rate: float, burst: int):
        self.rate, self.burst = rate, burst
        self.tokens = float(burst)
        self.last = time.monotonic()

    def allow(self, n: float = 1.0) -> bool:
        now = time.monotonic()
        self.tokens = min(self.burst, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= n:
            self.tokens -= n
            return True
        return False
```

| 要点 | 说明 |
|---|---|
| **键的选择** | 优先用 `client_id`（认证后），回退到 IP（未认证）。**不要只用 IP**——NAT 后的多个用户会互相影响（本项目单用户，影响小） |
| **内存上限** | 限流表必须有 LRU 上限（如 10000 条），否则攻击者用 100 万个 IP 撑爆内存 |
| **`Retry-After`** | 429 响应必须带 `Retry-After` 头，否则客户端会立刻重试，形成风暴 |
| **限流也要审计** | 频繁触发限流应写审计日志（可能是攻击信号） |
| **反代层也限流** | Caddy 的 `rate_limit` 可作为第一道防线；应用层是第二道 |

**为什么"限流"是安全机制而不只是性能优化**：没有限流时，攻击者可以：①用 100 个并发请求读 100 张原图 → 云端与电脑端同时被打爆；②用 10^6 次配对尝试爆破（§4.3）；③用 `limit=10^9` 让服务端 OOM。**限流是"资源耗尽类攻击"的唯一通用对策。**

### 7.4 资源耗尽防护：流控 credit window 是安全机制

**这是本项目最关键的一个"性能优化即安全措施"的设计。**

**威胁**：1 核 1 GB 的 VPS，用户请求一张 2 GB 的原图。

```
没有流控时：
  手机请求 /api/items/123/raw（2 GB）
    → 云端转发请求给电脑端
    → 电脑端开始发送 2 GB
    → 若云端 await resp.read() 而非流式 → 2 GB 进内存
    → VPS 只有 1 GB → OOM Killer 杀进程 → 服务不可用

即使流式转发也有风险：手机下载慢（4G）时，
TCP 接收窗口 + asyncio 缓冲会在云端堆积数百 MB。
```

**credit-based 流控如何解决**（设计文档 §4.3）：

```
HELLO_ACK 下发 credit_window = 8388608（8 MB）

规则：
  1. 电脑端只能发送【已被授权】的字节数
  2. 初始 credit = 8 MB
  3. 电脑端每发 N 字节，credit -= N
  4. 云端【成功写出一段数据给手机】后，发 CREDIT 帧归还对应字节数
  5. credit 归零时，电脑端【必须停止发送】，等待 CREDIT 帧
```

**为什么这是安全机制**：

| 属性 | 效果 |
|---|---|
| **内存上界可证明** | 云端在隧道上的缓冲**最多** `credit_window`（8 MB）+ TCP 缓冲。**与文件大小无关**——2 GB 文件与 2 MB 文件的云端内存占用相同 |
| **慢速客户端不能撑爆云端** | 手机下载慢 → 云端归还 credit 慢 → 电脑端发送慢 → **云端不堆积** |
| **恶意电脑端也不能** | 即使电脑端无视 credit 疯狂发送，云端在 `credit < 0` 时**直接断开连接**（协议违规） |
| **无需信任电脑端** | 流控是**强制**的，不是"建议"。云端校验每个 REQ_BODY/RES_BODY 帧的累计字节数 |

**定量分析**：

```
credit_window = 8 MB = 8388608 字节
云端每连接缓冲上界 ≈ 8 MB（隧道）+ 64 KB × 2（TCP 收发缓冲）
单隧道内存 ≈ 8.1 MB

VPS 内存预算（1 GB = 1024 MB）：
  Python 进程基线（FastAPI + uvicorn + sqlite3）  ≈ 80 MB
  单隧道流控缓冲                                ≈ 8.1 MB
  并发隧道数（本项目单用户单电脑）                = 1
  → 峰值 ≈ 90 MB

设计文档 §3.4 说"Relay 常驻 80-150 MB" → 【吻合】
即使 10 台电脑同时在线：80 + 10×8.1 = 161 MB，仍安全。
```

**必须实现的校验（安全关键）**：

```python
class CreditWindow:
    """credit 流控。既是性能优化，也是防内存耗尽的安全机制。"""

    def __init__(self, window: int = 8 * 1024 * 1024):
        self.window = window
        self.credit = window
        self.used = 0                  # 累计已发送字节（用于审计）

    def consume(self, n: int) -> None:
        """电脑端发送数据前调用。"""
        self.credit -= n
        self.used += n
        if self.credit < 0:
            # ★ 协议违规：电脑端无视 credit 继续发送 → 立即断开
            audit_security("credit_violation", f"credit={self.credit} n={n}")
            raise ProtocolError("E_CREDIT_VIOLATION", "发送超过授权额度，断开连接")

    def refund(self, n: int) -> None:
        """云端成功写出一段数据后调用。"""
        self.credit = min(self.window, self.credit + n)
        if n > 0:
            send_credit_frame(n)


# ★ 关键：即使流式转发，也必须【等待写完成】再归还 credit
async def stream_to_client(upstream, downstream, credit: CreditWindow):
    async for chunk in upstream.aiter_bytes(65536):
        await downstream.write(chunk)      # ← await：确保真的写出去了
        await downstream.drain()           # ← drain：确保 TCP 缓冲未满
        credit.refund(len(chunk))          # ← 写出后才归还
```

**最容易犯的三个错**：

| 错误 | 后果 |
|---|---|
| **在 `write()` 之前归还 credit** | 数据还在缓冲区里就归还 → 缓冲区无限增长 → **OOM**。必须在 `await write()` + `await drain()` **之后** |
| **不校验 credit 就接收** | 电脑端（可能被入侵）可以发 2 GB → **OOM** |
| **credit 归还粒度太大** | 一次归还整个 8 MB → 缓冲波动大。应按 chunk（64 KB）归还 |

**CREDIT 死锁防护**（07 文档重点测）：

```
死锁场景：双方互相等待
  电脑端：credit = 0，等云端发 CREDIT
  云端：  等电脑端发数据才能归还 credit
  → 永久卡死

防护：
  ① 云端在【每次写出数据后】无条件归还，不依赖电脑端先发
  ② credit 归还量 = 实际写出量；为 0 时不发帧（避免 CREDIT 帧风暴）
  ③ 心跳超时：90 秒无任何帧 → 断开重连（重连后 credit 重置）
  ④ 单元测试必须覆盖"credit 归零后收到部分数据"的场景
```

**其他资源耗尽防护**：

| 资源 | 防护 |
|---|---|
| **CPU** | 云端不做图像处理（零媒体原则）；正则用非回溯模式；JSON 解析拒绝 `NaN`/`Infinity` |
| **磁盘** | 云端**不落媒体**；日志轮转 50 MB × 5 份；SQLite 文件上限监控 |
| **文件描述符** | 单进程 fd 上限 1024；连接数限制 500 + 隧道 1 → 安全 |
| **req_id 表** | in-flight ≤ 64；超时 60 秒清理 |
| **上传会话** | 云端**不跟踪**上传会话（透传）；会话状态在电脑端 |
| **进程数** | 单进程 uvicorn（不用多 worker）——多 worker 会让内存翻倍 |

### 7.5 云端数据最小化

**这是本项目的架构核心承诺（设计文档 §1.1 需求 P1-7）。**

**云端数据库只存**（设计文档 §3.2）：

| 表 | 内容 | 敏感度 |
|---|---|---|
| `accounts` | `id, email, pass_hash, created_at, plan` | 中（邮箱 + 密码哈希） |

| 不存在 | 保证方式 |
|---|---|
| **任何媒体字节**（照片、缩略图、预览） | 代码中**没有** `media`/`photos`/`files` 表；所有媒体请求**直接透传**，不经任何缓存层 |

| **照片的 sha256** | 不存储（判重在电脑端） |
| **用户浏览历史** | 不记录（访问日志只记方法、路径模板、状态码、字节数） |

**必须强制执行的响应头**：

```python
@app.middleware("http")
async def no_store_headers(request: Request, call_next):
    response = await call_next(request)
    if request.url.path.startswith("/d/"):
        response.headers["Cache-Control"] = "private, no-store, max-age=0"
        response.headers["Pragma"] = "no-cache"
        response.headers["X-Accel-Expires"] = "0"            # Nginx 专用
        response.headers["Surrogate-Control"] = "no-store"   # CDN 专用
    return response
```

**为什么加这么多冗余的缓存控制头**：因为"云端零存储"是**承诺**，一旦某个中间层缓存了媒体，承诺就被打破。多个头是**纵深防御**——任何一个生效都够。

**验证方法**（07 文档覆盖）：在云端用 `lsof`/`du` 监控进程与磁盘，执行完整的浏览+上传+下载流程，断言：
- 进程 RSS 增长 ≤ 200 MB（流控生效）
- 磁盘上除 `cloud.db`、WAL、日志外**无新文件**
- `cloud.db` 的**大小不随媒体流量增长**

### 7.6 日志脱敏

```python
# cloud/relay/logging_setup.py
import re

_SENSITIVE_HEADERS = {"authorization", "cookie", "x-agent-token", "proxy-authorization"}
_TOKEN_IN_URL = re.compile(r"(token|code|key|secret|password)=[^&\s]+", re.IGNORECASE)
_BEARER = re.compile(r"(Bearer\s+)[A-Za-z0-9\-_\.=]+", re.IGNORECASE)

def scrub(text: str) -> str:
    text = _BEARER.sub(r"\1<redacted>", text)
    text = _TOKEN_IN_URL.sub(r"\1=<redacted>", text)
    return text

def scrub_headers(headers: dict) -> dict:
    return {k: ("<redacted>" if k.lower() in _SENSITIVE_HEADERS else v)
            for k, v in headers.items()}
```

**日志中必须脱敏的内容**：

| 不记 | 替代 |
|---|---|
| `Authorization` header 全文 | `<redacted>` |
| 令牌的任何部分（**含前 4 位**） | 完全不记 |
| 密码 | 完全不记 |
| `client_token` / `agent_token` | 完全不记 |
| 查询串中的 `token=`（纵深防御） | 正则替换为 `token=<redacted>` |
| 完整的 `rel_path` | 只记路径模板（`/d/{device_id}/api/items/{id}/raw`） |
| 请求/响应 body | 只记 `content_length` |
| 上传的文件名 | 不记（在 URL 或 body 中） |

**错误响应绝不返回内部细节**：

```python
# ❌ 错误写法
except Exception as exc:
    raise HTTPException(500, {"error": str(exc), "trace": traceback.format_exc()})

# ✅ 正确写法
except Exception:
    request_id = uuid4().hex
    log.exception("unhandled", extra={"request_id": request_id})   # 服务端记录，含堆栈
    raise HTTPException(500, {"error": "internal_error", "request_id": request_id})
```

**`request_id` 的价值**：客户端拿到一个 id，运维可用它去日志中查完整堆栈——**既不泄露细节，又能排查问题**。

## 8. 客户端安全（手机端 PWA）

### 8.1 token 存哪里：localStorage vs IndexedDB

| 维度 | `localStorage` | `IndexedDB` | 本项目 |
|---|---|---|---|
| **XSS 可达性** | ✅ 同步 API，一行拿到 | ⚠️ 异步 API，但**同样可达** | — |
| **容量** | 5-10 MB | 数百 MB ~ GB | IndexedDB |
| **数据类型** | 仅字符串 | 结构化对象、Blob | IndexedDB |
| **同步/异步** | 同步（阻塞主线程） | 异步 | IndexedDB |
| **Service Worker 可访问** | ❌ **不可**（SW 无 `window`） | ✅ **可** | **IndexedDB（决定性理由）** |
| **隐私模式** | 可用 | 可用 | — |

**决定性的技术理由**：**Service Worker 无法访问 `localStorage`**（SW 运行在 Worker 上下文，没有 `window` 对象）。若令牌存在 `localStorage`，SW 在拦截 `/raw` 请求时**无法附加 `Authorization` 头**。

**但真正的安全结论是：IndexedDB 并不比 localStorage 更安全对抗 XSS。** 两者都可被 JS 读取。**存储位置的选择是"功能需求"（SW 可访问）而非"安全需求"。真正的 XSS 防护在 §8.2。** 必须诚实说明这一点，不能让"用 IndexedDB"给人虚假的安全感。

```typescript
// frontend/src/lib/tokenStore.ts
import { openDB, IDBPDatabase } from 'idb'

const DB_NAME = 'photobridge'
const STORE = 'auth'

interface AuthRecord {
  deviceId: string
  clientToken: string
  clientName: string
  expiresAt: number
}

let dbp: Promise<IDBPDatabase> | null = null
function db() {
  dbp ??= openDB(DB_NAME, 1, {
    upgrade(d) { if (!d.objectStoreNames.contains(STORE)) d.createObjectStore(STORE) },
  })
  return dbp
}

export async function saveAuth(rec: AuthRecord) {
  await (await db()).put(STORE, rec, 'current')
}

export async function loadAuth(): Promise<AuthRecord | null> {
  const rec = await (await db()).get(STORE, 'current')
  if (rec && rec.expiresAt && rec.expiresAt < Date.now()) {
    await clearAuth()
    return null
  }
  return rec ?? null
}

export async function clearAuth() {
  await (await db()).delete(STORE, 'current')
  // ★ 同时清空所有缓存（撤销/过期时必须）
  const names = await caches.keys()
  await Promise.all(names.map((n) => caches.delete(n)))
}
```

**关键点**：

| 点 | 说明 |
|---|---|
| 令牌**不存**在 `localStorage` / `sessionStorage` / cookie | 统一走 IndexedDB |
| 令牌**不存**在 Pinia 的持久化插件里 | 避免多份副本 |
| 令牌**不**放进 URL、**不**放进 `postMessage` | — |
| **内存中保留一份**用于当前会话 | 减少 IDB 读取延迟；页面关闭即消失 |
| **过期即清** | `loadAuth()` 检查 `expiresAt` |
| **登出/撤销即清** | 同时清 Service Worker 缓存 |

### 8.2 XSS 防护

**这是手机端最重要的安全威胁**——因为 XSS 能直接读走令牌，进而读走全部照片。

| Vue 3 写法 | 是否安全 | 说明 |
|---|---|---|
| `{{ userInput }}` | ✅ **安全** | Vue 自动 HTML 转义 |
| `:title="userInput"` | ✅ 安全 | 属性绑定也转义 |
| `<img :src="userInput">` | ⚠️ **危险** | `javascript:` 协议、`data:` URI 可携带脚本。**必须校验协议** |
| `<div v-html="userInput">` | ❌ **禁止** | 直接插入 HTML |
| `v-bind="userInput"`（对象展开） | ❌ **禁止** | 可注入任意属性含事件处理器 |
| `<component :is="userInput">` | ❌ **禁止** | 可渲染任意组件 |
| `eval()` / `new Function()` / `setTimeout(string)` | ❌ **禁止** | — |
| `element.innerHTML = ...` | ❌ **禁止** | — |

```html
<!-- ❌ 错误写法 -->
<div v-html="item.file_name"></div>
<img :src="item.url">

<!-- ✅ 正确写法 -->
<div>{{ item.file_name }}</div>
<img :src="safeUrl(item.url)">
```

```typescript
// frontend/src/lib/safeUrl.ts
const ALLOWED_PROTOCOLS = new Set(['http:', 'https:', 'blob:'])

export function safeUrl(raw: string): string {
  try {
    const u = new URL(raw, window.location.origin)
    if (!ALLOWED_PROTOCOLS.has(u.protocol)) return ''
    if (u.origin === window.location.origin) return u.href
    if (isPrivateHost(u.hostname)) return u.href       // 局域网直连
    return ''
  } catch {
    return ''
  }
}
```

**文件名是攻击者可控的**（用户上传时自定名）→ **所有文件名渲染都必须走 `{{ }}`**。特别注意这些回显点：

| 场景 | 风险 |
|---|---|
| 时间线显示文件名 | 若用 `v-html` → 注入 |
| 搜索关键词回显 | 若用 `v-html` → 注入 |
| **EXIF 字段回显**（相机型号、镜头） | EXIF 是**文件内容**，攻击者可构造含 `<script>` 的相机型号字符串 → **若用 `v-html` 就中招** |
| 错误消息回显 | 服务端错误消息可能含用户输入 |

**CSP**（见 §5.1）：`script-src 'self'`，**不允许** `'unsafe-inline'` / `'unsafe-eval'`。这是 XSS 的第二道防线——即使有注入点，也无法执行内联脚本。

**lint 强制**：

```

vue/no-v-text-v-html-on-component: error
no-eval: error
no-implied-eval: error
no-new-func: error
no-script-url: error
```

建议加 `eslint-plugin-no-unsanitized` 检测 `innerHTML` 等危险赋值。

### 8.3 CSRF：token 在 header 而非 cookie，天然免疫

**为什么天然免疫**：CSRF 的攻击前提是"浏览器会自动携带凭证"。**自动携带的只有 cookie、HTTP Basic Auth、客户端证书、IP 白名单。** 本项目的 `client_token` 存在 **IndexedDB**，通过 **`Authorization` header 显式附加**。

```typescript
// frontend/src/lib/api.ts
async function apiFetch(path: string, init: RequestInit = {}) {
  const auth = await loadAuth()
  const headers = new Headers(init.headers)
  if (auth?.clientToken) {
    headers.set('Authorization', `Bearer ${auth.clientToken}`)   // 显式附加
  }
  return fetch(path, { ...init, headers, credentials: 'omit' })  // ★ 不带 cookie
}
```

**关键点**：①`credentials: 'omit'` 不发送任何 cookie；②服务端**不使用 cookie 做认证**（JWT 也存 IndexedDB）；③恶意站点无法读取 IndexedDB（同源策略）；④恶意站点无法设置 `Authorization` 头（自定义头触发 CORS 预检，而本服务不返回宽松 CORS 头）。

```python
# 云端：绝不使用 allow_origins=["*"]
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://photo.example.com"],   # ★ 只允许自己的域名
    allow_credentials=False,                        # ★ 不用 cookie
    allow_methods=["GET", "POST", "PATCH", "DELETE", "OPTIONS"],
    allow_headers=["Authorization", "Content-Type", "Content-Range"],
    max_age=600,
)
```

**直连（局域网 HTTP）的 CORS**：手机页面在 `https://photo.example.com`，直连请求到 `http://192.168.1.5:8787` → **跨源**。因此电脑端 `local_server.py` **必须**配置 CORS，且 `allow_origins` 同样是**白名单**（不是 `*`）。

> **一期实际情况（架构调整后）**：一期没有云端，手机页面本身就是从 `http://192.0.2.10:8787/`
> 加载的（`backend/app/static.py` 把前端 `dist/` 挂在同一个服务上），**同源**，
> 因此一期**不存在跨源请求，也不需要 CORS 白名单**。
> 上面的 CORS 设计保留给二期（HTTPS 云端页面 + HTTP 局域网直连的双通路场景）。

**⚠️ 混合内容（Mixed Content）—— 一期自动消失、二期会重新出现的架构风险**：

HTTPS 页面请求 `http://` 资源会被浏览器**阻止**（除 `localhost`）。这是一个**实际的技术障碍**：

| 方案 | 可行性 |
|---|---|
| 用 `http://192.168.1.5:8787` 直连 | ❌ 被 Mixed Content 阻止（Chrome 会拦截） |
| 把电脑端服务配自签 HTTPS | ⚠️ 需用户手动信任证书；**SW 无法注册**（非可信证书） |
| 用 `fetch` 而非 `<img src>` | ⚠️ 仍受 Mixed Content 限制 |
| 把直连请求放到 Service Worker 中 | ⚠️ SW 也受限制 |
| 电脑端自签证书 + 用户手动信任一次 | ✅ 可行，但体验有损 |
| 局域网直连也走 `https://` + mkcert 类证书 | ⚠️ 需分发 CA 到手机 |

> **✅ 一期不面对这个问题**：一期手机页面就是从电脑端 HTTP 服务加载的（同源、同为 HTTP），
> **不存在"HTTPS 页面请求 HTTP 资源"的组合**。这个风险随架构调整自动消解。
>
> **⚠️ 二期会重新出现**：二期的云端页面是 `https://<域名>/`，若仍保留局域网直连，
> 就回到"HTTPS 页面请求 `http://192.168.x.x`"的组合。**届时必须先做 30 分钟验证实验**
> （在 HTTPS 页面中用 `fetch` 请求 `http://192.168.x.x:8787/api/system/ping`，看 Chrome 是否阻止）。
> 若阻止，则：**方案 A** 局域网直连改用自签 HTTPS（生成证书、用户手动信任）；
> **方案 B** 放弃局域网直连，只用云端中继（性能损失，但架构简化）；
> **方案 C**（二期推荐）云端页面与直连都走同一个自签证书 + 引导用户装一次 CA。

**这是一个重要的架构风险，已记入 §12 发现清单。**

### 8.4 Service Worker 缓存的安全性

**缓存的是什么**：自己的照片缩略图与预览（`CacheStorage`）。

| 风险 | 说明 | 缓解 |
|---|---|---|
| **设备撤销后缓存残留** | 令牌被撤销，但已缓存的缩略图仍在手机磁盘上，可被离线查看 | **收到 401 时必须清空所有 cache**（`clearAuth()` 已实现） |
| **手机丢失** | 攻击者能看已缓存的照片 | ①用户应设置手机锁屏 ②PWA 提供"清除本地缓存"按钮 ③**接受**（R-4） |
| **缓存投毒** | 恶意响应被写入 cache | 只缓存**同源**响应；只缓存**成功的 GET**（200）；校验 `Content-Type` 为 `image/*` |
| **缓存膨胀** | 24 GB 照片全部缓存 → 手机存储耗尽 | ①只缓存缩略图与预览，**绝不缓存原图** ②处理 `QuotaExceededError` ③LRU 淘汰 |
| **敏感响应被缓存** | 元数据 JSON 含 GPS | 元数据响应**不缓存**（只缓存图片字节） |

```javascript
// frontend/src/sw.ts
const THUMB_CACHE = 'thumbs-v1'
const PREVIEW_CACHE = 'previews-v1'
const MAX_THUMB_ENTRIES = 3000
const MAX_PREVIEW_ENTRIES = 300

// ★ 绝不缓存 /raw（原图）与元数据 JSON
const NEVER_CACHE = [/\/raw(\?|$)/, /\/api\/items\/[^/]+$/,
                     /\/api\/(timeline|search|folders|events)/]

self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url)
  if (!isSameOriginOrPrivate(url)) return
  if (event.request.method !== 'GET') return
  if (NEVER_CACHE.some((re) => re.test(url.pathname))) {
    event.respondWith(fetch(event.request))          // 直接透传
    return
  }
  if (url.pathname.includes('/thumb')) {
    event.respondWith(cacheFirst(event.request, THUMB_CACHE, MAX_THUMB_ENTRIES))
    return
  }
  if (url.pathname.includes('/preview')) {
    event.respondWith(cacheFirst(event.request, PREVIEW_CACHE, MAX_PREVIEW_ENTRIES))
    return
  }
})

async function cacheFirst(request, cacheName, maxEntries) {
  const cache = await caches.open(cacheName)
  const hit = await cache.match(request)
  if (hit) return hit
  const resp = await fetch(request)
  // ★ 只缓存成功的、同源的、图片类型的响应
  if (resp.ok && resp.type === 'basic' &&
      (resp.headers.get('content-type') || '').startsWith('image/')) {
    await cache.put(request, resp.clone())
    await trimCache(cacheName, maxEntries)
  }
  return resp
}

// ★ 收到 401 时清空所有缓存
async function handleUnauthorized() {
  const names = await caches.keys()
  await Promise.all(names.map((n) => caches.delete(n)))
}
```

| 规则 | 理由 |
|---|---|
| **绝不缓存 `/raw`** | 原图体积大（24 GB 库），且缓存原图 = 手机上有完整照片副本 |
| **绝不缓存元数据 JSON** | 含 GPS |
| **绝不缓存非 GET** | 写操作不可缓存 |
| **只缓存同源/私网源** | 防跨源污染 |
| **只缓存 `resp.type === 'basic'`** | 排除 opaque 响应（跨源无 CORS 的响应无法检查内容） |
| **只缓存 `image/*`** | 防把 HTML 错误页当图片缓存 |
| **设置条目上限 + LRU** | 防存储耗尽 |
| **401 → 清空** | 撤销即时生效 |
| **版本化 cache 名** | `thumbs-v1` → 升级时清理旧版 |
| **`skipWaiting`/`clientsClaim` 谨慎使用** | 会让新版 SW 立即接管，可能导致正在进行的请求失败 |

**PWA 权限最小化**：

| 权限 | 是否需要 | 说明 |
|---|---|---|
| `geolocation` | ❌ **不需要** | 虽然照片有 GPS，但展示用的是 EXIF 数据，**不需要读取用户当前位置** |
| `camera` | ✅ 需要 | 拍摄上传（可选功能） |
| `microphone` | ❌ 不需要 | — |
| `notifications` | ⚠️ 可选 | 上传完成通知；**一期不做**（增加复杂度） |
| `clipboard-read` | ❌ 不需要 | — |
| `persistent-storage` | ⚠️ 建议申请 | 让 SW 缓存不被系统清理 |
| `wake-lock` | ✅ 需要 | 设计文档 §6.4：上传时防息屏 |
| `background-sync` | ⚠️ 二期 | 一期用前台上传 |
| `share-target` | ⚠️ 二期 | 从其他 App 分享照片到 PWA |

**明确拒绝 `geolocation`**——这是一个容易"顺手加上"但完全不需要的权限。

## 9. 供应链与依赖安全

### 9.1 依赖锁定

**为什么必须锁定**：不锁定的依赖会带来**不可预测的变更**——某天 `pip install` 拉到一个被投毒的版本，或一个不兼容的更新，都会破坏系统。

**Python：`requirements.txt` 带 hash**

```
# backend/requirements.txt —— 全部锁死版本 + hash
fastapi==0.115.6 --hash=sha256:...
uvicorn[standard]==0.34.0 --hash=sha256:...
pydantic==2.10.4 --hash=sha256:...
websockets==14.1 --hash=sha256:...
httpx==0.28.1 --hash=sha256:...
Pillow==12.3.0 --hash=sha256:...
pillow-heif==0.21.0 --hash=sha256:...
send2trash==1.8.3 --hash=sha256:...
python-multipart==0.0.20 --hash=sha256:...
```

```bash
pip install pip-tools
pip-compile --generate-hashes --output-file=requirements.txt requirements.in
pip install --require-hashes -r requirements.txt
```

**为什么用 `--require-hashes`**：即使攻击者控制了 PyPI 的某个包，hash 不匹配就会**拒绝安装**。这是供应链攻击最有效的防线。

**Node：`pnpm-lock.yaml`**

```bash
pnpm install --frozen-lockfile    # CI 中必须用 frozen，不允许更新 lockfile
```

`package.json` 中**固定版本**（不用 `^`/`~`），例：`"vue": "3.5.13"`、`"vite": "6.0.7"`、`"idb": "8.0.1"`。`pnpm-lock.yaml` 已记录完整依赖树与 integrity hash，**足够**。

### 9.2 依赖审计

| 工具 | 用途 | 频率 |
|---|---|---|
| **`pip-audit`** | 检查 Python 依赖的已知 CVE（对接 OSV） | 每次 `requirements.txt` 变更 + 每月 |
| **`pnpm audit`** | 检查 npm 依赖的已知漏洞 | 同上 |
| **Dependabot / Renovate** | 自动提 PR 更新依赖 | 可选（个人项目可手动） |
| **`pip-licenses`** | 检查许可证兼容性 | 一次 |

```bash
pip-audit -r backend/requirements.txt --strict
pnpm audit --audit-level=high
```

| 严重度 | 响应时限 | 动作 |
|---|---|---|
| Critical（CVSS ≥ 9.0） | **24 小时** | 立即升级或临时禁用相关功能 |
| High（7.0-8.9） | 7 天 | 升级 |
| Medium（4.0-6.9） | 30 天 | 计划升级 |
| Low（< 4.0） | 下次常规更新 | 记录 |

**重点关注的依赖**：

| 依赖 | 风险 | 理由 |
|---|---|---|
| **Pillow** | **高** | C 扩展，解析不可信输入，历史上有多个 RCE（如 CVE-2023-50447） |
| **pillow-heif** | **高** | 绑定 libheif（C++），解析不可信 HEIC |
| **`cryptography`**（二期） | 中 | C 扩展，但代码质量高 |
| **uvicorn / starlette** | 中 | HTTP 解析，历史上请求走私类问题 |
| **`websockets`** | 中 | 帧解析 |
| **`send2trash`** | 低 | 调用系统 API，但涉及删除 |

**为什么 Pillow 是最大风险**：它**必须**解析用户上传的任意图片，攻击者可构造畸形 JPEG/PNG 触发解码器漏洞。缓解：①锁版本 + 及时更新；②在**独立子进程**中解码（崩溃不影响主进程，一期建议实现）；③限制解码时间与像素数（§6.2）。

### 9.3 为什么谨慎引入新依赖

**每一个新依赖都是**：①**攻击面**（依赖代码在你的进程里运行，有你的全部权限）；②**供应链风险**（作者账号可能被接管，包可能被投毒——`event-stream`、`colors.js`、`xz-utils` 事件）；③**维护负担**（跟踪 CVE 与版本兼容）；④**体积**（PyInstaller 打包体积、前端 bundle 体积）；⑤**传递依赖**（一个依赖可能带来 20 个，每个都是攻击面）；⑥**许可证**（GPL 会传染）。

**本项目的依赖决策记录**：

| 依赖 | 引入理由 | 替代方案评估 |
|---|---|---|
| `fastapi` + `uvicorn` | 设计文档已定 | 可用 `aiohttp`，但 FastAPI 的 Pydantic 集成对输入校验有直接帮助 |
| `Pillow` | 图像处理必需 | 无替代 |
| `pillow-heif` | HEIC 支持必需 | 可用 `pyheif`（维护较差）；`pillow-heif` 是 Pillow 官方生态 |
| `send2trash` | 回收站删除必需 | 无替代（手写 `SHFileOperation` 太复杂） |
| `websockets` | 隧道必需 | `aiohttp` 也支持 WS |
| `watchdog` | 文件变更监控（`index.watch`） | ⚠️ **可选**——一期可用定期扫描代替。**建议一期不引入**，减少依赖 |
| `pytest` + `pytest-asyncio` + `httpx` | 测试必需 | 无替代 |
| `idb`（前端） | IndexedDB 的 Promise 封装（1.5 KB） | 可手写，但 `idb` 极小且成熟 |
| `Playwright` | E2E 测试 | ⚠️ **重**（下载浏览器 ~300 MB）。**见 07 文档的决策** |

**"不用"清单（明确拒绝的依赖）**：

| 拒绝 | 理由 |
|---|---|
| `python-jose` / `PyJWT` | 若只需简单 JWT 校验，可用 `cryptography` 手写（~50 行） |
| `passlib` | 已不活跃；直接用 `argon2-cffi` 或 `bcrypt` |
| `celery` / `redis` / `rabbitmq` | 单机单进程，**完全不需要**消息队列 |
| `sqlalchemy` | SQLite + 手写 SQL 更可控（且参数化查询是硬规则，ORM 会掩盖它） |
| `alembic` | 设计文档 §2.4 已定用 `migrations/NNN_xxx.sql` 手写迁移 |
| `loguru` | 标准 `logging` 足够 |
| `python-dotenv` | 用环境变量或 `config.json` 即可 |
| `axios` | 原生 `fetch` 足够 |
| `moment.js` / `dayjs` | 用原生 `Intl.DateTimeFormat`（日期需求简单） |
| `lodash` | 原生方法足够 |
| `element-plus` / `ant-design-vue` | 体积大（>500 KB）；**自写组件**（目标极简 PWA） |
| 任何 `*-sass` / CSS 框架 | 原生 CSS + CSS 变量足够 |

**原则：能用标准库解决的，不引入依赖。** 直接收益：PyInstaller 打包体积从 300 MB 降到 80 MB，前端 bundle 从 2 MB 降到 200 KB，攻击面大幅缩小。

## 10. 安全编码规范（必须遵守的硬规则）

> 这些规则是**强制**的。每条给出"错误写法 vs 正确写法"，并配 lint 检查。
> 人工 review 会漏，**必须自动化**。

### 规则 1：所有文件访问必须经过沙箱

```python
# ❌ 错误写法
from pathlib import Path
p = Path(cfg["roots"][0]["path"]) / user_input
with open(p, "rb") as f:
    return f.read()

# ✅ 正确写法
from app.sandbox import open_read, resolve
with open_read(root_cfg, user_input) as f:
    return f.read()
```

**检查**：`scripts/check_sandbox.py` 扫描 `backend/app/**/*.py`，命中 `open(` / `Path(` / `shutil.` / `os.remove` / `os.unlink` / `os.rename` / `os.replace` / `os.rmdir` / `.unlink()` / `.rmdir()` / `.write_bytes(` / `.read_bytes(` / `.write_text(` / `.read_text(` 即失败，除非文件在 `ALLOWED = {"sandbox.py"}` 白名单中。

### 规则 2：禁止 `os.unlink` / `os.remove` / `shutil.rmtree`

```python
# ❌ 错误写法
os.unlink(path); os.remove(path); shutil.rmtree(path)
Path(path).unlink(); path.unlink(missing_ok=True); os.rmdir(path)

# ✅ 正确写法
from send2trash import send2trash
send2trash(str(path))          # 唯一允许的删除方式
```

**检查**：grep `os\.unlink|os\.remove|shutil\.rmtree|\.unlink\(|os\.rmdir` 在整个仓库 → 必须为空。

### 规则 3：禁止字符串拼接 SQL

```python
# ❌ 错误写法
cur.execute(f"SELECT * FROM media WHERE id = {item_id}")
cur.execute("SELECT * FROM media WHERE name = '" + name + "'")
cur.execute("SELECT * FROM media WHERE rel_path = ?" % rel_path)

# ✅ 正确写法
cur.execute("SELECT * FROM media WHERE id = ?", (item_id,))
cur.execute("SELECT * FROM media WHERE rel_path = ?", (rel_path,))
```

**检查**：grep `execute\(f"|execute\(".*"\s*%|execute\(".*"\s*\+` → 必须为空。列名/表名必须走白名单映射。

> 一期落实的是"只追加"与"写入即落盘"这两条。

## 12. 安全事件响应

### 12.1 令牌泄露

**判定**：`agent_token` 或 `client_token` 可能被第三方获知。

| 场景 | 立即动作（5 分钟内） | 后续动作 |
|---|---|---|
| **`client_token` 泄露**（手机丢失、截图外泄） | ①手机端或电脑托盘点"移除设备" ②云端 `clients.revoked=1` ③隧道 NOTIFY 让电脑端立即失效 ④手机端 401 → 清空 SW 缓存 | 重新配对（生成新码） |
| **`agent_token` 泄露** | ①云端 `devices.revoked=1` → **立即断开隧道** ②电脑托盘"重新注册"生成新 `agent_token` ③云端更新 `devices.agent_token`（**应存 hash**） | 审查 `audit.log` 中该时间段的所有操作 |
| **账号密码泄露** | ①改密码 ②**撤销所有 `clients`**（因为攻击者可能已配对自己的手机） ③审查 `devices` 列表有无异常设备 ④撤销所有 `agent_token` 并重新注册 | 检查云端登录日志 |
| **配对码被截获** | 配对码 5 分钟自动失效；若已被使用，走"`client_token` 泄露"流程 | — |

**关键**：`agent_token` 泄露是**最严重的**——它能让攻击者建立一条到照片库的隧道。**云端撤销必须在 1 秒内生效**（`revoked` 检查在每次握手与每个请求上）。

**泄露后的取证清单**：

| 检查 | 位置 |
|---|---|
| 该 `client_token` 看过哪些照片 | `audit.log` **不记录读操作**（隐私设计）→ **无法回答**。这是本设计的一个取舍 |
| 该 `client_token` 删除/移动过哪些文件 | `audit.log` 的 `delete` / `move` 记录 |
| 该 `client_token` 上传过哪些文件 | `audit.log` 的 `upload.*` 记录 |
| 云端登录来源 | Caddy 访问日志（但已脱敏，不含令牌） |
| 隧道连接的 IP | Caddy 访问日志 |

**诚实指出**：由于审计日志**不记录读操作**（§6.8 的隐私决策），**无法知道泄露期间攻击者看了哪些照片**。若要能追溯，需要记录读操作——但这会让审计日志变成"用户行为监控"。**这是一个有意的隐私/取证取舍**，用户应知晓。

### 12.2 云服务器被入侵

**为什么损失小**（架构的核心价值）：

| 攻击者能拿到 | 攻击者**拿不到** |
|---|---|
| 账号邮箱与密码哈希 | **任何照片字节**（云端零存储） |
| `agent_token`（若未改 hash，**这是最严重的**） | 照片的 EXIF / GPS |
| `client_token` 的 hash（无法反推） | 文件名索引 |
| 设备列表与流量计数 | 照片的 sha256 |
| 配对码（短期） | 用户浏览历史 |

**重建流程**：

```
T+0    发现入侵（异常告警 / 用户报告 / 服务行为异常）
T+5min ①【隔离】在 VPS 控制台改防火墙：只允许自己的 IP 访问 SSH
       ②【保留证据】对 VPS 做快照（不要立即销毁，用于事后分析）
       ③【切断影响】电脑托盘 → 关闭"云端中继"或直接停掉 Agent
T+15min ④【重建】从快照创建一台全新的 VPS（不要修复被入侵的机器）
       ⑤ 重新执行 08 部署手册的全部加固步骤
       ⑥【轮换所有凭证】
           - 新 VPS 上重新初始化 cloud.db
           - 电脑端"重新注册" → 新 agent_token
           - 所有手机重新配对 → 新 client_token
           - 修改账号密码
T+1h   ⑦ 恢复服务，验证隧道建立、浏览、上传、下载
T+1d   ⑧ 分析快照，定位入侵途径（SSH 爆破？依赖漏洞？Caddy 配置？）
       ⑨ 修正根因，更新 08 部署手册
       ⑩ 检查电脑端 audit.log 有无异常操作（尤其 delete / move）
```

**关键原则**：

1. **不修复被入侵的机器，直接重建**。修复无法保证清除所有后门。
2. **必须轮换 `agent_token`**。若云端存的是明文，攻击者已拿到它。
3. **必须检查电脑端 `audit.log`**。攻击者可能通过隧道做了删除/移动操作。
4. **照片本身安全**。这是"云端零存储"架构的直接回报。

**预防措施**（§7.8 的加固清单）：
- `agent_token` 存 hash（**当前设计缺口，必须修**）
- SSH 密钥登录 + fail2ban
- 自动安全更新
- 监控告警（异常登录、异常流量）

### 12.3 电脑端被入侵

**这是最严重的场景**——照片库在电脑上，且 Agent 有写权限。

**判定信号**：

| 信号 | 来源 |
|---|---|
| `audit.log` 中有大量异常的 `delete` / `move` | 审计日志 |
| `audit.log` 中有 `security.escape_rejected` / `security.reparse_rejected` | 沙箱拦截记录 |
| `audit.log` 的**哈希链断裂** | 日志被篡改 |
| 出现未知的 `.staging/` 残留 | 未完成的上传 |
| 出现未知的 `client_token` | 未授权的配对 |
| 电脑上有未知进程 / 未知启动项 | 本机检查 |
| 照片数量异常减少 | 与索引对比 |

**响应流程**：

```
T+0    ①【立即断网】拔网线或关闭 Wi-Fi（阻止持续外传）
       ②【停掉 Agent】托盘退出（防止继续被利用）
T+5min ③【保护证据】复制 audit.log、photobridge.db 到外部介质（不要在原机分析）
       ④【评估范围】用 audit.log 判断：删除了什么？上传了什么？越界尝试？
       ⑤【检查照片】用 photobridge.db 的索引与磁盘实际文件对比，找出 missing 的文件
T+30min ⑥【恢复照片】从回收站恢复被删文件；从备份恢复
       ⑦【检查持久化】检查启动项（HKCU\...\Run）、计划任务、服务、浏览器扩展
       ⑧【杀毒扫描】用 Windows Defender 全盘扫描 + 第三方工具
T+1d   ⑨【重装系统】（若无法确定根因）——照片库在 E: 盘，重装 C: 不影响
       ⑩【重新配置】重装后重新部署 Agent，生成新 agent_token
       ⑪【复盘】定位入侵途径
```

**为什么"照片库在 E: 盘、系统在 C: 盘"是有利的**：重装系统不需要动照片库（只需重装后重新索引，实测 4952 个文件约 12.9 秒）。

**预防措施**：

| 措施 | 状态 |
|---|---|
| 沙箱（§3） | ✅ 已设计 |
| 删除进回收站（§6.6） | ✅ 已设计 |
| 审计日志哈希链（§6.8） | ✅ 已设计 |
| 本地服务默认只绑 `127.0.0.1`（§6.9） | ⚠️ **需修改 config.py** |
| 照片库定期备份到离线介质 | ❌ **设计文档未要求，建议补充** |

**建议补充**：**照片库必须有独立于本方案的备份**（外接硬盘 / NAS / 另一块盘）。理由：本方案的所有安全措施都是"防止通过 API 破坏"，但**无法防止**：①本机管理员恶意操作 ②硬盘故障 ③勒索软件 ④用户误操作。**备份是最后一道防线，且是唯一能应对"硬盘物理损坏"的措施。** 这条建议应写入 08 部署手册。

### 12.4 数据恢复流程

| 场景 | 恢复方式 | 预计耗时 | 成功率 |
|---|---|---|---|
| **误删单张照片** | Windows 回收站还原（`E:` 盘的回收站） | 1 分钟 | 高（只要未清空回收站） |
| **误删多张照片** | 回收站按时间排序批量还原 | 5 分钟 | 高 |
| **回收站已清空** | ①从备份恢复 ②数据恢复软件（Recuva / R-Studio） | 1 小时 - 1 天 | 中（取决于磁盘写入量） |
| **上传产生半截文件** | ①`audit.log` 找到 `upload.fail` 记录 ②删除 `.staging/` 下的残留 ③重新上传 | 10 分钟 | 高 |
| **索引损坏**（`photobridge.db` 损坏） | 删除 `photobridge.db` → 重新索引（**实测 4912 张图约 12.9 秒**） | 1 分钟 | **高（索引可完全重建）** |
| **缩略图缓存损坏** | 删除 `data/thumbs/` → 重新生成（后台任务） | 后台运行 | 高 |
| **照片库被勒索软件加密** | **只能从备份恢复** | 依赖备份 | **取决于备份** |
| **硬盘物理损坏** | **只能从备份恢复** | 依赖备份 | **取决于备份** |
| **云端被入侵** | 照片未受影响（零存储）；重建云 + 轮换令牌 | 1 小时 | 高 |
| **配置丢失**（`config.json`） | 重新配置（root 路径、上传规则）；`agent_token` 需重新注册 | 10 分钟 | 高 |

**恢复的优先级**：

```
1. 原图（不可再生）    ← 最高优先级，必须有备份
2. EXIF（嵌入原图）    ← 随原图
3. 索引数据库          ← 可从原图完全重建（12.9 秒）
4. 缩略图缓存          ← 可从原图重新生成
5. 审计日志            ← 可接受丢失（但会失去取证能力）
6. 配置                ← 手工重建
```

**结论：只有"原图"需要备份。** 其余全部可以从原图重建。这大大简化了备份策略：**只需备份 `D:\Photos`**。

**备份策略建议**（写入 08 部署手册）：

| 项 | 建议 |
|---|---|
| 备份对象 | `D:\Photos`（24 GB） |
| 备份介质 | 外接硬盘 / NAS / 第二块物理盘 |
| 频率 | 每周增量 + 每月全量 |
| 保留 | 最近 4 周 + 最近 3 个月 |
| 验证 | 每季度做一次**恢复演练**（随机抽 10 个文件验证可打开） |
| 离线 | 至少一份备份**离线保存**（防勒索软件） |
| 加密 | 若备份介质可能丢失，应加密（如 BitLocker / VeraCrypt） |

**为什么"恢复演练"必须做**：未经测试的备份等于没有备份。这是运维的基本常识。

## 附录 B：安全决策记录（ADR 摘要）

| # | 决策 | 备选方案 | 理由 |
|---|---|---|---|
| S1 | 路径沙箱采用"重解析点一律拒绝"而非"消解后放行" | 消解 + 边界断言 | 消解后放行存在 TOCTOU 窗口（实测：同一路径在两次调用间从安全变越界） |
| S2 | 用 `os.path.commonpath` + `normcase` 做边界断言 | `str.startswith` | `startswith` 有前缀歧义（`相册` vs `相册-备份`），且大小写敏感会误判 |
| S3 | 用 `st_file_attributes & 0x400` 检测重解析点 | `os.path.islink()` | **实测 `islink()` 对 junction 返回 False**（完全漏检），而 junction 不需要管理员权限 |
| S4 | `client_token` 存 IndexedDB 而非 localStorage | localStorage | Service Worker **无法访问 localStorage**，导致 SW 无法为 `/raw` 附加 `Authorization` 头 |
| S5 | 令牌走 `Authorization` header 而非 URL | URL 参数 | URL 会进反代访问日志、浏览器历史、`Referer`、云服务商日志 |
| S6 | 删除只用 `send2trash`，代码中禁止 `os.unlink` | 直接删除 | 用户照片不可再生；回收站给"后悔的机会"；即使被恶意删除也可恢复 |
| S7 | 上传"绝不覆盖"用 `"xb"` 内核级排他 | 先 `exists()` 再写 | `exists()` 与写入之间有 TOCTOU；两个并发同名上传会互相覆盖 |
| S8 | 缩略图默认剥离 EXIF（不传 `exif=`） | 保留 EXIF | 给手机看的图不需要元数据；**原图保留**（下载要完整） |
| S9 | 审计日志用哈希链防篡改 | 只追加 | "只追加"无法防止攻击者删除/修改行；哈希链让篡改**可检测** |
| S10 | 一期不做 E2E，但协议预留 `flags`/`enc` | 一期就做 E2E | 一期最大风险是架构能否跑通；协议预留让二期成本可控（§5.5） |
| S11 | 云端 `allow_origins` 用白名单而非 `*` | `["*"]` | 宽松 CORS 扩大攻击面；配合 `allow_credentials` 更是致命 |
| S12 | 本地服务默认只绑 `127.0.0.1` | 绑 `0.0.0.0` | 最小暴露面；局域网直连需显式开启 |
| S13 | 依赖锁定用 `--require-hashes` | 只锁版本号 | 即使 PyPI 上的包被投毒，hash 不匹配也会拒绝安装 |
| S14 | 图片解码放独立子进程 | 主进程解码 | 畸形图片导致解码器崩溃时，**主进程不受影响**（Pillow 是最大风险依赖） |
| S15 | 云端单进程 uvicorn（不用多 worker） | 多 worker | 多 worker 会让内存翻倍，1 GB VPS 承受不起；且流控状态需共享 |
