### 1.2 测试目标

**一句话**：证明 PhotoBridge 在**真实使用场景**下，能**稳定地**让用户通过手机访问电脑上的照片，并且**不会丢照片、不会被越界访问、不会把云端变成网盘**。

拆解为 6 个可验证的目标：

| # | 目标 | 对应需求 | 验证方式 | 通过标准 |
|---|---|---|---|---|
| **G1** | **功能可用**：手机能看照片、能上传、能下载 | P1-1 ~ P1-4 | 端到端手工验收（§6） | 12 个 E2E 场景全部通过 |
| **G2** | **照片不丢**：上传不产生半截文件，同名不覆盖，删除进回收站 | P1-3、P1-4 | 单元 + 集成 + E2E | 无任何场景导致原图被覆盖或损坏 |
| **G3** | **不越界**：路径沙箱无法被任何构造的路径穿越 | 06 §3 | 80 条恶意路径单元测试 | **80/80 通过，无例外** |
| **G4** | **不越权**：无令牌、错令牌、过期令牌、已撤销令牌、A 设备令牌都不能访问 | 06 §4 | 鉴权/越权安全测试（§7.2-7.3） | **47/47 通过，无例外** |
| **G5** | **云端零存储**：云上不落任何媒体字节 | P1-7 | 云端磁盘与内存监控（§7.11） | 云上除 DB/日志外无新文件；内存 ≤ 200 MB |
| **G6** | **性能达标**：首屏 ≤2.5s、上传 ≥1.5MB/s、1核1GB 可支撑 | §1.3 非功能目标 | 性能测试（§8） | 全部达标 |

## 2. 测试策略

### 2.1 测试金字塔

```
                    ▲
                   ╱ ╲          E2E 手工验收      12 条    ~8%
                  ╱   ╲         （业主执行，真人真机）
                 ╱─────╲
                ╱       ╲       集成测试          78 条    ~17%
               ╱         ╲      （pytest + httpx + 真实隧道）
              ╱───────────╲
             ╱             ╲    单元测试          ~200 条  ~75%
            ╱               ╲   （pytest，快，覆盖边界）
           ╱─────────────────╲
```

| 层 | 数量 | 工具 | 执行时机 | 耗时目标 | 覆盖 |
|---|---|---|---|---|---|
| **单元测试** | ~200 条 | `pytest` | 每次提交（pre-commit）+ CI | **< 60 秒** | 纯函数、边界、错误分支 |
| **集成测试** | 78 条 | `pytest` + `pytest-asyncio` + `httpx` + 真实 WSS | 每次提交（CI） | **< 10 分钟** | 模块间协作、协议、DB |
| **E2E 手工验收** | 12 条 | 人 + 真机 + 真云 | 每个里程碑 + 上线前 | **2-4 小时** | 真实用户场景 |
| **安全测试** | 277 条 | 分散在单元/集成/E2E | CI（大部分）+ 手工（部分） | — | 06 §11 |
| **性能测试** | 32 条 | 脚本 + `tracemalloc` + 云端监控 | C2 后 + 上线前 | **1-2 小时** | 非功能目标 |

**为什么单元测试要占 75%**：单元测试**快、稳、定位准**。集成测试慢且脆弱（网络、时序），E2E 更慢且只能手工。把尽可能多的验证下推到单元层，是"测试能持续跑下去"的前提。

**为什么 E2E 只有 12 条**：手工 E2E 的成本极高（需要真机、真云、真人操作），只能覆盖**最关键的端到端路径**。12 条对应设计文档 §9 的 4 个核心流程 + 8 个高风险场景。

### 2.2 各层工具选型

| 工具 | 用途 | 引入理由 | 不引入的替代方案 |
|---|---|---|---|
| **`pytest`** | 单元 + 集成测试框架 | Python 事实标准；`fixture` 机制强大；参数化测试（`@pytest.mark.parametrize`）**极适合沙箱的 80 条用例** | `unittest`（冗长，无 fixture） |
| **`pytest-asyncio`** | 测试 async 代码 | 云端与隧道是 async；`@pytest.mark.asyncio` | `anyio`（也可，但 `pytest-asyncio` 更常见） |
| **`pytest-cov`** | 覆盖率 | 强制门槛（§1.4） | — |
| **`pytest-timeout`** | 测试超时保护 | 防止死锁的测试**挂住 CI**（隧道测试特别需要） | — |
| **`httpx`** | HTTP 客户端（测试） | 支持 `async`；`ASGITransport` 可**直接测试 FastAPI app 而不起服务器**（快！） | `requests`（同步，无法测 async）；`TestClient`（基于 `requests`，有已知问题） |
| **`httpx-ws`** 或 `websockets` | 测试 WSS | 隧道测试必需 | — |
| **`freezegun`** 或 `time-machine` | 时间冻结 | 测"配对码 5 分钟过期"、"令牌 90 天过期"、"跨月归档"必须能控制时间 | 手工 `sleep`（太慢） |
| **`faker`** | 生成测试数据 | ⚠️ **不引入**——测试数据用真实库 + 手工构造样本，`faker` 的随机字符串对图片测试无用 | — |
| **`vitest`** | 前端单元测试 | Vue 3 生态标准；快（Vite 原生） | `jest`（慢，配置繁琐） |
| **`@vue/test-utils`** | Vue 组件测试 | 测 `safeUrl()`、token 存取、状态条逻辑 | — |
| **`Playwright`** | 浏览器 E2E | ⚠️ **见下方决策** | `Cypress`、`Selenium` |
| **`ruff`** | Python lint | 快；替代 `flake8`+`isort`+部分 `pylint` | `flake8`（慢，插件多） |
| **`eslint`** + `eslint-plugin-vue` | 前端 lint | `vue/no-v-html` 规则必需（06 §10 规则 5） | — |

#### 决策：是否引入 Playwright

| 维度 | 引入 | 不引入 |
|---|---|---|
| **能测什么** | 自动化的浏览器端回归（时间线渲染、上传交互、SW 缓存、CSP 生效、XSS 防御） | 只能手工 |
| **成本** | 下载浏览器 ~300 MB；CI 时间增加；维护 selector | 0 |
| **本项目适用性** | ⚠️ **PWA + Service Worker + 真机行为**是 Playwright 的**弱项**：SW 在 Playwright 中行为与真机有差异；PWA 安装无法自动化；`wakeLock` 无法自动化 | — |
| **关键判断** | 本项目的**核心风险在服务端**（沙箱、鉴权、上传、流控），不在前端渲染。前端只有 ~10 个组件，手工 E2E 覆盖足够 | — |
| **结论** | ❌ **一期不引入 Playwright**。理由：①核心风险在服务端 ②PWA/SW 是它的弱项 ③一期前端简单 ④节省 300 MB 与 CI 时间。**用 `vitest` + `@vue/test-utils` 覆盖纯逻辑（`safeUrl`、token 过期判断、状态条状态机），用 12 条手工 E2E 覆盖界面交互。** | — |
| **何时重新评估** | 若二期前端复杂度上升（如视频、地图、相册编辑），或发现前端回归频繁 | — |

**这个决策是诚实的取舍，不是"因为麻烦所以不做"。** 记录到 §10.3 的决策记录。

**为什么用真实库而不是 `faker` 生成的数据**：

1. **真实库有真实的"脏数据"**：缺失 EXIF、异常文件名、超大图、ICC 配置文件——这些是 `faker` 永远不会生成的。
2. **性能数据必须真实**：24 GB / 4915 张的扫描与缩略图吞吐，用 100 张假图测不出来。
3. **回归价值**：每次改动后重跑，能发现"对某类真实文件处理退化"。
4. **它就在那里**：零成本。

**使用真实库的三条纪律**：

| 纪律 | 说明 |
|---|---|
| **绝不修改真实库** | 测试**只读**真实库。需要写测试时，先复制到临时目录（`tests/fixtures/tmp_library/`） |
| **绝不删除真实文件** | 即使测"删除进回收站"，也只在临时副本上做 |
| **测试前记录指纹** | 记录文件数、总大小、每个文件的 mtime；测试后校验**完全一致**（§6.13 的"库完整性校验"） |

**库完整性校验脚本**（每次测试前后运行）：

```python
# tests/tools/library_fingerprint.py
import hashlib, json, os
from pathlib import Path

def fingerprint(root: Path) -> dict:
    """对库做轻量指纹（不读文件内容，只读元数据）。"""
    entries = []
    for p in sorted(root.rglob("*")):
        if not p.is_file():
            continue
        st = p.stat()
        entries.append({
            "rel": str(p.relative_to(root)),
            "size": st.st_size,
            "mtime_ns": st.st_mtime_ns,
        })
    h = hashlib.sha256(
        json.dumps(entries, sort_keys=True, ensure_ascii=False).encode()
    ).hexdigest()
    return {"count": len(entries), "total_size": sum(e["size"] for e in entries),
            "digest": h, "entries": entries}

if __name__ == "__main__":
    import sys
    fp = fingerprint(Path(sys.argv[1]))
    print(json.dumps({k: v for k, v in fp.items() if k != "entries"},
                     ensure_ascii=False, indent=2))
```

```bash
# 跑测试

# 测试后：必须完全一致
python tests/tools/library_fingerprint.py "E:/software/相册" > /tmp/lib_after.json
```

#### 辅数据源：构造的边界样本

放在 `tests/fixtures/`，用脚本生成（**不进 git**，因为含二进制）：

```python
# tests/fixtures/make_fixtures.py
"""生成测试用的边界样本。运行：python tests/fixtures/make_fixtures.py"""
from pathlib import Path
from PIL import Image
import io, struct, zlib

FIX = Path(__file__).parent

def make_normal_jpeg():
    im = Image.new("RGB", (800, 600), (120, 180, 240))
    im.save(FIX / "normal.jpg", "JPEG", quality=85)

def make_tiny_1x1():
    Image.new("RGB", (1, 1), (255, 0, 0)).save(FIX / "tiny_1x1.png")

def make_huge_dimensions():
    """超大尺寸但极小文件：测试 MAX_IMAGE_PIXELS。
    实测：661 字节的 PNG 声明 200000x200000 = 4e10 像素。"""
    # 手写 PNG：IHDR 声明巨大尺寸，IDAT 是极小数据
    def chunk(typ: bytes, data: bytes) -> bytes:
        c = struct.pack(">I", len(data)) + typ + data
        return c + struct.pack(">I", zlib.crc32(typ + data) & 0xFFFFFFFF)
    w = h = 200000
    ihdr = struct.pack(">IIBBBBB", w, h, 8, 0, 0, 0, 0)   # 8-bit 灰度
    raw = b"\x00" + b"\x00" * 16                            # 只有 16 字节的真实数据
    idat = zlib.compress(raw)
    png = (b"\x89PNG\r\n\x1a\n" + chunk(b"IHDR", ihdr)
           + chunk(b"IDAT", idat) + chunk(b"IEND", b""))
    (FIX / "bomb.png").write_bytes(png)

def make_truncated_jpeg():
```

### 2.5 实测基线数据（本机，用于设定性能目标）

> 以下数据是编写本文档时在**本机**实测所得（Python 3.13 + Pillow 12.3.0，单线程），作为性能目标的**基线参考**。

| 操作 | 实测值 | 说明 |
|---|---|---|
| 扫描 4915 张图并读元数据 | **12.9 秒** | ≈ 2.6 ms/张 |
| 缩略图 320px WEBP q78 | **76 ms/张** | `draft("RGB",(320,320))` + LANCZOS，60 张共 4.57 秒 |
| 预览 1600px WEBP q78 | **573 ms/张** | 60 张共 34.37 秒 |
| 解压炸弹检测 | `DecompressionBombError` | 661 字节 PNG 声明 4e10 像素 |
| 上限值 | `MAX_IMAGE_PIXELS × 2 = 178956970` | Pillow 默认 `MAX_IMAGE_PIXELS = 89478485` |

**由基线推导的性能目标**（§8 会逐条给出用例）：

| 指标 | 目标 | 推导 |
|---|---|---|
| 首次全量索引 4952 文件 | **≤ 30 秒** | 实测 12.9 秒，留 2.3 倍余量（含 DB 写入、缩略图任务入队） |
| 增量索引（100 个新文件） | ≤ 3 秒 | 线性外推 |
| 缩略图 320px 单张 | ≤ 150 ms | 实测 76 ms，留 2 倍余量 |
| 首屏 100 张缩略图（本地） | ≤ 3 秒 | 4 workers × 150 ms × 100 / 4 = 3.75 秒 → **需优化**（见 §8.2） |
| 首屏 100 张缩略图（4G） | **≤ 2.5 秒** | 设计文档 §1.3 硬指标；关键是**传输量**（100 × 25 KB = 2.5 MB） |
| 预览 1600px 单张 | ≤ 1 秒 | 实测 573 ms |

**首屏 2.5 秒的关键洞察**：4G 下 2.5 秒能传约 2-3 MB（按 1.6 Mbps ≈ 200 KB/s 算，2.5 秒只有 500 KB）。**100 张缩略图必须总大小 ≤ 500 KB**，即**平均 5 KB/张**。这要求：

- 缩略图尺寸 **320px 可能太大**（320×240 WEBP q78 约 15-25 KB）→ 建议**首屏用 160px 缩略图**（约 5-8 KB）或**降低质量到 q60**
- 或**首屏只加载 30 张**（滚动时懒加载）
- 设计文档 §1.3 说"1000 缩略图 ≤25MB" → **平均 25 KB/张** → 100 张 = 2.5 MB → **4G 下需 12.5 秒**（@200 KB/s）

**⚠️ 这是一个需要验证的指标矛盾**，记入 §10.2 发现清单（F1）。**08 性能测试必须实测并给出结论**。

## 4. 单元测试用例

> 全部用 `pytest`。运行：`pytest tests/unit/ -v`
> 目标耗时：**< 60 秒**（全部单元测试）

### 4.1 `sandbox.resolve()` —— 80 条（**最高优先级**）

**被测对象**：

```python
def resolve(root_cfg: dict, rel_path: str, *, need: str = "read") -> ResolvedPath
```

**测试文件**：`tests/unit/test_sandbox.py`

**测试骨架**：

```python
import pytest
from pathlib import Path
from app.sandbox import resolve, SandboxError

@pytest.fixture
def root(tmp_path: Path) -> dict:
    """一个真实的临时 root，含 sub/ 子目录与若干文件。"""
    (tmp_path / "sub").mkdir()
    (tmp_path / "sub" / "ok.jpg").write_bytes(b"\xff\xd8\xff\xe0" + b"\x00" * 100)
    (tmp_path / "相册").mkdir()
    (tmp_path / "相册" / "2024").mkdir()
    (tmp_path / "相册" / "2024" / "照片.jpg").write_bytes(b"\xff\xd8\xff\xe0")
    return {"id": "test", "path": str(tmp_path), "mode": "readwrite",
            "recursive": True, "include": ["*.jpg"], "exclude_dirs": []}

@pytest.mark.parametrize("rel,expect_code", [
    # ── A 组：正常路径（8 条）──
    ("sub/ok.jpg",            None),
    (r"sub\ok.jpg",           None),
    ("SUB/OK.JPG",            None),
    ("相册/2024/照片.jpg",      None),
    ("sub/ok.jpg/",           None),
    ("sub/../sub/ok.jpg",     "E_PATH_TRAVERSAL"),   # 见下注
    ("sub/./ok.jpg",          "E_PATH_SEGMENT"),
    ("sub//ok.jpg",           "E_PATH_SEGMENT"),
    # ... 共 80 条，逐条见下方表格
])
def test_resolve(root, rel, expect_code):
    if expect_code is None:
        rp = resolve(root, rel, need="read")
        assert rp.path.is_file()
        assert Path(root["path"]) in rp.path.parents
    else:
        with pytest.raises(SandboxError) as ei:
            resolve(root, rel, need="read")
        assert ei.value.code == expect_code
```

> **注**：`sub/../sub/ok.jpg` 虽然最终仍在 root 内，但**第 2 步就拒绝 `..`**（06 §3.3 第 2 步）。这是**有意的严格策略**——允许 `..` 再靠边界断言兜底，会多一层出错空间。前端与电脑端**不应该产生含 `..` 的路径**；若出现，说明上游有问题，拒绝是对的。

#### A 组：正常路径（8 条）

| 编号 | 输入 | 期望结果 | 理由 |
|---|---|---|---|
| TC-SANDBOX-FUNC-001 | `sub/ok.jpg` | ALLOW，返回 `root/sub/ok.jpg` | 基准 |
| TC-SANDBOX-FUNC-002 | `sub\ok.jpg` | ALLOW（反斜杠归一化为正斜杠） | Windows 客户端可能发反斜杠 |
| TC-SANDBOX-FUNC-003 | `SUB/OK.JPG` | ALLOW（大小写不敏感匹配真实文件） | Windows 文件系统不区分大小写 |
| TC-SANDBOX-FUNC-004 | `相册/2024/照片.jpg` | ALLOW | 中文路径（实测库中有中文目录） |
| TC-SANDBOX-FUNC-005 | `sub/ok.jpg/` | ALLOW（尾随分隔符被剥离） | 某些客户端会带尾随 `/` |
| TC-SANDBOX-FUNC-006 | `sub/ok.jpg`（need=write，mode=readwrite） | ALLOW | 写权限 + readwrite 模式 |
| TC-SANDBOX-FUNC-007 | `sub/ok.jpg`（need=read，mode=readonly） | ALLOW | 只读模式下的读 |
| TC-SANDBOX-FUNC-008 | `sub/ok.jpg`（need=read，mode=upload） | ALLOW | upload 模式允许读（需要读已有文件判重） |

#### B 组：`..` 路径穿越（9 条）

| 编号 | 输入 | 期望结果 | 理由 |
|---|---|---|---|
| TC-SANDBOX-SEC-001 | `../secret.txt` | DENY `E_PATH_TRAVERSAL` | 最经典的穿越 |
| TC-SANDBOX-SEC-002 | `../../etc/passwd` | DENY `E_PATH_TRAVERSAL` | 设计文档 §8.1 明确列出的用例 |
| TC-SANDBOX-SEC-003 | `..\..\secret.txt` | DENY `E_PATH_TRAVERSAL` | 反斜杠变体 |
| TC-SANDBOX-SEC-004 | `..` | DENY `E_PATH_TRAVERSAL` | 单独一个 `..` |
| TC-SANDBOX-SEC-005 | `sub/../../secret.txt` | DENY `E_PATH_TRAVERSAL` | 先进入再出来 |
| TC-SANDBOX-SEC-006 | `sub/..` | DENY `E_PATH_TRAVERSAL` | 只到上一级 |
| TC-SANDBOX-SEC-007 | `sub/ok/../../../secret.txt` | DENY `E_PATH_TRAVERSAL` | 多层 |
| TC-SANDBOX-SEC-008 | `....//....//secret.txt` | DENY `E_PATH_TRAILING` | 四点是非法尾随形态；**不是 `..`，但也不允许** |
| TC-SANDBOX-SEC-009 | `sub/..%2f..%2fsecret.txt` | DENY `E_PATH_CHAR` | URL 编码的穿越（`%` 已在非法字符集，06 §3.3 第 2 步）；**若不编码解码，`%2f` 在 Windows 上是普通文件名，会 404——但显式拒绝更清晰** |

#### C 组：绝对路径 / 盘符 / UNC / 设备命名空间（13 条）

|---|---|---|---|
