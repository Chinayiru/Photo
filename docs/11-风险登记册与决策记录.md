### 1.2 这份文档解决什么问题

项目文档体系里，[00-文档索引](00-文档索引与开发流程.md) 规定了"每份文档只回答一个问题"。本文档回答的是：

1. **有哪些坑**（风险登记册）—— 可能发生但**尚未发生**的坏事
2. **踩过什么决策**（ADR）—— 已经做出的架构/技术选择，以及为什么
3. **哪些疑问已经解决**（已解决问题记录）—— 避免重复讨论
4. **还有哪些没定**（待确认清单）—— 卡在谁那里、什么时候必须定

> **为什么风险要单独成册**：设计文档 §14 只有 11 行风险表，那是"架构层面的风险摘要"。
> 真正开发时，风险会从 11 条膨胀到 30 条以上，且每条都需要**触发条件、应对措施、责任人、状态**才能跟踪。
> 把风险写进设计文档会让设计文档失去焦点；单独成册才能持续更新而不动架构。

### 1.3 风险登记册的维护规则

#### 1.3.1 谁能新增风险

| 提出人 | 场景 | 是否必须登记 |
|---|---|---|
| **AI** | 设计/编码过程中发现的、设计文档未覆盖的风险 | ✅ **必须**，且需同时给出初步应对措施 |
| **你（业主）** | 你担心的任何事（哪怕说不清技术细节） | ✅ **必须**，由 AI 补齐技术细节 |
| **任何人** | 测试/联调/部署中暴露的隐患 | ✅ **必须** |
| **任何人** | 已经发生过的故障（事后复盘） | ✅ 登记为"已发生"，并转化为应对措施 |

#### 1.3.2 什么时候必须复核

| 时机 | 复核范围 | 产出 |
|---|---|---|
| 每个里程碑（L1–L7）结束 | 全部风险的状态、概率、影响 | 更新主表"状态"列 |
| **Go/No-Go 检查点**（G1–G5） | 与本次检查点相关的风险 | 若触发条件已出现，升级等级 |
| 需求变更时 | 新增风险 + 受影响风险 | 新增条目 |
| 故障发生后 | 全部 | 复盘 + 新增/升级 |
| **每季度**（长期运维期） | 运维类风险 | 检查证书、依赖、磁盘 |

#### 1.3.3 风险状态机

```
        ┌──────────────┐
        │  ① 识别       │  新提出，未分析
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  ② 分析       │  定概率、影响、等级、触发条件
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  ③ 已规划应对  │  选定策略（规避/减轻/转移/接受）+ 具体措施
        └──────┬───────┘
               ▼
        ┌──────────────┐        ┌──────────────┐
        │  ④ 监控中     │───────►│  ⑤ 已缓解     │  措施生效，等级降为中/低
        └──────┬───────┘        └──────┬───────┘
               │                       ▼
               │                ┌──────────────┐
               │                │  ⑥ 已关闭     │  归档，不再跟踪
               │                └──────────────┘
               ▼
        ┌──────────────┐
        │  ⑦ 已发生     │  转为"问题(Issue)"，进入故障处理流程
        └──────────────┘
```

| 状态 | 含义 | 后续动作 |
|---|---|---|
| 识别 | 刚提出 | 24 小时内完成分析 |
| 分析 | 已定概率/影响/等级 | 制定应对措施 |
| 已规划应对 | 措施已定，尚未执行 | 排进开发计划 |
| 监控中 | 措施在执行，或措施已就绪等待触发 | 每个检查点复核 |
| 已缓解 | 措施生效，等级下降 | 降低复核频率 |
| 已关闭 | 不再构成风险（如"VPS 未购买"在购买后关闭） | 归档，保留记录 |
| 已发生 | 风险变成现实 | 转 Issue，走故障处理 |

> **关闭不是删除**：关闭的风险保留在表中，状态标为"已关闭"，并注明关闭原因和日期。
> 这样后来者能看到"我们曾经担心过这个，后来怎么解决的"——这正是本文档第 4 节"已解决的问题记录"的价值。

### 1.4 风险等级定义

#### 1.4.1 概率分级

| 概率 | 定义 | 量化参考 |
|---|---|---|
| **高** | 大概率发生，或已有征兆 | > 60% |
| **中** | 有可能发生，条件具备时会发生 | 20% – 60% |
| **低** | 不太可能，但一旦发生影响大 | < 20% |

#### 1.4.2 影响分级

| 影响 | 定义（本项目语境） | 具体表现 |
|---|---|---|
| **高** | 导致**数据丢失**、**项目失败**、或**照片隐私泄露** | 照片被覆盖/删除；架构不成立；明文照片被第三方看到 |
| **中** | 导致**功能不可用**或**体验严重劣化**，但数据安全 | 手机连不上电脑；上传慢到无法忍受；时间线乱序 |
| **低** | 导致**体验小损**或**需要额外手工操作** | 证书要手动续；某张缩略图不显示；中文文件名显示为问号 |

#### 1.4.3 概率 × 影响矩阵

| 概率 \ 影响 | **影响 高** | **影响 中** | **影响 低** |
|---|---|---|---|
| **概率 高** | 🔴 **高** | 🔴 **高** | 🟡 中 |
| **概率 中** | 🔴 **高** | 🟡 中 | 🟢 低 |
| **概率 低** | 🟡 中 | 🟢 低 | 🟢 低 |

**矩阵说明**：任何"影响=高"且"概率≥中"的组合都是**高等级**——因为本项目的"影响高"定义里包含**数据丢失**和**照片隐私泄露**，这两件事的代价无法用时间补偿。

#### 1.4.4 各等级的响应时限

| 等级 | 响应时限 | 复核频率 | 是否阻塞里程碑 |
|---|---|---|---|
| 🔴 **高** | 立即（当轮交互内）给出应对措施 | 每个检查点 + 每周 | **是**：若在检查点触发，该里程碑 Go/No-Go 判定必须包含此风险 |
| 🟡 **中** | 3 天内给出应对措施 | 每个里程碑 | 否，但需在里程碑报告中说明 |
| 🟢 **低** | 排进待办即可 | 每季度 | 否 |

### 1.5 风险类别定义

| 类别 | 说明 | 本项目典型例子 |
|---|---|---|
| **技术** | 技术方案不成立、实现有坑、性能不达标 | 隧道多路复用踩坑、SQLite 写锁、HEIC 解码 |
| **进度** | 工期延误、依赖阻塞 | 二期 P1 超 4 天、单人项目精力不足 |
| **成本** | 花钱超预算、隐形成本 | VPS 涨价、流量超量、域名续费 |
| **安全** | 数据泄露、越权、被攻击 | 路径穿越、令牌泄露、配对码爆破、明文照片 |
| **运维** | 长期运行的可靠性 | 电脑关机、证书过期、磁盘满、依赖腐化 |

### 1.6 应对策略定义

| 策略 | 含义 | 本项目例子 |
|---|---|---|
| **规避** | 改变方案，让风险根本不存在 | 云端零存储 → 规避"云上照片泄露" |
| **减轻** | 降低概率或影响 | 流控窗口 → 减轻"内存撑爆" |
| **转移** | 把风险转给第三方 | 用 Let's Encrypt（证书风险转给 LE） |
| **接受** | 承认风险，不做额外投入，但记录在案 | 一期接受"云能看到明文照片" |

## 3. 高等级风险详细分析

> ⬜ **本章 3.1 属二期 P1** —— 一期不做云桥接，因此 R-001 的熔断与检查点在一期不适用。
> 保留是因为二期实现隧道时仍需要这套判据。其余小节（3.2 起）都是一期与二期共有的风险。

### 3.1 R-001 技术路线不成立（⬜ 二期 P1，一期已规避）

**风险描述**
"云服务器桥接"这条路线依赖三个尚未验证的技术点：① 反向 WebSocket 常驻隧道的稳定性；② 单连接上 `req_id` 多路复用的正确性（粘包/半包/乱序）；③ credit-based 流控在双向传输时不死锁。任何一点做不通，整个架构就塌了。

**为什么发生**
- 这是本项目**唯一有真正技术难度**的部分（[09](09-开发计划与任务分解.md) §1.2 已明确指出）
- WebSocket 是**流式**协议，帧边界需要自己处理：TCP 会粘包/半包，一个 `recv()` 可能拿到 0.7 个帧或 3 个帧
- asyncio 与 Pillow 的阻塞调用会互相拖累（缩略图生成是 CPU 密集，会卡住事件循环）
- 多路复用 + 流控 + 断线重连三者叠加，是典型的"每加一个维度，bug 面积翻倍"

**量化影响**
| 情景 | 影响 |
|---|---|
| **二期 P1** 超 4 天 | 二期工期吃掉预算的 25%+，后续二期里程碑顺延（**一期不受影响**） |
| **二期 P1** 完全做不通 | **二期跨网络访问**无法按当前架构交付，必须换方案（frp 或退回局域网）—— 但**一期方案（局域网直连）本身已实现并验证，不会作废** |
| 勉强做通但不稳 | 最坏情况：二期上线后随机断流，排查成本远超重做 |

**触发信号（怎么尽早发现）**
- **二期 P1** 第 2 天结束：帧编解码单测（粘包/半包/截断/非法 type）是否全绿 —— ✅ **一期已完成**（`shared/protocol.py`，`test_core.py` 22 条通过）
- **二期 P1** 第 3 天结束：`curl` 能否通过云打到电脑并拿到正确响应
- **二期 P1** 第 4 天：10 个并发请求是否互不干扰；100 MB 传输时云内存增量是否 < 50 MB
- **任一信号未达标，立即进入熔断评估**

**应对措施**
| 阶段 | 措施 |
|---|---|
| **预防** | ① **二期 P1** 先做**纯编解码单测**（不碰网络），把协议本身钉死；② 先做**回显测试**（最简路径），再叠多路复用；③ 多路复用通了再叠流控，一次只加一个维度 |
| **熔断** | **二期 P1** 累计 **4 天**未打通 → 停止自研，评估降级 |
| **降级路径 A** | 改用 **frp**（成熟的反向隧道）+ 自建鉴权网关（保留账号/配对/token 体系）。代价：失去应用层 req_id 多路复用与 credit 流控，需重新评估内存风险 |
| **降级路径 B** | 改用 **Tailscale/WireGuard** 组网，手机装客户端直连电脑。代价：放弃"浏览器打开就能用"的 PWA 体验，且不需要云服务器 |
| **降级路径 C** | 只保留局域网直连。代价：只能在家用 —— **注：这已是一期方案本身，二期即使云桥接失败也不会丢掉任何已有能力** |

**残留风险**
即使自研做通，**长期稳定性**仍需**二期 P1** 的 24 小时挂机验证。隧道类系统的 bug 往往在长尾场景（网络抖动、半开连接、时钟漂移）才暴露。

**关联检查点**
- **G1**（**二期 P1** 完成后）：隧道能通、多路复用与流控正确？不通过 → 复审隧道方案
- **G2**（原 C2 完成后）：**架构成立吗？** 这是决定项目要不要继续做的检查点 —— ✅ **一期已通过**：L3 交付后本机能看照片墙、真实库 4915 张索引正确，架构成立。二期只需验证隧道这一条新增通路，**不需要重新回答架构问题**。

### 3.2 R-002 电脑必须常开（🔴 架构固有缺陷）

**风险描述**
照片存在你自己的电脑上，所以**电脑关机 = 手机看不到照片**。这是"数据自主权"换来的必然代价，不是 bug，也无法通过编码消除。

**为什么发生**
架构选择（ADR-001）把媒体存储放在本地电脑，而不是云端。这个选择的收益是隐私与零成本，代价就是可用性绑定了这台电脑。

**量化影响**
| 场景 | 影响 |
|---|---|
| 电脑关机/睡眠 | 手机显示"电脑离线"，**完全不可用**（除非在家走局域网——但电脑关了局域网也没了） |
| Windows 自动更新重启 | 半夜重启，第二天早上发现连不上 |
| 电脑死机 | 同上，且无自动恢复 |
| 长期出差关电脑 | 整个服务停摆 |

**触发信号**
- 手机端出现 🔴 离线状态条
- 云端 `devices.last_seen` 超过 60 秒未更新
- 电脑端隧道日志出现"连接断开"

**应对措施**
| 类型 | 措施 |
|---|---|
| **预防** | ① 关闭 Windows 自动重启更新（改为手动）；② 电源计划设为"永不睡眠"，仅关闭显示器；③ 开机自启 PhotoBridge（注册表 `HKCU\...\Run`）；④ 单实例锁防止重复启动；⑤ 电脑端断线后**指数退避重连永不放弃**（1s→60s） |
| **事后** | ① 手机端明确提示"电脑离线，请确认电脑已开机且 PhotoBridge 正在运行"；② 提供"重试"按钮；③ 不缓存失败状态超过 30 秒（避免电脑开机后手机还显示离线） |
| **长期** | ① 改用低功耗 NUC / NAS 常驻（7×24 功耗 10–20 W）；② 或接受"电脑开着才可用"这个前提 |

**残留风险**
即使电脑常开，**Windows 系统更新、断电、硬件故障**仍会导致中断。这是自托管方案的根本取舍。

**关联检查点**：G2（架构成立性）、G3（手机实测）

### 3.3 R-003 云端能看到明文照片（🔴 隐私底线）

**风险描述**
TLS 在云服务器终止，所以云上理论上能看到明文照片。攻击面有两层：① 云服务器被入侵；② 云服务商主动查看。

**为什么发生**
一期**主动选择不做 E2E 加密**（ADR-006），理由是：一期最大的风险是架构不成立而非隐私，叠加密钥协商会把调试难度翻倍。

**量化影响**
| 情景 | 影响 |
|---|---|
| 云服务器被入侵 | 攻击者可看到**正在传输**的照片（但落盘的只有账号/设备元数据） |
| 云服务商偷看 | 小厂 VPS 理论上可行，但需要主动抓包且无批量收益 |
| **云端落盘了媒体字节** | 一旦发生，等于把 4900 张照片交给第三方——**这是真正的红线** |

**触发信号**
- 云端磁盘出现非 `cloud.db` 的大文件
- Docker volume 体积异常增长
- 云上出现 CDN / 缓存类配置

**应对措施**
| 层级 | 措施 |
|---|---|
| **架构层（最重要）** | ① **云端零存储**：relay 代码中**不存在**任何写媒体字节到磁盘的路径；② 云上**不做任何媒体缓存**（含 CDN）；③ 流式转发，字节只在内存中过路 |
| **元数据层** | ① 云上只有 5 张表（accounts/devices/clients/pair_codes/traffic），**没有 media 表**；② 云不知道你有哪些照片 |
| **协议层** | ① 帧头带 `flags` 位，`REQ_HEAD` 带 `enc` 字段，**二期只填实现不动结构** |
| **运维层** | ① 定期 `docker exec` 检查云上磁盘；② 云上不开无关服务；③ SSH 密钥登录 + 禁密码 + fail2ban |
| **接受** | 一期接受"云能看到明文"这件事，写进文档，不假装它不存在 |

**残留风险**
二期上 E2E 后，云仍可见 `device_id`、路径、长度、时间戳（元数据泄露）。文件名是否一并加密需二期再定。

**关联**：ADR-003（云端零存储）、ADR-006（一期不做 E2E）

### 3.4 R-006 隧道内存缓冲撑爆小 VPS（🔴 实现必须做对）

**风险描述**
手机下载一个 2 GB 文件时，如果云端把整个响应体缓冲在内存里再转发，1 GB 内存的 VPS 会**直接 OOM 崩溃**。

**为什么发生**
最自然的实现是"收完整包再发"，这在小数据量下没问题，但**媒体文件天生是大文件**。加上多路复用，30 张缩略图 + 1 个原图下载并发时，缓冲会叠加。

**量化影响**
| 情景 | 影响 |
|---|---|
| 云端 OOM | 服务崩溃，所有在线用户掉线，Docker 可能反复重启 |
| 无 swap | 直接 kill 进程；有 swap 则拖慢到不可用 |
| 反复 OOM | 被 VPS 提供商判定为滥用，可能被停机 |

**触发信号**
- `docker stats` 显示 relay 内存持续增长不回落
- `dmesg | grep -i oom` 出现 OOM killer 记录
- 传输大文件时服务重启

**应对措施**
| 措施 | 说明 |
|---|---|
| **credit-based 流控** | 每个方向维护信用窗口（默认 **8 MB**）；发送方只能发 ≤ 剩余信用；接收方每消费 N 字节回 `CREDIT` 帧补充 |
| **流式转发** | 云**边收边转发**，绝不整体缓冲响应体（[设计文档.md](../设计文档.md) §4.5） |
| **信用耗尽即暂停** | 只暂停该 `req_id`，其他请求不受影响 |
| **专项验证** | **二期 P1**：2 GB 文件传输时云端内存峰值 **< 200 MB** |
| **兜底** | VPS 配 1 GB swap；Docker 设 `mem_limit` 防止拖垮宿主机 |

**残留风险**
流控实现错误可能导致**死锁**（双方都在等对方补信用）。需专门设计"死锁防护"（[09](09-开发计划与任务分解.md) 二期 P1）并做压测。已知需要**双阈值**兜底：单 `req_id` 超 30 秒回 `ERROR` 并回收信用，整连接超 60 秒断连重连 —— 否则"对端一直不回 CREDIT"会让双方永久互等。

**关联**：ADR-008（WebSocket 多路复用）

### 3.5 R-012 手机切后台中断上传（🔴 高频发生）

**风险描述**
批量上传 100 张照片时，只要用户锁屏、切到微信、或系统省电策略杀进程，上传就断了。这在手机上**不是偶发，是必然**。

**为什么发生**
移动浏览器的生命周期由系统控制。Android 的省电策略会在后台冻结/杀死页面，`wakeLock` 只能防息屏，不能防"切到别的 App 后系统回收"。

**量化影响**
| 情景 | 影响 |
|---|---|
| 上传 100 张中途切后台 | 未做完的部分丢失（若无断点续传） |
| 无断点续传 | 必须从头重传，浪费流量和时间 |
| 用户体验 | "上传到一半就失败"是最容易被放弃的功能 |

**触发信号**
- 上传队列出现大量失败项
- 手机端 `visibilitychange` 事件后进度停滞
- 上传会话在 `upload_sessions` 表中大量滞留

**应对措施**
| 措施 | 说明 |
|---|---|
| **分片上传** | 云端走 2 MB 分片（[设计文档.md](../设计文档.md) §7.2）；每片独立，失败只重传该片 |
| **断点续传** | 恢复后 `GET /api/uploads/{id}` 拿 `offset`，从断点继续 |
| **幂等分片** | `PATCH` 用 `Content-Range`，重复提交同一片不产生副作用 |
| **wakeLock** | HTTPS 下可用，防息屏中断 |
| **队列持久化** | 上传队列写 IndexedDB，页面重载后恢复 |
| **明确 UI** | 显示"可安全切后台，回来会继续" |

**残留风险**
即使有断点续传，**会话过期**（`expires_at`）后临时文件被清理，用户仍需重传。需合理设置过期时间（建议 24 小时）。

**关联检查点**：G4（**L5** 完成后：上传可靠？断点续传生效？）

### 3.6 R-020 HEIC 兼容性（🔴 一定会遇到）

**风险描述**
iPhone 默认拍照格式是 HEIC。安卓浏览器的 `<img>` **原生不支持 HEIC**。如果服务端不转码，iPhone 用户传的照片在安卓手机上会显示为空白。

**为什么发生**
HEIC 是专利格式（HEVC 编码），Chrome/安卓默认不带解码器。这不是 bug，是格式生态问题。

**量化影响**
| 情景 | 影响 |
|---|---|
| 未转码 | 所有 HEIC 照片**在时间线里不可见**（显示破图） |
| 转码失败 | 该张标 `thumb_state=failed`，用户以为照片丢了 |
| 若忽略此问题 | iPhone 用户基本无法使用本功能 |

**触发信号**
- `media` 表中 `thumb_state='failed'` 的 HEIC 记录增多
- 手机上 HEIC 缩略图显示占位图
- 日志出现 `pillow_heif` 相关异常

**应对措施**
| 措施 | 说明 |
|---|---|
| **服务端统一转码** | 用 `pillow-heif` 把 HEIC 转成 WebP/JPEG 再给手机（[设计文档.md](../设计文档.md) §5.3） |
| **白名单包含** | `heic`/`heif` 在索引与上传白名单内 |
| **失败降级** | 解码失败标 `failed` + 显示占位图 + 提供原图下载 |
| **验收专测** | **L2/L4** 验收明确要求"HEIC 照片能正常显示" |
| **依赖打包** | PyInstaller 打包时必须把 `pillow_heif` 的二进制带进去（易漏） |

**残留风险**
`pillow-heif` 依赖 libheif，打包体积增加；某些 HEIC 变体（如 iPhone 的 HDR 多图）可能解码异常。

### 3.7 R-025 单人项目的时间风险（🔴 客观约束）

**风险描述**
12–16 个工作日是**理想估算**。单人项目 + AI 协作模式下，真实干扰来自：精力波动、联调返工、生活事务。

**为什么发生**
- 一期**没有**隧道这个真技术难点（云桥接整体推迟到二期），因此一期的主要风险不是返工而是**真实数据与真实设备**
- `scripts/smoke_real.py` 在真实 4915 张照片上就发现过**两个只有真照片才暴露的 bug**：73 个文件带非法 `Orientation=0` 会让整批 500 行写入失败；搜索命中不了目录名
- 联调阶段（**L4** 手机实测）问题往往不在代码而在环境（**Wi-Fi 网段隔离、浏览器缓存、安卓各家浏览器的差异**）—— 一期没有证书与 HTTPS 这两个变量，环境面比二期窄
- 单人项目没有"另一个人接手"的选项

**量化影响**
| 偏差 | 影响 |
|---|---|
| +50% | 12–16 天 → 18–24 天（**一期 L1–L6 已完成，实际未出现严重延期**） |
| +100% | 一个月以上，容易半途而废 |

**应对措施**
| 措施 | 说明 |
|---|---|
| **三点估算** | 期望值 15.2 天，区间上界 16 天已含约 1 天缓冲（[09](09-开发计划与任务分解.md) §1.3） |
| **最小验证路径** | 先做 **L1+L2/L3**，**确认架构成立再往下投入** —— ✅ **一期已完成并确认架构成立** |
| **L3 已完成** | 局域网直连已是**一期唯一主通路**，不是可选优化项（原"C5 可延后"的判断随架构调整作废） |
| **熔断点**（**二期 P1**） | 云桥接超 4 天触发架构复审；一期不存在此风险 |
| **偏差记录** | 估算偏差 > 50% 必须分析原因并记录到本文档 |
| **进度可见** | [09](09-开发计划与任务分解.md) §5 进度跟踪表逐任务打勾 |

**残留风险**
即使按计划完成，**长期维护**（R-027）是另一条时间线，容易被忽视。

### 3.8 R-026 需求蔓延（🔴 人性风险）

**风险描述**
开发到一半，看到视频、人脸识别、地图视图这些功能，很容易想"顺便加一下"。一旦开了口子，一期永远做不完。

**为什么发生**
- 单人项目没有外部约束，自己是唯一的范围守门人

**量化影响**

| E2E 加密 | +3–4 天 | 密钥管理、会话轮换、重放防护 |

**应对措施**
| 措施 | 说明 |
|---|---|
| **一期明确不做清单** | 视频、ffmpeg、人脸识别、公网分享、多用户（[设计文档.md](../设计文档.md) §1.1） |
| **变更走流程** | 提出 → 评估影响 → 决定是否插入 → 更新 [01](01-需求规格说明书.md) 与 [09](09-开发计划与任务分解.md) |

| **交付优先** | 一期目标：**能用的图片浏览 + 上传**。其他都是加分项 |

## 4. Top 5 风险排序

排序依据：**等级（高优先）→ 影响不可逆性（数据丢失/隐私 > 不可用 > 体验）→ 发生紧迫性（何时可能发生）**。

| 排名 | 编号 | 风险 | 等级 | 影响不可逆性 | 紧迫性 | 排序理由 |
|---|---|---|---|---|---|---|
| **1** | R-004 | 上传覆盖已有照片 | 🟡 中 | **不可逆**（照片没了就是没了） | **L5** | 一期**唯一可能造成永久数据丢失**的缺陷。这是数据安全底线，L5 的 G5 检查点就是为此设的 |
| **2** | R-002 | 电脑必须常开 | 🔴 高 | 中（不可用但数据在） | 上线后每天 | 概率**高**（每天都会发生），是日常体验的主要摩擦点。无法消除，只能减轻 |
| **3** | R-012 | 手机切后台中断上传 | 🔴 高 | 中（上传失败，可重试） | **L5/L7** | 概率**高**（手机上不是偶发是必然），且**一期是 HTTP，`wakeLock` 与 Service Worker 都不可用**，只能靠分片续传 + 队列持久化 |
| **4** | R-020 | HEIC 兼容性 | 🔴 高 | 中（照片打不开） | **L2/L4** | 一定会遇到（iPhone 默认格式），且**安卓浏览器原生不支持**。做对了就完全消失 |
| **5** | R-026 | 需求蔓延 | 🔴 高 | 高（一期做不完） | 全程 | 人性风险，唯一靠流程约束（明确不做清单 + 变更流程）来规避 |

> **排序为何变了**：原排名第 1 的 R-001（技术路线不成立）是"一期就要做云桥接"前提下的判断。
> 架构改为局域网优先后，一期**通过不做云桥接直接规避了 R-001**，它整体移到**二期 P1**；
> 同理 R-003（云端明文）与 R-006（隧道内存）在一期都没有施加对象。
> 因此一期真正的 Top 5 由"数据不可逆 + 高频发生 + 架构固有"三类组成 ——
> 全部是**一期自己必须做对**的事，而不是"路线可能不成立"。

**为什么 R-005（路径穿越）没进前 5**：影响确实是"高"（任意文件删除），但**概率低**（需要主动构造恶意请求，且本系统单用户），且有 **96 条**单元测试（`backend/tests/test_sandbox.py`）+ **41 条**手工演练（`scripts/check_sandbox.py`）专门覆盖，全部 PASS。它属于"做对了就不存在"的风险 —— 而且**已经做对了**。

**为什么 R-008（家宽上行小）没进前 5**：这是**物理约束**，不是"风险"而是"前提"。缓解手段（缩略图 + 局域网直连）已在架构中，无需额外动作；且**一期走局域网（1 Gbps），根本不受家庭宽带上行限制**。

### ADR-001 · 采用云服务器桥接而非局域网直连

| 项 | 内容 |
|---|---|
| **编号** | ADR-001 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 整体架构、成本、隐私模型、可用性 |

**背景**
v0.2 的方案是"手机与电脑必须同一 Wi-Fi 才能用"。这个限制在实际使用中非常致命：你在外面拍的照片想同步回家里的库、或者出差时想翻看家里的照片，局域网方案完全做不到。

**决策**
引入云服务器作为中继。手机通过 HTTPS 访问云，云通过电脑主动建立的常驻反向隧道把请求转发到电脑。**媒体字节永远只存在电脑上**，云只做转发 + 账号 + 设备管理。

**理由**
1. **解决核心痛点**：手机在任意网络（4G/5G/别处 Wi-Fi）都能访问照片
2. **不需要公网 IP / 端口映射 / DDNS**：电脑主动外连，天然穿过 NAT
3. **保留数据自主权**：照片不在任何第三方，云上只有元数据
4. **意外收益**：云上有 HTTPS 域名 → 浏览器进入**安全上下文** → Service Worker 可用（缩略图永久缓存）、PWA 可添加到主屏幕、`wakeLock` 防息屏上传。这三条在 v0.2 的局域网 HTTP 方案里全都拿不到（[设计文档.md](../设计文档.md) §6.4）
5. **局域网直连降级为加速路径**：在家时仍走直连，省云带宽、速度更快

**备选方案**
| 方案 | 说明 |
|---|---|
| **A. 纯局域网直连（v0.2）** | 手机和电脑同一 Wi-Fi |
| **B. 云服务器桥接（选中）** | 云中转，媒体在本地 |
| **C. 直接用现成网盘** | 群晖 Photos / Nextcloud / 阿里云盘 |
| **D. 公网 IP + 端口映射** | 家里开公网 IP，手机直连 |

**为什么没选备选方案**
- **A 局域网直连**：不能在外使用，这是**根本性功能缺失**，不是体验问题
- **C 现成网盘**：把照片交给第三方，与"照片存自己电脑"的初衷矛盾；且无法控制客户端行为；群晖需要买 NAS（¥2000+）
- **D 公网 IP + 端口映射**：国内家宽普遍**不提供公网 IP**（尤其是移动宽带），或需额外付费；暴露家庭网络到公网增加攻击面；IP 会变需要 DDNS；部分运营商封 80/443 入站

**后果**
| 正面 | 负面 |
|---|---|
| 手机任意网络可用 | **引入云服务器依赖**（R-010）：云挂了只能在家用 |
| 数据仍在本地，隐私可控 | **引入成本**：二期 ≈¥15/月（一期 ¥0） |
| ~~PWA / Service Worker / wakeLock 可用~~ → **仅二期**（一期是 HTTP，三者都不可用） | **电脑必须常开**（R-002）：这是最大的可用性代价 |
| 不需要公网 IP | 多了"云上能看到明文"的隐私顾虑（R-003，**二期**） |
| 局域网直连是一期唯一主通路 | 架构复杂度显著上升（隧道协议成为**二期**核心难点 R-001） |

**何时可能推翻**
- 若**二期 P1** 验证失败（G8 不通过）→ 一期方案（局域网直连）本身不受影响，二期可退回只用局域网或改用现成网盘
- 若长期不用外网访问 → 可以砍掉云，退回局域网（**这就是一期方案本身**）
- 若出现"云服务器被封/无法购买"的极端情况 → 考虑 Tailscale 组网方案

### ADR-002 · 反向隧道而非端口映射/DDNS

| 项 | 内容 |
|---|---|
| **编号** | ADR-002 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 网络架构、NAT 穿透、安全边界 |

**背景**
既然要用云中继（ADR-001），云怎么把请求送到电脑？两条路：① 云主动连电脑（需要电脑可被公网访问）；② 电脑主动连云（反向隧道）。

**决策**
**电脑主动发起 `wss://云/agent/ws` 并常驻**。云把 `device_id → 连接` 记入内存 map，收到手机请求时把请求封装成帧塞进这条已存在的连接。

**理由**
1. **不需要公网 IP**：国内家宽普遍没有公网 IP（尤其移动/联通部分地区），端口映射根本做不了
2. **不需要端口映射**：路由器不用做任何配置，非技术用户也能部署
3. **不需要 DDNS**：IP 变化无影响
4. **天然穿过运营商 NAT**：因为连接是**由内向外**发起的
5. **天然穿过企业防火墙**：443 出站通常被允许
6. **安全边界清晰**：电脑不监听公网端口，攻击面小

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 公网 IP + 端口映射** | 家里路由器把 8787 映射到公网 | 多数家宽无公网 IP；暴露家庭网络；IP 会变 |
| **B. DDNS + 端口映射** | 动态域名解析 + 映射 | 同上，且 DDNS 有生效延迟 |
| **C. UPnP 自动映射** | 程序自动请求路由器开端口 | 路由器普遍关闭 UPnP；安全性差 |
| **D. 反向隧道（选中）** | 电脑主动外连 | — |
| **E. IPv6 直连** | 用 IPv6 地址直连电脑 | 家宽 IPv6 前缀会变；部分网络无 IPv6；防火墙仍需放行 |

**后果**
| 正面 | 负面 |
|---|---|
| 零路由器配置 | 依赖云服务器中转（多一跳） |
| 穿 NAT / 企业防火墙 | 云成为单点（R-010） |
| 攻击面小（不监听公网） | 隧道协议成为核心复杂度（R-001） |
| 部署简单 | 若企业代理拦 WebSocket，需降级 SSE（R-011） |

**何时可能推翻**
- 若未来家宽提供了固定公网 IP 且用户愿意配置 → 可加一条直连快路径（但**保留隧道作为兜底**）
- 若改用 Tailscale/WireGuard 组网 → 反向隧道不再需要

### ADR-003 · 云端零存储（只转发不落盘）

| 项 | 内容 |
|---|---|
| **编号** | ADR-003 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 隐私模型、云端架构、重建成本 |

**背景**
云作为中转站，最自然的做法是"缓存一下"——缩略图缓存能大幅提速，上传临时落盘能简化断点续传。但这会让照片字节出现在第三方机器上。

**决策**
**云端不落任何媒体字节**。云上只存 5 张表：`accounts`（账号）、`devices`（设备）、`clients`（手机）、`pair_codes`（配对码）、`traffic`（流量计数）。**没有 media 表**——云不知道你有哪些照片。转发的字节只在内存中过路，立即流式转发出去。

**理由**
1. **隐私底线**：这是整个方案"照片永远只在自己电脑上"的具体落实（[设计文档.md](../设计文档.md) §2.1 决策②）
2. **重建成本极低**：云上数据丢了也不心疼，重装只需 10 分钟（[VPS选购建议.md](../VPS选购建议.md) §3）
3. **降低被入侵的收益**：攻击者拿下 VPS 也只能拿到账号和设备列表，拿不到一张照片
4. **降低带宽/存储成本**：不需要为云端存储付费，20 GB 硬盘绰绰有余
5. **合规清晰**：不存储用户内容，避免成为"内容提供者"

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 云端缓存缩略图** | 缩略图存云上，大幅提速（不必回源电脑） | 缩略图也是照片内容，等于把照片交给第三方；且缓存失效策略复杂；云盘空间与带宽成本上升 |
| **B. 云端缓存原图** | 相当于网盘 | **完全违背项目初衷** |
| **C. 云端临时落盘上传分片** | 上传先落云，再异步推给电脑 | 照片字节在云上停留；且需要云端磁盘管理、清理策略；断点续传在电脑端已能实现 |
| **D. 云端零存储（选中）** | 纯内存流式转发 | — |

**后果**
| 正面 | 负面 |
|---|---|
| 照片隐私有保障（R-003 的暴露面大幅缩小） | 缩略图必须回源电脑，云端无法加速第二次访问（但**手机端 Service Worker 已解决**这个问题） |
| 云端磁盘几乎不用，20 GB 够 | 上传断点续传完全依赖电脑端会话状态 |
| VPS 挂了/跑路/被墙都无所谓 | 云不能作为"照片备份" |
| 成本极低（¥13/月） | — |

**影响范围**：云端 relay 全部代码、Caddy 配置（**禁止配置任何缓存**）、Docker volume 设计、备份策略（只需备份 `cloud.db`）

**何时可能推翻**
- 若未来上 E2E 加密（ADR-006），云上看不到内容，**那时才可能考虑云端缓存密文**以提速
- 若云端带宽成为瓶颈且用户接受隐私权衡 → 可讨论"加密后的缩略图缓存"，但**必须是密文**
- **当前无推翻计划**

### ADR-004 · 单一根库（读写同一目录）而非双根

| 项 | 内容 |
|---|---|
| **编号** | ADR-004 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 库目录模型、上传目标、权限设计 |

**背景**
电脑端需要一个"根目录"概念（`root_id` + `rel_path` 的沙箱模型天然支持多根）。有两个设计选项：
- **双根**：`D:\Photos` 只读（照片本体），另设一个"手机上传"目录可写。手机上传的照片进上传目录，不进相册。
- **单根**：`D:\Photos` 读写同一目录。手机上传的照片**直接进相册**，按 `年\年-月\` 归档。

**决策**
**单一根库**。`D:\Photos` 既是浏览源也是上传目标，读写同一目录，权限模式为 `readwrite`。

**理由**
1. **用户要的就是"照片存进我的相册"**：上传到别处还要手动搬，等于没解决问题
2. **统一归档规则**：所有照片（原有 + 新上传）都按 `年\年-月\` 组织，时间线天然连续
3. **避免"两套库"的混乱**：双根会导致同一张照片可能在两处，去重逻辑复杂化
4. **沙箱已能兜住风险**：路径穿越有 `sandbox.py` 七步校验，写操作有"只新增不覆盖"（ADR-012）+ 回收站（ADR-011）+ 审计日志三条约束

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 双根（相册只读 + 上传目录可写）** | 隔离风险，相册绝不被写 | 上传的照片不在相册里，用户还要手动整理；时间线割裂；"存进相册"这个核心诉求没被满足 |
| **B. 单根只读** | 只能浏览，不能上传 | 上传是一期核心需求（P1-3） |
| **C. 单根读写（选中）** | 读写同一目录 | — |
| **D. 多根可配置** | 用户可配多个根，各自设权限 | 一期不需要；增加配置复杂度与测试面 |

**后果**
| 正面 | 负面 |
|---|---|
| 上传即入库，体验自然 | **相册目录可被写**——风险显著高于只读 |
| 归档规则统一 | 必须实现完整的四条硬约束，否则可能丢照片 |
| 索引与上传共用一套路径模型 | `sandbox.py` 的测试面变大（需覆盖写路径） |

**缓解措施（四条硬约束）**：① 所有文件操作过沙箱，越界拒绝；② 上传只新增不覆盖；③ 删除只进回收站；④ 删除/移动写审计日志（[设计文档.md](../设计文档.md) §8.4）

**何时可能推翻**
- 若实际使用中出现"照片被误覆盖/误删"的事故 → 立即改为双根（相册只读）
- 若用户想把相册目录设为只读保护 → 可加"只读根"选项

### ADR-005 · 一期只做图片，不做视频

| 项 | 内容 |
|---|---|
| **编号** | ADR-005 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 一期范围、依赖、打包体积、索引器 |

**背景**
`D:\Photos` 里有 **4952 个文件**，其中包含 **12 个 `.mov` + 3 个 `.mp4`** 视频。视频要不要在一期支持？

**决策**
**一期只做图片**。视频不索引、不播放、不转码，**不引入 ffmpeg**。`media.kind` 字段一期恒为 `'image'`（字段保留，为二期铺路）。

**理由**
1. **视频会让工作量翻倍**：需要封面抽帧、Range 播放（HTTP 206）、按需转码、码率自适应
2. **ffmpeg 是重依赖**：打包体积从几十 MB 涨到上百 MB；需要处理编解码许可；Windows 下还要处理路径与进程管理
3. **视频只占 15/4952 ≈ 0.3%**：为 0.3% 的文件付出 100% 的复杂度，性价比极低
4. **一期核心是验证"云桥接"路线**（R-001）：视频是干扰项
5. **字段已预留**：`kind`、`ext` 白名单、`Range` 请求处理在架构上都可后加

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 一期含视频** | 完整功能 | 工期 +5–7 天；引入 ffmpeg；风险叠加 |
| **B. 一期只做图片（选中）** | 跳过视频 | — |
| **C. 一期做视频但只索引不播放** | 视频出现在时间线但不能点开 | 半成品体验，用户困惑；仍需抽帧做封面 |

**后果**
| 正面 | 负面 |
|---|---|
| 工期可控（12–16 天） | 那 15 个视频在时间线里**看不到**（用户需知晓） |
| 打包体积小 | 二期需重新设计索引器 |
| 无 ffmpeg 依赖 | — |

**何时可能推翻**
- 二期规划已明确包含视频（[09](09-开发计划与任务分解.md) §7 高优先级）
- 若用户觉得"看不到视频"不可接受 → 提前二期

### ADR-006 · 一期不做 E2E 加密

| 项 | 内容 |
|---|---|
| **编号** | ADR-006 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受（由 AI 决定，业主可随时推翻） |
| **影响范围** | 安全模型、协议设计、二期工作量 |

**背景**
TLS 在云上终止，云理论上能看到明文照片（R-003）。E2E 加密能让云只看到密文。要不要一期就做？

**决策**
**一期不做 E2E，二期做**。但**协议从一期就预留**：帧头带 `flags` 位，`REQ_HEAD` 里带 `enc` 字段，二期只需填充实现，**不动协议结构、不改前端、不改云端转发逻辑**。

**理由**（[设计文档.md](../设计文档.md) §15.2）
1. **云是你自己的，且不落盘**：威胁模型是"云被入侵"或"服务商偷看"。前者 E2E 能挡，后者在自建 VPS 场景下不成立
2. **一期最大的风险是架构不成立，不是隐私**（R-001）：隧道多路复用 + 流控 + 断点续传本身坑就多，再叠密钥协商、会话轮换、重放防护，调试难度翻倍，而当前场景收益很低
3. **协议已预留，二期成本可控**：只需填充实现
4. **E2E 会牺牲功能**：云端无法做缩略图处理、无法做内容检索、调试变困难

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 一期上 E2E** | 全程密文 | 工期 +3–4 天；调试难度翻倍；当前威胁模型下收益低 |
| **B. 一期不做，二期做（选中）** | 协议预留 | — |
| **C. 永远不做** | 接受云看明文 | 若未来云被入侵，照片直接泄露；且二期想做时协议已定型，改造成本高 |
| **D. 用现成加密库（如 libsodium）** | 减少自研密码学 | 二期可考虑，但仍需设计密钥分发与会话管理 |

**二期的 E2E 设计（先记下，免得到时重新推演）**
```
配对时：电脑生成 X25519 密钥对，私钥永不离开电脑，公钥经云下发手机
会话时：手机 ↔ 电脑 ECDH → HKDF-SHA256 → AES-256-GCM 会话密钥（每设备独立，定期轮换）
传输时：请求/响应体加密后交给云转发
云可见：device_id、路径、长度、时间戳
云不可见：照片内容、EXIF、文件名（可选一并加密）
```

**后果**
| 正面 | 负面 |
|---|---|
| 一期聚焦架构验证 | 一期**接受**"云能看到明文"（R-003 保持高等级） |
| 调试简单 | 若云被入侵，正在传输的照片可被看到 |
| 二期成本可控 | 元数据（路径/时间）二期仍可能泄露 |

**何时可能推翻**
- 若云服务器被入侵过一次 → **立即**启动 E2E
- 若改用共享/第三方云 → 必须做 E2E
- 若二期启动 → 按上述设计实施

### ADR-007 · 游标分页而非 OFFSET

| 项 | 内容 |
|---|---|
| **编号** | ADR-007 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 时间线 API、索引设计、前端分页逻辑 |

**背景**
时间线要支持"无限滚动"，分页方式有两种：`LIMIT/OFFSET` 或游标（keyset）分页。

**决策**
**游标分页**。`GET /api/timeline?cursor=&limit=100`，游标基于 `(taken_at, id)` 复合键。SQLite 索引 `idx_media_timeline ON media(taken_at DESC, id DESC)` 直接支撑。

**理由**
1. **OFFSET 在深分页时性能急剧退化**：`OFFSET 5000` 需要先扫描并丢弃 5000 行，第 50 页会明显卡顿。用户明确要求"时间线翻页到第 50 页仍然流畅"（[09](09-开发计划与任务分解.md) **L2/L3** DoD）
2. **游标分页是 O(log n)**：直接走索引定位，与页码无关
3. **数据插入不会导致错行**：索引器边跑边翻页时，OFFSET 会因新数据插入而重复/漏项；游标基于稳定键，天然免疫
4. **天然支持"按天分组"**：游标即"上一批最后一条的 (taken_at, id)"

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. LIMIT/OFFSET** | 实现简单，`?page=5&size=100` | 深分页慢；数据变动时错行；4900 张虽不算海量，但索引器运行期间会插入 |
| **B. 游标分页（选中）** | `?cursor=<taken_at>_<id>` | — |
| **C. 一次性返回全部 ID** | 前端自己分页 | 4900 条 ID 约 50 KB，首屏多一次请求；数据变化时失效 |
| **D. 服务端缓存分页结果** | 快照式分页 | 需要缓存失效策略；内存占用 |

**后果**
| 正面 | 负面 |
|---|---|
| 任意深度翻页都是常数时间 | 不能"跳到第 N 页"（只能顺序翻）——但无限滚动不需要 |
| 数据变动免疫 | 游标需编码 `(taken_at, id)`，稍复杂 |
| 索引天然支撑 | — |

**影响范围**：`GET /api/timeline`、`idx_media_timeline` 索引、前端虚拟滚动逻辑

**何时可能推翻**
- 若需要"跳转到指定日期"功能 → 可另加按 `taken_at` 范围查询的接口（不是 OFFSET）
- **OFFSET 本身没有回退计划**

### ADR-008 · WebSocket 多路复用而非每请求一条连接

| 项 | 内容 |
|---|---|
| **编号** | ADR-008 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 隧道协议、云端连接管理、流控、内存占用 |

**背景**
手机浏览时间线时，屏幕上可能有 30 张缩略图同时请求。每条请求都开一条隧道连接？还是共用一条连接多路复用？

**决策**
**单条 WebSocket 连接上多路复用**。用 `req_id`（uint32 BE）区分并发请求，帧格式 `[type 1B][req_id 4B][payload]`。手机同时拉 30 张缩略图 = 30 个 `req_id` 在同一条隧道上并行。

**理由**
1. **连接数是稀缺资源**：30 条 TCP+TLS+WebSocket 连接的开销远大于 30 个 `req_id`
2. **手机电池与流量**：每连接都要心跳，多连接会显著增加耗电
3. **云上设备注册表简单**：`device_id → 一条连接` 的 map，无需管理连接池
4. **流控可以全局统一**：一条连接上一个信用窗口，比每条连接各管一个简单
5. **这正是 WebSocket 相对于"每请求开一条隧道"的价值**（[设计文档.md](../设计文档.md) §4.2）

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 每请求一条 WebSocket** | 实现简单，无 req_id 概念 | 连接数爆炸；云上要管理连接池；心跳开销大；建连延迟叠加（30 张图要等 30 次握手） |
| **B. 单连接多路复用（选中）** | req_id 区分 | — |
| **C. HTTP/2 多路复用 + 长轮询** | 用 HTTP/2 流 | 电脑端要主动"拉取"待处理请求，需双向长轮询，延迟高 |
| **D. 每请求一条 SSE + POST** | 降级方案 | 仅作为 WebSocket 被拦时的降级（R-011） |

**后果**
| 正面 | 负面 |
|---|---|
| 连接数恒为 1 | **必须自己处理粘包/半包**（帧边界）——这是 R-001 的技术难点来源 |
| 建连一次，后续零握手 | 一条连接承载全部流量，**必须做流控**否则内存爆（R-006） |
| 云上连接管理极简 | 单连接断开 = 全部请求失败（需逐个回 ERROR） |
| 省电、省流量 | 需要 pending 表 + 超时清理（防泄漏） |

**影响范围**：`protocol.py`（帧编解码 + FrameParser）、`tunnel.py`（多路复用器 + 流控）、云端请求转发路径

**何时可能推翻**
- 若单连接成为性能瓶颈（单用户场景下不会）→ 可拆分为"控制连接 + 数据连接"
- **基本不会推翻**

### ADR-009 · 自研隧道协议而非现成方案（frp / Cloudflare Tunnel / Tailscale / ngrok）

| 项 | 内容 |
|---|---|
| **编号** | ADR-009 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ⚠️ **待复议**（设 4 天熔断判据）—— ⬜ **属二期 P1**；一期已用局域网直连绕开本决策 |
| **影响范围** | **二期 P1** 的全部工作、二期可行性（R-001）；**一期不受影响** |

**背景**
这是本项目**最值得诚实讨论**的决策。"把手机请求转发到我家电脑"这件事，有大量成熟方案：
- **frp**（开源反向代理，TCP/HTTP 隧道）
- **Cloudflare Tunnel**（免费，无需公网 IP，自带 TLS）
- **Tailscale / WireGuard**（组网，直连）
- **ngrok**（快速验证）
- **rathole / bore / chisel**（更轻量的隧道）

自研隧道协议意味着：**二期 P1 的 2–3 天纯投入**，且这是全项目**唯一有真正技术难度**的地方（**一期已用局域网直连绕开它**）。这是不是过度设计？

**决策**
**二期 P1 自研**，但设 **4 天熔断**：若累计 4 天仍未打通隧道，**立即降级到 frp + 自建鉴权网关**。**一期不做云桥接**，因此本决策对一期不生效。

**理由（支持自研）**
1. **需要应用层语义，不只是 TCP 转发**：本项目要的是"把 HTTP 请求转发到电脑上的 FastAPI，并把响应流式回传"，需要 `req_id` 多路复用、`CREDIT` 流控、`NOTIFY` 推送（索引进度/上传完成）。frp 的 HTTP 隧道能转发，但**没有应用层多路复用与流控**，大文件仍会缓冲
2. **鉴权与配对体系必须自建**：账号、设备注册表、6 位配对码、`agent_token`/`client_token` 三层鉴权、设备吊销——这套东西 frp 完全没有，无论用不用 frp 都要自己写
3. **无第三方依赖**：Cloudflare Tunnel 要求流量过 CF；ngrok 免费版有限制；Tailscale 要求手机装 VPN 客户端。自研方案**零外部依赖**，符合"数据自主"的项目基调
4. **协议可控 = 可排查**：出问题时能加日志、能改帧格式；用现成方案遇到问题时只能提 issue 或读源码
5. **二期不需要额外服务端软件**：relay 本身就是 FastAPI 应用，与账号/配对在同一个进程里，部署简单
6. **协议已为二期 E2E 预留**（ADR-006）：自研协议才能自由地加 `enc` 字段与加密层；frp 要加 E2E 需要另做一层封装

**理由（反对自研，必须诚实列出）**
1. **这是重造轮子**：隧道是成熟领域，frp/rathole 已经处理了无数边界情况（半开连接、NAT 超时、TLS 重协商）
2. **二期 P1 的 2–3 天可能变成 4–6 天**：WebSocket 粘包/半包、asyncio 与 Pillow 阻塞冲突、流控死锁，每一个都是经典坑
3. **单人项目没有 review**：自研协议的 bug 可能在**二期压测**或真实使用才暴露
4. **维护成本**：二期还要在自研协议上叠 E2E，长期维护负担高于"用 frp + 薄封装"

**备选方案对比（诚实版）**

| 方案 | 优点 | 缺点（为什么没选） | 与项目冲突点 |
|---|---|---|---|
| **frp** | 开源成熟、TCP/HTTP/HTTPS 隧道齐全、文档好、性能不错、可自建服务端（数据不过第三方） | ① **无应用层 req_id 多路复用**（HTTP 隧道会为每个请求复用 TCP 流，但没有请求级并发控制）；② **无 credit 流控**，大文件传输需另做背压；③ 鉴权体系需另建；④ 配置文件式管理，与账号/设备动态注册不匹配；⑤ 需要额外跑一个 frps 进程 | 与"统一鉴权 + 动态设备注册 + 流控防 OOM"三个需求都需要额外适配层 |
| **Cloudflare Tunnel** | 完全免费、无需公网 IP、自带 TLS 与 DDoS 防护、`cloudflared` 客户端零配置 | ① **照片字节会经过 Cloudflare**——虽然 CF 声称不缓存，但流量确实过第三方，与 ADR-003"云端零存储/隐私底线"**精神冲突**；② 国内访问 CF 质量不稳（晚高峰丢包）；③ 依赖第三方账号与可用性；④ 无法自控协议 | **与隐私底线直接冲突**（R-003） |
| **Tailscale / WireGuard** | 最省事、组网直连、加密强、几乎零维护、性能最好（P2P 直连） | ① **要求手机装 VPN 客户端**——与"浏览器打开网址就能用"的 PWA 体验**直接冲突**；② 国内 DERP 中继质量不稳；③ 若用 P2P 直连，**等于不需要云服务器，架构全变**；④ 无法给"非本人设备"临时访问 | **与产品形态冲突**（PWA 免安装是核心体验） |
| **ngrok** | 5 分钟跑通、调试友好 | ① 免费版随机域名 + 连接数/带宽限制；② 付费 $8–20/月，比自己 VPS 贵；③ 流量过第三方；④ 不适合 7×24 常驻 | 成本 + 隐私 |
| **rathole / bore / chisel** | 轻量、Rust/Go 实现、性能好 | 同 frp：无应用层多路复用与流控、无鉴权体系；社区规模小于 frp | 同 frp |
| **自研（选中）** | 协议可控、与应用层语义契合、零外部依赖、可加 E2E、部署简单（同一进程） | **唯一的真技术难点**、可能超期、单人无 review | — |

**我的判断（明确回答"是不是过度设计"）**

**在"只做端口转发"这个层面，自研是过度设计。**
如果需求只是"把 443 的流量转发到家里电脑"，frp 一条命令就能解决，自研 2–3 天纯属浪费。

**但在本项目"转发 + 统一鉴权 + 请求级多路复用 + 流控防 OOM + 二期可加密"这组需求下，自研是合理选择。**
关键论据是：**即使用 frp，账号/设备注册/配对码/三层鉴权这套体系仍然必须自己写**（frp 完全没有），
而 frp 又**不提供**应用层 `req_id` 多路复用与 credit 流控——这两项恰恰是"30 张缩略图并发"和"2 GB 文件不撑爆 1 GB VPS"的必需品。
换句话说，frp 只能替代自研协议中**最简单的那部分**（TCP 连接管理），而**最难的部分（多路复用 + 流控）仍然要自己做**。

**因此自研的"净增量成本"其实低于表面上的 2–3 天**——因为用 frp 也要写鉴权层，且还要额外做流控适配。

**但必须承认**：自研方案**缺少 frp 经过多年实战打磨的边界处理**（半开连接检测、NAT 超时保活、异常断开清理）。
这部分风险是真实的，也是 R-001 被列为最高风险的原因。

**推荐的执行路径（可操作结论）**

> ⬜ **以下全部属二期 P1** —— 一期不做云桥接，这条路径在一期不执行。协议层的第 1 天工作**已经完成**（`shared/protocol.py` + 22 条单测）。

```
路径：二期先自研，设 4 天熔断；熔断后改用 frp + 自建鉴权网关。

第 1 天：纯帧编解码 + 单测（不碰网络）          ← ✅ 一期已完成
        → 通过：继续；不通过：协议设计有问题，重审帧格式
第 2 天：本机跑通"云 ↔ 电脑"握手 + 回显
        → 通过：继续；不通过：检查 WebSocket 粘包/半包处理
第 3 天：多路复用（10 并发不干扰）+ 请求转发路径
        → 通过：继续；不通过：进入熔断倒计时
第 4 天：流控 credit + 大文件传输（100 MB 内存增量 < 50 MB）
        → 通过：自研成立，关闭本 ADR 的复议状态
        → 不通过：★ 熔断 ★ 立即切换到 frp
```

**熔断后怎么改（保留已有投入）**

| 保留 | 替换 | 工作量 |
|---|---|---|
| 账号 / 设备注册 / 配对码 / 三层鉴权（`auth.py`、`devices.py`、`pairing.py`） | — | 0（本来就要写） |
| 云端 `/d/{device_id}/**` 转发入口 | 改为 frp 的 HTTP 隧道 + 自己写的鉴权中间件 | 0.5 天 |
| 帧协议 / 多路复用 / 流控 | 丢弃，改为 frp 的流式转发 + frp 自带背压 | 丢弃约 1.5 天 |
| 电脑端隧道客户端 | 改为 `frpc` 客户端 + 上报 `lan_ips` 的小脚本 | 0.5 天 |

**降级后新增的风险**：frp 大文件传输的背压行为需实测；`frps` 多一个进程要运维；frp 的 `privilege_token` 与自有鉴权要理清边界。

**后果**
| 正面（若自研成立） | 负面（若自研超期） |
|---|---|
| 协议完全可控，二期加 E2E 无障碍 | 工期吃掉 25%+（R-025） |
| 零外部依赖，部署最简 | 需自行处理 frp 已解决的所有边界情况 |
| 与鉴权体系原生融合 | 单人项目无 code review |

**何时可能推翻**
- **二期 P1 第 4 天未通过 → 立即推翻**（这是硬判据，不讨价还价）
- 若二期上 E2E 时发现自研协议难以承载 → 可评估换用支持 E2E 的方案
- 若长期运维发现隧道稳定性问题（半开连接堆积等）→ 可考虑迁移到 frp 并保留鉴权层

### ADR-010 · 电脑端与云端同语言（Python）共享协议代码

| 项 | 内容 |
|---|---|
| **编号** | ADR-010 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 技术栈、代码组织、协议一致性 |

**背景**
云端 relay 和电脑端 Agent 都要实现同一套帧协议（编解码、多路复用、流控）。两端可以选不同语言，也可以同语言。

**决策**
**两端都用 Python**，`protocol.py` **同一份文件，两边各拷一份同步**（[设计文档.md](../设计文档.md) §11）。

**理由**
1. **协议代码只写一遍**：帧编解码是最容易两端不一致的地方，同语言可以直接共享文件
2. **协议 bug 只修一处**：这是选同语言**最大的理由**（[设计文档.md](../设计文档.md) §11 明确写了这一点）
3. **电脑端本来就必须是 Python**：索引器要用 Pillow / pillow-heif / exifread，缩略图引擎也是 Python 生态最强
4. **云端用 FastAPI 也是 Python**：FastAPI + WebSocket 是 relay 的最佳选择
5. **单人可以只维护一套工具链**：pytest、依赖管理、打包逻辑都能复用
6. **降低认知负担**：单人项目切换语言上下文成本高

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 两端 Python（选中）** | 共享 `protocol.py` | — |
| **B. 云端 Go/Rust + 电脑端 Python** | 云端性能更好、内存更省（Go 的 goroutine 天然适合多路复用） | 协议要写两遍，两端必须逐字节对齐（帧格式、字节序、错误码）；bug 修两处；单人要维护两套工具链 |
| **C. 云端 Node.js + 电脑端 Python** | 与前端同语言 | 同上；且 Node 的二进制处理不如 Python/Go 直观 |
| **D. 两端 Go** | 性能与内存最优 | 电脑端要做 EXIF/缩略图/HEIC，Go 生态明显弱于 Python；打包与托盘也不如 Python + PyInstaller 成熟 |

**后果**
| 正面 | 负面 |
|---|---|
| 协议一致性强，bug 只修一处 | 云端内存占用高于 Go（Relay 常驻约 80–150 MB，1 GB VPS 可接受） |
| 单人维护成本低 | Python 的 GIL 限制并发（但本项目是 I/O 密集型，asyncio 足够） |
| 依赖管理统一 | **注意**：Pillow 是阻塞调用，在 asyncio 里必须放线程池，否则卡事件循环 |
| 测试代码可共享 | ~~`protocol.py` 是"拷贝同步"而非包依赖，**容易漂移**~~ → ✅ **已消除**：见下 |

**风险与缓解**：~~`protocol.py` 两边各拷一份，存在**版本漂移风险**。缓解：① 文件头写明"此文件为共享代码，修改必须同步另一端"；② 加一个校验脚本比对两边文件的 sha256；③ 开发初期就建立同步习惯。~~
→ ✅ **一期已从根上解决**：协议层改为**单一物理文件** `shared/protocol.py`（云端与电脑端共用同一份，通过 `sys.path` 或打包时一并收集引用），不再两边各拷一份。原来"拷贝同步 + sha256 校验脚本"的缓解措施**整套作废** —— 漂移风险不再是"要靠纪律避免"，而是"结构上不可能发生"。`shared/__init__.py` 里 `REPO_ROOT = Path(__file__).resolve().parent.parent` 就是为此服务的。

**何时可能推翻**
- 若云端内存/CPU 成为瓶颈（单用户场景下不会）→ 可把 relay 核心改为 Go
- 若 `protocol.py` 漂移导致过故障 → 可改为 Git submodule 或独立包

### ADR-011 · 删除只进回收站

| 项 | 内容 |
|---|---|
| **编号** | ADR-011 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 写权限设计、`sandbox.py`、审计日志 |

**背景**
用户确认"允许删除/移动"（[设计文档.md](../设计文档.md) §8.4）。删除是**唯一不可逆**的写操作，怎么做最安全？

**决策**
**删除只进 Windows 回收站**（`send2trash`）。**代码里不存在 `os.unlink` 路径**。删除/移动写审计日志 `data/audit.log`，托盘面板可查看。

**理由**
1. **回收站是可恢复的**：误删可以从回收站还原，这是"数据不可再生"场景的最后一道防线
2. **"代码里不存在 `os.unlink`"是硬约束**：不是"尽量不要用"，而是**架构上不给这条路**——这样即使将来有人改代码，也不会意外引入真删除
3. **审计留痕**：谁（哪台手机）、什么时候、删了什么，可追溯
4. **用户体验**：手机端删照片后，在电脑上还能找回，心理负担低

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 真删除（`os.unlink`）** | 立即释放空间 | **不可逆**；一次误操作就丢照片 |
| **B. 删除进回收站（选中）** | `send2trash` | — |
| **C. 软删除（数据库标记 + 文件保留）** | 只在库里标 `missing`，文件不动 | 用户以为删了但文件还在，磁盘不释放；用户困惑；库与文件系统不一致 |
| **D. 移到自建 `.trash` 目录** | 应用级回收站 | 需自己管理清理策略与保留期；用户找不到；Windows 回收站更符合直觉 |
| **E. 禁止删除** | 一期不做删除功能 | 用户明确要求要能删 |

**后果**
| 正面 | 负面 |
|---|---|
| 误删可恢复 | 回收站会占磁盘空间（需提醒用户定期清空） |
| 代码路径唯一，不易出错 | `send2trash` 在某些场景会失败（R-029）：网络盘、回收站被禁用、文件被占用 |
| 审计可追溯 | 跨盘删除行为可能不一致 |

**失败处理**：删除失败时**明确报错**给用户，**绝不静默改走 `os.unlink`**。这是硬约束。

**何时可能推翻**
- 若用户明确要求"彻底删除"（如隐私照片）→ 可加"彻底删除"选项，但**必须二次确认 + 显著警告**
- 若回收站频繁撑爆磁盘（R-023）→ 加回收站大小提醒

### ADR-012 · 上传只新增不覆盖

| 项 | 内容 |
|---|---|
| **编号** | ADR-012 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 归档逻辑、上传流程、数据安全 |

**背景**
手机上传的照片，如果目标路径已存在同名文件，怎么办？覆盖？跳过？改名？

**决策**
**只新增不覆盖**：
1. 同名冲突 → 追加 `_1` / `_2` / `_3`…
2. sha256 命中已有记录 → 判重丢弃（秒传）
3. **任何情况下不把新文件 rename 到已存在文件上**
4. 先落临时区，校验通过后 `os.replace` 原子落盘

**理由**
1. **照片是唯一不可再生数据**：覆盖 = 永久丢失，没有"撤销"
2. **用户可能故意上传同名但不同的照片**：如两张相机编号相同的照片（不同相机）、或编辑过的版本
3. **冲突加序号是"无损"策略**：宁可多一个文件，不可少一个
4. **sha256 判重避免真正的重复**：内容相同才判重，内容不同就并存
5. **原子落盘避免半截文件**（R-013）

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 覆盖同名** | 简单 | **不可逆数据丢失**，绝对不可接受 |
| **B. 跳过同名** | 不覆盖，也不新增 | 用户上传了但"没反应"，体验差；且无法区分"真重复"与"同名不同内容" |
| **C. 只新增不覆盖（选中）** | 加序号 | — |
| **D. 按 sha256 命名文件** | 内容寻址，天然无冲突 | 文件名变得不可读（用户要在资源管理器里看照片）；与原库命名规则冲突 |

**后果**
| 正面 | 负面 |
|---|---|
| 零数据丢失风险 | 目录可能出现 `IMG_0001.jpg` 与 `IMG_0001_1.jpg`，需在 UI 上说明 |
| 判重与并存逻辑清晰 | 序号逻辑需处理"已存在 `_1` 再上传"的情况（要找到最大序号 +1） |
| 与回收站策略互补 | 多次重复上传同一张 → 靠 sha256 拦住，不会产生无限副本 |

**实现要点**
```
1. 临时区：`<库根>/.photobridge_tmp/{upload_id}.part`（★ 在库根下，同卷才原子；原 `data/uploads_tmp` 方案已废弃）
2. 校验：size 一致 + sha256 一致
3. sha256 已在 media 表命中 → 判重，删除临时文件，返回已存在的 media_id
4. 计算目标路径：D:\Photos\{年}\{年-月}\{EXIF日期}_{序号}.jpg
5. 若目标存在 → 序号 +1，循环直到不存在
6. os.replace(临时, 目标)   ← 原子
7. 入库 → 生成缩略图 → NOTIFY 推送
```

**何时可能推翻**
- 若用户明确要求"同名就覆盖（我确定要替换）"→ 可加显式选项，但**必须二次确认**
- **默认行为永不改变**

### ADR-013 · 选择 SQLite 而非 PostgreSQL/MySQL

| 项 | 内容 |
|---|---|
| **编号** | ADR-013 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 两端数据库、部署复杂度、并发模型 |

**背景**
两端都要存数据：云端存账号/设备/配对码/流量，电脑端存 media/upload_sessions/settings/audit_log。用 SQLite 还是独立数据库服务？

**决策**
**两端都用 SQLite**。云端 `data/cloud.db`，电脑端 `data/photobridge.db`。开 WAL 模式。

**理由**
1. **零运维**：不需要装数据库服务、不需要配连接池、不需要备份服务——**单用户场景下这是决定性优势**
2. **部署简单**：云端 relay 容器只需要挂一个 volume；电脑端 PyInstaller 打包后无需额外安装
3. **备份简单**：就是**一个文件**，复制即可（配合 WAL 需用 `.backup` 命令或停服复制）
4. **性能足够**：电脑端 4952 张照片，SQLite 的 B-tree 索引毫秒级响应；云端只有几十行数据
5. **FTS5 全文检索内置**：`media_fts` 用 SQLite 的 FTS5 虚表，无需额外搜索引擎
6. **与"云端零存储"理念一致**（ADR-003）：云上数据极小，不值得起一个数据库服务

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. SQLite（选中）** | 嵌入式 | — |
| **B. PostgreSQL** | 功能强、并发好、支持 JSONB | 需要独立服务（容器/进程）；1 GB VPS 上跑 PG 约需 100–200 MB 内存，**与 relay 抢资源**；备份/升级复杂；单用户场景收益为零 |
| **C. MySQL/MariaDB** | 常见、生态好 | 同上；内存占用更大 |
| **D. 纯文件（JSON/CSV）存元数据** | 最简单 | 无法做索引与查询；4900 条时间线查询会很慢；无事务 |
| **E. 电脑端用 SQLite + 云端用 PG** | 各取所长 | 云端数据量极小，不值得 |

**后果**
| 正面 | 负面 |
|---|---|
| 零运维、零额外内存 | **并发写受限**（R-018）：同一时刻只有一个写者 |
| 单文件备份 | 深分页依赖索引（已用游标分页 ADR-007 解决） |
| 事务完整（ACID） | 网络文件系统上不可靠（本项目不用网络盘，OK） |
| FTS5 全文检索免费 | 无内置复制/高可用（单机场景不需要） |

**并发写缓解措施**（R-018）
1. `PRAGMA journal_mode=WAL` —— 读不阻塞写，写不阻塞读
2. `PRAGMA busy_timeout=5000` —— 遇到锁等待 5 秒而非立即报错
3. **单写者设计**：写操作（索引入库、上传完成、缩略图状态）集中到一个队列串行执行
4. 缩略图状态更新**批量提交**，避免大量短事务
5. 避免长事务（长时间持有写锁）

**何时可能推翻**
- 若将来做**多电脑设备**（[09](09-开发计划与任务分解.md) §7 低优先级）且需要云端同步 → 云端可考虑 PG
- 若电脑端照片量增长到 100 万级且查询变慢 → 可考虑加缓存或换库
- **当前规模下没有理由换**

### ADR-014 · 前端用 Vue3 而非 React

| 项 | 内容 |
|---|---|
| **编号** | ADR-014 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 前端技术栈、构建、PWA |

**背景**
手机端网页（时间线、查看器、上传队列、设置）需要一个前端框架。Vue3 还是 React？

**决策**
**Vue3 + Vite + TypeScript**。PWA 用 `vite-plugin-pwa`。

**理由**
1. **模板语法更接近 HTML**：`v-for` / `v-if` 比 JSX 更直观，单人项目可读性优先
2. **响应式系统开箱即用**：`ref` / `reactive` 无需手写 `useState` / `useMemo` 依赖数组
3. **单文件组件（SFC）**：`<template>/<script>/<style>` 三块在一起，组件文件更短
4. **Vite 官方生态**：Vue3 + Vite 是官方推荐组合，配置最少
5. **构建产物小**：Vue3 runtime 比 React + ReactDOM 略小，对手机首屏（≤2.5 秒目标）有帮助
6. **AI 协作效率**：Vue 的约定更少，生成代码的一致性更容易保证

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. Vue3（选中）** | SFC + Composition API | — |
| **B. React** | 生态最大、招人容易、React Native 可复用 | 本项目无招人需求；JSX + hooks 依赖数组的心智负担在单人项目中无收益；`useEffect` 依赖陷阱容易出 bug（尤其是虚拟滚动 + IntersectionObserver 场景） |
| **C. Svelte / SvelteKit** | 产物最小、无虚拟 DOM、性能最好 | 生态与 PWA 插件成熟度不如 Vue；社区规模小，遇到问题资料少 |
| **D. 原生 JS / 无框架** | 零依赖、体积最小 | 时间线虚拟滚动 + 查看器手势 + 上传队列状态管理，用原生写会变成一坨命令式代码，难维护 |
| **E. Solid / Qwik** | 性能优秀 | 生态太小，单人项目风险高 |

**后果**
| 正面 | 负面 |
|---|---|
| 代码量少、可读性好 | 若未来要做 React Native 原生 App 无法复用 |
| Vite 构建快，HMR 体验好 | Vue 生态在"复杂状态管理"上不如 React 丰富（但本项目用 Pinia 足够） |
| PWA 插件成熟 | — |

**影响范围**：`frontend/` 全部代码、构建配置、PWA manifest 与 Service Worker

**何时可能推翻**
- 若将来要做原生 App（二期之后）→ 可能改用 React Native，但 Web 端不必重写
- **当前无推翻计划**

### ADR-015 · 从 HTTP 局域网版（v0.2）改为 HTTPS 云桥接版（v0.3）

| 项 | 内容 |
|---|---|
| **编号** | ADR-015 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受（**取代 v0.2 的局域网架构决策**） |
| **影响范围** | 整体架构、成本、部署方式、前端能力 |

**背景**
v0.2 的架构是"手机与电脑同一 Wi-Fi 时局域网直连 HTTP"。v0.2 的骨架代码（`backend/app/config.py`、`backend/app/db.py`）已经写了。为什么要推翻？

**决策**
**改为 v0.3 云桥接版**。局域网直连从"唯一通路"**降级为加速路径**。v0.2 遗留骨架代码**删除重建**。

**理由**
1. **局域网方案有根本性功能缺失**：在外面（4G/5G/别处 Wi-Fi）完全不能用。这不是体验问题，是"这个产品没用"
2. **HTTPS 带来三项关键能力**（[设计文档.md](../设计文档.md) §6.4）：
   | 能力 | v0.2（HTTP 局域网） | v0.3（HTTPS 云） |
   |---|---|---|
   | Service Worker | ❌ 不可用（非安全上下文） | ✅ 缩略图永久缓存到手机，二次浏览零流量 |
   | 添加到主屏幕（完整 PWA） | ❌ 只能加书签 | ✅ 独立图标 + 启动画面 |
   | `navigator.wakeLock` | ❌ 不可用 | ✅ 上传时防息屏中断 |
   > 这三条是**改用云桥接的意外收益**——本来只是为了"在外面能用"，结果顺带解决了 PWA 能力问题
3. **不需要公网 IP / 端口映射**：反向隧道天然穿透 NAT（ADR-002）
4. **成本可接受**：≈¥15/月（R-024）
5. **v0.2 代码量很小**：只有两个骨架文件，删除成本几乎为零

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 保持 v0.2 局域网版** | 简单、零成本、零云依赖 | **在外不能用**——根本性缺失 |
| **B. v0.3 云桥接版（选中）** | 云中转 + 局域网加速 | — |
| **C. v0.2 + 自签证书局域网 HTTPS** | 保留局域网，用自签证书拿到安全上下文 | 手机要装根证书（麻烦）；证书过期要重装；局域网 IP 变化证书失效；**在外仍然不能用** |
| **D. 局域网 + 现成网盘双轨** | 在家用直连，在外用网盘 | 两套系统、两处照片、同步冲突；照片被上传到第三方 |

**后果**
| 正面 | 负面 |
|---|---|
| 手机任意网络可用 | 引入云服务器（成本 + 单点，R-010） |
| 拿到 PWA / Service Worker / wakeLock | 引入"云看明文"隐私顾虑（R-003） |
| 局域网直连（**一期唯一主通路**） | 架构复杂度大幅上升（隧道协议成为**二期**核心难点 R-001） |
| 不需要公网 IP | 电脑必须常开（R-002） |
| | **v0.2 骨架代码需删除重建** |

**迁移动作**
| 项 | 动作 |
|---|---|
| `backend/app/config.py` | ❌ 删除（v0.2 局域网架构遗留） |
| `backend/app/db.py` | ❌ 删除（同上） |
| 目录结构 | 按 [设计文档.md](../设计文档.md) §11 重建（`cloud/`、`backend/`、`frontend/`、`data/`） |
| 需求文档 | 已同步更新（[01-需求规格说明书.md](01-需求规格说明书.md)） |

**何时可能推翻**
- 若**二期 P1** 验证失败（G8 不通过）→ 一期方案（局域网直连）本身不受影响，无需重写；二期可退回只用局域网或改用现成网盘
- 若用户长期只在家使用 → 可砍掉云，退回局域网（保留局域网直连代码即可）
- **若推翻，必须同时更新 [设计文档.md](../设计文档.md) 与本文档**

### ADR-016 · 云上传分片 2 MB / 局域网 8 MB

| 项 | 内容 |
|---|---|
| **编号** | ADR-016 |
| **日期** | 2026-02（设计阶段） |
| **状态** | ✅ 已接受 |
| **影响范围** | 上传流程、前端分片逻辑、断点续传粒度 |

**背景**
分片上传需要选分片大小。走局域网和走云端，网络特性完全不同。

**决策**
**走云端时用 2 MB 分片；走局域网直连时用 8 MB 分片**。前端根据当前通路动态选择（[设计文档.md](../设计文档.md) §7.2）。

**理由**
1. **云带宽窄、RTT 高**：一个 8 MB 分片在 3 Mbps 链路上要传约 21 秒，一旦失败**重传代价极高**
2. **小分片吞吐更稳**：2 MB 分片在弱网下失败重传成本低，整体吞吐更稳定
3. **局域网带宽大、RTT 低**：千兆内网下 8 MB 分片瞬间传完，分片太小反而增加 HTTP 往返开销
4. **断点续传粒度**：分片越小，断线后重传的浪费越少
5. **两个数字都有实测依据**：8 MB 是局域网经验值；2 MB 是为窄带优化的保守值

**备选方案**
| 方案 | 说明 | 为什么没选 |
|---|---|---|
| **A. 统一 8 MB** | 实现简单 | 云端弱网下重传代价高，上传失败率高 |
| **B. 统一 2 MB** | 云端稳 | 局域网下分片过多，HTTP 往返开销占比上升 |
| **C. 动态分片（选中）** | 按通路选择 | — |
| **D. 自适应分片（按实测带宽调整）** | 最优 | 实现复杂（需带宽探测、动态调整、乱序处理）；一期收益不足以抵消复杂度 |

**后果**
| 正面 | 负面 |
|---|---|
| 两条通路各自最优 | 前端需感知当前通路（**二期 P1** 才需要双通路状态机；一期只有一条通路，前端零分支） |
| 弱网下重传成本低 | 云端上传的 HTTP 往返次数是 8 MB 方案的 4 倍（但每片都很小，总开销可接受） |
| 断点续传粒度细 | — |

**影响范围**：`api.ts`（分片逻辑）、`uploads.py`（分片写入与 offset 计算）、`upload_sessions.chunk_size` 字段

**何时可能推翻**
- 若实测发现 2 MB 分片在云上吞吐反而不如 4 MB → 可调整为 4 MB
- 若做自适应分片（二期）→ 本条被取代

### 8.1 ISSUE-021 补充：入站方向那处修复目前是潜伏的

> 这一节不属于 §8 的表格（表格单元格里放不下多段说明），单独列出。

**③ 的严重性必须如实降级 —— 实测它目前是潜伏的。**写这条修复时我在提交信息里说"上传时隧道会断"，随后跑端到端变异（`build/_mut_updown.py`：96 MB 上传限速 2 MB/s 与 20 KB/s 慢读并发、每 2 秒一次 ping）**没有抓到** —— 回退修复后探针仍 `ping fail=0`、`session_id` 不变、`RESULT: PASS`。原因是一段很简单的算术：`_BODY_QUEUE_MAX = CREDIT_WINDOW // MAX_BODY_CHUNK + 2` = `8388608 // 65530 + 2` = **130** 槽，容量 8.12 MB；而单个请求体最大就是上传分片 `chunk_mb_lan=8` MB（`backend/app/handlers/uploads.py:117` 的 `limit = chunk_size + 1024`）= **129 帧 ≤ 130 槽**，**永远撞不满队列**（`chunk_mb_wan=2` 时只要 33 帧，余量 97 帧）。所以那个 `put_nowait(None)` 的 `QueueFull` 与 `put()` 的阻塞在当前参数下都走不到。

结论：**③ 是一次正确性/对称性修复，不是已发生的故障。**它只有在三种前提下才会变成真故障：(a) 分片大小被调到超过一个信用窗（`chunk_mb_lan` > 8）；(b) 入站请求没有声明 `body_len`（`body_len = -1` 时 `iter_body()` 不设上限，队列可以被无限灌）；(c) 有人"优化"掉 `_BODY_QUEUE_MAX` 里那 `+ 2` 的裕量。第三种最危险，因为它看起来像去掉一个魔数。

保留这次修复的理由：它与响应侧严格对称，成本是 60 行且零额外分配；而**单元级不变量用例是唯一能钉住它的手段**（端到端测不出来，这正是"缺陷被队列容量意外掩盖"的教科书形态）。教训：**变异验证 MISSED 时，先算清边界条件的数值，再判断"探针不够狠"还是"缺陷本来就走不到"** —— 这次是后者，差点被当成前者去把探针改得更极端，那样只会得到一个假的自信。

### 8.2 ISSUE-022：10 KB/s 慢读会被**静默截断**（HTTP 200 + 半张照片）

> 同样不属于 §8 表格（多段说明），单独列出。这是 ISSUE-021 修完之后的**下一层**缺陷，
> 两者机制不同：021 是"整条隧道被读循环堵死而断开"，022 是"悄悄少发一段，谁都不知道"。

**现象**：ISSUE-021 修完（信用改在消费时归还、队列深度由窗口反推）之后，我用
`build/_p1_memory.py` 的慢速版（16 MB 图、10 KB/s）复跑，结果：

```
HTTP 200，收到 8.0 MB，耗时 816.3s ⇒ 0.01 MB/s
字节完整：FAIL（8388608 / 16777216）
```

**恰好停在 8388608 = `CREDIT_WINDOW`**，而 HTTP 状态是 **200**、日志里一行错都没有。

**三层根因（缺一不可）**：

1. **回补阈值只看字节**。`_CreditGate.on_recv()` 要累积到 `max(CREDIT_THRESHOLD, window//2)`
   = 4 MB 才回一次 `CREDIT`，而发送方只等 `CREDIT_DEADLOCK_TIMEOUT`=30 秒。10 KB/s 下
   凑满 4 MB 需要 **410 秒** ⇒ 发送方在 30 秒时判对端卡死，抛 `MuxClosed(E5010)`。
2. **放弃时不发终止帧**。`Mux._run_handler` 对 `MuxClosed` 只 `log.debug` 就返回 ——
   既不回 `ERROR` 也不回 `RES_END`。
3. **转发层把异常当"正常结束"**。`cloud/relay/forward.py` 的 `body_iter()` 用
   `except asyncio.TimeoutError: log.info(...)` 与 `except (MuxClosed, CancelledError): pass`
   收尾。而 `RES_HEAD` 早就把 200 发出去了，生成器正常结束在 chunked 传输下等于
   **一份合法的、完整的、短了的响应**。

**为什么这是数据完整性问题而不是性能问题**：用户看到的是"照片下半截是灰的"，而手机、
云端、电脑端三处的日志全部干净 —— 没有任何一处能定位。相比之下"连接断了一次"反而是
可观测的。

**修法（三层一起修，缺一层症状就还在）**：

- `shared/protocol.py`：把 `CREDIT` 从 `FIXED_LENGTH_TYPES` 移出（`docs/04` §2.3.10
  **本来就规定**它带 12 字节 payload，是实现擅自冻结成空帧的），新增
  `encode_credit()`/`decode_credit()`，`decode_frame()` 校验长度恰为 12 字节。
- `shared/mux.py`：`grant(n)` 由"重置满窗"改为**按字节累加并封顶**；`on_recv()` 增加
  **按时间触发**（`CREDIT_UPDATE_INTERVAL=20s`，显著小于 30 秒死锁线）；`take_pending()`/
  `restore_pending()` 分离"判断该回"与"真的发出去了"（帧发失败必须把额度还回去，否则
  那批信用永久丢失）；`_run_handler` 放弃前**尽力发一条 ERROR**；`PendingRequest` 新增
  `_body_error`，让 `iter_body()` 在收尾时把"头已发 200 之后才失败"抛出去。
- `cloud/relay/forward.py`：`body_iter()` 区分三种情况 —— 客户端主动取消（静默 `raise`
  CancelledError）、超时/`MuxClosed`（抛 `RuntimeError` 让连接异常终止，客户端能察觉
  "响应不完整"）、其他异常（记 warning 后重新抛出，不再吞掉）。

**能力协商（这次修复唯一有部署风险的改动）**：`CREDIT` 的线上格式变了，而老实现的
`decode_frame()` 见到 payload 会抛 `ProtocolError` **直接断连**。所以两端必须在
`HELLO.caps` / `HELLO_ACK.server_caps` 里都声明 `credit_v2` 才发带 payload 的帧；
任一端缺失就退回空帧（老语义，慢消费者仍会被误杀，但不比从前更坏）。没有这层协商，
"云端先升级、电脑端后升级"这个**最可能的部署顺序**会让大文件传输在第一条 CREDIT 上断。

**验证**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| mux 层，消费者停 40 秒（`build/_probe_slow_mux.py --stall`） | 停在 8.00 MB，`outcome = EOF（干净结束，无异常）` | 停在 8.00 MB，`outcome = MuxClosed: 传输中断，响应不完整（E5010）` —— **截断变成可观测** |
| mux 层，12 MB @ 100 KB/s（超过窗口，`--rate 100`） | 停在 8.39 MB，干净 EOF | **12582912 / 12582912 字节，100.0%，PASS** |
| 把"按时间回补"删掉（变异） | — | 停在 8.39 MB，`MuxClosed: 传输中断...（E5010）` ⇒ **该逻辑确实在起作用** |

★ 变异实验的第一次尝试是**假阴性**：目标只有 6 MB（< 8 MB 窗口），信用压根没耗尽，
删掉时间触发照样 PASS。改成 12 MB 才抓到。教训与 §8.1 同一条：**先算清边界数值，
再判断"探针不够狠"还是"缺陷本来就走不到"** —— 这次是前者，而第一次的参数让我差点
得出"修复无效"的错误结论。

### 8.3 ISSUE-023：P1 在我这里"全绿"，在产品上却不可达（三个缺口叠加）

> 同样不属于 §8 表格（多段说明），单独列出。这条与 020/021/022 的区别在于：
> 那三条是**实现没做对**，这一条是**根本没人从用户的位置走过一遍**。

**怎么发现的**：P1 的 DoD 全部达标 —— relay 通、隧道通、一期 12 条验收用例在
云端通路逐字段一致、2 GB 内存 0.1 MB、45/45 条 TC 有名有姓。但这些都是从
"测试的起点"出发的：测试里页面总是从电脑端（局域网 origin）加载，令牌也总是
局域网配对签发的。于是写了一支探针，**从用户真实的位置**出发——一个只知道域名、
手机里什么都没缓存的浏览器（`build/_probe_cloud_entry.py`）：

```
局域网领配对码           [201]
GET /                    [404] ct='text/plain' 'Not Found'
GET /index.html          [404] ct='text/plain' 'Not Found'
POST /d/{id}/api/pair    [401] {"error":{"code":"E2002","message":"缺少配对令牌"…}}
POST /api/pair (局域网)   [201]
GET /d/{id}/api/system/ping  [200]
```

隧道是通的（最后一行 200，`via=cloud`），但**用户打不开一个能点的界面，也拿不到令牌**。

**三个互相耦合的缺口（缺一个都进不去）**：

1. **云端 origin 上没有页面**。`cloud/relay/main.py` 的路由表 13 条里没有静态托管，
   `cloud/Caddyfile` 的兜底是 `respond "not found" 404`，`cloud/Dockerfile` 里也没有
   `COPY frontend/dist`。而 `docs/01` §G-1 的用户旅程是"手机用 4G 打开域名 → 时间线出现照片"。
2. **云端 origin 上无法配对**。`cloud/relay/forward.py` 的 `PUBLIC_PATHS` 只放
   `/api/system/ping`，且 `_is_public()` **只认 GET/HEAD**，所以 `POST /d/{id}/api/pair`
   必 401 —— 而产品里手机只会走这一条（`frontend/src/stores/auth.ts` 没有云端分支）。
3. **云端不发任何 CORS 头**。`main.py` 的模块注释原来明写"云端与 PWA 同源，不安装 CORS"。
   而最常见的真实路径是"页面由电脑端伺服、请求打云端"，那是**跨源**——
   `docs/06` §8.3 早就标过这个架构风险。

**为什么这三条叠加是致命的，不是"体验差"**：`localStorage` 与 cookie 都按
**origin 隔离**。用户在家 `http://192.0.2.10:8787` 上配对拿到的 `pb.token`，
在 `https://域名` 这个 origin 上读不到。所以就算把页面托管上去，出门打开域名看到的
仍是一个"未配对"的空白页，而那个页面提交的 `POST /d/{id}/api/pair` 又被 401 挡住。
⇒ **用户在外面永远进不去自己的相册**。P1 的全部价值（出门能用）在产品上不成立。

**修法（三处一起，缺一个都不成）**：

- `cloud/relay/pages.py`（新）：`frontend/dist` 的静态托管，两个前缀共用一份产物
  （`/` 与 `/d/{id}/`；`vite.config.ts` 的 `base: "./"` 要求相对路径在前缀下正确解析）。
  路径穿越用 `os.path.realpath` + `commonpath` 判，**不用 `startswith`**（`dist-evil/`
  会被误判成 `dist/` 子路径）。单页回退**收窄到"看起来不是文件"的路径**——
  注意不能用 `Path(rel).suffix`（`.env` 的 suffix 是空串，而它正是扫描器最先打的东西）。
- `cloud/relay/forward.py`：`PUBLIC_PATHS` 加 `/api/pair`，并新增
  `PUBLIC_POST_PATHS` 单列"允许匿名的非只读方法"（不能写成"路径命中就放行所有方法"）。
  独立限流桶 `PAIR_RATE_PER_MIN=10`（`window=60`），与探活的 300/s 分开——探活被限流
  会让状态条显示"离线"，两件事的用户体验完全不同。
- `cloud/relay/tunnel.py` + `forward.py`：帧头新增 `client_ip`，把真实来源 IP 送到
  电脑端。缺了它，电脑端的 `_PAIR_WINDOW_MAX`（20 次/600 秒按 IP）与审计全部落进
  同一个 `"cloud"` 桶。只送 IP 本身，**不送 `X-Forwarded-For` 原文**（那是客户端可伪造的串）。
- `cloud/relay/cors.py`（新）：按来源白名单回 CORS 头。判定用 `ipaddress`，普通域名
  一律拒（这一条是防 `192.168.0.1.evil.com` 的关键，写成 `startswith("192.168.")` 就废了）。
  预检就地回 204，不进隧道。
- 前端：`PairView` 在云端页面上**不再要求填 IP**（`cloudBaseFromLocation()`），
  `pair()` 也优先用当前 location 作基址——否则在云端页面上会拼成
  `http://域名:8787`（错协议、多端口）。

**验证**：`backend/tests/test_p1_pages.py` 19 条（真 uvicorn 全链路 9 条 + 纯单元 10 条），
以及 `build/_probe_cloud_entry.py` 复跑：`GET /` 200 `text/html`、`POST /d/{id}/api/pair` **201**、
`GET /d/{id}/api/system/ping` 200。同时钉住"没有因此放宽别的"：同一路径的
`PUT/DELETE/GET /api/pair` 仍 401/405、`/panel/**` 仍 `x-pb-tunnel` 缺席、
恶意 `Origin` 拿不到任何 `Access-Control-*` 头、`/api/../panel/...` 仍 403 `E1009`。

**教训**：DoD 里的每一条都是"从测试装置出发"的判断。**必须有至少一条从用户真实
起点出发的端到端**，否则一整套全绿的指标可以与"产品不可用"共存。这与 §8.1
"变异 MISSED 要先算边界"是同一类错误的两个方向：那次是**判据太松**，这次是
**起点选错**。

### 8.4 ISSUE-024：三个缺口都补上了，用户出门**还是**进不去（令牌不跨 origin）

> 不属于 §8 表格，单独列出。与 023 是同一条链上的下一环：023 修的是"云端
> 这个 origin 上什么都没有"，这一条修的是"用户手里的令牌在云端那个 origin 上
> 不存在"。两次都是**我按自己设想的使用方式在验，而不是按用户真实的走法**。

**怎么发现的**：023 修完后，用手写 HTTP 探针打云端已经全绿（`GET /` 200、
`POST /d/{id}/api/pair` 201、`GET /d/{id}/api/system/ping` 200）。但那个探针
**每一步都是自己造的**：账号是我插进库的、令牌是我直接在内存里用的、页面
我根本没打开过。于是换成一个真正的浏览器（Chrome 155，真 CDP，
`build/_probe_same_phone2.py`），并且**用同一个 `--user-data-dir` 起两次**——
模拟"同一台手机的同一次浏览器安装"：

```
[1] 家里：以局域网地址打开（= 扫码那一跳）  http://192.0.2.10:63994
    keys = ['pb.base','pb.device_id','pb.device_name','pb.token','pb.via']
    token = 'pbc1.eyJzdWI…'  via = 'lan'  cookie = pb_token=…
    配对成功；页面文字 = '照片 / 局域网直连 / YiRu / 今天 / 3 / 没有更多了…'
    ★ 学到的云端基址 pb.cloud = ''（空！）

[2] 出门：同一个 profile、以云端地址打开   http://<cloud>/d/<did>/
    keys = []   token = ''   via = ''   cookie = (无)
    页面文字 = '把手机里的照片，传到自己的电脑上 / 正在通过中继连接家里的电脑。
               输入电脑上显示的配对码即可。 / 配对码 / …'
    → ★ 回到配对页

[3] 若真的在云端 origin 上完成一次配对
    重载后 via='lan'、图片 3 张、解码成功 3 张、
    timeline 200 | thumb(无 Authorization) 200、<img> LOADED 160x120
    ⇒ 同源时一切正常；缺的只是"令牌怎么到那个 origin 上"
```

**根因**：`localStorage` 与 cookie 都按 **origin** 隔离。家里扫码配对拿到的
`pb.token` 落在 `http://192.0.2.10:8787`，而 `https://域名` 是另一个源。
一期只编局域网地址的二维码（`backend/app/tray.py`），所以**唯一**的配对入口
在家；而配对码 6 位、5 分钟过期、只显示在电脑屏幕上 —— 人已经出门了。

这不是"体验差"：`docs/01` G-1（"关闭手机 Wi-Fi 仅用蜂窝网络，能打开时间线
并上传成功"）与 AC-6.2 在产品上不成立，P1 的全部价值落空。

**同一轮实测暴露的另外两条（都是"页面与接口不同源"的连带后果）**：

- **跨源缩略图 401**。`<img src>` 指向 `{base}/api/items/{id}/thumb`，而 `<img>`
  发不出 `Authorization` 头，只能靠 `pb_token` cookie；`setTokenCookie` 是
  host-only 且云端刻意不发 `Access-Control-Allow-Credentials`（发了就等于允许
  任意网页带 cookie 打云端）。实测：timeline JSON 正常（`fetch` 带 Bearer），
  **缩略图全挂、`<img>` 不解码**。改成"页面与接口同源"后此问题自动消失。
- **`pb.cloud` 学不到**（★ **后来的核对推翻了一半结论**）。现象：真浏览器
  探针里 `pb.cloud` 一直是空串，`learnCloudBase()` 读的
  `info.tunnel.public_base` 看起来"缺席"。**但那是探针自己的错** ——
  `build/_probe_same_phone2.py` 把 `tunnel` 字典 `repr()` 出来时截断到
  80 字符（`…'heartbeat_sec':2…`），而 `public_base` 恰好排在
  `heartbeat_sec` **之后**，于是键被截在了视野外。用
  `build/_probe_public_base.py` 单独取一次：
  `GET /api/system/info` → `tunnel.public_base = "http://127.0.0.1:57142/d/9ea0…"`
  不是空的（`test_p1_tunnel.py:test_info_reports_public_base` 本来就钉着它）。
  ⇒ **"出门自动切云端"这条辅助路径是好的**，老用户（二维码还没改云端入口
  之前配对的那批）也能靠它迁移。真正的阻断仍然只有上一条（令牌不跨 origin）。
  教训：**打印被截断的字典不能当作"键不存在"的证据**，要么打印
  `sorted(d)`，要么单独断言那个键。

**决策（你选的 A：云端 origin 作主入口）**：二维码**主码**改成云端入口
`https://域名/d/<id>/?code=…`（隧道已连上时）；手机在云端 origin 上配对，
令牌、cookie、图片**全同源**，出门回家都能用。零新协议、当天可用。

代价与补偿：

- 在家里也走中继（中继带宽 + 家里上行）。补偿：二维码窗口里**明文列出局域网
  地址**（"在家直连（更快，需单独配一次）"），想直连的人照着输一次即可 ——
  那个 origin 会独立配一次对，两边互不干扰。
- 隧道没连上时**必须**退回局域网地址（编一个打不开的云端地址比编局域网地址
  更糟：用户会以为程序坏了）。`_cloud_entry()` 只在 `status()["connected"]`
  为真时才返回。
- **已配对的手机不会自动迁移**。令牌在旧 origin 上，改二维码不会搬它 ——
  老用户升级后第一次出门仍会看到配对页。**补救路径有两条，都依赖
  `public_base` 确实有值（已核实，见上）**：① 下一次在家打开旧页面时，
  `apply()` 走 LAN 分支 → `learnCloudBase()` 把 `pb.cloud` 落盘，此后出门
  自动切云端；② 若那次没开过，就重新扫一次新二维码（在云端 origin 配一次）。
  没有实现"把令牌从旧 origin 交接过去"的自动迁移 —— 那需要一个跨源的
  一次性凭据交换端点，属于新协议，未在本轮范围内。

**代码改动**：

- `backend/app/tray.py`：新增 `TrayController._cloud_entry()`（读
  `tunnel.get_tunnel().public_base()`，且要求 `status()["connected"]`；
  异常一律吞掉返回空串 —— 托盘任何功能都不该让服务崩）与
  `_alt_urls_for(url)`（判据是"这个 URL 是否以某个局域网地址开头"，而不是

### 8.5 ISSUE-025：不用域名、只给服务器一个 `http://IP:端口`，到底能不能用

**问题**：`docs/08` §3.1.3 只写了"不推荐不用域名"，但没写清楚**哪些功能会
坏、哪些不会**。而这个项目的所有云端探针（`_probe_cloud_entry.py`、
`_probe_cloud_user.py`、`_probe_cloud_primary.py`）**全部走 `127.0.0.1`**，
而**回环是 secure context** —— 在回环上全绿证明不了裸 IP 可用。

**实测**（relay 绑 `0.0.0.0`、电脑端拨 `ws://<局域网IP>:<port>/agent/ws`、
真 Chrome 155 以 `http://192.0.2.10:<port>/d/<id>/` 打开，
`build/_probe_ip_only.py` + `build/_probe_ip_browser.py`）：

| 项 | 结果 |
|---|---|
| 隧道握手 `ws://IP:port/agent/ws` | ✅ 通，`session_id` 正常，`via="cloud"` |
| 云端页面 `GET /` | ✅ 200 `text/html` |
| 云端源配对 `POST /d/<id>/api/pair` | ✅ 201，令牌 `pbc1.…` |
| 刷新会话（同 profile 重开裸地址） | ✅ 直接相册，不回配对页 |
| 缩略图 `<img>` | ✅ 3/3 解码，`LOADED 160x120` |
| `PB_CLOUD_HOSTS` 填**纯 IP** | ✅ 放行（`check_host` 是 `host == item` 比对，不要求域名） |

**三个坑**（都实测过，不是推测）：

1. **`base_url` 少写 `http://` 会静默变成 `wss://`**。`_ws_uri()` 在没有
   `://` 时先补 `https://`，于是 `"1.2.3.4:8000"` → `wss://1.2.3.4:8000/agent/ws`，
   对着纯 HTTP relay 做 TLS 握手。实测：`SSLError: [SSL: WRONG_VERSION_NUMBER]`，
   重连 5 次全失败（`build/_probe_ip_scheme.py`）。**必须写全 `http://IP:端口`**。
   这属于"配了却连不上，而日志那句话看起来很正常"那一类，`public_base_for()`
   的 docstring 早就为此写过四种写法归一，但**没有覆盖"用户想用明文 IP"**。
2. **裸 IP 页面 `isSecureContext === false`**，实测该页面上
   `crypto.randomUUID` 与 `navigator.clipboard` **都是 `undefined`**
   （`crypto.randomUUID is not a function`）。本产品当前不受影响 —— 前端没有
   关键路径依赖它们，复制有 `execCommand` 兜底（`frontend/src/api/clipboard.ts`
   那张表已经钉过同一件事）。但**以后任何新功能若用 `crypto.subtle` /
   `navigator.clipboard` / Service Worker / `wakeLock`，在裸 IP 下都会静默失效**。
3. **Caddy 不适合兜裸 IP**：站点地址 `{$DOMAIN}` 填 IP 时它会去申请 ACME
   证书，Let's Encrypt 不为 IP 签发，于是退回自签证书 ⇒ 手机每次访问都是证书
   错误，比直接 `http://IP:8000` 更难用。裸 IP 部署应当只跑 relay，或把站点
   地址显式写成 `http://{$DOMAIN}`。

**结论**：功能上能用；**安全性上不可接受**（全线明文，令牌与照片在公网裸奔，
`docs/06` T11 记为"唯一的 MITM 缺口"）。⇒ 定位为**受控网络内的验证/临时方案**，
不是生产形态。已写进 `docs/08` §3.1.4，含一段可以直接抄的最小验证步骤。

**教训**：这又是一次"回环 vs 真机"。仓库里已经有 `clipboard.ts:6-20` 那张
`isSecureContext` 对照表，说明这个坑**早就被发现过、但没有反过来检查其他
探针**。⇒ 判断"某支探针的结论能推广到真机吗"，第一件事是看它用的 origin：
`127.0.0.1` / `localhost` 得出的结论，对 `http://<IP>` 一律要重验。

### 8.7 ISSUE-027：`2>$null` 把「忽略这个错误」变成了「立刻中断」——首次部署必断在第 8 步

**现象**：2026-10-23 在阿里云 `203.0.113.10` 上**第一次**真机部署，`deploy.ps1`
的 0–7 步全绿（Python/依赖/云端库/设备/启动脚本/防火墙/试跑自检都 OK），
第 8 步「注册开机自启」直接**中断**，进程退出码非 0。后果不是「少一条自启」这么轻：
第 9 步的交付信息（`BASE_URL` / `DEVICE_ID` / `AGENT_TOKEN` / 自检地址）一行都没打印，
而那几行正是运维唯一需要抄回去的东西 —— 表现上像「部署失败」，实际是**失败的收尾**。

**根因**：脚本全程 `$ErrorActionPreference = "Stop"`，第 8 步第一句是

```powershell
schtasks /Delete /TN $taskName /F 2>$null | Out-Null   # 想「任务不存在就算了」
```

而 PowerShell 5.1 里把**原生命令**的 stderr 重定向到任何地方（`2>$null`、`2>&1`）
都会把每一行 stderr 变成一条 `ErrorRecord`，在 `Stop` 下立即终止；
`$null` 收得走内容，**收不走「这是一条错误」这件事**。首次部署时任务必然不存在，
所以这条路径**首次必炸、之后永不炸** —— 属于「一次性的、正好断在交付门口」的缺陷。

服务器本机 PS 5.1.26100 实测对照（任务名不存在时）：

| 写法 | 结果 |
|---|---|
| `schtasks /Delete ... /F 2>$null \| Out-Null` | **中断**：`RemoteException / ERROR: The system cannot find the file specified.` |
| `schtasks /Delete ... /F \| Out-Null`（不重定向 stderr） | 不中断，`$LASTEXITCODE=1` |
| `schtasks /Delete ... /F 2>&1 \| Out-Null` | **中断**（同上） |
| 补丁写法：EAP 临时降 `Continue` + `*>&1` | 不中断，`delete_rc=1` |

**修法**：把 `schtasks /Delete` 与 `schtasks /Create` 一起包进 `try/finally`，
临时 `$ErrorActionPreference = "Continue"`、用 `*>&1` 合并各流、用 `$LASTEXITCODE`
判定成功与否、`finally` 里还原 EAP；失败提示带上退出码。

**教训**：

1. **「忽略这个错误」≠「重定向到 `$null`」**。想忽略原生命令的非零退出，
   只能不重定向 stderr，或者临时把 EAP 降下来 —— 后者要配 `finally` 还原，
   否则后面所有步骤都会静默继续。
2. **交付物只在自己仓库里通过结构断言不算数**。这段代码此前只有
   「`deploy.ps1` 必须带 BOM」「必须写 `PB_CLOUD_WEB_DIR`」这类**静态**断言覆盖，
   一次都没在干净机器上真跑过；真机第一次跑就断。凡是「给别人的一键脚本」，
   必须有一张「在干净机器上从零跑一遍」的证据。本轮补了两样：
   静态回归 `test_windows_deploy_script_survives_schtasks_stderr_on_first_run`
   （钉死 `2>$null` 不许回来）＋ 一次真机全程复跑（`C:\PhotoBridgeVerify`
   独立安装目录/独立端口/独立 SQLite，9 步全绿 `exit=0`，验完即删）。
3. **不能靠「重跑一遍」验证这类补丁**：`deploy.ps1` 第 4 步对已登记账号是
   **故意 Fail** 的（防止重复建设备），所以补丁后原地重跑必然停在第 4 步。
   验证只能用一次性安装目录 —— 这也是「第 4 步非幂等」第一次被当成硬约束来用。

### 8.8 ISSUE-028：服务端一切正常，手机在 4G 下却「网页打不开」——裸 IP 不是可交付的入口

**现象**：2026-10-23 云端部署完成、外网自检全绿后，让用户用手机打开
`http://203.0.113.10:8000/d/<id>/`，手机（4G/5G、Wi-Fi 已关）卡在「正在加
载网页 20%」，随后「出错了 / 网页打不开」。换成 `:80` 同样打不开。

**先排除掉的（都有证据）**：

| 猜想 | 验证方式 | 结论 |
|---|---|---|
| 页面/前端坏了 | 真 Chrome 打开该地址，渲染出配对页 | 否 |
| 隧道断了 | 从公网 `POST /d/<id>/api/pair` → `201`，时间线取到 3 项 | 否 |
| 配对码问题 | 同上，配对码在有效期内即成功 | 否 |
| 端口被挡（8000） | 新开 `:80` 入口，公网 `GET /api/health` → `200` | 否（换 80 仍打不开） |

**决定性证据**：relay 访问日志里，全部请求的来源只有两个 —— `182.139.160.152`
（家里宽带的公网出口）和 `127.0.0.1`（本机回环）。**没有任何一条来自移动网络的
IP**。也就是说手机那两次尝试连 TCP 都没建起来，请求根本没到服务器：这不是「页
面 bug」，也不是「配对失败」，是**路径不通**。

**根因**：`http://<公网 IP>:<非标端口>` 不是可交付的入口。实测同一条链路上，
`:8080` / `:8888` 从外部直接被中间设备回 `502`（同机、同服务、只有端口不同），
说明链路上存在按端口策略拦/劫持的设备；而移动网络到这台机器的那一段，连
`:80` 都没放通。日志里「没有你的 IP」就是最终判据 —— 讨论「端口/页面/配对」
全都为时过早。

**修法**：换成**不需要入栈端口**的入口 —— Cloudflare Tunnel（`cloudflared`
quick tunnel）。服务器**主动向外**连 Cloudflare，手机只访问 `443/HTTPS`：

```
cloudflared tunnel --url http://127.0.0.1:8000
→ https://<random>.trycloudflare.com
```

用计划任务托管（`PhotoBridge Cloudflared`，`ONSTART /RU SYSTEM`）—— 从 SSH 会话
里 `Start-Process` 起的进程会随会话结束消失，这台机器上已经踩过一次（uvicorn 同理）。
用户手机随即连通。同时保留 `:8000`（原入口）与 `:80`（`build/_portfwd.py` 转发
到 `127.0.0.1:8000`），局域网/家宽用法不受影响。

**教训**：

1. **「我这边能打开」不是证据**。同一个 URL 在不同网络路径上结论可以完全相反。
   判据只有一个：**服务端日志里有没有对方的 IP**。
2. **排障顺序要倒过来**：先证明「请求到没到服务端」，再谈端口、页面、配对。
   本轮先查了页面渲染、隧道状态、配对码，最后才去看来源 IP —— 而来源 IP 一栏
   就能省掉前面全部工作。
3. **非标端口 + 裸 IP 在移动网络上是不可交付的**。产品级入口只能是「域名 + 443」；
   `trycloudflare.com` 的随机域名每次重启都会变，只能当验证期的逃生口，
   不能写进交付说明。
4. 中间设备会**按端口**发包级拦截（`502` 是它伪造的，不是我们的服务回的）。
   看到「同机不同端口结论不同」，第一反应应当是链路策略，而不是应用代码。
