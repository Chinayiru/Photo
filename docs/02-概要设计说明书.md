## 1. 设计目标与原则

> 原则是**取舍时的判据**。当两个方案都可行、无法靠"哪个更好"决定时，用这些原则投票。

### 1.1 设计目标

| 编号 | 目标 | 对应需求 | 可验证的体现 |
|---|---|---|---|
| DG-1 | 手机在**任意网络**下都能访问自己的照片 | P1-1、P1-2 | 关闭 Wi-Fi 仅用 4G 能打开时间线 |
| DG-2 | 照片**只存在自己的电脑上**，云端零媒体字节 | P1-7 | 云端全盘搜不到图片魔数 |
| DG-3 | 云侧成本 **≤ ¥30/月** | NFR-$ | 月度账单 |
| DG-4 | **零运维**：装好不用管，坏了重建 ≤ 30 分钟 | P1-7 AC-7.6 | 演练一次 |
| DG-5 | **不丢数据**：上传/删除都不可能造成照片丢失 | NFR-R-4~8 | 覆盖/半截文件/删除三类用例全过 |
| DG-6 | 在家时**快且省**：局域网直连优先 | P1-6 | 直连时云流量零增长 |

### 1.2 设计原则

| # | 原则 | 含义 | 为什么（理由） | 在哪体现 |
|---|---|---|---|---|
| **DP-1** | **云端零存储** | 云只转发，不落任何媒体字节，不使用任何媒体缓存（含 CDN） | ①**隐私底线**：照片不进第三方；②**架构韧性**：云上没有任何不可再生数据，所以"云被墙/宕机/跑路"只是可用性问题，不是数据安全问题。**这一条让"选最便宜的小厂商 VPS"成为合理决策而非冒险** | 云端 5 张表无 `media`；流式转发不整体缓冲 |
| **DP-2** | **失败安全优先**（fail-safe） | 任何失败路径都必须导致"数据完好"或"操作未发生"，绝不导致"数据损坏" | 单人自用系统没有运维团队，**没有人工兜底的机会**。一次数据损坏可能无法挽回 | 临时区隔离 + 原子 `os.replace`；只新增不覆盖；删除进回收站；同名加序号 |
| **DP-3** | **协议与实现分离** | 帧协议（`protocol.py`）独立于业务逻辑，云端与电脑端**共享同一份代码** | ①两端用同一语言（Python）的最大理由；②协议一旦不一致会产生极难调试的"半通"故障；③二期加 E2E 只需填充 `flags`/`enc` 字段，**不动协议结构** | `cloud/relay/protocol.py` 与 `backend/app/tunnel.py` 共享编解码 |
| **DP-4** | **两条通路，一套 API** | 局域网直连与云端中继走**完全相同的 API 路径**，前端零分支 | 若两条路 API 不同，每个功能都要写两遍、测两遍、修两遍。**这是"局域网加速"能以 1 天成本实现的原因** | `local_server.py` 与 `dispatch.py` 调用**同一套 handler** |
| **DP-5** | **显式失败优于静默等待** | 电脑离线、格式不支持、超过上限——一律明确报错并给出出口，绝不无限转圈 | 用户无法区分"在加载"和"坏了"。**静默失败会让人以为系统坏了而放弃使用** | 3 秒内返回 `device_offline`；离线状态不缓存超过 30 秒；上传超限明确拒绝 |
| **DP-6** | **单向数据流：只新增，不修改** | 上传只新增不覆盖；删除只进回收站；改名/移动写审计日志 | 写权限已开放（业主决定），风险必须用**机制**兜住而不是靠"小心一点"。**机制可以验证，小心不能** | 四条硬约束（设计文档 §8.4） |
| **DP-7** | **为二期留接口，但不为二期写代码** | 协议预留 `flags`/`enc` 字段；`media.kind` 预留视频取值；`root_id` 预留多根 | 预留字段成本几乎为零；**事后改协议结构的成本极高**（要同时改两端 + 前端 + 测试）。但**不提前实现**，避免为不确定需求付确定成本 | 帧头 `flags`；`REQ_HEAD.enc`；`kind` 恒为 `'image'` |
| **DP-8** | **单一事实来源** | 架构决策只写在 [设计文档.md](../设计文档.md)；接口只写在 [04](04-接口设计文档.md)；表结构只写在 [05](05-数据库设计文档.md)。其他文档**引用不复述** | 避免"改一处要动全文"和"文档间自相矛盾"。**复述即埋雷** | [00 文档](00-文档索引与开发流程.md) §1 的权威顺序表 |
| **DP-9** | **最贵的资源优先省** | 云带宽是最贵资源（也是体验瓶颈），一切设计优先减少云流量 | 云带宽 3–30 Mbps 是物理上限，且直接决定等待时间；**流量反而不是瓶颈**（月用 4.6 GB vs 套餐 500 GB）。省钱与提速在这里是**同一件事** | 缩略图极致压缩（20 KB）；局域网直连优先；三级渐进加载（浏览不拉原图） |

### 1.3 原则冲突时的优先级

当原则互相冲突时，按此顺序裁决（**越靠前越优先**）：

```
DP-2 失败安全  >  DP-1 云端零存储  >  DP-6 只新增  >  DP-5 显式失败
      >  DP-9 省带宽  >  DP-7 为二期留接口  >  DP-8 单一事实来源
```

**举例**：若"省带宽"（DP-9）与"失败安全"（DP-2）冲突——例如为省流量而跳过校验——**一律选择校验**。流量可以再花，数据丢了就没了。

## 2. 系统架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  L1  展示层（手机浏览器 / PWA）                                              │
│      时间线 · 查看器 · 上传队列 · 搜索 · 我的                                 │
│      技术：Vue3 + Vite + TypeScript                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│  L2  通路层（手机端策略）                                                    │
│      双通路选择器：局域网直连（1.5s 探测）优先 → 云端中继兜底                 │
│      对外暴露统一的 API 基址，上层无感知                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│  L3  接入层（云服务器）                                                      │
│      Caddy（TLS 终止 + 自动 Let's Encrypt）→ FastAPI Relay                   │
│      账号鉴权 · 设备注册表 · 配对 · 限流                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│  L4  转发层（云服务器 ⇄ 电脑）                                               │
│      反向隧道（WSS 常驻）· 帧编解码（protocol.py）· 多路复用（req_id）        │
│      流控（credit window 8MB）· 心跳（25s）· 指数退避重连                     │
├─────────────────────────────────────────────────────────────────────────────┤
│  L5  派发层（电脑端）                                                        │
│      cloud_tunnel.py：隧道请求 → 内部路由；local_http.py：同网直连            │
│      ★ 两者构造同一个 Ctx 交给同一个 Router（DP-4）                          │
├─────────────────────────────────────────────────────────────────────────────┤
│  L6  业务层（电脑端）                                                        │
│      索引器 · 缩略图引擎 · 上传管理 · 归档 · 搜索 · 事件推送                  │
├─────────────────────────────────────────────────────────────────────────────┤
│  L7  安全层（电脑端，被 L6 全部依赖）                                        │
│      sandbox.py：所有文件访问的唯一入口（路径校验 + 越界断言）                │
├─────────────────────────────────────────────────────────────────────────────┤
│  L8  存储层（电脑端）                                                        │
│      SQLite（photobridge.db）· 文件系统（D:\Photos）· 缩略图缓存       │
│      · 临时区（<库根>/.photobridge_tmp，见 Q-35）                            │
└─────────────────────────────────────────────────────────────────────────────┘
```

**为什么这样分层**

| 分层决策 | 理由 |
|---|---|
| **L7 安全层独立且"被依赖"而非"去调用"** | 沙箱不是"某个模块的功能"，而是**所有文件访问的强制关卡**。做成独立层才能保证没有遗漏（DP-2） |
| **L4 转发层与 L6 业务层完全解耦** | 转发层只认"帧"，不认"照片"。这使得二期加 E2E 时**转发层代码零改动**（DP-3） |
| **L2 通路层单独成层** | 把"走哪条路"的复杂度**收敛到一个地方**，使 L1 展示层完全不知道有两条路（DP-4） |
| **L3 接入层与 L4 转发层同进程不同模块** | 都在云上、都是 I/O 密集、都只需 1 核。拆成两个服务只增加运维成本，不带来收益 |

**三方部署的职责边界**

| 端 | 存什么 | 不存什么 | 生命周期 |
|---|---|---|---|
| **手机** | Service Worker 缓存的缩略图 | 任何权威数据 | 可随时清空，无影响 |
| **云** | 账号、设备列表、配对码、带宽计数（< 1 MB） | **任何媒体字节** | 可随时重建，无影响 |
| **电脑** | **照片本体 + 索引库 + 缩略图缓存** | — | **唯一不可再生的是照片本体**；索引库与缓存均可重建 |

**为什么"云侧可随时重建"如此重要**：它把"云服务器"从"基础设施"降级为"可替换零件"。这直接支撑了 DG-4（零运维）与 DP-1（零存储），也是 [VPS选购建议.md](../VPS选购建议.md) §3 说"用便宜小厂商是合理决策"的根据。

### 2.3 运行时视图：一次请求经过哪些组件

以**手机在外用 4G 请求时间线**为例：

```
① 手机浏览器
   │  GET https://<域名>/d/<device_id>/api/timeline?cursor=&limit=100
   ▼
② Caddy（云 :443）
   │  TLS 终止 → 反向代理到 relay:8000
   ▼
③ Relay · 接入层
   │  a) 校验 client_token（auth.py）
   │  b) 校验该 token 绑定的 device_id 与 URL 中的一致（越权检查）
   │  c) 查设备注册表：device_id → 活跃隧道连接？
   │       无 → 返回 503 {"error":"device_offline"}   ★ 3 秒内
   │  d) 限流检查（120 req/s）
   ▼
④ Relay · 转发层
   │  e) 分配 req_id
   │  f) 发 REQ_HEAD{method,path,query,headers} → REQ_END
   │  g) 检查 credit window（8MB）是否够用
   ▼
⑤ 隧道（WSS，已存在的常驻连接）
   │  帧：type|req_id|payload
   ▼
⑥ 电脑 · 隧道客户端（tunnel.py）
   │  h) 解帧 → 按 req_id 找到对应的请求上下文
   │  i) 交给 core/dispatch.py 的 Router
   ▼
⑦ 电脑 · 派发层（core/dispatch.py）
   │  j) 构造 Ctx → 调用与本地 HTTP 相同的 handler
   ▼
⑧ 电脑 · 业务层
   │  k) 查 SQLite：SELECT ... ORDER BY taken_at DESC, id DESC LIMIT 100
   │  l) 组装轻量项 JSON
   ▼
⑨ 电脑 · 隧道客户端
   │  m) 发 RES_HEAD{status:200,headers} → RES_BODY × N → RES_END
   ▼
⑩ 隧道 → Relay 转发层
   │  n) 边收边转发给手机（流式，不缓冲整个响应体）★ DP-1
   │  o) 按消费字节数回 CREDIT 帧补充窗口
   ▼
⑪ Caddy → 手机
   │  流式响应
   ▼
⑫ 手机浏览器
      渲染网格 → IntersectionObserver 触发缩略图请求（重复 ①~⑪，但每个是独立 req_id）
```

**缩略图请求（第二次循环）的差异点**

| 步骤 | 差异 |
|---|---|
| ⑧ | 先查缩略图缓存（磁盘）。**命中**：直接流式读文件；**未命中**：生成（30–80 ms）→ 写缓存 → 流式回 |
| ⑪ | 响应带 `ETag` + `Cache-Control: immutable` |
| ⑫ | **Service Worker 拦截并缓存该缩略图** → 二次浏览**不发请求**（流量为零） |

**关键路径耗时预算**（4G 走云端，单张缩略图 20 KB）

| 段 | 预估耗时 |
|---|---|
| 手机 ↔ 云（4G RTT） | 50–100 ms |
| 云 TLS + 鉴权 + 查表 | 1–5 ms |
| 云 ↔ 电脑（隧道 RTT） | 50–200 ms（境外 VPS） |
| 电脑查库 + 读缓存 | 5–100 ms |
| 传输 20 KB（3 Mbps） | ≈ 53 ms |
| **单张合计** | **≈ 160–460 ms** |

**为什么首屏 100 张能在 2.5 秒内**：100 张缩略图**并行**发起（多路复用，同一隧道上 100 个 `req_id`），浏览器限制同域并发约 6 条 HTTP/2 流，但隧道侧是并行派发的。实际首屏只需**先渲染出可见的约 12–20 张**（`IntersectionObserver` 懒加载），其余在滚动时按需加载。所以 2.5 秒的判据是"**可见区域**的缩略图出现"，而不是 100 张全部下载完。

### 2.4 关键数据流

```
【浏览流】  文件系统 → indexer → SQLite → dispatch → 隧道 → 云 → 手机
                    ↓
                 thumbs → 缩略图缓存 → 流式响应 → SW 缓存（手机本地）

【上传流】  手机 → 云 → 隧道 → dispatch → uploads
                                            ↓
                        <库根>/.photobridge_tmp/{id}.part（分片追加）
                                            ↓ 校验 size/sha256
                                    archive 计算目标路径
                                            ↓ os.replace（原子）
                                    D:\Photos\年\年-月\
                                            ↓
                                    indexer 入库 → thumbs 生成缩略图
                                            ↓
                                    NOTIFY 帧 → 云 → 手机

【下载流】  手机 → 云 → 隧道 → dispatch → sandbox 校验 → 文件
                                                    ↓
                                            流式读 → 隧道 → 云 → 手机
                                            （credit 流控，不整体缓冲）
```

### 4.2 模块接口契约（高层）

> 字段级定义见 [04-接口设计文档](04-接口设计文档.md)。这里只定义**模块之间的调用契约**。

| 调用方 | 被调方 | 契约（输入 → 输出） | 约束 |
|---|---|---|---|
| 传输适配器（`local_http.py` / `cloud_tunnel.py`） | `core/dispatch.py` 的 `Router` | 构造 `Ctx` → `Reply`（状态码 + 头 + body） | 两者传参**必须完全一致**；差异只允许出现在 `Ctx.via` 与"分片大小"这类由请求上下文携带的参数上 |
| `routers/*` | `sandbox.resolve` | `(root_cfg, rel_path, need)` → `Path` | **任何文件访问必须先过此函数**；越界抛异常，调用方不得捕获后继续 |
| `routers/timeline` | `db` | 游标 + limit → 轻量项列表 + 下一页游标 | 排序**必须** `taken_at DESC, id DESC`；游标分页不得退化为 OFFSET |
| `routers/uploads` | `uploads` | `init` / `PATCH` / 查询 / `complete` / 取消 | `PATCH` 必须**幂等**；`complete` 前必须校验 `size` 与 `sha256` |
| `uploads` | `archive` | 会话 + EXIF `taken_at` → 目标绝对路径 | 返回的路径**必须已过沙箱校验**；**必须保证目标不存在** |
| `archive` | `sandbox` + `os.replace` | 临时路径 + 目标路径 → 落盘结果 | 临时文件与目标**必须在同一卷**（保证 `os.replace` 原子性） |
| `uploads` / `archive` | `audit` | 动作 + 路径 + 详情 | 删除/移动/改名**必须**调用 |
| `indexer` | `exif` | 文件路径 → EXIF 字段集 + `taken_at` + `taken_src` | 无 EXIF 时**不得抛异常**，必须走降级链 |
| `indexer` | `thumbs` | 文件路径 + 目标尺寸 → 缩略图路径 | 索引时**不阻塞**（缩略图可后台生成，`thumb_state` 标记） |
| `thumbs` | `sandbox` | 源路径 + 缓存路径 | 缓存写入也要过沙箱 |
| `tunnel.py`（电脑） | `dispatch.py` | 帧（`REQ_HEAD`/`REQ_BODY`/`REQ_END`）→ 帧（`RES_HEAD`/`RES_BODY`/`RES_END`） | 一个 `req_id` 的帧序列**必须有序**；`CANCEL` 到来后立即停止 |
| `tunnel.py`（两端） | `protocol.py` | 字节流 ↔ 帧对象 | **纯函数、无 I/O、无状态** |
| `tunnel.py`（云） | `devices.py` | `device_id` → 连接对象 / 离线 | 查的是**内存 map**，不得查库 |
| `events` | `tunnel.py`（电脑） | 事件 → `NOTIFY` 帧 | 目标手机的路由见 §10 待确认 Q-15 |
| `auth.py` | `devices.py` | `client_token` → `device_id` | 用于**越权检查**：token 绑定的 device 必须等于 URL 中的 device |
| `tray.py` | `tunnel.py` / `indexer.py` | 状态查询 / 触发重扫 | 只读状态；不得直接操作文件 |

### 4.3 数据流向与所有权

| 数据 | 产生方 | 消费方 | 权威副本位置 |
|---|---|---|---|
| 照片字节 | 手机上传 / 手动拷入 | 手机浏览下载 | **`D:\Photos`**（唯一） |
| 照片元数据（EXIF） | `exif.py` | 前端展示、排序 | `media` 表（可从文件重建） |
| 时间线游标 | `routers/timeline` | 前端 | 无状态（由 `taken_at` + `id` 编码） |
| 缩略图 | `thumbs.py` | 前端 | `data/thumbs/`（**可重建**）+ 手机 SW 缓存 |
| 上传会话 | `uploads.py` | 前端续传 | `upload_sessions` 表 + `<库根>/.photobridge_tmp/*.part` |
| 账号 / 设备 / 配对码 | 云 `auth`/`devices`/`pairing` | 云自身 | 云端 `cloud.db`（**可重建**，代价是重新配对） |
| 带宽计数 | 云 `limiter` | 托盘面板 | 云端 `traffic` 表（**可丢弃**） |
| 审计日志 | `audit.py` | 托盘面板 | `data/audit.log`（**不可重建**，但非关键数据） |

**"可重建"标记的意义**：它决定了备份策略。**只有 `D:\Photos` 和 `data/audit.log` 是不可再生的**，其余全部可以从这两者推导出来。这直接支撑了 DG-4（零运维）——**换电脑只需拷回相册目录，索引与缓存自动重建**。

### 4.4 端到端接口层次

```
┌──────────────────────────────────────────────────────┐
│ 前端（手机）                                          │
│   调用统一 API 基址：/api/**                          │
└────────────┬─────────────────────────────────────────┘
             │ ①局域网：http://192.0.2.10:8787/api/**
             │ ②云端：  https://<域名>/d/{device_id}/api/**
             ▼
┌──────────────────────────────────────────────────────┐
│ 云：/d/{device_id}/api/**  ← 透明转发                 │
│   剥离前缀，还原成 /api/** 塞进隧道                    │
└────────────┬─────────────────────────────────────────┘
             │ 隧道帧（REQ_HEAD/REQ_BODY/REQ_END）
             ▼
┌──────────────────────────────────────────────────────┐
│ 电脑：dispatch.py 还原成 /api/** → 与直连同一套 handler │
└──────────────────────────────────────────────────────┘
```

**这个"前缀剥离/还原"设计是整个双通路方案的关键**：手机端只知道两个不同的**基址**，路径部分完全相同。云侧只做前缀剥离，**不理解业务语义**（它不知道 `/api/timeline` 是什么意思）——这正是 DP-1（云零存储）在接口层面的体现：**云对业务无知**。

## 5. 技术选型与理由

> 每项给出：**选了什么 / 为什么选 / 备选方案 / 为什么不选**。

### 5.1 后端语言与框架

| 项 | 内容 |
|---|---|
| **选择** | **Python 3.12 + FastAPI + uvicorn** |
| **为什么选** | ①**两端同一语言**：云端 Relay 与电脑端 Agent 用同一门语言，才能共享 `protocol.py`（DP-3）——这是最关键的理由；②**原生 async**：隧道是 I/O 密集型（大量并发帧读写），asyncio 天然适配；③**WebSocket 一等公民**：FastAPI 的 `@app.websocket` 直接支持，无需额外框架；④**Pydantic 校验**：接口参数校验开箱即用；⑤**生态**：Pillow / pillow-heif / send2trash / watchdog 都是成熟 Python 库；⑥**PyInstaller** 打包 Windows exe 成熟 |
| **备选 A** | **Node.js（Express/Fastify）+ TypeScript** |
| **为什么不选 A** | ①**图像处理是弱项**：EXIF 抽取、HEIC 转码、WebP 生成的库（`sharp`）体积大、依赖原生编译，PyInstaller 场景下比 Pillow 麻烦得多；②**PyInstaller 等价物缺失**：`pkg`/`nexe` 打包 Node 成单 exe 的体验远不如 PyInstaller；③**与前端同语言的收益在本项目很小**：前端只调 HTTP API，不需要共享类型（TS 类型可以从 OpenAPI 生成） |
| **备选 B** | **Go** |
| **为什么不选 B** | ①**图像处理生态薄**：Go 的 EXIF/HEIC 支持远不如 Python；②**开发速度**：单人项目，Python 的迭代速度明显更快；③**与前端无协同优势** |
| **代价** | Python 的 CPU 密集型性能弱于 Go/Node。**但本项目几乎没有 CPU 密集操作**——缩略图生成是唯一的重活，单张 30–80 ms 完全可接受（设计文档 §9.3） |

### 5.2 数据库

| 项 | 内容 |
|---|---|
| **选择** | **SQLite**（云端 `cloud.db` + 电脑端 `photobridge.db`） |
| **为什么选** | ①**单用户单机**：没有并发写入压力；②**零运维**：无独立服务进程，无端口，无密码，无备份体系（文件级拷贝即可）；③**随应用分发**：电脑端打包进 exe 后无需安装数据库；④**FTS5 内置**：全文检索 `media_fts` 开箱即用（设计文档 §5.2）；⑤**单文件**：备份、迁移、重建都只是拷文件；⑥**性能足够**：4915 行数据的索引查询是微秒级；⑦**WAL 模式**可支持"读写并发"（索引器写 + 浏览器读） |
| **备选 A** | **PostgreSQL** |
| **为什么不选 A** | ①需要独立服务进程，**违背 DG-4（零运维）**——电脑上多一个要装要管的服务；②打包进 PyInstaller 不现实；③单用户场景下它的并发能力、事务隔离、权限体系**全部用不上**；④云端也只需要存 5 张小表（< 1 MB），用 PG 是杀鸡用牛刀 |
| **备选 B** | **云端用托管数据库（如 Supabase/云厂商 RDS）** |
| **为什么不选 B** | ①**引入外部依赖**，且数据离开自己的 VPS，与 DP-1 的精神不符；②增加成本与网络往返；③数据量 < 1 MB，托管服务的最低档都远超需求 |
| **代价** | ①SQLite 的写并发是"单写者"，但本项目**只有索引器一个写者**（上传走同一进程的队列）；②不支持网络访问——但本项目**不需要**（云端和电脑端各自访问本地文件） |
| **注意** | 电脑端需开启 **WAL 模式**，否则索引器写入时会阻塞前端读请求 |

### 5.3 前端技术栈

| 项 | 内容 |
|---|---|
| **选择** | **Vue 3 + Vite + TypeScript** |
| **为什么选** | ①**Vue 3 Composition API** 对"组合式状态 + 生命周期"的表达力好，适合"通路切换 + 上传队列 + 时间线游标"这类状态密集场景；②**Vite** 构建快、配置少、HMR 体验好；③**TypeScript** 能约束接口字段（时间线项、EXIF 字段、上传响应），避免字段名拼写错误——**这类错误在隧道转发场景下极难调试**（错误发生在电脑端，但表现是手机端空白）；④**体积可控**：Vue 3 运行时约 34 KB（gzip），比 React + ReactDOM 小；⑤**PWA 插件成熟**：`vite-plugin-pwa` 直接生成 Service Worker 与 manifest |
| **备选 A** | **React + Vite + TS** |
| **为什么不选 A** | 技术上完全可行，**没有硬性劣势**。不选的理由是：①运行时体积更大（React + ReactDOM 约 45 KB gzip），对"首屏 2.5 秒"这个指标不利；②本项目没有使用 React 生态特有能力的场景；③**选 Vue 只是为了减少一个需要决策的变量**——两个方案都行时，选体积更小、模板更贴近 HTML 的那个 |
| **备选 B** | **原生 JS / 无框架** |
| **为什么不选 B** | 时间线虚拟滚动 + 上传队列状态机 + 查看器手势，这些用原生实现会显著增加代码量与 bug 面。**框架在这里是净收益** |
| **备选 C** | **原生 App（Flutter / React Native）** |
| **为什么不选 C** | ①**分发成本**：需要打包、签名、安装；②**失去 PWA 红利**：Service Worker 缓存、添加到主屏幕、`wakeLock` 全部是浏览器能力，原生 App 要各自实现一遍；③**核心诉求是"随时能看"**，网页零安装恰好最匹配 |
| **代价** | ①浏览器能力受限于 Chrome 的实现；②无法后台常驻上传（但 `wakeLock` + 分片续传已能覆盖主要场景） |

### 5.4 隧道传输协议

| 项 | 内容 |
|---|---|
| **选择** | **WebSocket（WSS）**，降级预案为 SSE + POST 长轮询 |
| **为什么选** | ①**双向**：隧道需要"云→电脑发请求"和"电脑→云回响应"两个方向，WebSocket 天然双向；②**多路复用**：单条连接上靠 `req_id` 跑任意并发请求（设计文档 §4.2 明确说明"这正是 WebSocket 相对于'每个请求开一条隧道'的价值"）；③**二进制帧**：帧格式是自定义二进制（`type + req_id + payload`），WebSocket 的 binary frame 直接承载；④**穿透性**：走 443 端口 + TLS，与普通 HTTPS 流量无异，家庭 NAT 与企业防火墙基本放行；⑤**FastAPI/Starlette 原生支持** |
| **备选 A** | **SSE + POST 长轮询** |
| **为什么不选 A（作为主方案）** | ①**单向**：SSE 只能云→电脑推送，电脑→云的方向需要另开 POST，等于两条独立通道，**流控与多路复用要在两条通道上协调**，复杂度反而更高；②**延迟**：POST 方向的请求要新建 HTTP 请求，比在已有连接上写帧慢；③**连接数**：高并发响应体传输时会占用大量 HTTP 连接 |
| **为什么仍保留 A（作为降级）** | 若企业代理或某些网络拦 WebSocket（设计文档 §4.1 提到），需要有退路。**关键设计**：帧格式不变（`protocol.py` 不变），只换承载方式——这就是 DP-3（协议与实现分离）的价值 |
| **备选 B** | **gRPC / HTTP2 双向流** |
| **为什么不选 B** | ①浏览器不支持 gRPC-Web 的双向流（前端不直接用它，但工具链更重）；②Python gRPC 生态与 FastAPI 集成不如 WebSocket 直接；③**本项目不需要 IDL 代码生成**——两端同语言，直接共享 `protocol.py` 更简单 |
| **备选 C** | **每个请求开一条独立隧道连接** |
| **为什么不选 C** | ①连接建立成本高（TLS 握手 + `HELLO`）；②NAT 映射会因连接过多而失效；③**手机同时拉 30 张缩略图就是 30 条连接**，不可接受 |

### 5.5 图像处理

| 项 | 内容 |
|---|---|
| **选择** | **Pillow + pillow-heif** |
| **为什么选** | ①**Pillow 是 Python 图像处理的事实标准**：打开/缩放/转 WebP 都是一行；②**pillow-heif 补齐 HEIC/HEIF**：设计文档 §5.3 明确要求"HEIC/HEIF 必须支持：服务端用 `pillow-heif` 统一转成 WebP/JPEG 再给手机，否则安卓浏览器打不开 iPhone 传来的 HEIC"；③**EXIF 读取**：`PIL.Image.getexif()` 可直接读；④**PyInstaller 友好**：纯 Python + 预编译 wheel，无额外系统依赖（不像 ImageMagick 需要装外部程序） |
| **备选 A** | **ImageMagick / GraphicsMagick（通过 subprocess 调用）** |
| **为什么不选 A** | ①**需要外部可执行文件**，PyInstaller 打包要额外携带二进制，体积和兼容性都变差；②subprocess 调用有进程开销与路径转义风险；③HEIC 支持需要额外编译 ImageMagick 的 delegate |
| **备选 B** | **sharp（Node）/ libvips** |
| **为什么不选 B** | ①**原生编译依赖**，Windows 上打包与分发麻烦；②本项目已经选定 Python 后端（§5.1），跨语言调用不值得 |
| **备选 C** | **ffmpeg（带图像处理能力）** |
| **为什么不选 C** | ①**一期明确不含 ffmpeg**（需求 N-4）——它会显著增大打包体积与复杂度；②图片缩略图用 Pillow 更直接 |
| **代价** | ①Pillow 的 WebP 编码质量/速度略逊于 libvips，但 20 KB 的缩略图场景下无感知；②`pillow-heif` 需要额外安装（已在需求中确认为必须） |

### 5.6 云部署与 HTTPS

| 项 | 内容 |
|---|---|
| **选择** | **Docker + Docker Compose + Caddy 2** |
| **为什么选** | ①**Docker Compose 一把梭**：`relay` + `caddy` 两个服务，一条命令起（设计文档 §10.1 给了完整 compose 文件）；②**Caddy 自动 HTTPS**：自动申请并续期 Let's Encrypt 证书，**无需手工折腾 TLS**（设计文档 §10.1 原话），这是 Caddy 相对 Nginx 的最大优势；③**Caddyfile 极简**：3 行配置完成 TLS + 反向代理；④**环境一致性**：Docker 让"本机验证"与"云上运行"用同一镜像，**避免"在我机器上能跑"**（**注**：本条属二期 P1，一期不部署云端） |
| **备选 A** | **Nginx + certbot** |
| **为什么不选 A** | ①**证书管理要手工配置**：certbot 的续期钩子、reload 时机、失败处理都要自己写；②Nginx 配置更冗长；③**没有收益**——Caddy 在"自动 HTTPS + 反向代理"这个场景下完全覆盖 Nginx 的能力，且更省心 |
| **备选 B** | **直接跑 uvicorn + 手工配 TLS** |
| **为什么不选 B** | ①证书续期要自己写定时任务；②没有反向代理层，后续加静态资源托管、压缩、限流都要在应用里做；③**HTTPS 是一期硬要求**（需求 TC-8，因为 PWA/Service Worker/`wakeLock` 依赖安全上下文），不能出错 |
| **备选 C** | **云厂商托管容器服务（如阿里云容器实例）** |
| **为什么不选 C** | ①**贵**（违背 NFR-$-1）；②**复杂**（要配 VPC、镜像仓库、负载均衡），而需求只有 1 核 1 GB 的一个容器 |
| **代价** | ①Docker 在 1 核 1 GB 上有约 100–200 MB 额外开销——但 Relay 常驻仅 80–150 MB（设计文档 §3.4），1 GB 够用；②Caddy 占用额外内存约 30–50 MB |

### 5.7 电脑端打包与分发

| 项 | 内容 |
|---|---|
| **选择** | **PyInstaller `--onedir`** |
| **为什么选** | ①**设计文档 §10.2 明确指定**：`PyInstaller --onedir → PhotoBridge\PhotoBridge.exe`；②**`--onedir` 而非 `--onefile`**：`--onefile` 每次启动要解压到临时目录，**启动慢且容易被杀软误报**；`--onedir` 启动快、目录结构透明、便于排查；③**无需目标机器装 Python**：业主电脑上不需要配环境；④**一期不含 ffmpeg**，体积大幅减小（设计文档 §10.2 原话"体积小很多"） |
| **备选 A** | **`--onefile` 单文件** |
| **为什么不选 A** | ①启动时解压到 `%TEMP%`，**首次启动可能 3–10 秒**；②杀软对自解压 exe 的误报率高；③**托盘常驻程序只需要启动一次**，单文件的分发便利性没有价值（业主是自己装机，不是分发给用户） |
| **备选 B** | **Nuitka** |
| **为什么不选 B** | ①编译时间长（本项目依赖 Pillow/pillow-heif，编译可能要 10 分钟以上）；②对动态导入的支持不如 PyInstaller 成熟；③**收益是"更难反编译"**，而本项目不分发，无此需求 |
| **备选 C** | **直接分发 Python 源码 + 要求装 Python** |
| **为什么不选 C** | ①违背 DG-4（零运维）；②业主电脑上要维护虚拟环境、依赖版本、Python 版本，**这本身就是运维负担**；③托盘程序需要开机自启，exe 更干净 |
| **代价** | ①产物体积约 100–200 MB（Pillow + pillow-heif + FastAPI + uvicorn 等）；②**杀软可能误报**（需要指导业主加白名单）；③PyInstaller 对某些动态导入需要手工 `hiddenimports` 配置 |

### 5.8 其他关键依赖

| 用途 | 选择 | 为什么 | 备选与不选理由 |
|---|---|---|---|
| Windows 回收站删除 | **`send2trash`** | 设计文档 §8.4 第 3 条明确要求"删除只进回收站（`send2trash`），代码里不存在 `os.unlink` 路径"。它是跨平台的、纯 Python 的、久经考验的库 | 自研：要调 Win32 API，易错；`os.remove`：**违背硬约束，禁止** |
| 文件系统监听 | **`watchdog`** | 设计文档 §5.1 明确列出。跨平台、成熟、支持 Windows 的 `ReadDirectoryChangesW` | 轮询扫描：浪费 I/O 且有延迟；自研：要处理 Windows 特有 API |
| Windows 托盘 | **`pystray`**（建议） | 纯 Python、跨平台、与 PyInstaller 兼容性好 | `pywin32`：Windows 专属、API 冗长；`PyQt`：**体积巨大**（几十 MB），为托盘引入整个 GUI 框架不划算 |
| 数据库 | **Python 内置 `sqlite3`** | 无需额外依赖；WAL 模式直接 `PRAGMA` 开启 | SQLAlchemy：增加抽象层，而本项目表结构简单且需要精细控制 FTS5；**建议不用 ORM**，直接写 SQL（见 [05](05-数据库设计文档.md)） |
| HTTP/WS 客户端（电脑端隧道） | **`websockets`** | 与 asyncio 原生集成，轻量，PyInstaller 友好 | `requests`：不支持 WebSocket 且是同步的；`httpx`：能力更强但本项目隧道只用 WS |
| 前端 PWA | **`vite-plugin-pwa`** | 自动生成 Service Worker 与 manifest，支持 Workbox 的缓存策略 | 手写 SW：容易踩缓存失效的坑 |

## 6. 关键设计决策

> **格式**：决策 / 背景 / 备选方案 / 选择 / 理由 / 影响 / 何时可能推翻。
> 决策本身来自 [设计文档.md](../设计文档.md)；本文档补充**背景、被否方案与推翻条件**——这是设计文档没写清的部分。

### D-1 云桥接 vs 局域网直连

| 项 | 内容 |
|---|---|
| **决策** | 采用**云服务器中继**作为主通路，局域网直连降级为**加速路径** |
| **背景** | v0.1/v0.2 设计为"同一 Wi-Fi 下局域网直连"。但业主的核心诉求是"**我在外面**（4G）也能看照片"，而局域网方案要求手机与电脑在同一 Wi-Fi——**与诉求直接矛盾，等于没解决问题** |
| **备选 A** | 保持**局域网直连**（v0.2 方案） |
| **备选 B** | **云桥接**（v0.3 方案） |
| **备选 C** | **公网 IP + 端口映射 / DDNS** |
| **选择** | **B（云桥接）**，并保留局域网直连作为加速路径 |
| **理由** | ①**A 不满足核心诉求**：业主在 4G 下完全不可用；②**C 在家庭宽带环境下往往不可行**：多数运营商不提供公网 IPv4，且需要改路由器配置、暴露端口、应对动态 IP；③**B 的代价可控**：云只做转发，成本 ≈ ¥13/月；④**B 还带来意外收益**：云上有 HTTPS 域名 → 安全上下文 → PWA / Service Worker / `wakeLock` 全部可用（**这三条在 v0.2 的局域网 HTTP 方案里全都拿不到**，设计文档 §6.4 原话）；⑤**B 保留了 A 的优势**：局域网直连仍然可用，且优先级更高 |
| **影响** | ①必须实现隧道协议（多路复用 + 流控 + 重连），这是本项目最大的技术复杂度来源；②引入云服务器成本与运维；③必须保证"两条路 API 一致"（DP-4）；④前端需要通路选择器（L2 层） |
| **何时可能推翻** | ①若业主不再需要外网访问（**不太可能**，这是项目存在的理由）；②若有了公网 IP 且愿意维护端口映射（可简化为直连，但会失去 PWA 红利）；③若云服务成本超出接受范围（可换更便宜的方案，但**架构不变**） |

### D-2 反向隧道 vs 端口映射

| 项 | 内容 |
|---|---|
| **决策** | 电脑**主动外连**云端建立反向隧道；**不使用**公网 IP / 端口映射 / DDNS |
| **背景** | 云要能把手机的请求送到电脑，必须先建立"云 → 电脑"的路径。但电脑在家里的 NAT 之后，**外部无法主动连接它** |
| **备选 A** | **公网 IP + 端口映射**：路由器把 8787 端口映射到公网 |
| **备选 B** | **DDNS + 端口映射**：动态 IP 用域名跟踪，再映射端口 |
| **备选 C** | **反向隧道**：电脑主动连云，云复用这条已存在的连接 |
| **选择** | **C（反向隧道）** |
| **理由** | ①**不需要公网 IP**：设计文档 §2.1① 明确"这样家里不需要公网 IP、不需要端口映射、不需要 DDNS"；②**天然穿透 NAT**：出站连接不受 NAT 限制；③**穿透企业防火墙**：出站 443 与普通 HTTPS 无异；④**无端口暴露**：端口映射会把电脑服务暴露到公网，**任何扫描器都能发现**——这是显著的安全劣势；⑤**IP 变化无影响**：不需要 DDNS |
| **影响** | ①**必须实现隧道协议**（复杂度的主要来源）；②电脑必须**主动且持续**保持连接（心跳 25s）；③若 WebSocket 被拦，需要降级预案（SSE + 长轮询） |
| **何时可能推翻** | ①若家里有固定公网 IP 且业主愿意接受端口暴露风险（**不推荐**，安全性明显下降）；②若改用 UPnP 自动端口映射（仍有暴露风险） |

### D-3 云端零存储

| 项 | 内容 |
|---|---|
| **决策** | 云端**只转发，不落任何媒体字节**；不使用任何媒体缓存（含 CDN） |
| **背景** | 云服务器是转发的中转点，技术上完全可以顺手缓存照片来"提升体验"。但这个选择有深远的隐私与架构含义 |
| **备选 A** | **云端缓存缩略图**（甚至原图），提升重复访问速度 |
| **备选 B** | **云端零存储**（纯转发） |
| **选择** | **B（零存储）** |
| **理由** | ①**隐私底线**：设计文档 §2.1② 原话"这条是整个方案的隐私底线"，照片不进第三方；②**架构韧性（更关键的理由）**：云上没有任何不可再生数据，所以"云被墙/宕机/服务商跑路"**只是可用性问题，不是数据安全问题**——VPS 挂了换一台重建只要 10 分钟，**照片一张都不会丢**；③**这让选最便宜的 VPS 成为合理决策**（[VPS选购建议.md](../VPS选购建议.md) §3 把这一点列为"低风险"的理由）；④**省云磁盘**：20 GB 的 VPS 不需要扩容 |
| **影响** | ①**每次缩略图请求都要穿透到电脑**，即使手机已看过——所以**手机端 Service Worker 缓存变得至关重要**（设计文档 §9.3："手机 Service Worker 缓存该缩略图（二次浏览零流量）"）；②**必须强制流控**（credit window 8 MB），因为不能靠"落盘后慢慢发"缓解内存压力；③云端必须严格实现"流式转发不整体缓冲"；④**禁止 CDN**（设计文档 §8.5） |
| **何时可能推翻** | ①**理论上不会**——这是隐私与韧性的双重底线；②若二期上 E2E，云端即使缓存也只是密文，**但届时仍不会缓存**，因为没有收益（密文也要占磁盘） |

### D-4 单根库 vs 双根库

| 项 | 内容 |
|---|---|
| **决策** | **单根**：库根目录为 `D:\Photos`，三个子目录（`全部备份\`、`相册1\`、`青甘环线\`）通过 `root_id` + `rel_path` 统一管理 |
| **背景** | 业主的相册分散在三个子目录，历史上可能来自不同的整理阶段。设计上可以选择"把每个子目录当作独立的根"或"统一在一个根下" |
| **备选 A** | **双根/多根**：每个子目录独立配置为一个根，各有独立的权限与上传策略 |
| **备选 B** | **单根**：一个根目录，子目录只是路径的一部分 |
| **选择** | **B（单根）**，但数据模型保留 `root_id` 字段 |
| **理由** | ①**时间线要跨目录统一排序**：业主想看到的是"所有照片按时间排"，而不是"先选目录再看照片"。多根会让时间线要么跨根 UNION（复杂），要么强制先选根（体验差）；②**上传归档规则统一**：按 `年\年-月\` 归档，不区分来源目录；③**沙箱只需校验一个根**：多根会让越界检查逻辑复杂化（要判断"在哪个根内"）；④**数据模型保留 `root_id`**：这是 DP-7（为二期留接口）的体现——将来若要加第二个物理盘（如 `F:\照片`），**不需要改表结构** |
| **影响** | ①`media` 表有 `root_id` 但一期恒为同一个值；②`UNIQUE(root_id, rel_path)` 约束保证路径唯一；③`/api/timeline` 有 `root=` 过滤参数（设计文档 §7.2 的 API 表中确实有），用于将来多根时按根过滤 |
| **何时可能推翻** | ①若业主新增第二个物理盘/网络盘存放照片，且**权限策略不同**（如只读 vs 可写）；②若某个子目录需要独立的上传策略（如"全部备份"只读） |

### D-5 游标分页 vs OFFSET

| 项 | 内容 |
|---|---|
| **决策** | 时间线使用**游标分页**（`cursor` 编码上一页最后一条的 `taken_at` + `id`） |
| **背景** | 库中有 4915 张照片，按 100 张一页约 50 页。分页方式直接影响深翻页的体验 |
| **备选 A** | **OFFSET 分页**：`LIMIT 100 OFFSET 4000` |
| **备选 B** | **游标分页**：`WHERE (taken_at, id) < (?, ?) ORDER BY taken_at DESC, id DESC LIMIT 100` |
| **选择** | **B（游标分页）** |
| **理由** | ①**深翻页不退化**：`OFFSET 4000` 需要 SQLite 扫描并丢弃前 4000 行；游标分页**每次都直接走索引定位**——这正是 AC-2.7（第 50 页与首页差异 ≤ 50 ms）的判据来源；②**翻页期间数据变化不会错位**：索引器在后台运行，翻页时若有新照片入库，`OFFSET` 分页会导致**重复或漏掉**照片（经典的"分页漂移"）；游标分页天然免疫；③**实现简单**：索引 `idx_media_timeline(taken_at DESC, id DESC)` 已存在（设计文档 §5.2），游标条件直接命中它；④**前端体验一致**：无限滚动场景下游标比页码更自然 |
| **影响** | ①**不能跳页**——但前端只有"年月快速跳转"，实现方式是**按日期定位游标**而非页码跳转，所以不受影响；②游标需要**编码**（通常是 base64 的 `taken_at\|id`），且应**防篡改**；③需要处理"游标指向的记录已被删除"的情况（用 `<` 比较而非 `=` 查找即可自然处理） |
| **何时可能推翻** | ①若前端需要"跳到第 N 页"的页码 UI（**一期没有这个需求**）；②若数据量小到 `OFFSET` 也不慢（**但游标分页成本几乎为零，没有理由退回**） |

### D-6 WebSocket vs SSE

| 项 | 内容 |
|---|---|
| **决策** | 隧道使用 **WebSocket（WSS）**；**SSE 仅作为降级预案** |
| **背景** | 隧道需要双向传输：云→电脑发请求（HEAD/BODY/END）、电脑→云回响应（HEAD/BODY/END）。同时需要承载任意并发（30 张缩略图）与流控 |
| **备选 A** | **SSE（云→电脑）+ POST（电脑→云）** 双通道 |
| **备选 B** | **WebSocket** 单连接双向 |
| **选择** | **B（WebSocket）**，A 作为降级 |
| **理由** | ①**双向单连接**：A 方案需要两条独立通道，**流控窗口要在两条通道上协调**（请求体在 POST 通道、响应体在 SSE 通道），复杂度显著上升；②**多路复用天然**：WebSocket 是字节流，`req_id` 直接区分并发；A 方案下 SSE 是单流，多个响应要**自己在一维字节流上交织**（本质是重新发明多路复用）；③**二进制帧**：自定义帧格式是二进制的，WebSocket binary frame 直接承载；SSE 是文本协议，二进制要 base64（**膨胀 33%**，直接伤害带宽预算）；④**延迟**：A 方案的 POST 方向每次要新建 HTTP 请求；⑤**FastAPI 原生支持** |
| **影响** | ①**若企业代理拦 WebSocket，需要降级**——因此 `protocol.py` 必须**与承载方式解耦**（DP-3），降级时帧格式不变；②需要自己实现心跳（设计文档定义了应用层 `PING` 0x09 / `PONG` 0x0A 帧，便于两端统一）；③需要自己实现重连与 `HELLO` 重放 |
| **何时可能推翻** | ①若实测发现目标网络环境**普遍拦截 WebSocket**（届时把降级方案提为主方案）；②若改用 HTTP/2 双向流（浏览器侧与 Python 侧工具链都更重） |

### D-7 HTTPS vs HTTP

| 项 | 内容 |
|---|---|
| **决策** | **一期用局域网 HTTP**（私网地址，无域名无证书）；**二期 P1 接入云中继时升级为 HTTPS**（域名 + Caddy 自动 Let's Encrypt） |
| **背景** | v0.2 的局域网方案只能用 HTTP，因为内网 IP 无法申请可信证书。这导致浏览器**不进入安全上下文** |
| **备选 A** | **全 HTTP**（局域网 HTTP，云端也用 HTTP） |
| **备选 B** | **云端 HTTPS + 局域网 HTTP** |
| **选择** | **一期 A → 二期 B**（架构调整后的分期选择，见下方「决策变更」） |
| **理由** | ①**一期的前提变了**：架构改为"局域网优先、远程留接口"后，一期**没有云端也没有域名**，因此 HTTPS 这个选项在一期根本不存在，不是"选择了 HTTP"而是"只有 HTTP"；②**HTTPS 带来的三项能力在一期全部无法兑现**：Service Worker 与完整 PWA 只在安全上下文可用，而一期没有 HTTPS；`wakeLock` 同理。**但一期也不依赖它们** —— 局域网 1 Gbps，缓存省下的流量毫无意义；上传时手机通常就在电脑旁边，息屏风险远小于走 4G 的场景；③**自签证书不划算**：安卓要装根证书（设置里翻好几层），换来的是一期用不上的能力；④**二期照搬原方案**：域名 ¥1–10 + Caddy 自动证书，成本几乎为零，届时 Service Worker 缓存才真正有意义（走公网时它服务于 DP-1 与 DP-9 省流量） |
| **影响** | ①**一期没有 Service Worker、没有完整 PWA、没有 `wakeLock`**，这些能力推迟到二期；②**手机端网页必须能在非安全上下文下工作**（不能用 `navigator.serviceWorker`、不能用 `wakeLock`，代码里要判空降级）；③一期**不需要域名、不需要云服务器、不需要备案**，成本 ¥0；④原 Q-26「HTTPS 页面请求局域网 HTTP 会被 Mixed Content 拦截」的架构风险**在一期自动消失** —— 一期页面本身就是 HTTP，不存在混合内容；二期若采用"HTTPS 云端页面 + HTTP 局域网直连"的双通路，该风险会重新出现，届时需按 06 附录 A D14 做验证实验 |
| **何时可能推翻** | ①若一期就想要 PWA 离线能力（**不推荐**：局域网下没有收益，却要引入域名 + 证书 + 备案的复杂度）；②若改用纯 IP + 自签证书（设计文档 §3.3 明确"**不推荐**"，因为手机要装根证书，很麻烦） |

> **决策变更记录（2026）**：本节原选择 **B（云端 HTTPS + 局域网 HTTP）**，前提是"一期就有云桥接"。
> 架构调整为「局域网优先、远程留接口」后，一期不再包含云端，**B 的后半段（云端 HTTPS）没有落地对象**，
> 因此一期实际执行的是 **A（全 HTTP）**，B 整体推迟到二期 P1。
> **这不是"放弃了 HTTPS"**，而是"HTTPS 的收益在一期无法兑现、成本在一期无法摊薄"。

### D-8 一期不做视频

| 项 | 内容 |
|---|---|
| **决策** | 一期**只做图片**，明确不含视频索引/播放/转码，**不引入 ffmpeg** |
| **背景** | 业主库中实测有 **12 个 `.mov` + 3 个 `.mp4`**，共 15 个视频文件（占 4952 个文件的 0.3%）。视频功能需要抽帧、封面、Range 播放、转码 |
| **备选 A** | **一期就做视频** |
| **备选 B** | **一期只做图片** |
| **选择** | **B** |
| **理由** | ①**工作量不是一个量级**：视频需要封面抽帧、`Range` 请求支持、按需转码，而转码必须引入 ffmpeg（设计文档 §1.2 二期内容明确列出这三项）；②**ffmpeg 的代价**：显著增大 PyInstaller 产物体积（几十 MB 到上百 MB），且带来平台相关的二进制兼容问题——设计文档 §10.2 明确"**一期不含 ffmpeg，体积小很多**"；③**收益极低**：15 个视频占 0.3%，且业主的核心诉求是"看照片"；④**云带宽不支持**：3 Mbps 下播放视频体验极差（设计文档 §1.3 的非功能目标里没有任何视频相关指标）；⑤**业主已明确确认**（设计文档 §15.1 第 4 项："**一期只做图片**，完全不含视频"） |
| **影响** | ①索引器白名单**不含视频扩展名**，15 个视频文件**不出现在时间线**；②上传白名单同样不含视频，**上传视频会被拒绝**；③**Live Photo 只处理静态图部分**，配套 `.mov` 不索引、不播放（见 [01](01-需求规格说明书.md) §6.3）；④`media.kind` 字段一期**恒为 `'image'`**——这是 DP-7 的体现，二期加视频**不需要改表结构**；⑤`caps:["image"]` 在 `HELLO` 帧中上报，为二期 `caps:["image","video"]` 预留 |
| **何时可能推翻** | ①**二期**（设计文档 §1.2 已规划：视频索引、封面抽帧、Range 播放、按需转码）；②若业主中途有大量视频需要管理（届时评估是否提前到一期，但**需要重新评估 ffmpeg 打包方案**） |

### D-9 一期不做 E2E 加密

| 项 | 内容 |
|---|---|
| **决策** | 一期**不做端到端加密**；二期做。但**协议从一期就预留** `flags` 位与 `enc` 字段 |
| **背景** | 云端终止 TLS，因此云"理论上"能看到明文照片。威胁模型是"云服务器被入侵"或"云服务商偷看" |
| **备选 A** | **一期就做 E2E** |
| **备选 B** | **一期不做，二期做（协议预留）** |
| **选择** | **B** |
| **理由** | ①**威胁模型部分不成立**：云是业主自己的 VPS，**"云服务商偷看"在自建场景下不成立**（设计文档 §15.2 第 1 点）；②**一期最大的风险是架构不成立，不是隐私**：隧道多路复用 + 流控 + 断点续传这套东西本身就有不少坑，再叠加密钥协商、会话轮换、重放防护，**会把调试难度翻倍，而收益在当前场景下很低**（设计文档 §15.2 第 2 点，这是最核心理由）；③**二期成本可控**：帧头带 `flags` 位，`REQ_HEAD` 里带 `enc` 字段，**二期只需填充实现，不用改协议结构、不用改前端、不用改云端转发逻辑**（设计文档 §15.2 第 3 点）——这正是 DP-3 + DP-7 的价值体现；④**云不落盘**（D-3）大幅降低了明文暴露的持续时间 |
| **影响** | ①**云上能看到明文照片**——这是**已知且明确接受**的安全缺口（见 §10）；②`protocol.py` 的帧头必须**预留 `flags` 位**，`REQ_HEAD` 的 JSON 必须**预留 `enc` 字段**——这两个字段一期不填，但**必须存在**；③二期的密钥协商（X25519 + HKDF + AES-256-GCM）**不需要改动云端的转发逻辑**，只在两端加解密 |
| **何时可能推翻** | ①**二期**（设计文档 §15.2 已给出完整设计：配对时电脑生成 X25519 密钥对，私钥永不离开电脑；手机↔电脑 ECDH → HKDF-SHA256 → AES-256-GCM 会话密钥，每设备独立定期轮换；云可见 `device_id`/路径/长度/时间戳，不可见照片内容/EXIF/文件名）；②若业主中途改变对威胁模型的判断（**可随时推翻**，设计文档 §15.2 明确"你可随时推翻"） |

### D-10 允许写操作（删除/移动/改名）用约束兜底

| 项 | 内容 |
|---|---|
| **决策** | **允许**删除（进回收站）、移动、改名、打标签相册；风险用**四条硬约束**兜住 |
| **背景** | 写权限开放是本项目的**最大风险点**——一个路径拼接漏洞或一个逻辑错误就可能损坏业主不可再生的照片库。但只读会让产品价值大幅缩水（无法整理、无法删掉拍糊的） |
| **备选 A** | **只读**（不允许任何写操作） |
| **备选 B** | **允许写操作 + 四条硬约束** |
| **选择** | **B**（业主已确认，设计文档 §15.1 第 7 项） |
| **理由** | ①**只读不可接受**：业主明确需要整理照片（删掉拍糊的、把照片归类）；②**风险可以用机制兜住，而不是靠"小心"**——机制可以测试，小心不能；③**四条硬约束覆盖了主要故障模式**：越界（沙箱）、覆盖（只新增）、误删（回收站）、无痕（审计）；④**"失败安全优先"原则（DP-2）的直接应用**：所有失败路径都导向"数据完好" |
| **四条硬约束** | 1. 所有文件操作**必须过沙箱**，越界一律拒绝<br>2. 上传**只新增不覆盖**：同名追加 `_1`/`_2`；`sha256` 命中判重丢弃；**任何情况下不把新文件 rename 到已存在文件上**<br>3. 删除**只进回收站**（`send2trash`），**代码里不存在 `os.unlink` 路径**<br>4. 删除/移动**写审计日志** `data/audit.log`，托盘面板可查看 |
| **影响** | ①`sandbox.py` 成为**安全核心**，必须有完整的逃逸测试用例集（设计文档 §8.1 已列出：`../../etc/passwd`、`C:\Windows\System32`、`\\?\GLOBALROOT\...`、`a:b`、`CON`、软链接外指、中文路径、超长路径）；②**代码审查必须验证"不存在 `os.unlink` 路径"**；③审计日志成为**不可重建数据**（见 §4.3）；④需要一个"撤销删除"的说明（去 Windows 回收站还原） |
| **何时可能推翻** | ①若出现**任何一次**数据事故，立即收紧为只读并复盘；②若沙箱测试无法覆盖 Windows 的所有路径怪癖，考虑改用**白名单目录 + 只读挂载**的更强隔离 |

### D-11 上传直接进库（不设 Inbox）

| 项 | 内容 |
|---|---|
| **决策** | 上传**直接进库** `D:\Photos`，按 `年\年-月\` 自动归档；**不设独立 Inbox 目录** |
| **背景** | 常见设计是"上传先进 Inbox/待整理目录，再由用户手动归类"。动机是"避免自动归档出错污染主库" |
| **备选 A** | **Inbox 模式**：上传进 `Inbox\`，用户手动整理到目标目录 |
| **备选 B** | **直接进库**：按 EXIF `taken_at` 自动归档到 `年\年-月\` |
| **选择** | **B**（业主已确认） |
| **理由** | ①**多一步整理 = 多一步不会做的事**：业主的真实痛点是"照片散在手机里**从未归集**"（见 [01](01-需求规格说明书.md) US-3）。如果上传后还要手动归位，**这套系统最终不会被使用**——这是最核心的理由；②**归档规则是确定的**：`年\年-月\` 由 EXIF `taken_at` 唯一决定，**不需要人工判断**；③**风险已被其他约束兜住**：不覆盖 + 加序号 + `sha256` 去重 + 原子落盘 + 审计留痕（与 D-10 的四条硬约束互补）；④**省一层目录**：Inbox 会带来"临时区 vs Inbox vs 正式库"三个位置，增加状态复杂度 |
| **影响** | ①归档模块（`archive.py`）的**正确性直接决定相册的整洁度**，必须仔细测试（EXIF 降级链、冲突序号、原子落盘）；②**上传的 `target_dir` 参数**（设计文档 §7.2 的 `POST /api/uploads/init` 有 `target_dir?`）允许指定目标目录，但默认走自动归档；③`<库根>/.photobridge_tmp` 仍然存在——它是**技术性的临时区**（保证原子性），与 Inbox 的语义不同：**用户永远不会看到它，且它的内容会被自动清理** |
| **何时可能推翻** | ①若归档规则频繁出错（如 EXIF 时间大量异常导致目录混乱），可加 Inbox 作为缓冲；②若业主需要"先上传再决定放哪"的工作流（**目前没有这个需求**） |

### 6.1 决策之间的关系

```
D-1 云桥接（根本决策）
 ├─► D-2 反向隧道      （如何建立通路）
 ├─► D-3 云端零存储    （云的职责边界）
 ├─► D-6 WebSocket     （用什么承载）
 ├─► D-7 HTTPS         （安全上下文 → PWA/SW/wakeLock）
 └─► D-9 不做 E2E      （一期接受明文）

D-3 云端零存储
 └─► 强化 D-7 的必要性（手机端 SW 缓存成为唯一缓存层）

D-10 允许写操作
 ├─► 沙箱成为安全核心
 └─► D-11 上传直接进库（风险由 D-10 的约束兜住）

D-5 游标分页 ◄── 依赖 §8.3 的 idx_media_timeline 索引
D-8 不做视频 ◄── 由 D-1 的带宽约束（L-1）与打包约束（§5.7）共同支撑
```

**为什么画这张图**：决策不是孤立的选择，而是**有依赖关系的网络**。当某个决策被推翻时（例如业主突然要求 E2E），受影响的决策会沿着箭头传导——D-9 推翻后，D-3（云零存储）从"隐私底线"降级为"架构韧性措施"，D-7（HTTPS）仍然必要（因为 SW 缓存），但 D-6（WebSocket）不受影响（因为协议已预留 `flags`/`enc`）。**这就是"协议预留"的工程价值**。

### 7.4 部署步骤概览

> 详细步骤见 [08-部署与运维手册](08-部署与运维手册.md)。这里只列架构相关的要点。

| 阶段 | 目标 | 关键产物 | 是否需要 VPS/域名 |
|---|---|---|---|
| **L1–L3** | 本机跑通沙箱/索引/缩略图/浏览 API，手机在同 Wi-Fi 下打开照片墙 | `PhotoBridge.exe`（或 `python -m backend.app.main`） | **不需要**（架构调整为局域网优先后，一期全程零外部依赖） |
| **L4–L5** | 手机端网页 + 上传归档 | 前端 `dist/` + 上传会话 | **不需要** |
| **L6** | 交付 | 打包 exe + 托盘 + 开机自启 | **不需要** |
| **P1**（二期） | 跨网络访问 | 云 Relay + 域名 + 证书 | **需要** |

**为什么一期完全不需要 VPS**：架构调整为"局域网优先、远程留接口"后，一期的主通路是
**手机与电脑在同一 Wi-Fi 下的直连 HTTP**，照片不出局域网，也没有任何需要公网可达的组件。
支撑二期云桥接的抽象（`shared/protocol.py` 帧协议、`transports/base.py` 传输接口、
`Ctx`/`Reply` 协议无关中间表示）在一期就已建好，因此**二期接隧道时业务代码零改动**，
不需要在一期就买服务器做"预留"。

## 8. 数据架构概述

> 表结构、字段、索引、迁移的详细定义见 [05-数据库设计文档](05-数据库设计文档.md)。这里只说明**三个存储各自存什么、生命周期如何**。

### 8.1 三个数据存储

| 存储 | 位置 | 内容 | 大小 | 生命周期 |
|---|---|---|---|---|
| **① 云端 SQLite** | 云 VPS `/data/cloud.db` | 5 张表：`accounts`、`devices`、`clients`、`pair_codes`、`traffic` | **< 1 MB** | 可随时重建（代价：重新注册账号与配对） |
| **② 电脑端 SQLite** | 电脑 `data/photobridge.db` | 4 张表 + 1 个 FTS5 虚拟表：`media`、`upload_sessions`、`settings`、`audit_log`、`media_fts` | 约 5–20 MB | **可从文件系统重建**（重新扫描即可） |
| **③ 文件系统** | 电脑 `D:\Photos` + `data\` | 照片本体 + 缩略图缓存 + 上传临时区 + 审计日志 | 照片：取决于库大小<br>缩略图：约 1.1 GB<br>临时区：通常 < 1 GB | **照片本体：永久，唯一不可再生**<br>缩略图：可重建<br>临时区：自动清理<br>审计日志：长期保留 |

### 8.2 云端数据（对应设计文档 §3.2）

| 表 | 存什么 | 为什么需要 | 丢失后果 |
|---|---|---|---|
| `accounts` | 账号（`id`、`email`、`pass_hash`、`created_at`、`plan`） | 登录凭证 | 重新创建账号（手工，无注册流程） |
| `devices` | 每台电脑一条：`id`、`account_id`、`name`、**`agent_token`**、`version`、`last_seen`、**`last_lan`**、`created_at`、`revoked` | 设备注册表 + 隧道鉴权 + **同网直连地址**（`last_lan` 是 JSON 数组，如 `["192.0.2.10:8787"]`） | 电脑需重新注册（重新配对手机） |
| `clients` | 每台手机一条：`id`、`device_id`、`name`、**`token_hash`**、`last_seen`、`created_at`、`revoked` | 手机鉴权与撤销 | 手机需重新配对 |
| `pair_codes` | `code`（6 位）、`device_id`、`expires_at`、`tries` | 配对流程 | 无影响（重新生成） |
| `traffic` | `device_id`、`day`、`bytes_in`、`bytes_out` | 带宽计数与用量展示 | 无影响（统计丢失） |

**★ 关键**：**没有 `media` 表**。云不知道业主有哪些照片（设计文档 §3.2 原话"注意：**没有 media 表**。云不知道你有哪些照片"）。

**云端内存状态（不入库）**：`device_id → 活跃隧道连接` 的映射，**断开即移除**（设计文档 §4.1）。这是"电脑是否在线"的**唯一判据**——注意它刻意不入库，因为进程重启后连接必然失效，持久化反而会制造"看似在线实则离线"的错误状态。

### 8.3 电脑端数据（对应设计文档 §5.2）

| 表 | 存什么 | 关键字段/索引 | 可重建 |
|---|---|---|---|
| `media` | 每张图片一条：路径、大小、`mtime`、`sha256`、**`taken_at`**、`taken_src`、EXIF（机型/镜头/ISO/光圈/曝光/焦距/GPS/方向）、宽高、`thumb_state`、`missing` | 索引：`idx_media_timeline(taken_at DESC, id DESC)`、`idx_media_root(root_id, rel_path)`、`idx_media_sha(sha256)`<br>约束：`UNIQUE(root_id, rel_path)` | ✅ 可重扫重建 |
| `media_fts` | FTS5 虚拟表：`file_name`、`rel_path`、`camera` | `content='media'`, `content_rowid='id'` | ✅ 可重建 |
| `upload_sessions` | 上传会话：`id`、`root_id`、`target_rel`、`temp_path`、`total_size`、`received`、`chunk_size`、`sha256`、`declared_name`、`taken_at`、`created_at`、`expires_at`、`status` | 主键 `id` | ✅ 可丢弃（未完成的上传作废） |
| `settings` | 键值对 | 主键 `key` | ⚠️ 部分需保留（如库根目录配置） |
| `audit_log` | 写操作留痕：`id`、`ts`、`device_name`、`action`、`rel_path`、`detail` | 主键 `id` | ❌ **不可重建**（但非关键数据） |

**为什么 `taken_at` 是排序主键**：相册的核心体验是"按拍摄时间回忆"，而不是按文件拷贝时间（`mtime`）。索引 `idx_media_timeline(taken_at DESC, id DESC)` 正是为游标分页（D-5）设计的——它让 `WHERE (taken_at, id) < (?, ?)` 直接走索引。**如果只按 `taken_at` 排序，同一秒内多张照片的顺序会不稳定**，翻页时可能重复或漏掉，所以必须把 `id` 作为第二排序键。

**为什么 `taken_src` 必须存在**：有些图（截图、下载图、被工具重存过的图）**没有 EXIF**。如果没有降级链（`exif` → `filename` → `mtime`），这些图会掉出时间线或排到 1970 年。`taken_src` 记录了降级的来源，**便于排查"这张照片为什么排在错误的位置"**。

### 8.4 数据生命周期

```
【照片本体】创建（上传/手动拷入）→ 索引 → 浏览/下载 → 可选删除（进回收站）
            ★ 永不自动删除、永不覆盖、永不修改内容
            ★ 唯一不可再生数据

【索引记录】创建（索引器）→ 更新（mtime 变化/watchdog）→ 标记 missing（文件消失）
            → 可全量重建（重扫）

【缩略图】  按需生成 → 缓存 → （二期可加 LRU 淘汰，见附录 A Q-6）
            → 可全量重建

【上传会话】init → 分片追加 → complete（转正）/ 过期清理 / 显式取消
            ★ 未完成会话的临时文件在 expires_at 后被清理

【审计日志】追加写入 → 按月轮转（建议）→ 长期保留
            ★ 不可重建，但非关键

【云端数据】账号/设备/配对码/流量 → 长期保留 → 可全量重建（重新配对）
```

### 8.5 数据一致性与并发

| 场景 | 风险 | 设计对策 |
|---|---|---|
| 索引器写库 与 前端读库 并发 | SQLite 单写者导致读阻塞 | **开启 WAL 模式** |
| 索引器扫描 与 用户上传 并发 | 同一文件被两条路径处理 | 上传完成后**主动入库**（不等下次扫描）；扫描时跳过 `.photobridge_tmp`（已在 `DEFAULT_EXCLUDE_DIRS`） |
| 两次上传同一文件并发 | 产生两份 | `sha256` 秒传 + `UNIQUE(root_id, rel_path)` 约束 + 冲突加序号 |
| 索引器扫描 与 文件被手动删除 并发 | 索引记录指向不存在的文件 | 扫描时校验存在性，标记 `missing=1`；读取时二次校验 |
| 上传 `complete` 与 目标目录不存在 | `os.replace` 失败 | 归档时**确保父目录存在**（自动创建） |
| 云端连接 map 与 实际连接 并发 | 陈旧映射导致请求发往已断开的连接 | 断开时**立即**从 map 移除；发帧失败时也移除并回 `device_offline` |
| 上传临时区与目标不同卷 | `os.replace` 失去原子性 | **未解决，见附录 A Q-35** |

## 9. 非功能设计概览

> 具体指标与验收标准见 [01-需求规格说明书](01-需求规格说明书.md) §5。这里说明**用什么机制达成这些指标**。

### 9.1 性能策略

| 指标 | 机制 | 为什么这样设计 |
|---|---|---|
| 首屏 2.5 秒（100 张缩略图） | ①三级渐进加载（320 模糊占位 → 1600 预览 → 后台原图）；②`IntersectionObserver` 懒加载（只加载可见项）；③多路复用并行请求；④`Service Worker` 缓存 | **用户感知的"首屏"是可见区域**，不是 100 张全部下载完。先给低质量占位，感知速度立刻提升 |
| 单张缩略图 ≤ 30 KB | 320px WebP（有损） | WebP 在同质量下比 JPEG 小 25–35%；320px 是手机 3 列网格的合适尺寸 |
| 已缓存缩略图 ≤ 100 ms | 磁盘缓存 + 直接流式读文件（不走图像库） | 缓存命中时**不应有任何图像解码开销** |
| 未缓存缩略图 ≤ 500 ms | 缩略图工作线程池（避免阻塞事件循环） | Pillow 生成是同步 CPU 操作，必须放线程池 |
| 深翻页不退化 | 游标分页（D-5）+ `idx_media_timeline` 索引 | 见 D-5 |
| 上传 ≥ 1.5 MB/s | ①分片（云端 2 MB / 直连 8 MB）；②并行 ≤ 3 个分片；③流式转发不缓冲 | 小分片在高 RTT 窄带宽下吞吐更稳（设计文档 §7.2） |
| 大文件传输不爆内存 | **credit window 流控**（8 MB）+ 流式转发 | **必须实现**（设计文档 §4.3："没有流控的话……会把 1 GB 内存的 VPS 撑爆"） |
| 深翻页与首屏并行不互相阻塞 | 多路复用（`req_id`）+ 每 `req_id` 独立信用窗口 | 一个慢请求耗尽自己的窗口时，其他 `req_id` 不受影响（AC-1.8） |

### 9.2 可靠性策略

| 风险 | 机制 | 为什么这样设计 |
|---|---|---|
| 隧道断开 | 指数退避重连（1s→2s→4s→…→60s 封顶，**永不放弃**）+ 重连后重新 `HELLO` | 家庭网络抖动是常态；"永不放弃"保证无人值守时也能自愈 |
| 空闲被中间设备掐断 | 应用层心跳 25 秒（`PING`/`PONG` 帧 0x09/0x0A） | 许多 NAT/代理会在 30–60 秒无流量时回收连接 |
| 云侧连接表陈旧 | 断开**立即**从内存 map 移除；发帧失败也移除 | 陈旧映射会让请求发往死连接，表现为"卡住"而非"报错" |
| 上传中断 | 分片幂等 + `GET /api/uploads/{id}` 查 `offset` 续传 | 分片天然幂等，重传一片无害；移动网络下断网是常态 |
| 手机息屏中断上传 | `wakeLock`（HTTPS 下可用） | 这是 D-7（HTTPS）带来的直接收益 |
| 上传崩溃产生半截文件 | 临时区隔离 + 校验通过后才 `os.replace` | 库目录中**永远不出现未完成文件**（AC-3.8） |
| 覆盖已有照片 | 只新增不覆盖 + 冲突加序号 + `sha256` 去重 | 见 D-10 硬约束 2 |
| 误删 | `send2trash` 只进回收站；代码中不存在 `os.unlink` 路径 | 见 D-10 硬约束 3 |
| 删除无痕 | 审计日志 | 见 D-10 硬约束 4 |
| 电脑离线 | 云侧查内存 map 立即返回 `503 device_offline`；UI 明确提示 + "重试"；失败状态不缓存超过 30 秒 | 显式失败优于静默等待（DP-5） |
| 云服务器宕机 | 局域网直连仍可用；云上数据可重建 | 架构韧性的体现（D-3） |
| 索引库损坏 | 可全量重扫重建 | 索引是**派生数据**，不是权威数据 |

### 9.3 安全策略

| 层 | 机制 | 为什么 |
|---|---|---|
| **路径层** | `sandbox.py`：所有文件访问的唯一入口；拒绝绝对路径/盘符/UNC/`..`/NTFS 数据流/Windows 保留名/超长段/非法字符；逐段检查 symlink/junction/reparse point；`os.path.commonpath` 断言在根内（大小写不敏感） | 写权限开放后，**沙箱是唯一防线**（D-10）。Windows 路径语义坑多，必须逐条拒绝 |
| **认证层** | 三层凭证：`agent_token`（电脑↔云，长期）、`client_token`（手机↔云，90 天，可撤销）、直连复用 `client_token` | 见 [01](01-需求规格说明书.md) P1-5 |
| **授权层** | `client_token` **绑定单台电脑**；越权检查：token 的 device 必须等于 URL 中的 device | 防止"配对了一台电脑就能访问所有电脑" |
| **配对层** | 6 位配对码 + 5 分钟有效 + 错 5 次锁 10 分钟 | 带外信道（人在电脑前）的物理在场证明 |
| **传输层** | 全程 TLS（手机↔云 `https`、电脑↔云 `wss`） | 防中间人；同时获得安全上下文（D-7） |
| **限流层** | 单 client 120 req/s；上传并发 ≤ 3；配对码爆破防护 | 防止单点滥用与爆破 |
| **网络层** | 电脑本地服务只监听私网，启动时检测并拒绝在公网 IP 上绑定 | 防止意外暴露 |
| **数据层** | 云零存储（D-3）；禁止 CDN；日志只记元数据 | 隐私底线 |
| **运维层** | 依赖锁版本；`agent_token` 与配置文件权限收紧；密钥不入源码 | 减少供应链与配置风险 |
| **一期缺口** | **云上可见明文照片** | 一期明确接受（D-9），二期 E2E |

### 9.4 可扩展性（二期怎么接）

| 二期功能 | 一期预留 | 需要改动 |
|---|---|---|
| **视频索引/播放/转码** | `media.kind` 字段（一期恒为 `'image'`）；`HELLO.caps:["image"]` | ①白名单加视频扩展名；②`kind` 填 `'video'`；③引入 ffmpeg（PyInstaller 打包调整）；④前端加播放器；**表结构不变** |
| **E2E 加密** | 帧头 `flags` 位；`REQ_HEAD.enc` 字段 | ①配对时交换 X25519 公钥；②两端加解密；**云端转发逻辑不变、协议结构不变、前端不变**（设计文档 §15.2 第 3 点） |
| **多电脑设备** | 云端 `devices` 表天然支持多行；`/d/{device_id}/` 已按设备区分 | ①前端加设备切换 UI；**后端几乎不变** |
| **多根库** | `media.root_id` 字段；`/api/timeline?root=` 参数 | ①配置支持多个根；②沙箱支持多根校验；**表结构不变** |
| **相册/标签** | **无预留**（见 [01](01-需求规格说明书.md) Q-2） | 需新增 `albums`/`tags`/`album_items` 表 + 迁移脚本 + API |
| **地图视图** | `media.gps_lat`/`gps_lon` 字段已存在 | ①加聚合查询 API；②前端地图组件 |
| **重复文件查找** | `idx_media_sha(sha256)` 索引已存在 | ①开启 `hash_on_index`（全库算 sha256）；②加重复查询 API |
| **分享链接** | **无预留** | 需设计"无凭证访问"的权限模型（会与三层鉴权冲突，需仔细设计） |
| **SSE 降级（应对 WebSocket 被拦）** | `protocol.py` 与承载方式解耦（DP-3） | ①实现 SSE + POST 承载；②帧格式不变 |

**为什么一期的预留是"字段级"而不是"代码级"**：预留字段的成本几乎为零（一个列、一个 JSON 键），但**事后改协议/表结构的成本极高**（要同时改两端 + 前端 + 测试 + 迁移脚本）。而提前实现功能代码是为**不确定的需求**付**确定的成本**——这是 DP-7 的核心。

## 10. 已知设计局限

> **诚实列出这套设计的弱点。** 这些不是"待办事项"，而是**在当前约束下主动接受的取舍**。

| # | 局限 | 具体表现 | 为什么会这样（根因） | 缓解手段 | 能否根本解决 |
|---|---|---|---|---|---|
| **L-1** | **云带宽是硬瓶颈** | 3 Mbps 下下载一张 4 MB 原图要 11 秒；批量下载原图体验差 | 云带宽是**花钱买的物理资源**，且是最贵的（设计文档 §3.4："3 Mbps ≈ 375 KB/s"） | ①缩略图极致压缩（浏览只需 20 KB/张）；②**局域网直连优先**（在家不受云带宽限制）；③三级渐进加载（浏览不拉原图）；④建议 5–10 Mbps 套餐 | ❌ **不能**。这是物理限制。只能通过"少走云"（局域网直连）和"少传字节"（缩略图）绕开 |
| **L-2** | **电脑必须开机** | 电脑关机/睡眠时，云端访问返回 503 | 数据全在电脑上（这是 DP-1 的另一面） | ①UI 明确提示"电脑离线" + "重试"；②局域网直连在电脑开机时仍可用（关机时同样不可用）；③可考虑低功耗 NAS 常驻（设计文档 §14 风险表提到） | ⚠️ **部分**。可改用低功耗常驻设备（NAS/迷你主机），但**"数据在本地"这个前提不变**，所以"设备必须在线"是必然的 |
| **L-3** | **云端能看到明文照片** | 云终止 TLS，理论上能看到照片内容、EXIF、文件名 | 一期不做 E2E（D-9），因为一期最大风险是"架构是否成立"而非隐私 | ①云是业主自己的 VPS（"云服务商偷看"不成立）；②**云不落盘**（D-3），明文只在内存中短暂存在；③协议已预留 `flags`/`enc`（二期 E2E 不改协议） | ✅ **能**。二期 E2E（X25519 + HKDF + AES-256-GCM），设计文档 §15.2 已给出完整方案 |
| **L-4** | **家庭宽带上行限制下载速度** | 手机拉原图慢——瓶颈其实在**你家宽带的上行**（通常 30–50 Mbps），不在 VPS | 数据从家里发出，必须经过家庭宽带上行 | ①局域网直连（在家完全绕过）；②缩略图方案（浏览不需要原图）；③升级宽带套餐（[VPS选购建议.md](../VPS选购建议.md) §7 明确建议"钱该花在保证家里宽带上传速度上"） | ❌ **不能**（除非升级宽带）。这是**比 VPS 带宽更本质的瓶颈** |
| **L-5** | **WebSocket 可能被拦截** | 某些企业代理、公共 Wi-Fi 会拦 WebSocket | 中间设备对 WebSocket 的识别与策略不可控 | ①走 443 + TLS，与普通 HTTPS 流量无异（多数情况放行）；②协议支持降级为 SSE + POST 长轮询，**帧格式不变** | ⚠️ **部分**。降级方案可用，但复杂度上升（见附录 A Q-16） |
| **L-6** | **无断点续传的下载** | 下载原图中断后需从头重来 | 一期只为**上传**实现了分片与续传（上传是移动网络下的高频场景，下载是低频场景） | ①下载受限于家庭宽带上行（L-4），本身较慢，续传的复杂度收益比不高；②二期可加 `Range` 支持（与视频播放的 Range 需求一起做） | ✅ **能**。二期加 HTTP `Range` 支持即可 |
| **L-7** | **索引器首次全量索引慢** | 4915 张图片的首次扫描需要数分钟 | 需要打开每个文件读 EXIF（I/O + 解码开销） | ①增量索引（后续只处理变化）；②`thumb_state` 标记让缩略图生成不阻塞索引；③10 分钟的目标（AC-2.1）已考虑这点 | ⚠️ **部分**。可并行化与限速优化，但首次全量必然需要时间 |
| **L-8** | **缩略图缓存占磁盘** | 两级缩略图全库约 1.1 GB（320px ≈ 20 KB × 4915 + 1600px ≈ 200 KB × 4915） | 缓存是为了性能（避免重复生成） | ①可重建，删除无损失；②二期可加 LRU 淘汰与上限（见 [01](01-需求规格说明书.md) Q-6） | ✅ **能**。加淘汰策略即可 |
| **L-9** | **单写者限制** | SQLite 不支持多进程并发写 | 选 SQLite 换零运维（§5.2） | ①单进程架构：索引器与上传在同一进程内，通过队列串行化写入；②WAL 模式让读不阻塞 | ⚠️ **部分**。若将来需要多进程写，需换 PostgreSQL（届时"零运维"目标要重新权衡） |
| **L-10** | **云服务器是单点** | 云宕机时，外网访问完全不可用 | 需要双方都能连到的公共点 | ①**在家仍可局域网直连**；②云上数据可重建（换 VPS 10 分钟）；③照片零影响 | ❌ **不能**（架构性）。除非做多地域冗余（对单人项目不值得） |
| **L-11** | **依赖域名与证书** | 没有域名就没有 HTTPS，进而失去 PWA/SW/`wakeLock` | 安全上下文需要可信证书（D-7） | ①域名仅需 ¥1–10/年；②Caddy 自动管理证书；③开发阶段 localhost 也有安全上下文 | ✅ **能**（买个域名即可，成本极低） |
| **L-12** | **写权限带来的残余风险** | 即使有四条硬约束，仍可能存在未覆盖的路径怪癖或逻辑错误 | 业主明确需要写权限（D-10），风险只能**降低**不能**消除** | ①沙箱 + 完整逃逸测试用例集；②只新增不覆盖；③只进回收站；④审计留痕；⑤**任何一次数据事故即收紧为只读** | ⚠️ **部分**。这是**主动接受的风险**，用约束和监控兜底 |
| **L-13** | **不支持跳页** | 时间线无法"跳到第 25 页" | 游标分页的固有特性（D-5） | 提供"年月快速跳转"（按日期定位游标），这比页码更符合相册的使用直觉 | ✅ **能**（但**没有理由做**——页码跳转对相册无意义） |
| **L-14** | **Live Photo 丢失动态部分** | 时间线上显示为普通静态图 | 一期不做视频（D-8），Live Photo 的 `.mov` 不索引 | 二期视频功能上线后自动恢复 | ✅ **能**（二期） |
| **L-15** | **杀软可能误报 exe** | PyInstaller 产物可能被 Windows Defender 等误报 | PyInstaller 打包的可执行文件是常见的误报对象 | ①`--onedir` 比 `--onefile` 误报率低（§5.7）；②指导业主加白名单；③可考虑代码签名（**成本较高，一期不做**） | ⚠️ **部分**。代码签名可解决，但需要付费证书 |

### 10.2 明确"不做优化"的项

以下项**看起来可以优化，但主动不做**：

| 项 | 为什么不做 |
|---|---|
| 云端缓存缩略图 | 违背 DP-1（云零存储）；手机端 SW 缓存已解决"二次浏览零流量" |
| 多地域云冗余 | 单人项目，收益远低于成本；云上数据可重建 |
| 图片 CDN 加速 | 明确禁止（设计文档 §8.5："云不做任何媒体缓存（含 CDN），避免照片在第三方落盘"） |
| 原图预生成多尺寸 | 一期只有 320/1600 两级（设计文档 §5.1），足够覆盖网格与查看器；多尺寸增加存储与生成开销 |
| 时间线预取下一页 | 增加云流量（违背 DP-9）；用户滚动速度不可预测，预取命中率低 |
| 索引时全库算 sha256 | 显著拖慢首次索引（设计文档 §15.3 明确 `hash_on_index` **关闭**） |
| 下载断点续传（一期） | 低频场景，复杂度收益比不高（见 L-6） |

> ### ★ Q-35 是本文档发现的最严重设计缺口
>
> **问题**：设计文档 §11 的目录结构把上传临时区放在 `D:\Photos\data\uploads_tmp\`，而照片库在 `D:\Photos\`——**这是两个不同的卷（盘）**。设计文档 §9.2 依赖 `os.replace(临时, 目标)` 实现"原子落盘"，但 Windows 上 `os.replace` **跨卷时不是原子操作**：它会失败（`OSError`），或者被上层库退化为"复制 + 删除"。
>
> **后果**：
> - 直接冲击 **DP-2（失败安全优先）**——失败路径不再必然导向"数据完好"；
> - 直接冲击 **AC-3.8**（上传中断不污染库）——跨卷复制中途断电会留下半个文件；
> - 使"临时区 + 校验 + 原子转正"这套核心机制**在最关键的一步失效**。
>
> **可选方案**：
> 1. **把 `uploads_tmp` 移到 `D:\Photos` 同一卷**（例如 `D:\Photos\.photobridge_uploads\`，加隐藏属性 + 索引器跳过 + 沙箱显式放行）——**推荐**，保留原子性；
> 2. 接受"复制 + 校验 + 删除"的非原子流程，并**补一个启动时的残留清理与校验机制**——复杂度更高，且仍有一个非原子的窗口；
> 3. 目标目录与临时区都放在 `E:\`，但把索引库仍放 `H:\`——**最小改动**，只需调整 `config.py` 的临时区路径。
>
> **必须解决的时机**：**L5（分片上传 + 归档）开始之前**。L1–L3 不涉及上传，可以先做。
>
> **✅ 已解决（L5 实现时）**：采用方案 1，临时区改为 `<库根>/.photobridge_tmp/{upload_id}.part`
> （`backend/app/sandbox.py:349 tmp_dir()` / `:364 tmp_path()`），并把 `.photobridge_tmp`
> 加进 `DEFAULT_EXCLUDE_DIRS`（`backend/app/config.py:89`）让索引器跳过。
> ★ **按 root 逐个放置**而不是全库一个固定目录：多 root 时每个 root 各自同卷，`os.replace` 必然原子。
> ★ 名字是 `.photobridge_tmp`（带前导点、隐藏），不是方案里的 `.photobridge_uploads`。
