## 1. 引言

### 1.1 目的

本文档定义 PhotoBridge 一期（仅图片）的**功能需求、非功能需求、范围边界与验收标准**，作为：

1. 开发实现的依据（做什么）；
2. 验收测试的判据（怎么算做完）；
3. 需求变更的基线（改什么要重新确认）。

**本文档不回答"怎么实现"**——技术方案、模块划分、协议帧格式分别见 [02](02-概要设计说明书.md)、[03](03-详细设计说明书.md)、[04](04-接口设计文档.md)。

### 1.2 范围

| 维度 | 一期范围 |
|---|---|
| **产品** | 一套"手机随时随地访问自己电脑上照片库"的私有远程照片系统，代号 **PhotoBridge** |
| **媒体类型** | **仅静态图片**（jpg/jpeg/png/webp/gif/bmp/tif/tiff/avif/heic/heif）。**不含任何视频** |
| **用户数** | **1 人**（业主本人），1 个账号，1 台电脑，手机台数不限但通常是 1 台 |
| **部署** | 云服务器（转发）+ 家里的 Windows 电脑（数据）+ 手机浏览器/PWA |
| **交付形态** | 云侧 Docker 镜像 + 部署脚本；电脑侧 `PhotoBridge.exe`（PyInstaller `--onedir`）+ 托盘；手机侧网页（由云侧托管） |
| **不覆盖** | 视频、人脸识别、公网分享链接、多用户体系、端到端加密（均属二期，见 §6） |

### 1.3 术语表

**本项目所有专有名词在此定义。其他文档出现这些词时，含义以本表为准。**

| 术语 | 英文/代码名 | 定义 | 为什么需要它 |
|---|---|---|---|
| **Agent** | PhotoBridge Agent | 常驻在**业主电脑**上的托盘程序。它同时是"隧道客户端""本地 HTTP 服务""索引器""缩略图引擎""上传管理器""沙箱"。数据全在它这里 | 电脑是数据的唯一归属地；Agent 是数据出口 |
| **Relay** | 中继服务 | 跑在**云服务器**上的 FastAPI 服务。负责账号、设备注册表、配对、反向隧道接入、请求转发。**不存任何媒体字节** | 手机与电脑之间没有直接可达的网络路径，需要一个双方都能连到的公共点 |
| **隧道** | Tunnel | 电脑**主动**向云发起的常驻 `WSS` 长连接（`wss://<域名>/agent/ws`）。云把手机的 HTTP 请求封装成帧塞进这条连接，电脑处理后把响应帧送回 | 家里没有公网 IP、不能做端口映射，只有"主动外连"才能穿透 NAT |
| **帧** | Frame | 隧道上传输的最小协议单元：`1 字节 type + 4 字节 req_id(uint32 BE) + 变长 payload` | 一条 TCP/WS 连接上要跑很多并发请求，必须能区分彼此（见 req_id） |
| **req_id** | 请求标识 | 帧头里的 4 字节无符号整数，标识一次请求-响应往返。同一条隧道上 `req_id` 不同 = 不同请求并行 | 实现**多路复用**：手机同时拉 30 张缩略图 = 30 个 req_id 在同一条隧道上并行，不必开 30 条连接 |
| **多路复用** | Multiplexing | 单条隧道连接承载多个并发请求 | 连接建立成本高、NAT 映射易失效；复用一条连接更稳更省 |
| **配对码** | pair_code | 电脑托盘上显示的 **6 位数字**，**5 分钟有效**，错 5 次锁 10 分钟。手机输入它来证明"我确实在这台电脑旁边" | 手机登录账号 ≠ 有权访问某台电脑；配对码是一次**带外信道**（人在电脑前）的物理在场证明 |
| **配对** | Pairing | 手机用配对码换取 `client_token` 的过程，成功后该手机绑定到该电脑 | 一次性动作，之后长期免密使用 |
| **agent_token** | — | 电脑 ↔ 云 的**长期令牌**。电脑首次注册为设备时由云端生成，存本地配置文件，可云端吊销 | 隧道入口凭证；泄露等于别人能冒充你的电脑 |
| **client_token** | — | 手机 ↔ 云 的令牌，**配对时签发**，绑定单台电脑，可单独撤销，**默认有效期 90 天** | 手机侧凭证；撤销一台手机不影响其他设备 |
| **三层鉴权** | — | ①电脑↔云：`agent_token`；②手机↔云：`client_token`；③手机↔电脑（局域网直连时）：**复用同一个 `client_token`**，电脑本地校验 | 直连时不需要额外凭证，避免两套密钥体系 |
| **沙箱** | `sandbox.py` | 电脑端**所有文件访问的唯一入口**。任何路径必须经 `resolve()` 校验：拒绝绝对路径/盘符/UNC/`..`/NTFS 数据流/Windows 保留名/符号链接与 junction 段，并断言最终路径在根目录之内 | 这是防止"一个路径拼接漏洞 = 全盘泄露"的**唯一防线**；写权限已开放，必须靠它兜底 |
| **秒传** | dedup / instant-upload | 上传前用 `sha256` 查库，若库中已有相同内容则**不传字节**，直接返回已存在结果 | 手机里大量照片可能与 `全部备份\` 重复；秒传省流量、省时间 |
| **分片上传** | chunked upload | 大文件切成小块（局域网 **8 MB**，走云端 **2 MB**）逐块 `PATCH`，服务端按 `offset` 追加进临时文件 | 手机切后台/断网是常态，整文件重传不可接受 |
| **断点续传** | resume | 客户端用 `GET /api/uploads/{id}` 查询已收字节数，从该 `offset` 继续 | 同上；分片天然幂等，重传一片无害 |
| **临时区** | `data/uploads_tmp/` | 分片先落这里的 `{id}.part`，**校验通过后才 `os.replace` 到库中** | 断网/崩溃只会产生半截临时文件，不污染相册库 |
| **原子落盘** | atomic rename | 用 `os.replace(临时, 目标)` 完成"最后一跳"，同卷内是原子操作 | 保证库里永远不出现"写了一半的照片" |
| **归档** | archive | 上传完成后按 `年\年-月\` 规则计算目标路径并命名，同名冲突追加 `_1`/`_2` | 让手机上传的照片和你手动整理的照片有同一套目录逻辑 |
| **Live Photo** | — | iPhone 拍摄的"一张静态图 + 一段短视频"组合 | **一期只处理其中的静态图**，配套 `.mov` 不索引、不播放（二期） |
| **EXIF** | — | 图片文件内嵌的元数据：拍摄时间、机型、镜头、光圈、快门、ISO、焦距、GPS、方向等 | 时间线的排序依据和"详情"面板的数据来源 |
| **taken_at** | — | **拍摄时间**，时间线排序的**主键**（`ORDER BY taken_at DESC, id DESC`）。注意它**不等于**文件修改时间 | 相册的核心体验是"按拍摄时间回忆"，而不是按拷贝时间 |
| **taken_src** | — | `taken_at` 的来源，取值 `exif` / `filename` / `mtime`。**降级顺序**：EXIF 有 → 用 EXIF；没有 → 从文件名解析（如 `IMG_20240512_183000.jpg`）；再没有 → 用文件 `mtime` | 有些图（截图、下载图、被工具重存过的图）没有 EXIF，必须有兜底，否则会掉出时间线 |
| **游标分页** | cursor pagination | 用 `cursor`（上一页最后一条的位置标记）而非 `OFFSET` 翻页 | `OFFSET 10000` 在 SQLite 上要扫过前 1 万行；游标分页每次都是索引定位，**深翻页不退化**。且翻页期间有新照片入库也不会错位/重复 |
| **credit window** | 信用窗口 | 隧道流控机制：每个方向维护默认 **8 MB** 的信用额度，发送方只能发送不超过剩余信用的字节数，接收方消费后回 `CREDIT` 帧补充 | 没有它，手机下载一个 2 GB 文件时云端转发缓冲会把 1 GB 内存的 VPS 直接撑爆。**必须实现** |
| **双通路** | 局域网直连 / 云端中继 | 手机有两条路可达电脑：①同 Wi-Fi 时直连 `http://192.0.2.10:8787`；②否则走云。**两条路 API 完全一致**，前端零分支 | 在家时直连比云端快 10~50 倍且不耗云带宽（云带宽是最贵资源） |
| **降级为加速路径** | — | 局域网从 v0.2 的"唯一通路"变成 v0.3 的"可选加速路径" | 保证手机在外面也能用，同时在家时不浪费云带宽 |
| **PWA** | Progressive Web App | 可"添加到主屏幕"的网页，有独立图标与启动画面 | 免去开发原生 App；HTTPS 下才可用 |
| **Service Worker** | SW | 浏览器后台脚本，可拦截请求并缓存响应 | 一期用它把缩略图**永久缓存到手机本地**，二次浏览几乎零流量 |
| **wakeLock** | `navigator.wakeLock` | 浏览器 API，请求屏幕不休眠 | 批量上传时防止手机息屏导致上传中断 |
| **安全上下文** | secure context | 浏览器对 `https://` 或 `localhost` 才开放 SW / wakeLock 等能力 | 这是"上云 + HTTPS"带来的**意外收益**——v0.2 的局域网 HTTP 方案拿不到 |
| **FTS5** | SQLite FTS5 | SQLite 全文检索虚拟表 `media_fts`，覆盖 `file_name`、`rel_path`、`camera` | 搜索的文件名/相机字段检索 |
| **重扫** | rescan | 手动触发索引器重新扫描库目录 | 用户绕过系统直接往 `D:\Photos` 里放文件后需要它 |
| **watchdog** | — | 文件系统变更监听，感知库目录被外部改动 | 避免每次都要手动重扫 |
| **审计日志** | `data/audit.log` | 记录每一次删除/移动操作（时间、设备名、动作、路径、详情） | 写权限已开放，必须留痕，出问题能追 |
| **回收站** | `send2trash` | 删除操作**只进 Windows 回收站**，代码里不存在 `os.unlink` 路径 | 误删可恢复；这是"允许删除"这一决定的硬约束之一 |
| **离线卡片** | device_offline | 云查不到电脑的活跃隧道时返回 `503 {"error":"device_offline"}`，手机 UI 显示红条提示 | 电脑关机是常态场景，必须有明确反馈而不是转圈 |
| **kind** | — | `media.kind` 字段，一期**恒为 `'image'`** | 二期加视频时用它区分，一期先占位，避免二期改表 |

## 2. 项目背景与目标

### 2.1 背景

| 项 | 说明 |
|---|---|
| **现状** | 照片全部存放在家里 Windows 电脑的 `D:\Photos`，**实测 4952 个文件**。人在外面时无法访问 |
| **痛点** | ①在外面想找某次旅行的照片，只能打电话让家里人开电脑翻；②手机拍的新照片散在手机里，从未系统归集到电脑；③商用网盘要上传全部原图、要付费扩容，且照片存在别人服务器上 |
| **为什么不用现成网盘** | ①隐私：照片不能存在第三方；②成本：全库原图上传 + 长期存储远超预算；③体验：网盘不按 `taken_at` 分组、EXIF 展示弱、秒传/去重不可控 |
| **已有条件** | 家里有一台常开的 Windows 电脑；库目录已整理好三个子目录；手机是安卓；有云服务器（待购买）；有域名（待购买） |
| **架构起点** | v0.1/v0.2 设计为"同一 Wi-Fi 局域网直连"，但**在 4G 下完全不可用**，等于没有解决问题。v0.3 改为**云桥接** |

**为什么 v0.3 的转变是必要的**：业主的核心诉求是"**我在外面**也能看"，而局域网方案要求"手机和电脑在同一 Wi-Fi"——这与诉求直接矛盾。v0.3 让电脑主动外连建隧道，手机从任何网络都能到达，同时保留局域网直连作为"在家时更快"的加速路径。

### 2.2 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G-1 | **随时随地可达**：手机在 4G/5G/任意 Wi-Fi 下都能浏览和上传 | 关闭手机 Wi-Fi 仅用蜂窝网络，能打开时间线并上传成功 |
| G-2 | **数据主权**：照片永远只存在自己的电脑上 | 云端磁盘上检索不到任何图片字节（见 §4 P1-7 验收标准） |
| G-3 | **成本可控**：云侧总支出 ≤ ¥30/月 | 按 [VPS选购建议.md](../VPS选购建议.md) 最低档 ≈ ¥13/月 + 域名摊销，达标 |
| G-4 | **零运维负担**：装好之后不用管；坏了重建成本极低 | 云侧重建（换 VPS 重装）≤ 30 分钟且不影响照片 |
| G-5 | **不丢数据**：任何上传/删除操作都不可能导致照片丢失 | 只新增不覆盖 + 原子落盘 + 删除进回收站 + 审计留痕 |

### 2.3 成功判据（一期结束时的验收总纲）

一期**全部满足**以下 5 条即视为成功：

1. 手机用 4G 打开域名 → 时间线出现照片 → 点开看大图 → 看到 EXIF（G-1、G-2）
2. 手机选 20 张照片上传 → 全部出现在电脑 `D:\Photos` 的正确年月目录下 → 无重复、无覆盖（G-5）
3. 云端服务器磁盘上搜不到任何媒体字节（G-2）
4. 手机在家连 Wi-Fi 时自动切到局域网直连，状态条显示 🟢（G-1）
5. 单月云侧费用 ≤ ¥30（G-3）

## 3. 用户角色与使用场景

### 3.1 用户角色

| 角色 | 人数 | 说明 | 权限 |
|---|---|---|---|
| **业主（唯一用户）** | 1 | 同时是**决策方、开发协作方、验收方、运维方**。既是产品的使用者，也是服务器的所有者 | 全部：浏览、上传、下载、删除、移动、改名、打标签相册、管理设备、撤销配对 |
| 电脑 | — | 不是"用户"，是**数据持有者**。由业主的账号绑定 | 持有 `agent_token`，主动外连 |
| 手机 | — | 业主的设备，配对后获得 `client_token` | 同业主，但受 token 有效期与撤销约束 |
| **不存在的角色** | — | 一期**没有**：访客、分享接收者、管理员、家庭成员、注册用户 | — |

**为什么只有一个角色**：这是单人自用系统。引入角色/权限体系会带来"权限模型设计 + 越权测试 + 界面复杂度"三项成本，而收益为零。多用户体系明确列为二期（见 §6）。

### 3.2 使用场景（用户故事）

以下故事来自业主的实际生活场景，**每条都是需求来源**，编号 `US-n`。

---

**US-1 在旅途中找去年的照片**（对应 P1-1、P1-2）

> 我在外面用手机 4G，突然想给朋友看去年青甘环线拍的照片。我打开浏览器（已添加到主屏幕），
> 时间线直接出现缩略图，我往下滑，找到"青甘环线"那几天的分组，点开大图，
> 朋友问"这什么相机拍的"，我点顶部的 `i`，看到机型、镜头、光圈、快门、ISO。

**为什么这个场景重要**：这是**最核心的场景**，也是 v0.3 改用云桥接的唯一理由。如果这个场景做不到，整个项目没有意义。

**US-2 在家整理照片，秒开**（对应 P1-6）

> 我在家沙发上，手机连着家里 Wi-Fi。打开同一个网页，顶部状态条是 🟢 局域网直连。
> 我翻几百张缩略图，几乎秒出，而且我知道这些流量完全没走云。

**为什么这个场景重要**：云带宽是最贵的资源（也是体验瓶颈），家里能直连就直连，是省钱和提速的双重收益。

**US-3 把手机里攒的照片归集到电脑**（对应 P1-3）

> 我手机里有 300 张这半年拍的照片，一直没整理。我打开"上传"页，全选，
> 点上传，看着队列进度走。中途我切出去回了个微信，回来发现进度还在（没中断）。
> 完成后我在电脑上打开 `D:\Photos`，照片按 `2024\2024-05\` 这样分好了。

**为什么这个场景重要**：照片散在手机里从未归集，是业主的第二个真实痛点。这个场景也是"断点续传 + 归档规则"两项需求的来源。

**US-4 传了一半手机没电/断网**（对应 P1-3 的续传子需求）

> 上传 500 张照片到一半，地铁进隧道断网了。出隧道后我重新打开页面，
> 队列显示"已传 xx/500"，点继续，从断的地方接着传，没有重传已经传好的。

**为什么这个场景重要**：移动网络下断网是常态而非异常。**断点续传不是加分项，是必需项**——否则一次上传 500 张几乎不可能成功。

**US-5 把一张照片下载回手机**（对应 P1-4）

> 我在外面看到电脑上的一张老照片，想存到手机里发朋友圈。我点开，点下载，原图存进了手机相册。

**US-6 电脑关机了**（对应 P1-1 的失败路径）

> 我在外面打开页面，顶部红条提示"电脑离线，请确认电脑已开机且 PhotoBridge 正在运行"，
> 有个"重试"按钮。我打电话让家里开机，几分钟后点重试，正常了。

**为什么这个场景重要**：电脑关机是**必然会发生**的场景（睡眠、断电、系统更新）。设计要求：**失败必须明确、可恢复、有出口**，而不是无限转圈。

**US-7 第一次把手机和电脑连起来**（对应 P1-5）

> 我在电脑托盘上点"显示配对码"，看到一个 6 位数字和二维码。我在手机上登录账号，
> 看到设备"书房的台式机"，点配对，扫码，绑定成功。手机多了一个"我的"页面能看设备状态。

**为什么这个场景重要**：这是一次性但**必须顺畅**的流程。这里卡住，整个产品用不起来。

**US-8 手机丢了**（对应 P1-5 的撤销子需求）

> 我换手机了（或旧手机丢了）。我在新手机上重新配对，然后在"我的 → 设备管理"里把旧手机撤销。
> 旧手机的 token 立刻失效。

**为什么这个场景重要**：这是**安全兜底**。没有撤销能力，token 泄露后无法止血。

**US-9 传了一张电脑上已经有的照片**（对应 P1-3 的秒传子需求）

> 我传了一批照片，其中有几张之前在电脑上备份过。系统识别出来是重复的，
> 秒传完成，没有真的传字节，也没在相册里多出一份。

**为什么这个场景重要**：`全部备份\` 目录很可能已有重复内容（设计文档 §15.3 也提到这点）。没有去重，相册会被垃圾填满。

**US-10 在手机里搜索**（对应 P1-2 的搜索子需求）

> 我想找"2023 年用某台相机拍的有 GPS 的照片"。我在搜索页填日期范围 + 相机 + 勾"有 GPS"，
> 结果出来，我还能点 GPS 跳到地图看拍摄地点。

**US-11 直接往电脑里放照片**（对应 P1-2 的重扫子需求）

> 我懒得用手机传，直接在电脑上把一批照片拷进 `D:\Photos\相册1\`。
> 托盘里点"重新扫描"，等进度跑完，手机时间线里就出现了。

**US-12 删掉一张拍糊的照片**（对应 P1-2 的管理子需求）

> 我在手机上看到一张拍糊的，长按选中，点删除。它进了 Windows 回收站（不是永久删除）。
> 我不小心删错了，去电脑回收站还原回来了。

**为什么这个场景重要**：写权限开放是本项目的**最大风险点**。场景里"能还原"这个细节，就是 §4 里"只进回收站"这条硬约束的验收体现。

### P1-1 云桥接 · ⬜ 二期 P1

> **本节整体移到二期。** 一期不做云桥接，因此以下 9 条验收标准**不在一期验收范围内**。
> 保留原文是因为它是二期实现的完整依据，且**一期已经完成了它依赖的协议层**：
> `shared/protocol.py`（14 种帧类型、编解码、`FrameParser` 粘包半包、多路复用 `req_id`、
> 流控窗口常量、`Transport` 协议）已实现并有 22 条单测通过 —— 二期接隧道时不用从零设计协议。
>
> **一期对应的替代验收**：一期的通路是局域网直连，验收标准见 P1-6。

| 项 | 内容 |
|---|---|
| **编号** | P1-1 |
| **名称** | 云桥接（电脑主动外连 + 云端透明转发） |
| **优先级** | ~~必须~~ → **二期 P1** |
| **里程碑** | ~~C1~~ → **二期 P1** |
| **来源** | [设计文档.md](../设计文档.md) §2.1①、§4 |

**描述**

电脑上的 Agent 主动向云发起一条常驻 `WSS` 隧道连接（`wss://<域名>/agent/ws`，携带 `agent_token` 鉴权），**不需要公网 IP、不需要端口映射、不需要 DDNS**。云侧维护 `device_id → 活跃连接` 的内存映射，把手机的 HTTP 请求封装成隧道帧转发给电脑，再把电脑的响应帧流式回传给手机。手机侧访问路径形如 `https://<域名>/d/{device_id}/api/**`。

隧道必须支持：**单连接多路复用**（`req_id` 区分并发请求）、**credit 流控**（默认 8 MB 窗口，防 VPS 内存爆炸）、**25 秒心跳**、**指数退避重连**（1s→2s→4s→…→60s 封顶，永不放弃）。

**验收标准**

| # | 验收标准 | 验证方式 |
|---|---|---|
| AC-1.1 | 电脑启动 Agent 并配好云端地址 + 账号后，**60 秒内**隧道建立成功，托盘图标变为"已连接" | 人工观察托盘 |
| AC-1.2 | 手机通过 `https://<域名>/d/{device_id}/api/system/ping` 能拿到电脑返回的 `200` 响应 | `curl` 或浏览器 |
| AC-1.3 | **多路复用**：单条隧道上并发 30 个请求，全部在 **10 秒内**正确返回且响应不串号（每个 `req_id` 拿到的都是自己请求的结果） | 自动化测试 |
| AC-1.4 | **流控生效**：传输一个 ≥ 1 GB 的文件过程中，云端 Relay 进程的常驻内存增量 **≤ 200 MB**（证明没有整体缓冲） | 传输中采样进程内存 |
| AC-1.5 | **断线重连**：手动切断电脑网络 **5 秒内**恢复网络后，隧道在 **60 秒内**自动重建，无需人工干预；托盘图标自动恢复 | 拔网线/禁用网卡 |
| AC-1.6 | **重连后功能正常**：重连后手机再发请求能正常返回（云侧连接映射被新连接覆盖，不残留旧记录） | 重连后立即请求 |
| AC-1.7 | **离线反馈**：电脑 Agent 停止后，手机请求在 **3 秒内**收到 `503 {"error":"device_offline"}`，UI 显示红色离线提示条 | 关掉 Agent 后请求 |
| AC-1.8 | **并发隔离**：一个慢请求（大文件传输）进行中时，另一个小请求（如 `/api/system/ping`）在 **1 秒内**返回（不被阻塞） | 并发测试 |
| AC-1.9 | 隧道**连续运行 24 小时**不掉线，且期间心跳正常（无因空闲被中间设备掐断的情况） | 长时间挂机 |

**为什么这些标准是这些值**

- 60 秒重连上限：指数退避到 60s 封顶是业界常规值，再长用户会觉得"坏了"，再短会产生无谓的重连风暴。
- 200 MB 内存增量：1 GB 的 VPS 上 Relay 常驻约 80–150 MB（设计文档 §3.4），留给缓冲的空间约 200 MB。若不做流控，转发 2 GB 文件会直接把 VPS 打爆（设计文档 §4.3 明确说明）。
- 3 秒离线反馈：云侧查的是**内存 map**，这个判断本身是微秒级的；3 秒是给网络往返留的余量。

### P1-2 图片浏览

| 项 | 内容 |
|---|---|
| **编号** | P1-2 |
| **名称** | 图片浏览（索引 → 时间线 → 查看器 → EXIF → 搜索） |
| **优先级** | **必须** |
| **里程碑** | L2（索引）、L3（后端 API）、L4（前端） |
| **来源** | [设计文档.md](../设计文档.md) §5.1、§5.3、§6.2、§6.3、§7.2、§9.3 |

**描述**

电脑端索引器扫描库目录 `D:\Photos`，抽取 EXIF，写入 SQLite；缩略图引擎生成 **320px / 1600px 两级 WebP** 并磁盘缓存。手机端提供时间线网格、全屏查看器、EXIF 详情、搜索、目录树浏览。前端通过 `IntersectionObserver` 懒加载、虚拟滚动，`Service Worker` 缓存缩略图。

**子需求**

| 子编号 | 子需求 | 优先级 |
|---|---|---|
| P1-2.1 | 索引器：扫描库目录、抽 EXIF、增量更新、watchdog 感知变更、手动重扫 | 必须 |
| P1-2.2 | 缩略图：320 / 1600 两级 WebP 生成与磁盘缓存 | 必须 |
| P1-2.3 | 时间线：按天分组、3 列网格、虚拟滚动、懒加载、年月快速跳转 | 必须 |
| P1-2.4 | 查看器：左右滑动切换、双指缩放、双击放大、下滑关闭、三级渐进加载 | 必须 |
| P1-2.5 | EXIF 详情：机型/镜头/光圈/快门/ISO/焦距/GPS/尺寸 | 必须 |
| P1-2.6 | 搜索：文件名 / 日期范围 / 相机 / 有无 GPS | 应该 |
| P1-2.7 | 目录树：展示 `全部备份\`、`相册1\`、`青甘环线\` 及每层数量 | 应该 |
| P1-2.8 | 管理：删除（进回收站）、移动、改名、打标签相册 | 应该 |

**关键约束（来自设计文档 §5.3）**

索引与上传的**图片白名单**：`jpg jpeg png webp gif bmp tif tiff avif heic heif`

**排除**：
- `.jpg-lx2` —— 小米相册回收站残留，**非真实图片**，实测 22 个，白名单不含，**直接不索引**
- 全部视频扩展名 —— 一期不索引
- RAW（`dng/cr2/nef/arw`…）—— 二期

**HEIC/HEIF 必须支持**：服务端用 `pillow-heif` 统一转成 WebP/JPEG 再给手机，否则安卓浏览器打不开 iPhone 传来的 HEIC。

**验收标准**

| # | 验收标准 | 验证方式 |
|---|---|---|
| AC-2.1 | 首次全量索引 `D:\Photos` 的 **4915 张**白名单图片（4952 文件 − 22 个 `.jpg-lx2` − 12 `.mov` − 3 `.mp4`），在**普通家用电脑上 10 分钟内**完成 | 计时 |
| AC-2.2 | 索引结果中 `kind='image'` 的行数 **恰为 4915**；`.jpg-lx2`、`.mov`、`.mp4` **一条都不出现** | SQL 查询 |
| AC-2.3 | **时间线首屏 100 张缩略图在 4G 下 2.5 秒内出现**（走云端中继） | 手机 4G 实测计时 |
| AC-2.4 | 单张 320px 缩略图 WebP 体积 **≤ 30 KB**（目标 ≈ 20 KB） | 抽样统计 |
| AC-2.5 | 缩略图**已缓存**时，电脑侧响应 **≤ 100 ms**；**未缓存**时首次生成 **≤ 500 ms**（设计目标 30–80 ms） | 打点 |
| AC-2.6 | 缩略图响应带 `ETag` 与 `Cache-Control: immutable`，手机二次请求命中缓存返回 `304` | 查看响应头 |
| AC-2.7 | 时间线深翻页（第 50 页，约第 5000 条）响应时间与第 1 页**差异 ≤ 50 ms**（证明游标分页未退化） | 对比打点 |
| AC-2.8 | 时间线排序**严格按 `taken_at DESC, id DESC`**；对无 EXIF 的图，`taken_src` 依次降级为 `filename` → `mtime`，且**排序不出现回退到 1970 年**的异常项 | 抽查 + SQL |
| AC-2.9 | 时间线**按天分组**，同一天的照片归入同一组，组头显示日期 | 人工核对 |
| AC-2.10 | 查看器三级渐进：先出 320px 模糊占位 → 1600px 预览 → 后台静默拉原图，**用户感知到首屏不白屏** | 人工体验 |
| AC-2.11 | 查看器支持左右滑动切换、双指缩放、双击放大、下滑关闭 **四项操作全部可用** | 人工操作 |
| AC-2.12 | EXIF 面板正确显示机型/镜头/光圈/快门/ISO/GPS；**GPS 坐标点击可跳转地图** | 人工核对一张已知 GPS 照片 |
| AC-2.13 | HEIC/HEIF 文件在**安卓 Chrome** 中能正常显示（服务端已转码），不出现裂图 | 用 HEIC 样本实测 |
| AC-2.14 | 搜索支持 4 个维度组合：文件名、日期范围、相机、有无 GPS，结果正确 | 人工 + 自动化 |
| AC-2.15 | **watchdog**：直接在电脑上往库目录拷入 1 张新图，**30 秒内**手机时间线**自动**可见（无需手动重扫、无需刷新页面）—— 由 `POST` 后服务端推 `media_changed`、前端 `EventSource` 接收并刷新时间线实现 | 拷文件后计时 |
| AC-2.16 | **手动重扫**：托盘点"重新扫描"后，进度通过 `SSE /api/events` 推送到手机，UI 显示进度 | 人工观察 |
| AC-2.17 | 时间线首屏请求的**流量 ≤ 2.5 MB**（100 张 × 20 KB ≈ 2 MB） | 流量统计 |
| AC-2.18 | 浏览 1000 张缩略图的累计云带宽 **≤ 25 MB**（设计文档 §1.3 指标） | 云端流量计数 |

**为什么这些标准是这些值**

- **2.5 秒**：这是设计文档 §1.3 明确写下的非功能目标。取这个值的依据是"200 ms 延迟 + 20 KB 图片 ≈ 0.3 秒/张"（§10.1.1），加上首屏并行拉取与渲染开销。
- **20 KB / 张**：这是整套带宽预算（§12）的基石。3000 张缩略图 × 20 KB = 60 MB/月，是"月度 4.6 GB"里唯一的主要项之一。
- **4915 张**：这是**实测值**，不是估算。4952 − 22 − 12 − 3 = 4915。设计文档 §9.1 写的"约 4900 张"与此一致。
- **深翻页 ≤ 50 ms 差异**：游标分页的价值**只体现在深翻页**。如果浅翻页就达标而深翻页退化，说明实现退化成了 `OFFSET`。

### P1-3 图片上传

| 项 | 内容 |
|---|---|
| **编号** | P1-3 |
| **名称** | 图片上传（分片 + 断点续传 + 秒传 + 归档） |
| **优先级** | **必须** |
| **里程碑** | L5 |
| **来源** | [设计文档.md](../设计文档.md) §7.2、§9.2、§5.1 |

**描述**

手机批量选择相册图片，通过**分片上传**写入电脑库目录。上传**直接进库**（不设独立 Inbox 目录），完成后按 `年\年-月\` 规则自动归档。支持断点续传、sha256 秒传去重、同名冲突加序号、EXIF 取拍摄时间、原子落盘、写后入库并生成缩略图。

**子需求**

| 子编号 | 子需求 | 优先级 |
|---|---|---|
| P1-3.1 | 分片上传（局域网 8 MB / 云端 2 MB），`PATCH` + `Content-Range`，幂等 | 必须 |
| P1-3.2 | 断点续传：`GET /api/uploads/{id}` 查 `offset`，从断点继续 | 必须 |
| P1-3.3 | 秒传：`sha256` 命中库中已有记录则不传字节 | 应该 |
| P1-3.4 | 自动归档：读 EXIF 拍摄时间 → `年\年-月\` → 命名 `YYYYMMDD_HHMMSS.ext` | 必须 |
| P1-3.5 | 冲突处理：同名追加 `_1`/`_2`；**任何情况下不覆盖已有文件** | 必须 |
| P1-3.6 | 原子落盘：临时区 → 校验 → `os.replace` | 必须 |
| P1-3.7 | 上传队列 UI：进度、速度、暂停/继续、失败重试 | 必须 |
| P1-3.8 | 上传白名单校验：非图片格式直接拒绝 | 必须 |

**关键约束**

| 约束 | 值 | 理由（设计文档 §7.2） |
|---|---|---|
| 单文件上限 | **2 GB** | 一期图片足够；超过则拒绝 |
| 分片大小（局域网直连） | **8 MB** | 内网快、RTT 低，大分片吞吐更高 |
| 分片大小（走云端） | **2 MB** | 云带宽窄、RTT 高，大分片一旦失败重传代价高，小分片吞吐更稳 |
| 上传并发 | **≤ 3** | 云端限流要求（§8.5） |
| 秒传算法 | **sha256** | 碰撞概率可忽略；`media.sha256` 有索引 |
| 临时区 | `data/uploads_tmp/{id}.part` | 半截文件不污染相册库 |

**验收标准**

| # | 验收标准 | 验证方式 |
|---|---|---|
| AC-3.1 | 手机批量选择 **20 张**照片上传，**全部成功**，电脑端 `media` 表新增 20 条 | 端到端实测 |
| AC-3.2 | 上传吞吐（走云端）**≥ 1.5 MB/s**（设计文档 §1.3 指标） | 计时 |
| AC-3.3 | 上传的照片落在**正确的年月目录**下，文件名形如 `20240512_183000.jpg`（取自 EXIF 拍摄时间） | 检查文件系统 |
| AC-3.4 | 对**无 EXIF** 的图片，回退到文件名解析，再回退到 `mtime`，**不失败** | 用无 EXIF 样本实测 |
| AC-3.5 | 上传**同一张**照片两次：第二次**秒传**（不传字节），库中**只有 1 条**记录 | 观察流量 + SQL |
| AC-3.6 | 上传**同名不同内容**的照片：第二个文件被命名为 `xxx_1.jpg`，**原文件内容未被修改** | 校验 md5 |
| AC-3.7 | **断点续传**：上传中途断开网络，恢复后从断点继续，**已成功分片不重传**（对比上传总字节数） | 抓包/日志 |
| AC-3.8 | **中断不污染库**：上传中途强制杀进程，库目录**不出现半截文件**，只有 `uploads_tmp` 下有 `.part` | 检查目录 |
| AC-3.9 | **切后台不中断**：上传中切到微信 60 秒再切回，上传继续（`wakeLock` 生效） | 人工实测 |
| AC-3.10 | 上传一个 **> 2 GB** 的文件被**明确拒绝**并给出提示，不占用磁盘 | 构造大文件实测 |
| AC-3.11 | 上传一个 `.txt` / `.mov` 被拒绝（不在白名单） | 实测 |
| AC-3.12 | 上传完成后**自动生成缩略图**，`thumb_state` 由 `pending` 变 `ok` | SQL 查询 |
| AC-3.13 | 上传完成后手机收到 `upload_done` 帧推送（SSE，二期改经隧道 `NOTIFY`），UI 显示"✓ 完成" | 代码 + 真实 HTTP 上传后查总线 |
| AC-3.14 | 上传 500 张照片（含断网若干次）**最终全部成功**，无重复、无丢失 | 压力场景 |
| AC-3.15 | 云端 `traffic` 表按天正确累计上传字节数（进 + 出） | SQL 查询 |

**为什么"不设独立 Inbox"**（业主已确认的决定）

v0.2 曾设想"上传先进 Inbox，再手动整理"。v0.3 取消它，理由：

1. **多一步整理就是多一步不会做的事**。业主的真实痛点是"照片散在手机里从未归集"，如果上传后还要手动归位，这套系统最终不会被用。
2. **归档规则是确定的**：`年\年-月\` 由 EXIF 拍摄时间唯一决定，不需要人工判断。
3. **风险已由其他约束兜住**：不覆盖、加序号、原子落盘、sha256 去重、审计留痕——这些保证了"直接进库"不会造成数据事故。

**为什么"不覆盖"是硬约束**（业主已确认的写权限）

删除/移动/改名权限已开放，风险用四条硬约束兜住（设计文档 §8.4）：

1. 所有文件操作必须过**沙箱**，越界一律拒绝
2. 上传**只新增不覆盖**：同名追加 `_1`/`_2`；sha256 命中判重丢弃；**任何情况下不把新文件 rename 到已存在文件上**
3. 删除**只进回收站**（`send2trash`），代码里不存在 `os.unlink` 路径
4. 删除/移动**写审计日志** `data/audit.log`，托盘面板可查看

### P1-5 配对与鉴权

| 项 | 内容 |
|---|---|
| **编号** | P1-5 |
| **名称** | 配对与鉴权（三层凭证 + 配对码 + 设备撤销） |
| **优先级** | **必须** |
| **里程碑** | L3（配对与本地鉴权）、L4（手机端流程）；云端签发改 P1 |
| **来源** | [设计文档.md](../设计文档.md) §8.2 |

**描述**

**三层鉴权模型**：

| 层 | 凭证 | 说明 |
|---|---|---|
| 电脑 ↔ 云 | `agent_token` | 长期令牌，电脑首次注册时生成，存本地配置文件，可云端吊销 |
| 手机 ↔ 云 | `client_token` | 配对时签发，绑定单台电脑，可单独撤销，**默认 90 天** |
| 手机 ↔ 电脑（直连时） | **同一 `client_token`** | 直连时电脑本地校验，无需额外凭证 |

**配对流程**：电脑托盘显示 **6 位配对码 + 二维码**（二维码内容含 `device_id`）→ 手机登录账号后扫码或输码 → 云校验（**5 分钟有效**、**错 5 次锁 10 分钟**）→ 签发 `client_token`。

**账号体系**：**极简单账号**（一个邮箱 + 密码），**无注册流程、无找回密码流程**，只服务业主一人（设计文档 §15.1 第 5 项已定）。

**验收标准**

| # | 验收标准 | 验证方式 |
|---|---|---|
| AC-5.1 | 电脑首次注册后拿到 `agent_token` 并**写入本地配置文件**；令牌**不出现在源码中** | 检查配置文件与源码 |
| AC-5.2 | 托盘可显示 **6 位配对码 + 二维码**，二维码 URL 含 `device_id`（`?code=..&did=..`）；手机扫码后**配对前**先核对 `did`，不一致直接拒绝并提示「连到了另一台电脑」（静态二维码 + DHCP 换 IP 会让手机绑到别人的电脑上、显示别人的照片） | 真实 Chrome E2E `[4f]` + `test_tray.py` |
| AC-5.3 | 手机输入正确配对码 → 拿到 `client_token`，绑定成功 | 端到端实测 |
| AC-5.4 | 配对码**超过 5 分钟**后失效，使用它返回错误 | 等待后实测 |
| AC-5.5 | 配对码**连续输错 5 次**后锁定 **10 分钟**，期间正确码也不通过 | 实测 |
| AC-5.6 | 手机用 `client_token` 访问 `/d/{device_id}/api/**` 正常；**用错 device 的 token 访问返回 401/403** | 越权测试 |
| AC-5.7 | 撤销某台手机后，该手机的 `client_token` **立即失效**（下一次请求返回 401），**不影响其他手机** | 撤销后实测 |
| AC-5.8 | 撤销某台电脑（`agent_token`）后，该电脑**无法再建立隧道** | 实测 |
| AC-5.9 | 局域网直连时，电脑用**同一个 `client_token`** 校验通过，无需二次配对 | 实测 |
| AC-5.10 | `client_token` **90 天**过期后需重新配对；过期时刻**落库**并在每次请求校验（策略由 `auth.token_ttl_days` 配置，`0` = 永不过期） | 构造过期 token 实测 |
| AC-5.11 | 云端限流：单 `client` **120 req/s** 上限生效；**上传并发 ≤ 3** | 压测 |
| AC-5.12 | 云端爆破防护：短时间大量错误配对码尝试被限流/锁定 | 压测 |

**为什么用"配对码"而不是"直接输入账号密码登录电脑"**

配对码解决的是**授权粒度**问题：登录账号只证明"你是这个账号的人"，不证明"你有权访问这台电脑"。6 位码 + 5 分钟有效 + 人在电脑前看到它，是一次**物理在场证明**（带外信道）。这是最简的实现里最有效的一层保护。

### P1-6 局域网访问

> **架构调整说明（重要）**：本节在"云端优先"方案里叫「局域网加速」，优先级是**应该**，
> 定位是"省云带宽的优化项"。**2026 年架构调整为"局域网优先、远程留接口"后，
> 它的地位反过来了** —— 局域网直连成为一期的**主通路**，云端中继移到二期 P1。
> 因此：优先级由「应该」升为「**必须**」，里程碑由 C5 改为 **L3**，
> 验收标准中原"双通路切换"部分（`AC-6.3` 通路切换耗时、`AC-6.5` 双通路一致性）
> 改为二期，其余全部保留。
>
> **一期实现的事实**：`transports/base.py` 定义了 `Transport` 抽象，
> `transports/local_http.py` 是唯一的实现；业务逻辑写成协议无关的 `Ctx`/`Reply`
> 中间表示，二期加隧道时只需新增一个适配器。**"两条路一套 API"这条设计没有变，
> 只是二期那条路还没接上。**

| 项 | 内容 |
|---|---|
| **编号** | P1-6 |
| **名称** | 局域网访问（手机与电脑同一 Wi-Fi 直连） |
| **优先级** | **必须**（原「应该」；架构调整后升为必须） |
| **里程碑** | L3（原 C5） |
| **来源** | [设计文档.md](../设计文档.md) §2.1③、§6.1 |

**描述**

手机与电脑处于同一局域网时，直接访问**直连**地址 `http://192.0.2.10:8787`
（电脑端 `LocalHttpTransport` 绑定 `0.0.0.0:8787`），**不经过任何云服务**。
一期只有这一条通路，因此没有"切换"逻辑：

```
启动 → 读取配对时保存的局域网地址
  ├─ 能连上 → 标记「🟢 局域网直连」，所有请求走它
  └─ 连不上 → 标记「🔴 电脑离线」，提示用户检查电脑是否开机、是否同一 Wi-Fi

（二期 P1 才在"连不上"之后增加一步：→ 尝试 https://<域名>/d/{device_id}）
```

顶部状态条显示当前通路：**🟢 局域网直连 / 🔵 云端中继（二期）/ 🔴 电脑离线**。

**关键设计**：局域网 HTTP 与隧道走**完全相同的 API 路径**，业务逻辑写成
`Ctx`/`Reply` 中间表示，两个传输适配器调用**同一套路由函数**，所以前端代码**零分支**
—— 这一点在一期就已通过 `transports/base.py` 的抽象与 `TC-SWITCH-FUNC-006`
（同一组请求分别经 `local_http` 适配器与直接调用 handler，结果必须一致）落实。

**验收标准**

> **一期验收（✅ 本期）** —— 只保留与"局域网直连可用"直接相关的条目：

| # | 验收标准 | 验证方式 | 一期状态 |
|---|---|---|---|
| AC-6.9 | 电脑本地服务**只监听私网**；启动时检测到在公网 IP 上绑定则**拒绝启动** | 代码审查 + 构造测试 | ✅ `check_bind_safety()` 已实现 |
| AC-6.4 | 直连下浏览缩略图的加载速度**明显快于**云端中继 | 计时对比 | ⬜ 二期（无云端可比） |
| AC-6.7 | 直连与云端的 **API 行为一致**：同一请求在两条路上返回相同的 JSON 结构 | 对比测试 | 🔄 一期以 `TC-SWITCH-FUNC-006`（`local_http` 适配器 vs 直接调用 handler）替代 |
| AC-6.8 | 直连时手机上传用 **8 MB 分片**（云端用 2 MB，二期） | 抓包/日志 | ✅ `chunk_mb_lan=8` / `chunk_mb_wan=2` |
| — | **新增**：手机与电脑同一 Wi-Fi 时，打开 `http://<电脑IP>:8787/` 能看到照片墙 | 真机实测 | ⬜ **待做**（L4 未完成的实测） |
| — | **新增**：电脑未开机时，手机给出**明确提示**而不是白屏或转圈 | 真机实测 | ✅ 状态条显示 🔴 电脑离线 |

> **二期验收（⬜ P1）** —— 以下条目依赖云端中继，一期无法验证：

| # | 验收标准 | 验证方式 | 二期 |
|---|---|---|---|
| AC-6.1 | 手机在 Wi-Fi 且电脑在线时，**1.5 秒内**探测成功并切到直连，状态条显示 🟢 | 人工观察 | ⬜ P1 |
| AC-6.2 | 手机切到蜂窝网络后，自动走云端中继，状态条显示 🔵 | 关 Wi-Fi 实测 | ⬜ P1 |
| AC-6.3 | 直连时**云带宽计数不增长**（`traffic` 表无新增） | SQL 对比 | ⬜ P1 |
| AC-6.5 | **探测失败不卡顿**：直连探测失败时，页面**不在 1.5 秒内阻塞**主流程 | 人工体验 | ⬜ P1 |
| AC-6.6 | **同会话不重复探测**：本次会话直连失败后，后续请求**不再重复尝试直连** | 日志 | ⬜ P1 |
| AC-6.10 | 云端中继不可用但局域网可用时，**在家仍能正常使用** | 停掉云端服务实测 | ⬜ P1 |

**为什么优先级从「应该」升为「必须」**：原判断的前提是"不做它系统仍然可用（全程走云）"。
架构调整后这个前提不成立了 —— **局域网直连是一期唯一的通路，不做它就没有任何通路**。
它从"优化项"变成"基础设施"。反过来，它现在的性价比更高了：**零成本、零外部依赖、
零备案**，且不消耗任何云资源。

**描述**

云服务器**只做转发，不落任何媒体字节**。云端 SQLite 只有 5 张表：`accounts`、`devices`、`clients`、`pair_codes`、`traffic`。**没有 `media` 表**——云不知道你有哪些照片。

云端允许存在的数据：**账号、设备列表、配对码、带宽计数**。这四类数据丢了也不心疼，重装即可。

**明确禁止**：

| 禁止项 | 理由 |
|---|---|
| 云端磁盘写入任何图片/视频字节 | 隐私底线 |
| 云端使用任何媒体缓存（**含 CDN**） | 避免照片在第三方落盘 |
| 云端整体缓冲响应体后再转发 | 内存会爆炸（见 P1-1 AC-1.4），且构成事实上的临时存储 |
| 云端保留请求/响应体副本用于调试 | 同上；日志只允许记录元数据 |

**验收标准**

| # | 验收标准 | 验证方式 |
|---|---|---|
| AC-7.1 | 完整跑一遍"浏览 100 张 + 上传 20 张 + 下载 5 张"后，云端**磁盘占用增长 ≤ 1 MB**（只有日志与计数） | `du` 对比 |
| AC-7.2 | 在云端全盘检索已知照片的 sha256 或文件头魔数（`FF D8 FF` / `89 50 4E 47`），**零命中** | 全盘扫描 |
| AC-7.3 | 云端 SQLite 的表清单**恰为** `accounts / devices / clients / pair_codes / traffic`，**不存在 `media` 表** | `sqlite3 .tables` |
| AC-7.4 | 上传一个 2 GB 文件过程中，云端内存增量 **≤ 200 MB** | 采样内存 |
| AC-7.5 | 云端**不配置任何 CDN**；Caddy/Nginx 配置中**无媒体缓存指令** | 审查配置文件 |
| AC-7.6 | 云端**重建成本**：把 VPS 换一台、重装、重跑部署脚本，**≤ 30 分钟**完成，且**照片零影响** | 演练一次 |
| AC-7.7 | 云端日志中**不出现**媒体文件内容或 base64 编码的图片数据 | 审查日志 |

**为什么这是"隐私底线"**

设计文档 §2.1② 的表述："这条是整个方案的隐私底线。"它的价值不只是隐私，还有**架构韧性**：因为云上没有任何不可再生的数据，所以"云服务器被墙/宕机/跑路"都只是可用性问题，**不是数据安全问题**。这也让"选最便宜的小厂商 VPS"成为合理决策而非冒险（[VPS选购建议.md](../VPS选购建议.md) §3）。

```
缩略图 3000×20KB = 60 MB
预览   500×200KB = 100 MB
下载   100×4MB   = 400 MB
上传   500×8MB   = 4 GB
─────────────────────────
合计 ≈ 4.6 GB/月
```

### 6.2 关于"视频"的特别说明

业主库中实测有 **12 个 `.mov` + 3 个 `.mp4`**，共 15 个视频文件。一期的处理方式是：

| 项 | 处理 |
|---|---|
| 索引 | **不索引**（不在白名单） |
| 时间线 | **不出现** |
| 播放 | **不支持** |
| 封面 | **不生成** |
| 上传 | **拒绝**（白名单校验） |

**为什么可以这样处理而不影响体验**：15 个视频在 4952 个文件中占 0.3%，且业主的核心诉求是"看照片"。跳过它们让一期**完全不需要 ffmpeg**，打包体积和复杂度大幅下降。

### 6.3 关于"Live Photo"的特别说明

iPhone 的 Live Photo 是"一张静态图 + 一段短视频"（通常是一张 `.heic`/`.jpg` + 同名 `.mov`）。一期的处理：

| 部分 | 一期行为 |
|---|---|
| 静态图（`.heic` / `.jpg`） | **正常索引、浏览、上传**（HEIC 经 `pillow-heif` 转码） |
| 配套视频（`.mov`） | **不索引、不播放**（同 N-1） |

**影响**：Live Photo 在时间线上显示为一张普通照片，失去"长按播放动态"的效果。**一期接受**，二期视频功能上线后自动恢复。

## 11. 需求变更流程

需求一旦确认，**任何变更必须走以下流程**（来源：[00-文档索引与开发流程.md](00-文档索引与开发流程.md) §3.1）：

| 步骤 | 动作 | 责任人 |
|---|---|---|
| 1 | 提出变更（加功能 / 砍功能 / 改验收标准） | 业主 |
| 2 | 评估影响：涉及哪些需求、哪些文档、哪些里程碑 | AI |
| 3 | **业主确认**（不确认不得开工） | 业主 |
| 4 | 更新本文档（升 `Y` 版本号；结构性变更升 `X`） | AI |
| 5 | 同步更新受影响的下游文档（[02](02-概要设计说明书.md)~[11](11-风险登记册与决策记录.md)） | AI |
| 6 | 若涉及架构，同步更新 [设计文档.md](../设计文档.md) | AI |
| 7 | 记录到 [11-风险登记册与决策记录](11-风险登记册与决策记录.md) | AI |

**硬约束**（不可违反）：
- 加功能/砍功能**必须业主点头**（[00 文档](00-文档索引与开发流程.md) §3.1）
- 不擅自扩大范围：一期只做图片，不碰视频、不引入 ffmpeg
- 不擅自安装依赖：新增依赖须先说明理由
- 改表必须给迁移脚本
