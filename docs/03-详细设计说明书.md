## 2. 隧道协议实现（协议层）★

> **为什么这一章放最前面**：整个系统的技术风险 80% 集中在隧道协议上。协议写错了，云端、电脑端、手机端全部要返工；
> 协议写对了，三端就只是"填业务逻辑"。**C1 阶段唯一要交付的就是本章的代码 + 回显测试。**

### 2.1 设计目标与约束

| 目标 | 约束来源 | 实现手段 |
|---|---|---|
| 一条连接跑多请求 | 手机同时拉 30 张缩略图 | `req_id` 多路复用 |
| 不撑爆 1 GB 内存 VPS | §14 风险表 | credit 流控（窗口 8 MB） |
| 断线 5 秒内恢复 | §1.3 非功能目标 | 指数退避重连 + 会话重建 |
| 双向流式 | 上传/下载大文件 | HEAD/BODY/END 三段式帧 |
| 穿企业代理 | §14 风险表 | 帧格式与传输无关（可降级 SSE+POST） |
| 二期上 E2E 不改协议 | §8.3 决策 | 帧头保留 `flags` 位、`REQ_HEAD.enc` 字段 |

**关键决策：帧头只放 5 字节（type + req_id），不放长度字段。**
理由：WebSocket 本身是**消息边界协议**，一条 WS 消息就是一条完整帧，无需自定义长度前缀。
只有在"降级为 SSE + POST 长轮询"时，才需要额外的长度前缀（见 §2.8）。
**禁止**把长度写进帧头——那会让 WebSocket 与降级模式产生两套编解码器。

### 2.2 帧格式与常量

#### 2.2.1 帧布局【一期】

```
 0        1                              5                        N
+--------+------------------------------+------------------------+
|  type  |      req_id (uint32 BE)      |        payload         |
| 1 byte |          4 bytes             |   变长（可为空）        |
+--------+------------------------------+------------------------+
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | `uint8` | 帧类型，见下表 |
| `req_id` | `uint32` 大端 | 请求标识；**心跳/CREDIT 也复用该字段**承载参数 |
| `payload` | `bytes` | 二进制或 UTF-8 JSON，取决于 type |

#### 2.2.2 type 常量表【一期】

| 十六进制 | 十进制 | 名称 | 方向 | payload 内容 |
|---|---|---|---|---|
| `0x01` | 1 | `REQ_HEAD` | 云→电脑 | UTF-8 JSON：`{method, path, query, headers, enc?}` |
| `0x02` | 2 | `REQ_BODY` | 云→电脑 | 上传分片**原始字节** |
| `0x03` | 3 | `REQ_END` | 云→电脑 | 空 |
| `0x04` | 4 | `RES_HEAD` | 电脑→云 | UTF-8 JSON：`{status, headers}` |
| `0x05` | 5 | `RES_BODY` | 电脑→云 | 响应体分片**原始字节** |
| `0x06` | 6 | `RES_END` | 电脑→云 | 空 |
| `0x07` | 7 | `ERROR` | 双向 | UTF-8 JSON：`{code, message, detail?}` |
| `0x08` | 8 | `CANCEL` | 双向 | 空（`req_id` 即目标） |
| `0x09` | 9 | `PING` | 双向 | 空；`req_id` 承载**非零**序号 |
| `0x0A` | 10 | `PONG` | 双向 | 空；`req_id` 回显 PING 的序号 |
| `0x0B` | 11 | `CREDIT` | 双向 | 空；`req_id` = 0 表示**连接级**窗口，非 0 表示该请求级窗口 |
| `0x0C` | 12 | `NOTIFY` | 电脑→云→手机 | UTF-8 JSON：`{topic, data}` |

#### 2.2.3 帧头 `flags` 的预留【二期】

v0.3 设计文档 §8.3 要求"帧头带 `flags` 位"。**一期实现方式**：把 `req_id` 的高 2 位预留给标志位，实际 `req_id` 只用低 30 位。

```
req_id (uint32 BE)
 31      30      29 ........................ 0
+-------+-------+---------------------------+
| flag1 | flag2 |      req_id (30 bits)     |
+-------+-------+---------------------------+
| F_ENC | 保留  |   0 ~ 1,073,741,823       |
```

| 位 | 名称 | 含义 |
|---|---|---|
| bit31 | `F_ENC` | payload 已 E2E 加密【二期】；一期恒为 0 |
| bit30 | 保留 | 一期恒为 0，读取时必须忽略 |

**为什么用位而不是加字节**：帧头保持 5 字节不变，一期不实现加密时代码路径完全一致（`F_ENC` 恒 0），
二期只需在收发两侧各加一个"若置位则解密"的分支，**不动协议结构**。

```python
# cloud/relay/protocol.py
REQ_ID_MASK = 0x3FFFFFFF          # 低 30 位
FLAG_ENC    = 0x80000000          # bit31
FLAG_RESERVED = 0x40000000        # bit30

def pack_req_id(req_id: int, flags: int = 0) -> int:
    assert 0 <= req_id <= REQ_ID_MASK, "req_id out of 30-bit range"
    return (req_id & REQ_ID_MASK) | flags

def unpack_req_id(raw: int) -> tuple[int, int]:
    return raw & REQ_ID_MASK, raw & (FLAG_ENC | FLAG_RESERVED)
```

### 2.3 `protocol.py` 完整设计 ★

**文件位置**：`cloud/relay/protocol.py`，**由云端与电脑端共享同一份文件**（§11 目录结构要求）。

#### 2.3.1 数据结构

```python
from __future__ import annotations
from dataclasses import dataclass, field
from enum import IntEnum
import json, struct
from typing import Any

class FrameType(IntEnum):
    REQ_HEAD = 0x01
    REQ_BODY = 0x02
    REQ_END  = 0x03
    RES_HEAD = 0x04
    RES_BODY = 0x05
    RES_END  = 0x06
    ERROR    = 0x07
    CANCEL   = 0x08
    PING     = 0x09
    PONG     = 0x0A
    CREDIT   = 0x0B
    NOTIFY   = 0x0C

HEADER_SIZE = 5                    # type(1) + req_id(4)
MAX_FRAME   = 65536                # HELLO_ACK 下发的 max_frame
_HEADER = struct.Struct(">BI")     # 大端：uint8 + uint32

@dataclass(slots=True)
class Frame:
    type: FrameType
    req_id: int                    # 已剥离 flags 的 30 位值
    payload: bytes = b""
    flags: int = 0                 # F_ENC 等，一期恒 0

    # ---- 便捷视图 ----
    @property
    def json(self) -> dict[str, Any]:
        """payload 当 JSON 解析（仅 HEAD/ERROR/NOTIFY 用）。"""
        if not self.payload:
            return {}
        return json.loads(self.payload.decode("utf-8"))

    @property
    def enc(self) -> bool:
        return bool(self.flags & FLAG_ENC)
```

#### 2.3.2 编解码函数【一期，必须】

```python
class ProtocolError(Exception): ...

def encode_frame(type: FrameType, req_id: int = 0,
                 payload: bytes | str | dict | None = None,
                 flags: int = 0) -> bytes:
    """把一条逻辑帧编码成 WebSocket 二进制消息。

    为什么 payload 允许 str/dict：HEAD/ERROR/NOTIFY 三种帧永远是 JSON，
    调用方写 encode_frame(T.REQ_HEAD, rid, {"method":"GET"}) 比先 dumps 更不容易出错。
    """
    if payload is None:
        body = b""
    elif isinstance(payload, bytes):
        body = payload
    elif isinstance(payload, str):
        body = payload.encode("utf-8")
    elif isinstance(payload, dict):
        # separators 去空格：JSON 头平均省 8%~12% 字节，且确定性输出便于测试断言
        body = json.dumps(payload, ensure_ascii=False,
                          separators=(",", ":")).encode("utf-8")
    else:
        raise TypeError(f"unsupported payload type: {type(payload)}")

    if len(body) > MAX_FRAME:
        raise ProtocolError(
            f"payload {len(body)} exceeds max_frame {MAX_FRAME}; "
            f"caller must split into REQ_BODY/RES_BODY chunks"
        )
    return _HEADER.pack(int(type), pack_req_id(req_id, flags)) + body


def decode_frame(data: bytes) -> Frame:
    """把一条完整的 WebSocket 二进制消息解码成 Frame。

    前置条件：data 恰好是一条完整帧（WebSocket 已保证消息边界）。
    因此这里不做"半包"处理——半包是 FrameParser 的职责（见 §2.4）。
    """
    if len(data) < HEADER_SIZE:
        raise ProtocolError(f"frame too short: {len(data)} < {HEADER_SIZE}")
    raw_type, raw_rid = _HEADER.unpack_from(data, 0)
    try:
        ftype = FrameType(raw_type)
    except ValueError:
        raise ProtocolError(f"unknown frame type: 0x{raw_type:02X}")
    rid, flags = unpack_req_id(raw_rid)
    return Frame(type=ftype, req_id=rid, payload=data[HEADER_SIZE:], flags=flags)
```

#### 2.3.3 payload 序列化方式约定

| 帧类型 | payload 编码 | 校验规则 |
|---|---|---|
| `REQ_HEAD` / `RES_HEAD` / `ERROR` / `NOTIFY` | UTF-8 JSON（`ensure_ascii=False`, `separators=(",",":")`） | 解析失败 → 回 `ERROR{bad_json}` 并关闭该 `req_id` |
| `REQ_BODY` / `RES_BODY` | 原始字节，**禁止**任何编码转换 | 长度计入流控 |
| `REQ_END` / `RES_END` / `CANCEL` / `PING` / `PONG` / `CREDIT` | 空（`b""`） | 若收到非空 payload → 忽略并记 warning |

**为什么 JSON 头不带 Content-Length**：长度由 WebSocket 消息边界天然给出；且 HEAD 帧本身很小（< 1 KB），
省掉一层长度协商能减少一个出错点。

#### 2.3.4 单元测试要求【C1 必须交付】

| 用例 | 断言 |
|---|---|
| 12 种 type 各编码再解码 | `Frame` 全字段相等（含 flags 位） |
| `req_id = 0 / 1 / 0x3FFFFFFF` | 边界值往返一致 |
| `req_id = 0x40000000` | 抛 `AssertionError`（超出 30 位） |
| `flags = FLAG_ENC` 往返 | `frame.enc is True`，`frame.req_id` 仍正确 |
| 空 payload | `payload == b""`，`json == {}` |
| `len(data) = 4` | 抛 `ProtocolError("frame too short")` |
| `type = 0xFF` | 抛 `ProtocolError("unknown frame type")` |
| payload = 65537 字节 | 抛 `ProtocolError`（超 max_frame） |
| 中文路径 JSON | `ensure_ascii=False` 后 payload 含 UTF-8 字节，往返不乱码 |

### 2.4 流式解析器 `FrameParser`（粘包/半包处理）★

> **为什么需要它**：WebSocket 保证消息边界，所以**理论上不需要**。但两个场景必须用它：
> ① **降级模式**（§2.8）下 SSE/POST 是纯字节流，必然粘包/半包；
> ② 电脑端把隧道帧写入**本地回环 socket** 或落盘做协议抓包回放时，读到的是字节流。
> **协议层的正确性必须不依赖传输层**，这是本节存在的理由。

**缓冲区维护策略（这是重点，讲清楚）**：

```
feed(data) 被调用
   │
   ├─ 1. self._buf += data            ← 只追加，不预分配、不切片拷贝整块
   │
   ├─ 2. 循环尝试解析（while True）：
   │     ├─ len(self._buf) < 5 ?        → break（头都不够，等下次 feed）
   │     ├─ 读头 5 字节，得 type / raw_rid
   │     ├─ 判断该 type 是否"自定长"
   │     │    ├─ 定长帧（END/CANCEL/PING/PONG/CREDIT）→ body_len = 0
   │     │    └─ 变长帧（HEAD/BODY/ERROR/NOTIFY）    → body_len = self._length_of(buf)
   │     ├─ len(self._buf) < 5 + body_len ? → break（半包，等下次 feed）
   │     ├─ 切出 body → decode → 追加到 out
   │     └─ self._buf = self._buf[5+body_len:]    ← 只在成功消费后推进
   │
   └─ 3. return out
```

**变长帧的长度怎么来？** 这里必须做一个取舍：

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 头里加长度字段 | 帧头变 9 字节 | ❌ 破坏 WebSocket 模式与降级模式的一致性，且 §2.1 已决策不加 |
| B. **用外层容器长度**（采纳） | 降级模式下，每个逻辑帧用 **4 字节大端长度前缀**包裹后再写入流 | ✅ 帧格式不变，长度信息由"流适配层"提供，协议层零改动 |
| C. 靠 JSON 大括号配对 | 扫描 `{...}` 平衡 | ❌ 原始字节体（REQ_BODY）里可能含 `{}`，无法可靠解析 |

**采纳方案 B**：`FrameParser` 工作在**流适配层**，它假设输入是"长度前缀 + 帧"的序列。
WebSocket 模式下**不经过** `FrameParser`（直接 `decode_frame(ws_message)`）；降级模式下经过。

```python
_LEN = struct.Struct(">I")          # 流适配层长度前缀，4 字节大端

class FrameParser:
    """流式帧解析器：处理粘包/半包。

    输入流格式（降级模式）：
        [4B len][5B header + body] [4B len][5B header + body] ...

    缓冲区策略：
      * self._buf 是 bytearray，追加 O(1) 摊还；
      * 仅在成功解析一帧后才 del self._buf[:n]（推进读指针），
        绝不每帧重新切片整个缓冲区（否则 O(n²)）；
      * 用 self._need 记录"还差多少字节才够一帧"，避免重复解析。
    """

    __slots__ = ("_buf", "_need", "_max_frame", "_bad")

    def __init__(self, max_frame: int = MAX_FRAME) -> None:
        self._buf = bytearray()
        self._need = 4                  # 先要 4 字节长度前缀
        self._max_frame = max_frame
        self._bad = False

    def feed(self, data: bytes) -> list[Frame]:
        if self._bad:
            raise ProtocolError("parser poisoned by previous oversized frame")
        self._buf += data
        out: list[Frame] = []

        while True:
            if len(self._buf) < self._need:
                return out              # 半包：等下次 feed

            if self._need == 4:         # 刚够长度前缀
                (n,) = _LEN.unpack_from(self._buf, 0)
                if n < HEADER_SIZE:
                    self._bad = True
                    raise ProtocolError(f"declared length {n} < header size")
                if n - HEADER_SIZE > self._max_frame:
                    self._bad = True    # 毒化：长度不可信，继续读会吃光内存
                    raise ProtocolError(
                        f"declared length {n} exceeds max_frame {self._max_frame}")
                self._need = 4 + n
                continue

            # 够一整帧了
            frame_bytes = bytes(self._buf[4:self._need])
            del self._buf[:self._need]
            self._need = 4
            out.append(decode_frame(frame_bytes))   # 复用同一套解码，不重复实现
            # 循环继续：缓冲区里可能还粘着下一帧

    @property
    def buffered(self) -> int:
        """当前缓冲区字节数（用于监控告警：持续 > 1 MB 说明对端异常）。"""
        return len(self._buf)


def pack_stream(frames: list[Frame]) -> bytes:
    """把若干帧编码成带长度前缀的字节流（降级模式发送侧用）。"""
    parts = []
    for f in frames:
        raw = encode_frame(f.type, f.req_id, f.payload, f.flags)
        parts.append(_LEN.pack(len(raw)))
        parts.append(raw)
    return b"".join(parts)
```

|---|---|---|

| 逐字节喂 | 循环 `feed(b)` | 最后一次才返回 Frame，中途返回 `[]` |

### 2.5 多路复用器设计 ★

#### 2.5.1 为什么这样设计

一条隧道上要并行跑几十个请求（30 张缩略图 + 1 个上传 + 心跳）。
多路复用的本质是**用 `req_id` 把字节流重新解复用成独立请求**。
两个最容易出 bug 的地方：**`req_id` 回绕**和**超时清理遗漏**——后者会造成 `pending` 表内存泄漏，长期运行必崩。

#### 2.5.2 `req_id` 分配策略

| 方案 | 评价 |
|---|---|
| 全局自增 uint32，回绕到 0 | 简单；回绕时若旧请求还在，会撞号 |
| 随机 30 位 | 撞号概率低但不确定，且测试不可复现 |
| **单调自增 + 回绕时跳过活跃 id**（采纳） | 确定可测，且保证不撞号 |

```python
class ReqIdAllocator:
    """30 位 req_id 分配器。

    回绕策略：自增到 REQ_ID_MASK 后回到 1（0 保留给连接级 CREDIT/心跳）。
    每次分配前检查是否仍在 self._active 中；若在，继续 +1 直到找到空位。
    活跃请求上限设 4096，远超单手机并发（实测峰值 < 100），
    因此"回绕且撞号"在实践中需要 10 亿次请求才会发生一次，但仍要正确实现。
    """
    MAX_ACTIVE = 4096

    def __init__(self) -> None:
        self._next = 1
        self._active: set[int] = set()

    def alloc(self) -> int:
        if len(self._active) >= self.MAX_ACTIVE:
            raise TooManyRequests("tunnel req_id pool exhausted")
        for _ in range(REQ_ID_MASK):
            rid = self._next
            self._next = 1 if rid >= REQ_ID_MASK else rid + 1
            if rid not in self._active:
                self._active.add(rid)
                return rid
        raise TooManyRequests("no free req_id after full scan")

    def release(self, req_id: int) -> None:
        self._active.discard(req_id)
```

**规则**：`req_id = 0` 是**保留值**，禁止分配给业务请求。
用途：`CREDIT` 帧中 `req_id = 0` 表示**连接级**窗口（见 §2.6）；`PING` 的序号从 1 开始。

#### 2.5.3 `pending` 表结构

**为什么不用"每个请求一个 asyncio.Future"**：转发路径需要**边收边转发**，
若用 Future 就得先把整个响应体攒在内存里再 resolve，这与 §2.1"不撑爆内存"的目标直接冲突。
**采纳队列 + Future 混合**：头部用 Future（一次性），响应体用 `asyncio.Queue`（流式）。

```python
@dataclass
class PendingRequest:
    req_id: int
    created_at: float
    deadline: float                      # 绝对超时时刻
    head_ready: asyncio.Future           # 收到 RES_HEAD / ERROR 时 resolve
    body: asyncio.Queue[bytes | None]    # RES_BODY 入队；RES_END 入 None 哨兵
    cancel: asyncio.Event                # 手机断开/客户端取消时置位
    send_credit: int                     # 本请求剩余发送信用（字节）
    recv_unacked: int                    # 已收但未回补的字节数
    bytes_in: int = 0                    # 统计：电脑→云 方向
    bytes_out: int = 0                   # 统计：云→电脑 方向
    done: bool = False
```

| 字段 | 作用 | 清理时机 |
|---|---|---|
| `head_ready` | 让转发协程 await 到响应头 | 收到 `RES_HEAD`/`ERROR` 后 set_result |
| `body` | 流式传递响应体分片 | 收到 `RES_END` 后 put `None` |
| `cancel` | 中断传播（手机关页面 → 停电脑端生成） | `finally` 中 set |
| `send_credit` | 发送侧剩余信用 | 收到 `CREDIT` 时增加 |
| `recv_unacked` | 累计已消费未回补字节 | 每超阈值就发 `CREDIT` 并清零 |

#### 2.5.4 事件循环派发：单读协程 + 单写协程

**为什么单读协程**：WebSocket 的 `recv()` 不能并发调用（不同库行为不一致，易丢帧）。
**为什么单写协程 + 写队列**：`send()` 也不是线程安全的；且流控暂停需要"排队但不发"。

```python
class Mux:
    """一条隧道上的多路复用器。云端与电脑端各持有一个实例。"""

    def __init__(self, ws, side: str, credit_window: int = 8 * 1024 * 1024):
        self.ws = ws
        self.side = side                       # "cloud" | "agent"
        self.allocator = ReqIdAllocator()
        self.pending: dict[int, PendingRequest] = {}
        self._outq: asyncio.Queue[bytes] = asyncio.Queue(maxsize=256)
        self._writer_task = asyncio.create_task(self._writer())
        self._reader_task = asyncio.create_task(self._reader())
        self._sweeper = asyncio.create_task(self._sweep_timeouts())
        self.credit_window = credit_window
        self.conn_credit = credit_window       # 连接级信用（防全连接堆积）

    # ---------- 写侧 ----------
    async def send_frame(self, ftype: FrameType, req_id: int = 0,
                         payload=None, flags: int = 0) -> None:
        raw = encode_frame(ftype, req_id, payload, flags)
        # 入队即返回；真正的背压由 maxsize=256 提供（队列满 → 转发协程被挂起）
        await self._outq.put(raw)

    async def _writer(self) -> None:
        try:
            while True:
                raw = await self._outq.get()
                await self.ws.send_bytes(raw)
        except (ConnectionError, asyncio.CancelledError):
            pass

    # ---------- 读侧 ----------
    async def _reader(self) -> None:
        try:
            while True:
                raw = await self.ws.recv_bytes()
                frame = decode_frame(raw)      # WebSocket 模式直接解码，无 FrameParser
                await self._on_frame(frame)
        except (ConnectionError, ProtocolError):
            await self.shutdown(reason="tunnel_closed")

    async def _on_frame(self, f: Frame) -> None:
        handler = self._HANDLERS.get(f.type)
        if handler is None:
            log.warning("unhandled frame type=%s req_id=%s", f.type, f.req_id)
            return
        await handler(self, f)
```

#### 2.5.5 超时清理

**为什么必须有**：电脑端生成缩略图可能卡死（坏文件、磁盘 IO 阻塞），
若没有超时，`pending` 表只增不减 → 每泄漏 1 条约 1 KB，一天能泄漏几十 MB，且 `req_id` 池耗尽后新请求全部失败。

| 阶段 | 超时值 | 说明 |
|---|---|---|
| 响应头超时 | 30 秒 | 从发出 `REQ_HEAD` 到收到 `RES_HEAD`/`ERROR` |
| 空闲超时（体传输中） | 60 秒 | 两次 `RES_BODY` 之间的最大间隔 |
| 总超时 | 30 分钟 | 兜底（2 GB 文件在 1.5 MB/s 下约 22 分钟） |

```python
HEAD_TIMEOUT   = 30.0
IDLE_TIMEOUT   = 60.0
TOTAL_TIMEOUT  = 1800.0
SWEEP_INTERVAL = 5.0

async def _sweep_timeouts(self) -> None:
    """每 5 秒扫一遍 pending，清理超时请求。O(n)，n < 4096，开销可忽略。"""
    while True:
        await asyncio.sleep(SWEEP_INTERVAL)
        now = time.monotonic()
        for rid, p in list(self.pending.items()):
            if p.done:
                continue
            idle = now - p.last_activity
            too_long = now - p.created_at > TOTAL_TIMEOUT
            if not p.head_ready.done() and now - p.created_at > HEAD_TIMEOUT:
                await self.fail_request(rid, "upstream_head_timeout")
            elif p.head_ready.done() and (idle > IDLE_TIMEOUT or too_long):
                await self.fail_request(rid, "upstream_body_timeout")

async def fail_request(self, rid: int, code: str, message: str = "") -> None:
    """统一的失败收敛路径：通知对端取消 → 让本地等待者醒来 → 释放 req_id。"""
    p = self.pending.get(rid)
    if p is None or p.done:
        return
    p.done = True
    p.cancel.set()
    # ① 让对端停止工作（发 CANCEL，对端幂等处理：不存在就忽略）
    try:
        await self.send_frame(FrameType.CANCEL, rid)
    except Exception:
        pass
    # ② 唤醒本地等待者
    if not p.head_ready.done():
        p.head_ready.set_result({"error": code, "message": message})
    await p.body.put(None)             # 哨兵：结束流式读取
    # ③ 释放
    self.pending.pop(rid, None)
    self.allocator.release(rid)
```

### 2.6 流控 credit 机制 ★

#### 2.6.1 为什么这样设计

> 设计文档 §4.3 的原话：*"没有流控的话，手机下载一个 2 GB 文件时，云端的转发缓冲会直接把 1 GB 内存的 VPS 撑爆。"*

流控的本质：**接收方用自己的"消费速度"反向控制发送方的"生产速度"**。
采用 **credit（信用）** 而不是 TCP 式窗口缩放，因为实现简单、语义清晰、可测。

#### 2.6.2 参数

| 参数 | 值 | 说明 |
|---|---|---|
| `credit_window` | **8 MB**（`8388608`） | 每个方向、**每个 req_id** 的初始窗口，由 `HELLO_ACK` 下发 |
| `conn_credit_window` | 16 MB | 连接级总窗口，防止 30 个并发各占 8 MB（=240 MB） |
| `CREDIT_THRESHOLD` | 512 KB | 消费满 512 KB 回补一次，避免每 4 KB 发一个 CREDIT 帧 |
| `CREDIT_DEADLOCK_TIMEOUT` | 30 秒 | 信用耗尽后多久没收到 CREDIT 就强制关掉该 req_id |

#### 2.6.3 发送方状态机（每个 req_id 独立）

```
        ┌──────────────┐
        │   RUNNING    │  credit > 0：可继续发 BODY
        └──────┬───────┘
               │ 发出 N 字节后 credit -= N
               ▼
      credit == 0 ?
        ├─ 否 → 留在 RUNNING
        └─ 是 → ┌──────────────┐
                │   PAUSED     │  不再发 BODY；其他 req_id 不受影响
                └──────┬───────┘  同时启动 30s 死锁计时器
                       │
        收到 CREDIT(rid, n)  ──► credit += n；取消计时器 → 回到 RUNNING
                       │
        30s 内无 CREDIT ──► ┌──────────────┐
                            │  DEADLOCKED  │ 发 ERROR{credit_deadlock}
                            └──────┬───────┘ → 释放 req_id（对端若后来补信用，忽略即可）
```

**关键：暂停是"该 req_id 暂停"，不是"整条连接暂停"。**
实现上用一个 `asyncio.Event`：信用为 0 时 `clear()`，补上时 `set()`；发送循环 `await ev.wait()`。

```python
class FlowController:
    """单个方向的 credit 流控。发送侧与接收侧各用一个实例。"""

    def __init__(self, window: int, mux: "Mux", on_deadlock):
        self.window = window
        self.mux = mux
        self.on_deadlock = on_deadlock
        self._credit: dict[int, int] = {}         # rid -> 剩余信用
        self._gate: dict[int, asyncio.Event] = {} # rid -> 放行信号
        self._stall_at: dict[int, float] = {}     # rid -> 开始暂停的时刻
        self.conn_used = 0                        # 连接级已用信用

    def open(self, rid: int) -> None:
        self._credit[rid] = self.window
        ev = asyncio.Event(); ev.set()
        self._gate[rid] = ev

    def close(self, rid: int) -> None:
        self._credit.pop(rid, None)
        self._gate.pop(rid, None)
        self._stall_at.pop(rid, None)

    async def send_body(self, rid: int, chunk: bytes) -> None:
        """发送一块响应/请求体，自动遵守信用。调用方不需要自己判断。"""
        offset = 0
        while offset < len(chunk):
            await self._gate[rid].wait()           # 信用耗尽时在这里挂起
            avail = min(self._credit[rid], len(chunk) - offset)
            if avail <= 0:
                self._gate[rid].clear()
                self._stall_at.setdefault(rid, time.monotonic())
                continue
            piece = chunk[offset:offset + avail]
            await self.mux.send_frame(FrameType.RES_BODY, rid, piece)
            self._credit[rid] -= avail
            offset += avail

    async def on_credit(self, rid: int, n: int) -> None:
        if rid == 0:                                # 连接级信用
            self.conn_used = max(0, self.conn_used - n)
            return
        if rid not in self._credit:
            return                                  # 请求已结束，忽略
        self._credit[rid] += n
        self._stall_at.pop(rid, None)
        self._gate[rid].set()

    async def check_deadlock(self) -> None:
        """由 mux 的 sweeper 每 5 秒调用一次。"""
        now = time.monotonic()
        for rid, t0 in list(self._stall_at.items()):
            if now - t0 > CREDIT_DEADLOCK_TIMEOUT:
                self._stall_at.pop(rid, None)
                await self.on_deadlock(rid, "credit_deadlock")
```

#### 2.6.4 接收方回补时机

```python
class CreditReceiver:
    """接收侧：消费 N 字节后回补 CREDIT。"""

    def __init__(self, mux: "Mux", threshold: int = 512 * 1024):
        self.mux = mux
        self.threshold = threshold
        self._unacked: dict[int, int] = {}

    async def consumed(self, rid: int, n: int) -> None:
        """每把一块 BODY 字节写出去（给手机 / 给本地 handler），就调一次。"""
        total = self._unacked.get(rid, 0) + n
        if total >= self.threshold:
            self._unacked[rid] = 0
            await self.mux.send_frame(FrameType.CREDIT, rid, struct.pack(">I", total))
        else:
            self._unacked[rid] = total

    async def flush(self, rid: int) -> None:
        """RES_END 前把零头补上，避免最后一次不足阈值的信用永久丢失。"""
        rest = self._unacked.pop(rid, 0)
        if rest:
            await self.mux.send_frame(FrameType.CREDIT, rid, struct.pack(">I", rest))
```

**CREDIT 帧 payload 编码**：4 字节大端无符号整数（要补的字节数）。
**为什么不用 JSON**：CREDIT 是高频帧（每 512 KB 一次，下载 2 GB 会发 4000 次），
4 字节二进制比 `{"n":524288}` 省 90% 字节。

#### 2.6.5 死锁防护：对端一直不回 CREDIT 怎么办 ★

这是设计文档没有展开、但**必须明确**的场景。三种可能原因与对应处置：

| 原因 | 现象 | 处置 |
|---|---|---|
| 对端进程卡死（线程池被 Pillow 占满） | 30 秒无任何帧 | 触发死锁超时 → 关该 `req_id` + 回 `ERROR` 给手机；同时计一次健康告警 |
| 对端逻辑 bug（忘记调 `consumed()`） | 其他 req_id 正常，仅此 req_id 卡住 | 同上；日志打 `credit_deadlock` 并附 `rid`/`stalled_bytes`，便于定位 |
| 对端故意不发（恶意） | 大量 req_id 同时卡住 | 连接级信用也耗尽 → 触发连接级死锁（见下）→ 主动断连并退避重连 |

**连接级死锁**：当 `conn_used` 达到连接级窗口且 60 秒内无任何 CREDIT 帧到达，
判定整条隧道不可信，**主动 `close()` 并进入重连流程**（§2.7）。

```python
CONN_DEADLOCK_TIMEOUT = 60.0

async def _watch_conn_credit(self) -> None:
    while True:
        await asyncio.sleep(10)
        if (self.fc.conn_used >= self.conn_credit_window
                and time.monotonic() - self._last_credit_at > CONN_DEADLOCK_TIMEOUT):
            log.error("connection-level credit deadlock, forcing reconnect")
            await self.shutdown(reason="conn_credit_deadlock", reconnect=True)
```

#### 2.6.6 流控测试要求【C1 必须】

| 用例 | 做法 | 断言 |
|---|---|---|
| 正常回补 | 对端每收 512 KB 回 CREDIT | 全程无暂停，吞吐 ≥ 100 MB/s（本机） |
| 信用耗尽暂停 | 对端只收不回 | 发送方发出量 ≤ 8 MB 后停止 |
| 只暂停一个 req_id | rid=1 不回信用，rid=2 正常 | rid=2 完整传完，rid=1 卡住 |
| 死锁超时 | 信用耗尽后 30 秒不管 | 收到 `ERROR{credit_deadlock}`，`pending` 表中该 rid 已清除 |
| 内存上界 | 传 2 GB 假数据 | 进程 RSS 增量 < 64 MB |
| 零头回补 | 最后一块不足 512 KB | 收到一次 CREDIT，数值 = 零头字节数 |

### 2.7 心跳与断线重连

#### 2.7.1 心跳

| 参数 | 值 | 理由 |
|---|---|---|
| `HEARTBEAT_SEC` | **25 秒**（`HELLO_ACK` 下发） | 小于多数 NAT/代理的空闲超时（常见 30–60 秒） |
| `PONG_TIMEOUT` | **75 秒**（3 个周期） | 容忍单次丢包/一次 GC 停顿，又能在 1 分半内发现断线 |
| `PING` 序号 | `req_id` 从 1 单调自增 | 防乱序误判；`PONG` 必须回显同号 |
| 超时动作 | 关闭连接 → 走重连 | 见下 |

**为什么不用 WebSocket 自带的 ping/pong**：部分反向代理（Nginx/Caddy）不转发控制帧，
且应用层心跳能顺带携带"当前活跃 req_id 数"用于监控。

```python
class Heartbeat:
    def __init__(self, mux: "Mux", interval: float = 25.0):
        self.mux = mux
        self.interval = interval
        self.timeout = interval * 3                    # 75s
        self._seq = 0
        self._last_pong = time.monotonic()
        self._task = asyncio.create_task(self._loop())

    async def _loop(self) -> None:
        while True:
            await asyncio.sleep(self.interval)
            if time.monotonic() - self._last_pong > self.timeout:
                log.warning("heartbeat lost for %.0fs, closing tunnel",
                            time.monotonic() - self._last_pong)
                await self.mux.shutdown(reason="heartbeat_timeout", reconnect=True)
                return
            self._seq += 1
            # PING 的 req_id 用序号，不用业务 req_id 池（避免污染 pending 表）
            await self.mux.send_frame(FrameType.PING, self._seq)

    async def on_pong(self, seq: int) -> None:
        self._last_pong = time.monotonic()
```

**对端处理**：收到 `PING` **必须立即**回 `PONG`（同 `req_id`），
且心跳处理**不得**排在任何业务处理之后——否则大文件传输会把心跳饿死，导致对端误判断线。

#### 2.7.2 断线重连（指数退避 + 抖动）

```python
RECONNECT_BASE = 1.0
RECONNECT_MAX  = 60.0
RECONNECT_JITTER = 0.20        # ±20% 抖动

def next_backoff(attempt: int) -> float:
    """attempt 从 0 开始：1,2,4,8,16,32,60,60,...
    为什么要抖动：云服务器重启时，所有电脑会在同一时刻重连（惊群）。
    抖动把重连时刻打散，避免把刚起来的云再打挂。"""
    base = min(RECONNECT_BASE * (2 ** attempt), RECONNECT_MAX)
    return base * (1 + random.uniform(-RECONNECT_JITTER, RECONNECT_JITTER))

async def run_tunnel_forever(cfg) -> None:
    attempt = 0
    while True:
        try:
            await connect_and_serve(cfg)          # 正常返回 = 服务端要求重连
            attempt = 0                            # 连上并稳定运行过 → 重置退避
        except (ConnectionError, OSError, asyncio.TimeoutError) as e:
            log.warning("tunnel down: %s", e)
        except Exception:
            log.exception("unexpected tunnel error")
        delay = next_backoff(attempt)
        attempt = min(attempt + 1, 10)             # 上限 60s，attempt 不必无限涨
        log.info("reconnect in %.1fs (attempt %d)", delay, attempt)
        await asyncio.sleep(delay)
```

**`attempt` 何时重置**：进入 `connect_and_serve` 后，**成功完成 HELLO_ACK 并稳定运行 ≥ 30 秒**才重置。
若连上就掉（如 token 无效），不重置，避免"1 秒一次疯狂重试"打爆云端。

#### 2.7.3 重连后的会话恢复

| 事项 | 做法 |
|---|---|
| 重新 HELLO | 必须；`HELLO` 带 `device_id`，云端用新连接**覆盖**内存 map 中的旧连接 |
| 旧连接上的 pending 请求 | **全部回 ERROR**，见下 |
| 上传续传 | 不依赖隧道状态；手机重新 `GET /api/uploads/{id}` 拿 `offset` |
| 未发出的写队列 | 丢弃（`_outq` 清空），因为语义上"这次请求已失败" |
| 云端设备状态 | 新连接覆盖后立即置 `online`；旧连接的 `shutdown` 不得把新连接置为 offline |

**为什么旧 pending 必须回 ERROR 而不是静默丢弃**：
若不回，手机端会一直等到 30 秒头超时，用户看到的是"转圈 30 秒后失败"；
立即回 ERROR 则是"1 秒内明确报错 + 自动重试"，体验差距巨大。

```python
async def shutdown(self, reason: str, reconnect: bool = False) -> None:
    if self._closed:
        return
    self._closed = True

    # ① 先把所有 pending 收敛掉（在关闭连接之前，日志里能带上原因）
    for rid, p in list(self.pending.items()):
        if not p.done:
            p.done = True
            if not p.head_ready.done():
                p.head_ready.set_result(
                    {"error": "tunnel_closed", "message": reason})
            await p.body.put(None)
        self.allocator.release(rid)
    self.pending.clear()

    # ② 取消后台任务
    for t in (self._reader_task, self._writer_task, self._sweeper):
        t.cancel()

    # ③ 关连接（注意：云端必须防止"旧连接关闭时把新连接置 offline"）
    try:
        await self.ws.close()
    except Exception:
        pass

    # ④ 通知上层
    await self.on_closed(reason, reconnect)
```

**云端防误标离线（竞态）**：

```python
async def unregister(self, device_id: str, conn: "TunnelConnection") -> None:
    """只有"当前注册的仍然是这条连接"时才移除。"""
    cur = self._registry.get(device_id)
    if cur is conn:                       # 身份比对，而非存在性判断
        self._registry.pop(device_id, None)
        await self.set_device_offline(device_id)
    else:
        log.info("stale connection closed for %s, ignored", device_id)
```

### 2.8 降级模式：SSE + POST 长轮询【一期预留，二期实现】

> 设计文档 §14 风险表：*"运营商 NAT / 企业防火墙拦 WebSocket → 协议支持降级为 SSE + POST 长轮询，帧格式不变"*。

| 项 | 设计 |
|---|---|
| 上行（电脑→云） | `GET /agent/stream`，`Content-Type: text/event-stream`，每帧一个 `data:` 事件，payload 为 base64 或直接二进制（用 `application/octet-stream` 分块） |
| 下行（云→电脑） | `POST /agent/push`，body = `pack_stream(frames)`（§2.4 的长度前缀流） |
| 帧格式 | **完全不变**，只多一层长度前缀 |
| 复用点 | 电脑端只替换"传输适配器"（`WsTransport` → `SseTransport`），`Mux`/`FlowController`/业务逻辑零改动 |
| 一期状态 | 只定义接口与 `pack_stream`/`FrameParser`（**已实现**，因为它们是纯函数且被测试覆盖），传输适配器二期写 |

```python
class Transport(Protocol):
    async def send_bytes(self, raw: bytes) -> None: ...
    async def recv_bytes(self) -> bytes: ...
    async def close(self) -> None: ...
```

**一期必须做的准备**：`Mux` 构造函数接收 `Transport` 而不是具体 `websockets.ClientConnection`，
这样二期加降级模式时，改动面只有 `tunnel.py` 的一个工厂函数。


**`HELLO_ACK` 参数**：

| 字段 | 类型 | 值 | 说明 |
|---|---|---|---|

### 3.2 设备注册表

#### 3.2.1 为什么用内存 map

| 方案 | 评价 |
|---|---|
| 内存 map | ✅ 零延迟、零依赖；进程重启后电脑 1 秒内自动重连即恢复 |
| Redis | ❌ 为单用户项目引入一个中间件，运维成本远超收益 |
| 数据库 | ❌ 每次请求查库 + 连接状态本身是易失的，存库无意义 |

**结论**：内存 map 是唯一正确的选择。代价是"多进程部署不可行"——因此 **Relay 必须单进程运行**
（`uvicorn --workers 1`）。这一点必须在 [08 部署手册](08-部署与运维手册.md) 里写明。

#### 3.2.2 数据结构

```python
@dataclass
class TunnelConnection:
    device_id: str
    account_id: str
    ws: Any                                  # websockets / starlette WebSocket
    mux: "Mux"
    connected_at: float
    last_frame_at: float
    version: str
    lan_ips: list[str]
    caps: set[str]
    inflight: int = 0                        # 当前活跃 req_id 数
    bytes_in_today: int = 0                  # 电脑→云（下载方向）
    bytes_out_today: int = 0                 # 云→电脑（上传方向）

class DeviceRegistry:
    """device_id → TunnelConnection。

    并发安全：FastAPI 是单事件循环，dict 读写天然原子（无 await 穿插时）。
    但 register/unregister 之间有 await（写库、发通知），
    因此必须用 asyncio.Lock 保护"检查-修改"复合操作，避免两条连接同时注册。
    """

    def __init__(self) -> None:
        self._map: dict[str, TunnelConnection] = {}
        self._lock = asyncio.Lock()

    async def register(self, conn: TunnelConnection) -> None:
        async with self._lock:
            old = self._map.get(conn.device_id)
            self._map[conn.device_id] = conn        # 覆盖旧连接
        if old is not None:
            # 旧连接必须主动踢掉，否则它还在收帧、造成"双份响应"
            log.info("device %s reconnected, closing stale tunnel", conn.device_id)
            await old.mux.shutdown(reason="superseded_by_new_connection")

    async def unregister(self, conn: TunnelConnection) -> None:
        async with self._lock:
            if self._map.get(conn.device_id) is conn:   # 身份比对，防竞态
                self._map.pop(conn.device_id, None)

    def get(self, device_id: str) -> TunnelConnection | None:
        return self._map.get(device_id)              # 只读，无需加锁

    def is_online(self, device_id: str) -> bool:
        c = self._map.get(device_id)
        return c is not None and not c.mux.closed
```

**为什么 `unregister` 要身份比对**：电脑重连时，新连接先注册覆盖，旧连接的 `finally` 随后才执行 `unregister`。
若只判断"key 存在"就 pop，会把**刚建立的新连接**删掉，导致设备永远显示离线。这是真实会踩的坑。

#### 3.2.3 并发安全小结

| 场景 | 是否需要锁 | 说明 |
|---|---|---|
| `get` / `is_online` | 否 | 单次 dict 读，无 await |
| `register` / `unregister` | **是** | 含 await（关旧连接、写库） |
| 遍历所有连接发通知 | 否（用快照） | `list(self._map.values())` 先快照，避免迭代中被改 |
| 带宽计数累加 | 否 | 单事件循环内 `+=` 原子；落库由独立任务做 |

### 3.3 请求转发路径 ★

#### 3.3.1 为什么这样设计

设计文档 §4.5 要求"云边收边转发，不缓冲整个响应体"。
这意味着**转发协程不能是 `response = await forward(); return response`** 这种阻塞式写法，
而必须是"把隧道来的字节**流式**喂给 HTTP 响应"。

**采纳方案：`asyncio.Queue` + 异步生成器 + `StreamingResponse`。**

#### 3.3.2 路由挂载

```python
# main.py
app = FastAPI()
app.include_router(auth.router)          # /api/auth/*
app.include_router(devices.router)       # /api/devices/*
app.add_api_websocket_route("/agent/ws", tunnel.agent_ws)

# 透明转发：捕获 /d/{device_id}/ 下的任意方法、任意路径
@app.api_route("/d/{device_id}/{path:path}",
               methods=["GET", "POST", "PATCH", "PUT", "DELETE", "HEAD", "OPTIONS"])
async def relay(device_id: str, path: str, request: Request):
    return await tunnel.forward(device_id, path, request)
```

**为什么用 `api_route` 而不是自己写 ASGI 中间件**：
FastAPI 路由能天然复用依赖注入（鉴权、限流），且路径参数解析免费。

#### 3.3.3 完整转发流程（逐步）

```
手机 GET https://域名/d/{device_id}/api/timeline?cursor=...&limit=100
 │
 ├─ ① auth.check_client_token(request)
 │      Header: Authorization: Bearer <client_token>
 │      校验：token 哈希命中 clients 表 && clients.device_id == 路径 device_id && !revoked
 │      失败 → 401 {"error":"unauthorized"}
 │
 ├─ ② 限流 rate_limit(client_id, 120 req/s)      ← §3.8
 │      超限 → 429 {"error":"rate_limited", "retry_after_ms": n}
 │
 ├─ ③ conn = registry.get(device_id)
 │      为 None → 503 {"error":"device_offline"}   ← §3.7
 │
 ├─ ④ 单设备并发上限检查 conn.inflight < 64
 │      超限 → 429 {"error":"device_busy"}
 │
 ├─ ⑤ rid = conn.mux.allocator.alloc()
 │      p = PendingRequest(rid, ...) 写入 pending；fc.open(rid)
 │
 ├─ ⑥ 组装 REQ_HEAD 并发送：
 │      {"method": "GET",
 │       "path": "/api/timeline",              ← 去掉 /d/{device_id} 前缀
 │       "query": {"cursor": "...", "limit": "100"},
 │       "headers": {"accept": "application/json",
 │                   "user-agent": "...",
 │                   "x-pb-client": "小米14"},  ← 白名单过滤，见下
 │       "enc": null}
 │
 ├─ ⑦ 若有请求体（POST/PATCH）→ 流式读 request.stream() → REQ_BODY × N → REQ_END
 │      无请求体 → 直接 REQ_END
 │
 ├─ ⑧ 等待 p.head_ready（超时 30s）
 │      {"error": "..."} → 把隧道错误映射成 HTTP 状态返回（§6.1）
 │      {"status": 200, "headers": {...}} → 继续
 │
 ├─ ⑨ return StreamingResponse(body_iter(p), status_code=..., headers=过滤后的响应头)
 │
 └─ ⑩ body_iter 边从 p.body 取字节边 yield；同时调 credit.consumed(rid, n) 回补信用
        取到 None 哨兵 → 结束 → fc.close(rid)、allocator.release(rid)
```

**请求头白名单（必须）**：**禁止**原样透传 `Authorization`、`Cookie`、`Host`、`Content-Length`。

```python
FORWARD_REQ_HEADERS = {
    "accept", "accept-language", "content-type", "range",
    "if-none-match", "if-modified-since", "user-agent",
}
# 为什么必须过滤：Authorization 里是给云的 client_token，透传给电脑毫无意义，
# 且会在电脑端日志里留下凭证。Host 透传会让电脑端的 URL 生成逻辑出错。
```

**响应头白名单**：

```python
FORWARD_RES_HEADERS = {
    "content-type", "content-length", "content-range", "accept-ranges",
    "etag", "last-modified", "cache-control", "content-disposition",
}
# 为什么过滤：隧道帧里若带 transfer-encoding，FastAPI 会与自身的分块编码冲突，
# 产生 "Content-Length mismatch" 之类的诡异错误。
```

#### 3.3.4 流式转发实现（核心代码骨架）

```python
async def forward(device_id: str, path: str, request: Request) -> Response:
    client = await auth.check_client_token(request)          # ① 鉴权
    await rate_limit.check(client.id)                        # ② 限流

    conn = registry.get(device_id)                           # ③ 在线判定
    if conn is None:
        return JSONResponse({"error": "device_offline"}, status_code=503)

    if conn.inflight >= MAX_INFLIGHT_PER_DEVICE:             # ④ 并发上限
        return JSONResponse({"error": "device_busy"}, status_code=429)

    rid = conn.mux.allocator.alloc()
    p = conn.mux.new_pending(rid, total_timeout=TOTAL_TIMEOUT)
    conn.inflight += 1
    try:
        # ⑥ 发头
        await conn.mux.send_frame(FrameType.REQ_HEAD, rid, {
            "method": request.method,
            "path": "/" + path,
            "query": dict(request.query_params),
            "headers": pick(request.headers, FORWARD_REQ_HEADERS),
            "enc": None,                                     # 二期 E2E 用
        })

        # ⑦ 流式发体（关键：不能 await request.body()，那会把 2 GB 上传吃进内存）
        if request.method in ("POST", "PATCH", "PUT"):
            async for chunk in request.stream():
                await conn.mux.fc.send_body_req(rid, chunk)   # 受 credit 约束
                await traffic.add_out(conn, len(chunk))
        await conn.mux.send_frame(FrameType.REQ_END, rid)

        # ⑧ 等响应头
        head = await asyncio.wait_for(p.head_ready, timeout=HEAD_TIMEOUT + 5)
        if "error" in head:
            return map_tunnel_error(head)

        # ⑨ 流式响应
        return StreamingResponse(
            _body_iter(conn, p),
            status_code=head["status"],
            headers=pick(head.get("headers", {}), FORWARD_RES_HEADERS),
            media_type=None,                                 # 由 content-type 头决定
        )
    except asyncio.TimeoutError:
        await conn.mux.fail_request(rid, "upstream_timeout")
        return JSONResponse({"error": "upstream_timeout"}, status_code=504)
    except asyncio.CancelledError:
        # 手机主动断开：必须通知电脑停止生成缩略图，否则电脑白白烧 CPU
        await conn.mux.fail_request(rid, "client_gone")
        raise
    finally:
        conn.inflight -= 1


async def _body_iter(conn: "TunnelConnection", p: PendingRequest):
    """从隧道队列流式取出响应体，边发边回补信用。

    为什么是 async generator 而不是 list：StreamingResponse 会逐块 send，
    内存里任意时刻只有一个 chunk（≤ 64 KB），而不是整个文件。
    """
    recv = CreditReceiver(conn.mux)
    try:
        while True:
            chunk = await p.body.get()
            if chunk is None:                    # RES_END 哨兵
                break
            yield chunk
            await recv.consumed(p.req_id, len(chunk))
            await traffic.add_in(conn, len(chunk))
    finally:
        # 无论正常结束、客户端断开、异常，都必须收敛：
        await recv.flush(p.req_id)
        conn.mux.release(p.req_id)
```

**必须验证的行为**（C1 测试用例）：

| 用例 | 断言 |
|---|---|
| 转发 100 MB 响应 | 云端进程 RSS 增量 < 20 MB |
| 手机中途断开（`curl` Ctrl-C） | 电脑端收到 `CANCEL`，生成任务被取消 |
| 电脑端返回 404 | 手机收到 404 且 body 原样 |
| 电脑端返回 500 + 自定义头 | 状态码与白名单头透传正确 |
| 上传 100 MB 到电脑 | 云端 RSS 增量 < 20 MB |

### 3.4 请求体的流式接收

**核心约束**：**禁止**在云端调用 `await request.body()`。它会把整个请求体读进内存，
一个 2 GB 上传直接打死 1 GB 的 VPS。必须用 `request.stream()`。

| 事项 | 做法 |
|---|---|
| 分块大小 | Starlette 默认按 `http.disconnect` 事件切块，通常 64 KB；无需手工调 |
| 流控 | 每块经 `fc.send_body_req(rid, chunk)`，受 8 MB 信用约束 |
| 背压传导 | 信用耗尽 → 转发协程挂起 → Starlette 停止从 socket 读 → TCP 窗口收缩 → 手机侧 XHR 变慢（**端到端背压，这是正确的**） |
| 中途断开 | `request.stream()` 抛 `ClientDisconnect` → 走 `fail_request` → 发 `CANCEL` 给电脑 |
| 已收字节记账 | 每块累加 `conn.bytes_out_today` 与 session 的 `received`（在电脑端计） |

```python
async def send_body_req(self, rid: int, chunk: bytes) -> None:
    """与 send_body 相同的信用逻辑，但帧类型是 REQ_BODY。"""
    offset = 0
    while offset < len(chunk):
        await self._gate[rid].wait()
        avail = min(self._credit[rid], len(chunk) - offset)
        if avail <= 0:
            self._gate[rid].clear(); continue
        await self.mux.send_frame(FrameType.REQ_BODY, rid, chunk[offset:offset+avail])
        self._credit[rid] -= avail
        offset += avail
```

### 3.5 配对码生成与校验

#### 3.5.1 为什么这样设计

设计文档 §8.2：*"6 位配对码 + 二维码 → 云校验码（5 分钟有效、错 5 次锁 10 分钟）"*。
6 位数字只有 100 万种可能，**防爆破是唯一的安全支柱**，因此：

1. **码必须用 CSPRNG 生成**（`secrets`，不能用 `random`）
2. **错误次数限制必须落在"设备维度"和"IP 维度"两层**
3. **校验必须是常数时间比较**（虽然 6 位数字的时间侧信道风险极低，但成本为零）
4. **码只能用一次**（成功即删）

#### 3.5.2 生成

```python
CODE_TTL      = 300          # 5 分钟
MAX_TRIES     = 5            # 单码错误上限
LOCK_DURATION = 600          # 锁 10 分钟

async def issue_code(device_id: str) -> str:
    """生成并持久化一个配对码。同一设备已有未过期码时先作废（保证托盘上只显示一个有效码）。"""
    async with db.write() as conn:
        conn.execute("DELETE FROM pair_codes WHERE device_id=?", (device_id,))
        for _ in range(10):                       # 防撞码重试
            code = f"{secrets.randbelow(1_000_000):06d}"
            try:
                conn.execute(
                    "INSERT INTO pair_codes(code, device_id, expires_at, tries) "
                    "VALUES(?,?,?,0)",
                    (code, device_id, time.time() + CODE_TTL))
                return code
            except sqlite3.IntegrityError:
                continue
        raise RuntimeError("failed to allocate unique pair code")
```

#### 3.5.3 校验（含防爆破）

```python
@dataclass
class PairAttempt:
    count: int = 0
    locked_until: float = 0.0

# 内存中的爆破防护：key 为 (device_id) 与 (client_ip) 两个维度
_attempts: dict[str, PairAttempt] = defaultdict(PairAttempt)

async def verify_code(device_id: str, code: str, client_ip: str,
                      client_name: str) -> str:
    """校验配对码并签发 client_token。返回明文 token（仅此一次可见）。"""
    now = time.time()

    # ① 设备维度锁定检查（主防护）
    att = _attempts[f"dev:{device_id}"]
    if att.locked_until > now:
        raise PairLocked(retry_after=int(att.locked_until - now))

    # ② IP 维度锁定检查（防换设备刷；阈值放宽，因为家庭/公司可能 NAT 共用出口）
    ip_att = _attempts[f"ip:{client_ip}"]
    if ip_att.locked_until > now:
        raise PairLocked(retry_after=int(ip_att.locked_until - now))

    # ③ 查码（注意：不区分"码不存在"与"码已过期"，统一回"无效"，
    #    否则攻击者能通过错误文案差异判断某个码是否曾经存在）
    row = db.query_one(
        "SELECT device_id, expires_at, tries FROM pair_codes WHERE code=?", (code,))
    if row is None or row["device_id"] != device_id or row["expires_at"] < now:
        await _bump_failure(device_id, client_ip)
        raise PairInvalid("配对码无效或已过期")

    if row["tries"] >= MAX_TRIES:
        await _lock(device_id, client_ip)
        raise PairLocked(retry_after=LOCK_DURATION)

    # ④ 常数时间比较（本处比较的是"路径 device_id 是否匹配"，避免时序泄漏）
    if not hmac.compare_digest(str(row["device_id"]), str(device_id)):
        await _bump_failure(device_id, client_ip)
        raise PairInvalid("配对码无效或已过期")

    # ⑤ 成功：删码 + 清零计数 + 签发 token
    token = secrets.token_urlsafe(32)
    async with db.write() as conn:
        conn.execute("DELETE FROM pair_codes WHERE code=?", (code,))
        conn.execute(
            "INSERT INTO clients(id, device_id, name, token_hash, last_seen, "
            "created_at, revoked) VALUES(?,?,?,?,?,?,0)",
            (secrets.token_hex(8), device_id, client_name,
             sha256_hex(token), now, now))
    _attempts.pop(f"dev:{device_id}", None)
    _attempts.pop(f"ip:{client_ip}", None)
    return token


async def _bump_failure(device_id: str, client_ip: str) -> None:
    dev = _attempts[f"dev:{device_id}"]
    dev.count += 1
    if dev.count >= MAX_TRIES:
        dev.locked_until = time.time() + LOCK_DURATION
        dev.count = 0
        log.warning("pair lock engaged for device=%s ip=%s", device_id, client_ip)
    ip = _attempts[f"ip:{client_ip}"]
    ip.count += 1
    if ip.count >= MAX_TRIES * 4:                 # IP 维度阈值放宽 4 倍
        ip.locked_until = time.time() + LOCK_DURATION
        ip.count = 0
```

### 3.6 带宽计数的写入策略

#### 3.6.1 为什么不能每次请求写库

设计文档 §3.2 有 `traffic(device_id, day, bytes_in, bytes_out)` 表。
若每转发一个 64 KB chunk 就 `UPDATE`，一次原图下载会产生 64 次写事务；
云端 SQLite 在 WAL 下虽能承受，但**写锁争用会拖慢转发路径**，且毫无必要。

#### 3.6.2 三层策略

```
① 内存累加（零成本）
   conn.bytes_in_today  += n          # 每个 chunk 一行代码

② 定时刷库（每 30 秒）
   flush 任务遍历 registry 中所有连接，把累加值 UPSERT 进 traffic 表

③ 按天聚合
   PRIMARY KEY(device_id, day) + UPSERT(+=)，
   天然按天一行，不会随请求数增长
```

```python
FLUSH_INTERVAL = 30.0

class TrafficCounter:
    def __init__(self, registry: DeviceRegistry):
        self.registry = registry
        self._pending: dict[tuple[str, str], list[int]] = {}
        self._lock = asyncio.Lock()

    async def add_in(self, conn: TunnelConnection, n: int) -> None:
        """电脑→手机方向（下载）。纯内存操作，无 await 竞争。"""
        conn.bytes_in_today += n

    async def add_out(self, conn: TunnelConnection, n: int) -> None:
        """手机→电脑方向（上传）。"""
        conn.bytes_out_today += n

    async def _flush_loop(self) -> None:
        while True:
            await asyncio.sleep(FLUSH_INTERVAL)
            await self.flush()

    async def flush(self) -> None:
        day = time.strftime("%Y-%m-%d", time.gmtime())
        rows = []
        for conn in list(self.registry._map.values()):
            if conn.bytes_in_today or conn.bytes_out_today:
                rows.append((conn.device_id, day,
                             conn.bytes_in_today, conn.bytes_out_today))
                conn.bytes_in_today = 0
                conn.bytes_out_today = 0
        if not rows:
            return
        async with db.write() as c:                 # 单写连接，一次事务写全部
            c.executemany(
                "INSERT INTO traffic(device_id, day, bytes_in, bytes_out) "
                "VALUES(?,?,?,?) ON CONFLICT(device_id, day) DO UPDATE SET "
                "bytes_in = bytes_in + excluded.bytes_in, "
                "bytes_out = bytes_out + excluded.bytes_out", rows)
```

**进程退出时必须 flush**（`@app.on_event("shutdown")` 调 `await traffic.flush()`），
否则最后 30 秒的流量会丢。丢计数不致命，但会让"带宽用量"显示不准。

### 3.7 离线判定与 503 响应

| 判定条件 | 结果 |
|---|---|
| `registry.get(device_id)` 为 `None` | `503 {"error":"device_offline"}` |
| 连接存在但 `last_frame_at` 超过 75 秒 | 视为离线（连接可能"假死"，TCP 还没超时） |
| 设备被 `revoked` | `403 {"error":"device_revoked"}` |
| `device_id` 不属于该账号 | `404 {"error":"device_not_found"}` |

```python
STALE_AFTER = 75.0        # 与心跳 PONG 超时一致

def is_online(self, device_id: str) -> bool:
    c = self._map.get(device_id)
    if c is None or c.mux.closed:
        return False
    return (time.monotonic() - c.last_frame_at) < STALE_AFTER
```

**为什么要有 `last_frame_at` 判定**：TCP 连接在"电脑休眠"场景下不会立刻断开，
云端可能持续 15 分钟以为它还活着，期间所有请求都会挂到 30 秒超时。
用 `last_frame_at` 兜底，让手机在 75 秒内就能看到"离线"，而不是"转圈 30 秒"。

**503 响应体约定**（[04 接口文档](04-接口设计文档.md) 同步）：

```json
{
  "error": "device_offline",
  "message": "电脑未开机或 PhotoBridge 未运行",
  "retryable": true,
  "retry_after_ms": 3000
}
```

**手机端配合**：设计文档 §9.4 要求"不缓存失败状态超过 30 秒"。
实现上手机端对 503 做 **3 秒退避 + 最多 5 次自动重试**，之后转手动"重试"按钮。

### 3.8 限流设计

#### 3.8.1 方案选择

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 固定窗口计数 | 实现最简单 | 窗口边界突发可达 2× 限额 | ❌ |
| 滑动窗口日志 | 精确 | 每请求存时间戳，内存 O(请求数) | ❌ 单用户场景过重 |
| **令牌桶**（采纳） | 允许短时突发（时间线一次拉 30 张缩略图是正常的）、内存 O(1) | 实现稍复杂 | ✅ |

**为什么令牌桶适合这里**：手机打开时间线会**瞬间并发 30 个缩略图请求**。
固定窗口会在边界把它判成"超限"，令牌桶只要桶有容量就放行，桶容量设为 `rate × 0.5`（60 个令牌）刚好覆盖这种突发。

#### 3.8.2 参数

| 维度 | 速率 | 桶容量 | 超限响应 |
|---|---|---|---|
| 单 `client_id` 普通请求 | **120 req/s** | 60 | `429` + `Retry-After: 1` |
| 单 `client_id` 上传并发 | 3 个 session | — | `429 {"error":"too_many_uploads"}` |
| 单 `client_id` 配对尝试 | 见 §3.5 | — | `429 {"error":"pair_locked"}` |
| 单 IP 登录尝试 | 10 次 / 5 分钟 | 5 | `429` |

```python
class TokenBucket:
    """O(1) 内存的令牌桶。单事件循环内无需加锁。"""
    __slots__ = ("rate", "capacity", "tokens", "updated")

    def __init__(self, rate: float, capacity: float):
        self.rate = rate
        self.capacity = capacity
        self.tokens = capacity
        self.updated = time.monotonic()

    def allow(self, cost: float = 1.0) -> tuple[bool, float]:
        now = time.monotonic()
        self.tokens = min(self.capacity,
                          self.tokens + (now - self.updated) * self.rate)
        self.updated = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True, 0.0
        need = (cost - self.tokens) / self.rate
        return False, need                      # 需等待秒数


class RateLimiter:
    def __init__(self, rate: float = 120.0, burst: float = 60.0):
        self.rate = rate
        self.burst = burst
        self._buckets: dict[str, TokenBucket] = {}
        self._last_gc = time.monotonic()

    async def check(self, client_id: str) -> None:
        b = self._buckets.get(client_id)
        if b is None:
            b = self._buckets[client_id] = TokenBucket(self.rate, self.burst)
        ok, wait = b.allow()
        if not ok:
            raise RateLimited(retry_after_ms=int(wait * 1000) or 1000)
        # 惰性 GC：每 10 分钟清一次空桶，防止撤销的设备长期占内存
        if time.monotonic() - self._last_gc > 600:
            self._gc()
            self._last_gc = time.monotonic()

    def _gc(self) -> None:
        now = time.monotonic()
        for k, b in list(self._buckets.items()):
            if b.tokens >= b.capacity and now - b.updated > 600:
                self._buckets.pop(k, None)
```

**注意：限流必须在鉴权之后**——否则未鉴权请求无法归属到 `client_id`，
只能按 IP 限流，而 NAT 环境下会误伤。顺序：**鉴权 → 限流 → 转发**。

### 4.0 进程结构与启动顺序

### 4.1 索引器 `indexer.py`

#### 4.1.1 为什么这样设计

4952 个文件（一期约 4900 张图片）的首次全量扫描必须在**后台**完成且**可中断**，
因为：① 用户装完软件要立刻能用（不能等 3 分钟白屏）；② EXIF 抽取是 IO 密集的，会阻塞事件循环；
③ 扫描中途改文件会造成重复入库，必须有幂等保证。

#### 4.1.2 扫描流程

```
scan(root, full: bool)
 │
 ├─ ① 遍历：os.walk(followlinks=False) + os.scandir 语义
 │      ├─ 跳过 exclude_dirs（@eaDir / $RECYCLE.BIN / .git / node_modules / #recycle / .photobridge_tmp）
 │      ├─ 跳过符号链接与 junction（防越界，与沙箱一致）
 │      ├─ 扩展名白名单过滤（设计文档 §5.3）：小写化后比对
 │      ├─ 跳过 `.jpg-lx2` 等黑名单后缀
 │      └─ 每 200 个文件让出一次事件循环：await asyncio.sleep(0)
 │
 ├─ ② 增量判断（full=False 时）
 │      SELECT size, mtime FROM media WHERE root_id=? AND rel_path=?
 │      ├─ 不存在 → 新增
 │      ├─ size 或 mtime 变了 → 更新
 │      └─ 一致 → 跳过（★ 这是增量的核心，避免重复抽 EXIF）
 │
 ├─ ③ EXIF 抽取（丢线程池，见 §4.1.3）
 │
 ├─ ④ 攒够 batch_size=500 条 → 单事务 executemany 入库（§4.1.6）
 │
 └─ ⑤ 收尾：全量扫描时标记未出现的文件 missing=1；统计写 job_state；广播 SSE
```

```python
async def scan_root(root: dict, *, full: bool = False,
                    progress: Callable[[ScanProgress], Awaitable[None]] | None = None
                    ) -> ScanResult:
    """扫描一个根目录。可被 /api/index/rescan 重复调用；重入保护见下。"""
    if root["id"] in _scanning:
        raise AlreadyScanning(root["id"])
    _scanning.add(root["id"])
    try:
        known = {} if full else await _load_known(root["id"])   # rel_path -> (size, mtime)
        batch: list[MediaRow] = []
        seen: set[str] = set()
        stats = ScanResult()

        for dirpath, dirnames, filenames in os.walk(root["path"], followlinks=False):
            dirnames[:] = [d for d in dirnames if d not in EXCLUDE_DIRS]
            for fn in filenames:
                rel = _rel(root["path"], dirpath, fn)
                ext = fn.rsplit(".", 1)[-1].lower() if "." in fn else ""
                if ext not in IMAGE_EXTS or _is_blacklisted(fn):
                    continue
                full_path = os.path.join(dirpath, fn)
                try:
                    st = os.stat(full_path, follow_symlinks=False)
                except OSError:
                    stats.errors += 1
                    continue
                if _is_reparse_point(full_path):
                    continue                                # 符号链接/重解析点跳过
                seen.add(rel)

                prev = known.get(rel)
                if prev and prev[0] == st.st_size and abs(prev[1] - st.st_mtime) < 1e-6:
                    continue                                # ★ 增量跳过

                row = await _build_row(root, rel, fn, ext, st)
                batch.append(row)
                if len(batch) >= BATCH_SIZE:
                    await db.insert_media_batch(batch)      # 500 条一事务
                    batch.clear()
                    stats.indexed += BATCH_SIZE
                    if progress:
                        await progress(stats.snapshot())
                    await asyncio.sleep(0)                  # 让出事件循环

        if batch:
            await db.insert_media_batch(batch)
        if full:
            await db.mark_missing(root["id"], seen)         # ★ 只有全量扫描才能判"消失"
        return stats
    finally:
        _scanning.discard(root["id"])
```

**为什么 `full=False` 时不标记 `missing`**：增量扫描只看新增/变更，没遍历到的文件不代表消失了。
只有全量扫描才有"全集"，才能安全判定"文件已删除"。**这是一个必须写进代码注释的约束。**

#### 4.1.3 EXIF 抽取

**为什么必须丢线程池**：Pillow 的 `Image.open` + `_getexif()` 是**同步阻塞**调用，
一个 50 MB 的 TIFF 可能耗时 200 ms。若在事件循环里跑 4900 次，隧道心跳会被饿死，
云端直接判定电脑离线。**这是整个项目最容易犯的并发错误。**

```python
THREAD_POOL = ThreadPoolExecutor(max_workers=4, thread_name_prefix="pillow")

async def extract_exif(path: str) -> ExifInfo:
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(THREAD_POOL, _extract_exif_sync, path)


def _extract_exif_sync(path: str) -> ExifInfo:
    """同步实现，只能在线程池里调用。"""
    info = ExifInfo()
    try:
        with Image.open(path) as im:
            info.width, info.height = im.size
            info.orientation = _int_or_none(im.getexif().get(0x0112)) or 1
            exif = im.getexif()
            # 0th IFD：基础字段
            info.camera = _clean(exif.get(0x010F), exif.get(0x0110))   # Make + Model
            # Exif 子 IFD：拍摄参数
            sub = exif.get_ifd(0x8769)
            info.iso      = _int_or_none(sub.get(0x8827))
            info.fnum     = _float_or_none(sub.get(0x829D))
            info.exposure = _ratio_to_float(sub.get(0x829A))
            info.focal    = _ratio_to_float(sub.get(0x920A))
            info.lens     = _clean(sub.get(0xA434))
            info.taken_at = _parse_exif_dt(sub.get(0x9003)) or _parse_exif_dt(sub.get(0x9004)) \
                            or _parse_exif_dt(exif.get(0x0132))
            # GPS IFD
            gps = exif.get_ifd(0x8825)
            info.gps_lat, info.gps_lon = _parse_gps(gps)
            # 部分机型尺寸只在 Exif IFD
            if not info.width:
                info.width  = _int_or_none(sub.get(0xA002))
                info.height = _int_or_none(sub.get(0xA003))
    except Exception as e:
        # ★ 坏文件不抛给调用方：记 debug 日志，返回空 EXIF，走三级回退
        log.debug("exif extract failed for %s: %s", path, e)
```

#### 4.1.4 `taken_at` 三级回退

```
① EXIF DateTimeOriginal / DateTimeDigitized / DateTime
       │ 解析成功 → taken_src = "exif"
       ▼ 失败
② 文件名日期解析（§4.1.5）
       │ 命中 → taken_src = "filename"
       ▼ 失败
③ 文件 mtime
          taken_src = "mtime"
```

```python
def resolve_taken_at(exif: ExifInfo, file_name: str, mtime: float) -> tuple[float, str]:
    if exif.taken_at:
        return exif.taken_at, "exif"
    ts = parse_datetime_from_name(file_name)
    if ts:
        return ts, "filename"
    return mtime, "mtime"
```

**为什么顺序是这个**：EXIF 最准；文件名次之（截图、微信保存的图常无 EXIF 但名字带时间）；
mtime 最不准（复制、同步会改 mtime），但总比没有强。
`taken_src` 必须入库，因为**用户在时间线上可能看到排序"不对"，需要能解释为什么**。

**边界处理（必须）**：

| 情况 | 处理 |
|---|---|
| EXIF 时间早于 1980 | 判为脏数据 → 走下一级 |
| EXIF 时间晚于 `now + 1 天` | 判为脏数据（相机时间没设） → 走下一级 |
| 文件名解析出 13 位毫秒时间戳 | 支持（微信/QQ 导出常见） |
| 解析出的日期不存在（`20240230`） | `datetime` 构造失败 → 走下一级 |
| 全部失败 | 用 mtime |

#### 4.1.5 文件名日期解析正则（必须覆盖常见格式）

```python
# 按优先级排列：越具体的格式越靠前，避免 "20240512" 被更宽泛的规则误匹配
NAME_PATTERNS: list[tuple[re.Pattern, str]] = [
    # IMG_20240512_183000 / PXL_20240512_183000123（连写日期+时间，可带毫秒）
    (re.compile(r"(?<!\d)(?P<Y>19|20\d{2})(?P<m>0[1-9]|1[0-2])(?P<d>0[1-9]|[12]\d|3[01])"
                r"[_\-T ]?(?P<H>[01]\d|2[0-3])(?P<M>[0-5]\d)(?P<S>[0-5]\d)(?P<ms>\d{0,3})(?!\d)"),
     "YmdHMS"),
    # 2024-05-12 18:30:00 / 2024-05-12_18-30-00 / 2024.05.12 18.30.00 / 2024年05月12日 18:30:00
    (re.compile(r"(?<!\d)(?P<Y>19|20\d{2})[-.\u5e74](?P<m>0?[1-9]|1[0-2])[-.\u6708]"
                r"(?P<d>0?[1-9]|[12]\d|3[01])\u65e5?[ _\-T]?"
                r"(?P<H>[01]?\d|2[0-3])[:\-.](?P<M>[0-5]?\d)(?:[:\-.](?P<S>[0-5]?\d))?"),
     "YmdHMS"),
    # 2024-05-12（只有日期，无时间）→ 补 12:00:00
    (re.compile(r"(?<!\d)(?P<Y>19|20\d{2})[-.\u5e74](?P<m>0?[1-9]|1[0-2])[-.\u6708]"
                r"(?P<d>0?[1-9]|[12]\d|3[01])\u65e5?(?![\d:])"),
     "Ymd"),
    # 20240512（连续 8 位，前后不能再有数字）→ 补 12:00:00
    (re.compile(r"(?<!\d)(?P<Y>19|20\d{2})(?P<m>0[1-9]|1[0-2])(?P<d>0[1-9]|[12]\d|3[01])(?!\d)"),
     "Ymd"),
    # 13 位毫秒时间戳（微信/QQ 导出）
    (re.compile(r"(?<!\d)(?P<ts>1[0-9]{12})(?!\d)"), "MS_EPOCH"),
    # 10 位秒级时间戳
    (re.compile(r"(?<!\d)(?P<ts>1[0-9]{9})(?!\d)"), "S_EPOCH"),
]

def parse_datetime_from_name(name: str) -> float | None:
    stem = name.rsplit(".", 1)[0]
    for pat, fmt in NAME_PATTERNS:
        m = pat.search(stem)
        if not m:
            continue
        try:
            g = m.groupdict()
            if fmt == "MS_EPOCH":
                ts = int(g["ts"]) / 1000.0
            elif fmt == "S_EPOCH":
                ts = float(g["ts"])
            else:
                h = int(g.get("H") or 12); mi = int(g.get("M") or 0); s = int(g.get("S") or 0)
                us = int((g.get("ms") or "0").ljust(3, "0")[:3]) * 1000
                dt = datetime(int(g["Y"]), int(g["m"]), int(g["d"]), h, mi, s, us)
                ts = dt.timestamp()
            if 315532800 <= ts <= time.time() + 86400:      # 1980-01-01 ~ 明天
                return ts
        except (ValueError, KeyError, OSError):
            continue
    return None
```

#### 4.1.7 watchdog 增量感知（防抖 + 事件合并）

**为什么必须防抖**：手机上传一张照片会触发 `created`（临时区）→ `moved`（归档目标）→
可能还有 `modified` 三次事件；Windows 上某些操作会连发 10+ 次。不去抖会导致同一文件被索引 10 次。

```python
DEBOUNCE_SEC = 2.0          # 单个路径的事件静默期

class WatchCollector:
    """把 watchdog 的原始事件合并成"路径 → 最终动作"。"""

    def __init__(self):
        self._pending: dict[str, tuple[str, float]] = {}   # abspath -> (action, due_ts)
        self._lock = asyncio.Lock()

    async def on_event(self, action: str, src: str, dest: str | None) -> None:
        if _is_ignored(src) or (dest and _is_ignored(dest)):
            return                                        # ★ 临时区/缩略图/中间态文件
        now = time.monotonic()
        async with self._lock:
            if action == "moved" and dest:
                self._pending.pop(src, None)              # 源路径的待办作废
                self._pending[dest] = ("created", now + DEBOUNCE_SEC)
            elif action == "deleted":
                self._pending.pop(src, None)
                await self._mark_missing_now(src)         # 删除不防抖，立刻标记
            else:
                self._pending[src] = (action, now + DEBOUNCE_SEC)

    async def _flush_loop(self) -> None:
        while True:
            await asyncio.sleep(1.0)
            now = time.monotonic()
            ready = []
            async with self._lock:
                for path, (action, due) in list(self._pending.items()):
                    if now >= due:
                        ready.append((path, action))
                        del self._pending[path]
            if ready:
                await self._process(ready)                # 批量走一遍索引逻辑
```

**必须忽略的路径**（否则会索引临时文件）：

| 忽略项 | 理由 |
|---|---|
| `<root>/.photobridge_tmp/**` | 半截上传文件（见 §4.3.2） |
| `data/thumbs/**` | 生成的缩略图 |
| `*.tmp` / `*.part` / `*.crdownload` / `*.partial` | 下载/写入中间态 |
| `~$*` | Office 临时文件 |
| `*.jpg-lx2` | 小米相册回收站残留（设计文档 §5.3 明确排除） |
| `Thumbs.db` / `desktop.ini` / `.DS_Store` | 系统元数据文件 |

**为什么 `data/` 整个目录不在监听范围内**：`data/` 不在库根目录下（库是 `D:\Photos`，
data 在 `D:\Photos\data`），天然隔离。但**上传归档的最终目标在库内**，所以归档完成时会触发一次
`created`——这是**预期行为**，索引器会用 UPSERT 幂等处理（`complete` 已入库，UPSERT 只更新字段）。

### 4.2 缩略图引擎 `thumbs.py`

#### 4.2.1 为什么这样设计

缩略图是全系统**唯一的高 CPU 操作**，也是最影响体验的（首屏 2.5 秒目标）。
设计要点：① 两级尺寸，网格用小图、查看器用中图，**永远不为了看一张图而解码原图**；
② 必须处理 EXIF Orientation，否则手机拍的照片 90% 是躺着的；③ 必须限制并发，
否则 4 核机器被 8 个 Pillow 任务打满，隧道心跳被饿死。

#### 4.2.2 参数

| 参数 | 值 | 来源 |
|---|---|---|
| 尺寸 | `[320, 1600]` | 设计文档 §5.1 |
| 格式 | WebP | `config.thumbs.format` |
| 质量 | 78 | `config.thumbs.quality` |
| 并发 worker | 4 | `config.thumbs.workers` |
| 320 最大边长 | 320 px（等比，不放大） | — |
| 1600 最大边长 | 1600 px（等比，不放大） | — |
| 失败重试 | 最多 3 次，退避 5s / 30s / 300s | 本节 |
| 失败上限 | 3 次后 `thumb_state='failed'`，不再自动重试 | 本节 |

#### 4.2.3 缓存路径规则

```
data/thumbs/{root_id}/{sha1 前 2 位}/{sha1 全长}_{size}.webp
```

```python
def thumb_path(root_id: str, rel_path: str, size: int) -> Path:
    """为什么要 hash 分片而不是直接用原路径：
    ① Windows 路径长度限制 260（未开长路径），hash 后固定 40 字符，永远不会超；
    ② 避免中文/特殊字符在不同文件系统下的编码问题；
    ③ 前 2 位分目录，单目录文件数从 4900 降到约 76，NTFS 目录遍历更快。
    代价：无法从缓存路径反推原图 —— 不需要，DB 里有映射。"""
    h = hashlib.sha1(f"{root_id}\x00{rel_path}".encode("utf-8")).hexdigest()
    return THUMBS_DIR / root_id / h[:2] / f"{h}_{size}.webp"
```

**缓存失效规则**：源文件 `mtime` 或 `size` 变化 → 重新生成。
**采纳方案**：在 `media` 行上记录 `thumb_mtime`（见 [05 数据库设计](05-数据库设计文档.md) 的字段补充），
不额外产生 `.meta` 文件。生成前比对 `thumb_mtime == media.mtime`，不等就重生成。

#### 4.2.4 EXIF Orientation 处理 ★

**这是必须实现的，且是最容易漏的**：

| Orientation 值 | 含义 | 需要的变换 |
|---|---|---|
| 1 | 正常 | 无 |
| 2 | 水平镜像 | `FLIP_LEFT_RIGHT` |
| 3 | 旋转 180° | `ROTATE_180` |
| 4 | 垂直镜像 | `FLIP_TOP_BOTTOM` |
| 5 | 转置 | `TRANSPOSE` |
| 6 | **旋转 90° CW**（手机竖拍最常见） | `ROTATE_270`（Pillow 为逆时针语义） |
| 7 | 横置 | `TRANSVERSE` |
| 8 | 旋转 270° CW | `ROTATE_90` |

```python
ORIENTATION_OPS = {
    2: Image.Transpose.FLIP_LEFT_RIGHT,
    3: Image.Transpose.ROTATE_180,
    4: Image.Transpose.FLIP_TOP_BOTTOM,
    5: Image.Transpose.TRANSPOSE,
    6: Image.Transpose.ROTATE_270,      # ★ 竖拍手机：必须转，否则躺着
    7: Image.Transpose.TRANSVERSE,
    8: Image.Transpose.ROTATE_90,
}

def _apply_orientation(im: Image.Image, orientation: int) -> Image.Image:
    op = ORIENTATION_OPS.get(orientation or 1)
    if op is not None:
        im = im.transpose(op)            # ★ 用 transpose 而非 rotate：不插值，无质量损失
    return im
```

**注意**：应用变换后，输出的 WebP **不写** Orientation 标签（`exif=b""`），
否则浏览器会**再转一次**，照片就转反了。这是必须显式保证的（Pillow 保存 WebP 时若传入 exif 会原样保留）。

#### 4.2.5 大图内存控制 ★

一个 100 MP 的照片（如 12000×8000）解码后是 `12000 × 8000 × 3 ≈ 288 MB` RGB。
4 个 worker 同时处理 = 1.1 GB，直接 OOM。

**三层防护**：

| 层 | 手段 | 效果 |
|---|---|---|
| ① JPEG `draft` 模式 | `im.draft("RGB", (target*2, target*2))` | JPEG 解码器**直接按 1/2、1/4、1/8 缩放解码**，内存降到 1/64，且更快 |
| ② `Image.MAX_IMAGE_PIXELS` | 设为 `300_000_000` | 超过则触发 `DecompressionBombWarning` → 拒绝处理，防恶意大图 |
| ③ `im.reduce(factor)` | 先整数倍降采样再精缩 | 大倍率缩放分两步走，峰值内存更低、速度更快（Pillow ≥ 9.1） |

```python
Image.MAX_IMAGE_PIXELS = 300_000_000
DRAFT_MAX = 2048                      # 先按 ≤2048 解码，再精缩

def _open_downscaled(path: str, target: int) -> Image.Image:
    im = Image.open(path)
    # ① JPEG：让解码器直接出小图（对 HEIC/PNG 无效，会自动忽略）
    if im.format == "JPEG":
        im.draft("RGB", (DRAFT_MAX, DRAFT_MAX))
    # ③ 先整数倍降采样（快且省内存）
    factor = max(1, min(im.width, im.height) // (target * 2))
    if factor >= 2:
        im = im.reduce(factor)         # 需要 Pillow >= 9.1
    return im


def _generate_sync(src: str, dst: Path, size: int, quality: int,
                   orientation: int) -> tuple[int, int]:
    with _open_downscaled(src, size) as im:
        im = _apply_orientation(im, orientation)              # ★ 先转正
        if im.mode not in ("RGB", "RGBA"):
            im = im.convert("RGB")
        im.thumbnail((size, size), Image.Resampling.LANCZOS)  # 等比，只缩不放
        dst.parent.mkdir(parents=True, exist_ok=True)
        tmp = dst.with_name(dst.name + ".tmp")
        im.save(tmp, "WEBP", quality=quality, method=4, exif=b"")   # ★ 不写 Orientation
        os.replace(tmp, dst)                                  # 原子落盘
        return im.size
```

**为什么用 `thumbnail()` 而不是 `resize()`**：`thumbnail` 保证等比且**不会放大**。
一张 200×200 的图请求 1600 缩略图时，`resize` 会插值放大成 1600×1600（浪费带宽且更糊）。

**为什么先写 `.tmp` 再 `os.replace`**：生成中途断电/崩溃会留下半截 WebP，
浏览器会拿到损坏图片且**被 Service Worker 永久缓存**（§5.6），这是最恶心的 bug。
原子替换彻底消除它。

#### 4.2.6 并发 worker 与失败重试

```python
class ThumbEngine:
    def __init__(self, workers: int = 4):
        self.queue: asyncio.Queue[int] = asyncio.Queue(maxsize=2000)
        self.workers = workers
        self._tasks: list[asyncio.Task] = []
        self._fail_count: dict[int, int] = {}          # media_id -> 失败次数
        self._sem = asyncio.Semaphore(workers)         # 限制同时在跑的 Pillow 调用

    def start(self) -> None:
        for i in range(self.workers):
            self._tasks.append(asyncio.create_task(self._worker(i)))

    async def _worker(self, idx: int) -> None:
        while True:
            media_id = await self.queue.get()
            try:
                await self._generate_one(media_id)
            except Exception as e:
                await self._on_failure(media_id, e)
            finally:
                self.queue.task_done()

    async def _generate_one(self, media_id: int) -> None:
        row = await db.get_media(media_id)
        if row is None or row.missing:
            return
        src = sandbox.resolve(root_by_id(row.root_id), row.rel_path, "read")   # ★ 过沙箱
        async with self._sem:                          # 同时最多 4 个线程池任务
            loop = asyncio.get_running_loop()
            for size in THUMB_SIZES:
                dst = thumb_path(row.root_id, row.rel_path, size)
                if dst.exists() and row.thumb_mtime == row.mtime:
                    continue                            # 命中缓存
                await loop.run_in_executor(
                    THREAD_POOL, _generate_sync,
                    str(src), dst, size, THUMB_QUALITY, row.orientation)
        await db.set_thumb_state(media_id, "ok", row.mtime)

    async def _on_failure(self, media_id: int, e: Exception) -> None:
        n = self._fail_count.get(media_id, 0) + 1
        self._fail_count[media_id] = n
        if n >= 3:
            await db.set_thumb_state(media_id, "failed")
            log.warning("thumb permanently failed media_id=%s: %s", media_id, e)
            self._fail_count.pop(media_id, None)
        else:
            backoff = (5, 30, 300)[n - 1]
            log.info("thumb retry %d/3 for media_id=%s in %ds", n, media_id, backoff)
            asyncio.get_running_loop().call_later(
                backoff, lambda: self.queue.put_nowait(media_id))
```

**失败标记的意义**：`thumb_state='failed'` 让 API 层返回一张**内置的占位图**（而不是 500），
时间线不会出现破图。托盘面板显示"N 张图片无法生成缩略图"，用户可手动重试。
**为什么是 3 次**：瞬时失败（文件被占用、磁盘忙）通常 1 次重试就过；
持续失败（文件损坏）重试 100 次也没用，只是烧 CPU。

### 4.3 上传管理 `uploads.py`

#### 4.3.1 为什么这样设计

上传是唯一会**写用户数据**的路径，必须满足：断点续传（切后台/断网不重传）、
秒传（重复文件零传输）、完整性校验（不落半截文件）、绝不覆盖（§8.4 硬约束 2）。

#### 4.3.2 临时区路径规则

```
<库根>/.photobridge_tmp/{upload_id}.part        ← 正在接收的数据
```

| 项 | 规则 |
|---|---|
| `upload_id` | `secrets.token_urlsafe(16)`，22 字符，URL 安全 |
| 临时文件名 | 固定 `{upload_id}.part`，**与原名无关**（原名可能含非法字符） |
| 目录 | **必须与目标同卷**，见下 |
| 清理 | 启动时 + 每小时扫描，删除 `expires_at < now` 的会话 |

**关键陷阱：`os.replace` 不能跨卷**。
若临时区放在 `D:\Photos\data`（H 盘），而库在 `D:\Photos`（E 盘），
**跨盘 rename 会抛 `OSError: [WinError 17] 系统无法将文件移到不同的磁盘驱动器`**。

| 方案 | 评价 |
|---|---|
| 临时区放 `data/`（H 盘） | ❌ 跨卷；退化成"复制+删除"，**非原子**，中途失败留半截文件 |
| **临时区放库根下 `.photobridge_tmp/`** | ✅ 同卷，`os.replace` 真原子；索引器忽略该目录 | **采纳** |
| 临时区放 `E:\` 根 | ⚠️ 同卷但污染根目录，且可能无写权限 |

**必须同步修改**：`config.py` 增加 `tmp_dir = <root>/.photobridge_tmp`；
索引器 `EXCLUDE_DIRS` 必须包含 `.photobridge_tmp`；沙箱必须允许写该目录。

**① `POST /api/uploads/init`**

```python
@dataclass
class InitRequest:
    name: str
    size: int
    mtime: float | None = None
    sha256: str | None = None
    target_dir: str | None = None       # 相对库根的目录，可选

@dataclass

    upload_id: str
    chunk_size: int
    offset: int
    exists: bool
    media_id: int | None = None

async def init_upload(req: InitRequest, ctx: Ctx) -> InitResponse:
    # ① 校验
    if req.size <= 0 or req.size > MAX_FILE_SIZE:            # 一期 2 GB
        raise BadRequest("file_too_large")
    ext = _ext_of(req.name)
    if ext not in IMAGE_EXTS:
        raise BadRequest("unsupported_type")
    sandbox.check_name(req.name)                             # 保留名/非法字符

    if req.sha256:
        row = await db.find_by_sha256(req.sha256)
        if row is not None and not row.missing:
            return InitResponse("", CHUNK_SIZE, req.size, exists=True, media_id=row.id)

    # ③ 复用未过期会话（同一 (name,size,sha256) 重复 init → 返回原会话，实现幂等）
    old = await db.find_open_session(req.name, req.size, req.sha256)
    if old is not None:
        return InitResponse(old.id, old.chunk_size,
                            os.path.getsize(old.temp_path), exists=False)

    # ④ 建会话
    upload_id = secrets.token_urlsafe(16)
    temp = sandbox.tmp_path(upload_id)                       # <root>/.photobridge_tmp/{id}.part
    temp.parent.mkdir(parents=True, exist_ok=True)
    temp.touch(exist_ok=False)
    await db.create_session(UploadSession(
        id=upload_id, root_id=..., target_rel=req.target_dir or DEFAULT_SUBDIR,
        temp_path=str(temp), total_size=req.size, received=0,
        chunk_size=CHUNK_SIZE, sha256=req.sha256, declared_name=req.name,
        taken_at=req.mtime, created_at=time.time(),
        expires_at=time.time() + SESSION_TTL, status="open"))
    return InitResponse(upload_id, CHUNK_SIZE, 0, exists=False)
```

**`chunk_size` 的确定**（设计文档 §7.2）：**必须按通路动态决定**。

**② `PATCH /api/uploads/{id}`（分片写入）★**

**必须明确回答"乱序还是顺序"**：

| 方案 | 实现复杂度 | 断点续传正确性 | 采纳 |
|---|---|---|---|
| **仅支持顺序追加**（`start` 必须 == 当前文件长度） | 低 | ✅ `received` 即真实文件长度 | ✅ **一期采纳** |
| 支持随机 offset（`seek` 后写） | 中 | ⚠️ 需维护已收区间位图，否则 `received` 会算错 | 二期（若需并行分片） |
| 支持乱序 + 位图 | 高 | ✅ | ❌ 一期不做 |

**一期决策：顺序追加（append-only）**。理由：
① 手机端本来就是顺序上传（单条 HTTP 流），没有并行分片需求；
② 顺序追加时"文件长度 = 已收字节数"，断点续传只需 `os.path.getsize()`，
**无需额外状态**，永不与 DB 不一致；
③ 若客户端传了不连续的 `Content-Range`，直接回 **409 + 当前 offset**，客户端据此重对齐。

```python
@dataclass
class PatchResult:
    offset: int          # 服务器当前已确认的字节数

async def patch_upload(upload_id: str, content_range: str,
                       body: AsyncIterator[bytes]) -> PatchResult:
    """Content-Range 格式：bytes {start}-{end}/{total}"""
    sess = await db.get_session(upload_id)
    if sess is None or sess.status != "open":
        raise NotFound("upload_not_found")
    if time.time() > sess.expires_at:
        await cancel_upload(upload_id, reason="expired")
        raise Gone("upload_expired")

    start, end, total = parse_content_range(content_range)
    cur = os.path.getsize(sess.temp_path)              # ★ 真实长度，不信 DB

    # 幂等：重传已收到的分片 → 直接回当前 offset，不写盘
    if end < cur:
        return PatchResult(offset=cur)
    # 乱序（有空洞）→ 拒绝并告知正确 offset
    if start != cur:
        raise Conflict("offset_mismatch", current=cur)
    if total != sess.total_size:
        raise BadRequest("size_mismatch")

    written = 0
    async with aiofiles.open(sess.temp_path, "ab") as f:   # 追加模式
        async for chunk in body:
            if written + start > end:                      # 防御：客户端多发
                break
            await f.write(chunk)
            written += len(chunk)
    # 只在真正写完并 flush 后更新 DB（顺序：先盘后库，崩溃时以盘为准）
    new_off = await db.set_received(upload_id, os.path.getsize(sess.temp_path))
    return PatchResult(offset=new_off)
```

**为什么"先写盘再更新 DB"**：如果先更新 DB 后写盘，崩溃时 DB 说"收到 8 MB"，盘上只有 2 MB，
续传时客户端从 8 MB 开始，中间 6 MB 永久丢失且**校验能发现但用户要重传整个文件**。
反过来（盘 8 MB、DB 2 MB）只需 `os.path.getsize()` 就能修正——**盘是唯一真相**。

**④ `POST /api/uploads/{id}/complete`**

```python
async def complete_upload(upload_id: str, expect_sha256: str | None) -> CompleteResult:
    sess = await db.get_session(upload_id)
    if sess is None:
        raise NotFound("upload_not_found")
    temp = Path(sess.temp_path)

    # ① 尺寸校验
    actual = temp.stat().st_size
    if actual != sess.total_size:
        raise BadRequest("incomplete", received=actual, expected=sess.total_size)

    # ② sha256 校验（流式算，不读进内存）
    digest = await _sha256_file_async(temp)
    if expect_sha256 and digest != expect_sha256.lower():
        await cancel_upload(upload_id, reason="hash_mismatch")
        raise BadRequest("hash_mismatch")
    # 二次查重：init 时没给 sha256，或期间别的设备传了同一张
    dup = await db.find_by_sha256(digest)
    if dup is not None and not dup.missing:
        temp.unlink(missing_ok=True)                       # 丢弃临时文件
        await db.close_session(upload_id, "deduped")
        return CompleteResult(deduped=True, media_id=dup.id)

    # ③ 确定 taken_at（三级回退，与索引器同一份代码）
    exif = await extract_exif(str(temp))
    taken_at, src = resolve_taken_at(exif, sess.declared_name, sess.taken_at or time.time())

    # ④ 归档（见 §4.4）——返回真实落盘路径
    target = await archive.place(
        root=root_path, subdir=sess.target_rel, taken_at=taken_at,
        name=sess.declared_name, temp=temp)

    # ⑤ 入库（sha256 直接写，避免之后再算一遍）
    media_id = await db.insert_media_from_upload(sess, target, exif, taken_at, src, digest)

    # ⑥ 生成缩略图（异步入队，不阻塞响应）
    thumb_engine.enqueue(media_id)

    # ⑦ 审计日志
    await audit.write("upload", rel_path=str(target), device=sess.client_name)

    # ⑧ 关闭会话
    await db.close_session(upload_id, "done")

    # ⑨ NOTIFY 推送（若走隧道）
    await events.publish("upload_done", {"media_id": media_id, "rel_path": str(target)})

    return CompleteResult(deduped=False, media_id=media_id, rel_path=str(target))
```

| 失败场景 | 处理 |
|---|---|
| `complete` 校验失败（size/hash） | 保留临时文件（可能是客户端 bug，允许重传剩余部分），回 400 |
| `os.replace` 失败（磁盘满/权限） | 回 507/500，**保留临时文件**，会话状态仍 `open`，可重试 |
| 进程崩溃 | 启动时扫描：`status='open'` 且 `expires_at < now` → 删临时文件 + 关会话 |
| 客户端 `DELETE /api/uploads/{id}` | 立即删临时文件 + `status='cancelled'` |
| 会话过期（24 小时） | 后台任务每小时扫一次，删文件 + 标 `expired` |

```python
SESSION_TTL = 24 * 3600

async def cleanup_expired() -> int:
    """每小时跑一次。为什么是 24 小时：用户可能今天传一半、明天接着传；
    超过一天基本可以认为放弃了，且磁盘上留 2 GB 半截文件不可接受。"""
    n = 0
    for sess in await db.list_sessions(status="open"):
        if sess.expires_at < time.time():
            Path(sess.temp_path).unlink(missing_ok=True)
            await db.close_session(sess.id, "expired")
            n += 1
    # 孤儿文件（DB 里没有对应会话）
    known = {Path(s.temp_path).name for s in await db.list_sessions()}
    for f in TMP_DIR.glob("*.part"):
        if f.name not in known and time.time() - f.stat().st_mtime > SESSION_TTL:
            f.unlink()
            n += 1
    return n
```

### 4.4 归档 `archive.py`

#### 4.4.1 为什么这样设计

设计文档 §8.4 硬约束 2：*"上传只新增不覆盖：同名追加 `_1`/`_2`；sha256 命中判重丢弃；
**任何情况下不把新文件 rename 到已存在文件上**"*。
这条约束必须用**代码结构**保证，而不是靠"我记得检查一下"。

#### 4.4.2 目标路径规则

```
<库根>\<子目录>\{YYYY}\{YYYY-MM}\{YYYYMMDD_HHMMSS}_{seq}{ext}
例：D:\Photos\手机上传\2024\2024-05\20240512_183000_1.jpg
```

| 部分 | 规则 | 来源 |
|---|---|---|
| `子目录` | 配置 `upload.subdir`，默认 `手机上传` | `config.py` |
| `YYYY` | `taken_at` 的年份，4 位 | — |
| `YYYY-MM` | `taken_at` 的年月 | — |
| `YYYYMMDD_HHMMSS` | `taken_at` 本地时间 | — |
| `_seq` | 冲突序号，**从 1 开始**，无冲突则不加 | 本节 |
| `ext` | 小写化，`.jpeg` → `.jpg` 统一 | 本节 |

```python
EXT_ALIAS = {"jpeg": "jpg"}          # 只统一 jpeg→jpg；tiff/tif 保留原样

def build_target(root: Path, subdir: str, taken_at: float,
                 name: str, seq: int | None = None) -> Path:
    dt = datetime.fromtimestamp(taken_at)
    ext = EXT_ALIAS.get(_ext_of(name), _ext_of(name))
    stem = dt.strftime("%Y%m%d_%H%M%S")
    if seq is not None:
        stem = f"{stem}_{seq}"
    return root / subdir / f"{dt:%Y}" / f"{dt:%Y-%m}" / f"{stem}.{ext}"
```

**为什么用 `taken_at` 而不是"上传时间"**：照片按**拍摄时间**归档才有意义
（一张 2019 年的照片今天上传，应该进 `2019\2019-XX\`，而不是今天）。这是设计文档 §9.2 的明确要求。

#### 4.4.3 绝不覆盖的具体实现 ★

**核心手法：`os.open(..., O_CREAT|O_EXCL)` 原子占位，而不是"先 exists 再 replace"。**

| 方案 | 是否安全 | 分析 |
|---|---|---|
| `if not target.exists(): os.replace(temp, target)` | ❌ **TOCTOU 竞态**：两个并发上传同一秒的照片都判"不存在"，后者覆盖前者 | 拒绝 |
| `target = unique_name(...); os.replace(...)` | ❌ 若 `unique_name` 里用 `exists()` 判断，仍有竞态窗口 | 拒绝 |
| **`os.open(target, O_CREAT\|O_EXCL)` 占位 + `os.replace`** | ✅ 占位原子；`O_EXCL` 保证同一时刻只有一个调用者拿到这个名字 | **采纳** |

```python
MAX_SEQ = 9999

def _reserve(root: Path, subdir: str, taken_at: float,
             name: str) -> tuple[Path, int | None]:
    """原子地"预订"一个不存在的目标路径。

    为什么不是 exists() 检查：
    exists() 与 replace() 之间有时间窗口，两个并发请求会同时通过检查。
    O_EXCL 由内核保证"创建成功 ⟺ 此前不存在"，是唯一无竞态的方式。
    """
    dt = datetime.fromtimestamp(taken_at)
    ext = EXT_ALIAS.get(_ext_of(name), _ext_of(name))
    folder = root / subdir / f"{dt:%Y}" / f"{dt:%Y-%m}"
    folder.mkdir(parents=True, exist_ok=True)          # 沙箱已校验 root 内的路径
    stem = dt.strftime("%Y%m%d_%H%M%S")

    for seq in [None] + list(range(1, MAX_SEQ + 1)):
        cand = folder / (f"{stem}.{ext}" if seq is None else f"{stem}_{seq}.{ext}")
        try:
            fd = os.open(cand, os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)
        except FileExistsError:
            continue                                   # 已被占（含并发占位）
        os.close(fd)
        return cand, seq                               # ★ 占位成功，名字归我
    raise ArchiveError(f"no free name after {MAX_SEQ} attempts")


async def place(root: Path, subdir: str, taken_at: float,
                name: str, temp: Path) -> Path:
    target, _seq = _reserve(root, subdir, taken_at, name)   # ① 原子占位（0 字节文件）
    try:
        os.replace(temp, target)                            # ② 同卷原子覆盖"占位文件"
    except Exception:
        target.unlink(missing_ok=True)                      # ③ 失败清理占位，避免留空文件
        raise
    return target
```

**为什么 `os.replace` 覆盖"我自己刚创建的空占位文件"不算违反"不覆盖"约束**：
占位文件是本函数在纳秒级之前创建的空文件，覆盖它不丢失任何用户数据。
**约束的真实含义是"不覆盖任何已有内容的文件"**，而 `O_EXCL` 恰好精确保证了这一点。

**必须通过的并发测试**：

| 用例 | 做法 | 断言 |
|---|---|---|
| 100 并发同一秒同名 | `asyncio.gather(*[place(...) for _ in range(100)])` | 100 个不同文件名（`_1`…`_99`），无覆盖 |
| 目标已存在同名真实文件 | 预置一个真实文件 | 新文件变成 `_1`，预置文件内容**逐字节不变** |
| 磁盘满 / 权限失败 | mock `os.replace` 抛 `OSError` | 占位文件被清理，无 0 字节残留 |
| seq 超过 9999 | mock 全部已存在 | 抛 `ArchiveError`，不覆盖任何文件 |

### 4.5 沙箱 `sandbox.py` ★

#### 4.5.1 为什么这样设计

设计文档 §8.1：*"所有文件访问的唯一入口"*。
这是**唯一**能阻止"手机端构造 `../../Windows/System32/xxx` 删你系统文件"的东西。
因此：① 所有路径必须经过 `resolve()`；② 校验必须逐条可测；③ 权限位必须与配置一致。

**硬约束**：代码中除了 `sandbox.py`，任何模块都禁止直接拼路径访问库文件。
自检命令：`grep -rn "open(" backend/app/ | grep -v sandbox.py` 的结果必须能逐条解释。

#### 4.5.2 七步校验（逐条实现要点）

```
resolve(root_cfg, rel_path, need) -> Path
 │
 ├─ 步 1  形态拒绝：绝对路径 / 盘符 / UNC / 前导分隔符 / 设备路径
 │        reject: "/etc/passwd"  "C:\Windows"  "\\?\GLOBALROOT\..."  "\\server\share"
 │                "\foo"  "/foo"  以及空字符串与纯空白
 │
 ├─ 步 2  段级拒绝：'..' 段、空段、NTFS 数据流 ':'、Windows 保留名、结尾空格/点
 │        reject: "a/../../b"  "a//b"  "a:b"  "CON" "PRN" "AUX" "NUL"
 │                "COM1".."COM9" "LPT1".."LPT9"（含带扩展名形式 "CON.txt"）
 │                "a." "a " （Windows 会静默去掉，导致校验名 ≠ 实际名）
 │
 ├─ 步 3  字符与长度：单段 > 255、非法字符 <>:"|?* 与控制字符 < 0x20、总长 > 1024
 │        注意：'\' 在 Windows 上也是分隔符，必须与 '/' 一并归一化
 │
 ├─ 步 4  归一化拼装：(real_root / rel).resolve(strict=False) 语义
 │        为什么用 realpath(root)：root 自身可能是 junction，不用 realpath 会被绕过
 │
 ├─ 步 5  逐段 reparse point 检查：任一段是 symlink / junction → 拒绝
 │        ★ 必须逐段，不能只查最终路径：中间目录是 junction 就足以越界
 │
 ├─ 步 6  前缀断言：normcase(p).startswith(normcase(real_root) + sep)
 │        ★ 用 normcase 而非直接比较：Windows 大小写不敏感
 │        ★ 不能只用 startswith 字符串比较，否则 "/root2" 会被判为 "/root" 的子路径
 │          → 必须比较 commonpath 或加分隔符后比较
 │
 └─ 步 7  权限位：need='read'   → mode ∈ {readonly, readwrite}
                 need='write'  → mode ∈ {upload, readwrite}
                 need='delete' → mode == readwrite 且 auth.allow_delete
```

#### 4.5.3 代码骨架

```python
ILLEGAL_CHARS = set('<>:"|?*') | {chr(c) for c in range(0x20)}
RESERVED_NAMES = {"CON", "PRN", "AUX", "NUL",
                  *[f"COM{i}" for i in range(1, 10)],
                  *[f"LPT{i}" for i in range(1, 10)]}
MAX_SEGMENT = 255
MAX_RELPATH = 1024
FILE_ATTRIBUTE_REPARSE_POINT = 0x400

class SandboxError(Exception): ...


def resolve(root_cfg: dict, rel_path: str, need: str = "read") -> Path:
    """把相对路径解析为可安全访问的绝对路径。所有文件访问的唯一入口。"""
    # ---------- 步 1：形态 ----------
    if not rel_path or not rel_path.strip():
        raise SandboxError("empty path")
    if rel_path.startswith(("/", "\\")):
        raise SandboxError("absolute path not allowed")
    if re.match(r"^[A-Za-z]:", rel_path):
        raise SandboxError("drive letter not allowed")
    if rel_path.startswith("\\\\") or rel_path.startswith("//"):
        raise SandboxError("UNC path not allowed")
    if rel_path.startswith("\\\\?\\") or rel_path.startswith("\\\\.\\"):
        raise SandboxError("device path not allowed")

    # 归一化分隔符（Windows 上两者等价，统一成 '/' 再切段）
    norm = rel_path.replace("\\", "/")

    # ---------- 步 2：段级 ----------
    parts = [s for s in norm.split("/")]
    for seg in parts:
        if seg == "":
            raise SandboxError("empty path segment")
        if seg == ".":
            continue                                  # '.' 段无害
        if seg == "..":
            raise SandboxError("parent traversal not allowed")
        if ":" in seg:
            raise SandboxError(f"NTFS data stream not allowed: {seg!r}")
        if seg.split(".", 1)[0].upper() in RESERVED_NAMES:
            raise SandboxError(f"reserved device name: {seg!r}")
        if seg.endswith((" ", ".")):
            raise SandboxError(f"trailing space/dot in segment: {seg!r}")

    # ---------- 步 3：字符与长度 ----------
    for seg in parts:
        if seg in ("", "."):
            continue
        if len(seg) > MAX_SEGMENT:
            raise SandboxError(f"segment too long: {len(seg)} > {MAX_SEGMENT}")
        bad = ILLEGAL_CHARS & set(seg)
        if bad:
            raise SandboxError(f"illegal characters {sorted(bad)!r} in {seg!r}")
    if len(norm) > MAX_RELPATH:
        raise SandboxError("relative path too long")

    # ---------- 步 4：拼装 ----------
    real_root = Path(os.path.realpath(root_cfg["path"]))   # ★ 防 root 自身是 junction
    candidate = real_root / norm

    # ---------- 步 5：逐段 reparse point 检查 ----------
    cur = real_root
    for seg in parts:
        if seg in ("", "."):
            continue
        cur = cur / seg
        try:
            st = os.lstat(cur)                             # ★ lstat 而非 stat
        except FileNotFoundError:
            break                                          # 后续段不存在 → 无需再查
        except OSError as e:
            raise SandboxError(f"stat failed: {e}")
        if _is_reparse_or_link(cur, st):
            raise SandboxError(f"symlink/junction/reparse point not allowed: {seg!r}")

    # ---------- 步 6：前缀断言 ----------
    p = Path(os.path.realpath(candidate))                  # resolve(strict=False) 语义
    a = os.path.normcase(str(real_root))
    b = os.path.normcase(str(p))
    if a != b:
        if os.path.commonpath([a, b]) != a:                # ★ commonpath 而非 startswith
            raise SandboxError(f"path escapes root: {p} not under {real_root}")

    # ---------- 步 7：权限 ----------
    mode = root_cfg.get("mode", "readonly")
    if need == "read" and mode not in ("readonly", "readwrite"):
        raise SandboxError(f"read not permitted in mode {mode}")
    if need == "write" and mode not in ("upload", "readwrite"):
        raise SandboxError(f"write not permitted in mode {mode}")
    if need == "delete":
        if mode != "readwrite" or not config.get()["auth"]["allow_delete"]:
            raise SandboxError("delete not permitted")

    return p


def _is_reparse_or_link(path: Path, st: os.stat_result) -> bool:
    """Windows 上判断 symlink / junction / reparse point。

    为什么不能只看 os.path.islink：
    junction（目录联接）不是 symlink，islink() 返回 False，
    但它能把路径指向任意位置 —— 这是 Windows 上最容易被忽略的越界方式。
    判断方式：stat.FILE_ATTRIBUTE_REPARSE_POINT (0x400) 位。
    """
    if os.path.islink(path):
        return True
    if hasattr(st, "st_file_attributes"):                  # 仅 Windows
        return bool(st.st_file_attributes & FILE_ATTRIBUTE_REPARSE_POINT)
    return False


def tmp_path(root_cfg: dict, upload_id: str) -> Path:
    """上传临时区：必须与目标同卷（§4.3.2）。"""
    real_root = Path(os.path.realpath(root_cfg["path"]))
    d = real_root / ".photobridge_tmp"
    d.mkdir(parents=True, exist_ok=True)
    if not re.fullmatch(r"[A-Za-z0-9_-]{16,32}", upload_id):
        raise SandboxError(f"bad upload_id: {upload_id!r}")   # ★ 防 upload_id 注入
    return d / f"{upload_id}.part"
```

### 4.6 本地服务 `local_server.py` + `dispatch.py` ★

#### 4.6.1 为什么这样设计（"前端零分支"的实现基础）

设计文档 §4.5 关键点：*"电脑上的 Agent 既是'本地 HTTP 服务'又是'隧道服务端'，
两者调用**同一套路由函数**。所以手机走局域网直连和走云端中继，API 完全一致，前端无感切换。"*

**实现要点**：把业务逻辑写成**不依赖 FastAPI `Request`/`Response` 的纯函数**，
接收一个**协议无关的 `Ctx`**，返回一个协议无关的 `Reply`。然后写两个薄适配器：

```
                    ┌───────────────────────────────┐
   本地 HTTP  ──────►│ adapt_http(Starlette Request) │──┐
                    └───────────────────────────────┘  │
                                                       ├──► Ctx ──► handler(ctx) ──► Reply
                    ┌───────────────────────────────┐  │                              │
   隧道帧    ──────►│ adapt_tunnel(Frame 流)         │──┘                              │
                    └───────────────────────────────┘                                 │
                    ┌───────────────────────────────┐                                 │
   输出  ◄──────────│ to_http(Reply) / to_frames(Reply) ◄──────────────────────────────┘
                    └───────────────────────────────┘
```

**收益**：① 一处业务逻辑，两种协议，零重复；② 单元测试可以直接构造 `Ctx` 调用 handler，
不需要起 HTTP 服务，测试速度快 10 倍；③ 二期加 E2E 加密只需改 `adapt_tunnel`。

#### 4.6.2 协议无关的中间表示

```python
@dataclass
class Ctx:
    """一次请求的协议无关表示。handler 只认这个。"""
    method: str
    path: str                              # "/api/timeline"
    query: dict[str, str]
    headers: dict[str, str]                # 已小写化
    body: AsyncIterator[bytes]             # ★ 流式，不是 bytes
    client_name: str                       # 从 token 解出的设备名
    client_id: str
    via: str                               # "lan" | "relay"

@dataclass
class Reply:
    """一次响应的协议无关表示。"""
    status: int
    headers: dict[str, str]
    body: AsyncIterator[bytes]             # ★ 流式
    media_type: str | None = None
```

#### 4.6.3 路由表（两种协议共用）

```python
]

def match_route(method: str, path: str) -> tuple[Callable, dict] | None:
    for m, pat, fn in ROUTES:
        if m != method:
            continue
        mo = pat.match(path)
        if mo:
            return fn, mo.groupdict()
    return None
```

**为什么用 `re.Pattern` 而不是 FastAPI 的装饰器**：装饰器把路由绑死在 FastAPI 上，
而隧道请求没有 FastAPI `Request` 对象，无法复用。用裸正则表 + `Ctx` 才能真正共用。

#### 4.6.4 HTTP 适配器

```python
def make_asgi_app() -> FastAPI:
    app = FastAPI(docs_url=None, redoc_url=None)

    @app.api_route("/{path:path}",
                   methods=["GET","POST","PATCH","PUT","DELETE","HEAD"])
    async def _entry(request: Request, path: str):
        ctx = await adapt_http(request, path)
        try:
            fn, params = match_route(ctx.method, ctx.path) or (None, None)
            if fn is None:
                return JSONResponse({"error": "not_found"}, 404)
            reply = await fn(ctx, params)
        except AppError as e:
            reply = e.to_reply()                    # §6.1 统一错误映射
        except Exception:
            log.exception("handler crashed: %s %s", ctx.method, ctx.path)
            reply = Reply(500, {"content-type": "application/json"},
                          aiter_bytes(json_bytes({"error": "internal"})),
                          "application/json")
        return to_http(reply)

    return app


async def adapt_http(request: Request, path: str) -> Ctx:
    return Ctx(
        method=request.method,
        path="/" + path,
        query=dict(request.query_params),
        headers={k.lower(): v for k, v in request.headers.items()},
        body=request.stream(),                      # ★ Starlette 的流式体
        client_name=getattr(request.state, "client_name", "local"),
        client_id=getattr(request.state, "client_id", "local"),
        via=request.headers.get("x-pb-via", "lan"),
    )


def to_http(reply: Reply) -> StreamingResponse:
    return StreamingResponse(reply.body, status_code=reply.status,
                             headers=reply.headers, media_type=reply.media_type)
```

**本地鉴权**：局域网直连也必须带 `client_token`（设计文档 §8.2"手机 ↔ 电脑（直连时）用同一 client_token"）。
中间件从 `Authorization` 头取 token，查**本地缓存的**已配对 client 列表
（配对时由云端下发并落 `data/clients.json`）。校验失败 → 401。

#### 4.6.5 隧道适配器（`dispatch.py`）

```python
async def handle_tunnel_request(conn, rid: int, head: Frame) -> None:
    """收到 REQ_HEAD 后：把后续 REQ_BODY 组装成异步生成器，调用同一个 handler。"""
    meta = head.json
    body_q: asyncio.Queue[bytes | None] = asyncio.Queue(maxsize=32)
    conn.mux.register_body_queue(rid, body_q)         # REQ_BODY 帧入这个队列

    async def body_iter():
        while True:
            chunk = await body_q.get()
            if chunk is None:
                return
            yield chunk
            await conn.mux.credit.consumed(rid, len(chunk))   # ★ 回补信用

    ctx = Ctx(
        method=meta["method"],
        path=meta["path"],
        query=meta.get("query", {}),
        headers={k.lower(): v for k, v in meta.get("headers", {}).items()},
        body=body_iter(),
        client_name=meta.get("client_name", ""),
        client_id=meta.get("client_id", ""),
        via="relay",
    )

    try:
        fn, params = match_route(ctx.method, ctx.path) or (None, None)
        if fn is None:
            await send_error(conn, rid, "not_found", "no such route", 404)
            return
        reply = await fn(ctx, params)
    except AppError as e:
        await send_error(conn, rid, e.code, e.message, e.status)
        return
    except Exception:
        log.exception("tunnel handler crashed: %s %s", ctx.method, ctx.path)
        await send_error(conn, rid, "internal", "handler crashed", 500)
        return

    # 回帧：HEAD → BODY × N → END
    await conn.mux.send_frame(FrameType.RES_HEAD, rid, {
        "status": reply.status,
        "headers": {**reply.headers, "x-pb-via": "agent"},
    })
    fc = conn.mux.fc
    async for chunk in reply.body:
        await fc.send_body_res(rid, chunk)             # 受信用约束
    await conn.mux.send_frame(FrameType.RES_END, rid)
```

**必须验证的行为**（C1/C2 测试用例）：

| 用例 | 断言 |
|---|---|
| 同一 handler 走 HTTP 与走隧道 | 响应 status / body / 关键头**完全一致** |
| 隧道上传 100 MB | 电脑端内存增量 < 30 MB |
| 手机中途 CANCEL | handler 的 `body_iter` 被 `GeneratorExit` 中断，临时文件清理 |
| 路由不存在 | 回 `ERROR{not_found}`，HTTP 侧回 404 |

### 4.7 事件推送 `events.py`

#### 4.7.1 为什么这样设计

设计文档 §7.2 有 `GET /api/events`（SSE）。用途：索引进度条、缩略图生成进度、上传完成提示。
**为什么用 SSE 而不是 WebSocket**：① 单向推送足够；② SSE 走普通 HTTP，**在隧道里天然可复用**
（`RES_BODY` 流式回传就是 SSE 的字节流）；③ 浏览器 `EventSource` 自带重连。

#### 4.7.2 实现

```python
class EventBus:
    def __init__(self) -> None:
        self._subs: set[asyncio.Queue[dict]] = set()

    def subscribe(self) -> asyncio.Queue[dict]:
        q: asyncio.Queue[dict] = asyncio.Queue(maxsize=100)
        self._subs.add(q)
        return q

    def unsubscribe(self, q: asyncio.Queue[dict]) -> None:
        self._subs.discard(q)

    async def publish(self, topic: str, data: dict) -> None:
        """非阻塞广播：队列满则丢弃最旧事件（进度类事件允许丢，不能拖慢索引器）。"""
        evt = {"topic": topic, "ts": time.time(), "data": data}
        for q in list(self._subs):                 # ★ 快照，防迭代中被改
            try:
                q.put_nowait(evt)
            except asyncio.QueueFull:
                try:
                    q.get_nowait()                 # 丢最旧
                    q.put_nowait(evt)
                except asyncio.QueueEmpty:
                    pass

bus = EventBus()


async def sse(ctx: Ctx, params: dict) -> Reply:
    q = bus.subscribe()

    async def gen():
        try:
            # 首帧：立即发一次当前状态，避免客户端白等
            yield _sse_frame("hello", {"ts": time.time()})
            # 心跳注释行，防中间代理 60s 断流
            while True:
                try:
                    evt = await asyncio.wait_for(q.get(), timeout=15)
                except asyncio.TimeoutError:
                    yield b": keepalive\n\n"       # SSE 注释行，客户端忽略
                    continue
                yield _sse_frame(evt["topic"], evt["data"])
        except asyncio.CancelledError:
            raise
        finally:
            bus.unsubscribe(q)                     # ★ 客户端断开必须退订，否则泄漏

    return Reply(200, {"content-type": "text/event-stream",
                       "cache-control": "no-cache",
                       "x-accel-buffering": "no"},     # ★ 禁用 Nginx/Caddy 缓冲
                 gen(), "text/event-stream")


def _sse_frame(topic: str, data: dict) -> bytes:
    payload = json.dumps(data, ensure_ascii=False, separators=(",", ":"))
    return f"event: {topic}\ndata: {payload}\n\n".encode("utf-8")
```

### 4.8 托盘 `tray.py`

#### 4.8.1 为什么这样设计

设计文档 §10.2 要求：托盘菜单、开机自启、单实例锁、配对码 + 二维码展示。

```python
MUTEX_NAME = "Global\\PhotoBridgeAgent_v1"

def acquire_single_instance() -> bool:
    """Windows 命名互斥体。返回 False 表示已有实例在跑。
    为什么用互斥体而不是"端口占用检测"：
    ① 端口可能被别的程序占用，误判；② 互斥体随进程退出自动释放，无残留锁文件。"""
    import ctypes
    from ctypes import wintypes
    kernel32 = ctypes.windll.kernel32
    kernel32.CreateMutexW.restype = wintypes.HANDLE
    handle = kernel32.CreateMutexW(None, False, MUTEX_NAME)
    if not handle:
        return False
    if kernel32.GetLastError() == 183:            # ERROR_ALREADY_EXISTS
        return False
    globals()["_MUTEX_HANDLE"] = handle           # 必须持有引用，否则会被 GC 释放
    return True
```

**第二个实例的行为**：不静默退出，而是**激活已有实例的托盘窗口**并提示"PhotoBridge 已在运行"。
（一期简化为：弹 `MessageBox` 后退出。）

### 5.1 双通路切换状态机 ★

#### 5.1.1 为什么这样设计

设计文档 §6.1 要求：Wi-Fi 下先试局域网（1.5 秒超时），失败走云端；
"记住这次失败，本次会话不再试直连"。

**为什么"记住失败"而不是"每次请求都试直连"**：直连探测有 1.5 秒超时成本，
若每次请求都试，用户会持续感受到 1.5 秒延迟。记住失败后，本次会话所有请求直接走云端。

**代价**：用户在家从"手机流量"切到"家里 Wi-Fi"后，本次会话不会自动升级到直连。
**缓解**：监听 `online`/`offline` 事件 + 页面重新可见（`visibilitychange`）时**重置一次**探测机会。

#### 5.1.4 "记住失败"策略

```typescript
interface ProbeMemory {
  lanFailedAt: number | null;      // 直连失败的时刻（会话内）
  cloudFailedAt: number | null;
  lastProbeAt: number | null;
  reProbeCooldownMs: number;       // 5000 次探测的最小间隔
}

const RE_PROBE_COOLDOWN = 5 * 60 * 1000;

function shouldTryLan(): boolean {
  if (!navigator.onLine) return false;
  // 蜂窝网络直接走云（设计文档 §6.1：蜂窝网络直接走云）
  if (isCellular()) return false;
  if (!cachedLanUrl) return false;
  // ★ 记住失败：本会话内直连失败过就不再试（除非冷却期已过且网络发生了变化）
  if (memory.lanFailedAt && Date.now() - memory.lanFailedAt < RE_PROBE_COOLDOWN) {
    return false;
  }
  return true;
}
```

**为什么蜂窝网络不试直连**：局域网地址在蜂窝网络下**必然不可达**，
试一次就是白等 1.5 秒。判断方式：`navigator.connection?.type === "cellular"`
（Chrome/Android 支持）；不支持的浏览器用"探测失败记忆"兜底。

#### 5.1.5 切换时正在进行的请求怎么办 ★

**这是设计文档没有明确、但必须回答的问题。** 采用**分层策略**：

| 请求类型 | 切换时的处理 | 理由 |
|---|---|---|
| **缩略图 GET** | **不重试**，直接让 `<img>` 走新 baseUrl 重新加载 | 幂等且廉价；重试逻辑复杂且收益低 |
| **时间线/详情 GET** | **自动重试一次**（换通路后立即重发） | 幂等；用户不该因为通路切换看到错误 |
| **SSE `/api/events`** | 断开并**用新通路重连** | EventSource 自带重连，但会连旧 baseUrl，必须手动重建 |
| **上传 PATCH 分片** | **不自动重试**，标记该分片失败，进入重试队列 | 见 §5.5：先 `GET /uploads/{id}` 拿 offset 再续传，避免重复写 |
| **上传 complete** | 自动重试 1 次 | 幂等（服务端 sha256 去重 + 会话状态机） |
| **删除/移动 POST** | **绝不自动重试**，直接报错给用户 | 非幂等，重试可能造成二次删除（虽然进回收站，但会让用户困惑） |

```typescript
// 统一的重试判定
function shouldRetryOnSwitch(req: ApiRequest): boolean {
  if (req.method === "GET" && req.idempotent !== false) return true;
  if (req.method === "POST" && req.op === "complete") return true;
  return false;                       // 其他一律不自动重试
}

async function onTransportSwitched(newBase: string): Promise<void> {
  // ① 重建 SSE
  events.close();
  events = new EventSource(`${newBase}/api/events`);
  // ② 取消所有 in-flight 的、不可重试的请求，并给用户明确提示
  for (const req of inflight.values()) {
    if (!shouldRetryOnSwitch(req)) {
      req.abort(new TransportSwitchedError());
      toast.warn(`网络通路已切换，请重试「${req.label}」`);
    }
  }
  // ③ 可重试的请求重新入队
  for (const req of inflight.values()) {
    if (shouldRetryOnSwitch(req)) requeue(req);
  }
}
```

**上传的特殊处理**：切换通路时，**正在传输的分片**（XHR `upload.onprogress` 有进度但未完成）
必须 `abort()` 并丢弃；恢复时**重新从服务端 offset 开始**。
绝不能"从中断处继续写"——因为服务端可能已经收到了部分字节，客户端不知道收到哪了。

### 5.2 请求层设计

#### 5.2.1 统一 API client

```typescript
// src/api/client.ts
export interface ApiError extends Error {
  status: number;
  code: string;          // 统一错误码（§6.1）
  retryable: boolean;
}

class ApiClient {
  private baseUrl = "";                    // 由 transport 动态设置
  private token = "";                      // client_token

  setBase(url: string): void { this.baseUrl = url; }
  setToken(t: string): void { this.token = t; }

  private buildHeaders(extra?: HeadersInit): Headers {
    const h = new Headers(extra);
    if (this.token) h.set("Authorization", `Bearer ${this.token}`);
    h.set("X-PB-Client", deviceName);       // 电脑端审计日志用
    return h;
  }

  async request<T>(path: string, init: RequestInit & { retry?: number } = {}): Promise<T> {
    const url = `${this.baseUrl}${path}`;
    let lastErr: unknown;
    const maxRetry = init.retry ?? 0;

    for (let attempt = 0; attempt <= maxRetry; attempt++) {
      try {
        const res = await fetch(url, { ...init, headers: this.buildHeaders(init.headers) });
        if (res.ok) return await this.parse<T>(res);
        const err = await this.toError(res);
        // ★ 只重试"可重试"的错误：5xx / 408 / 429 / 网络错
        if (!err.retryable || attempt === maxRetry) throw err;
        await sleep(backoffMs(attempt, res.headers.get("Retry-After")));
      } catch (e) {
        lastErr = e;
        if (attempt === maxRetry) break;
        await sleep(backoffMs(attempt));
      }
    }
    throw lastErr;
  }

  /** 流式 GET（用于原图下载到 Blob 时避免一次性占内存，二期可用） */
  async stream(path: string): Promise<ReadableStream<Uint8Array>> { /* … */ }
}

function backoffMs(attempt: number, retryAfter?: string | null): number {
  if (retryAfter) return Math.min(parseInt(retryAfter, 10) * 1000 || 1000, 30_000);
  const base = Math.min(500 * 2 ** attempt, 8000);
  return base * (0.8 + Math.random() * 0.4);      // ★ 抖动，防所有客户端同时重试
}
```

#### 5.2.2 基地址动态切换

**关键点**：`baseUrl` 必须在**每次请求时读取**，不能缓存在闭包里。


**云端路径前缀**：走云时 `baseUrl = "https://域名/d/{device_id}"`，
所以同一个 `/api/timeline` 在两种通路下分别拼成：
- 直连：`http://192.0.2.10:8787/api/timeline`
- 云端：`https://域名/d/abc123/api/timeline`

**这正是设计文档 §2.1 "两条路走完全相同的 API 路径，前端代码零分支"的实现方式**。

#### 5.2.3 鉴权头注入

| 通路 | 头 | 说明 |
|---|---|---|
| 云端 | `Authorization: Bearer <client_token>` | 云端校验 |
| 直连 | `Authorization: Bearer <client_token>` | 电脑端本地校验同一 token |

#### 5.2.4 上传的独立通道（XHR 而非 fetch）★

**为什么必须用 XHR**：`fetch` **无法获取上传进度**（`Request` 没有 `upload.onprogress`）。
`fetch` 的 `ReadableStream` 请求体在 Safari/iOS 上支持极差，且仍拿不到"已发送字节数"。
**上传必须用 `XMLHttpRequest`。**

```typescript
// src/api/uploader.ts
export interface UploadProgress {
  loaded: number;      // 已发送字节（本次分片）
  total: number;       // 本次分片总字节
  rate: number;        // 字节/秒（滑动平均）
}

export function uploadChunk(
  url: string, token: string, blob: Blob, contentRange: string,
  onProgress: (p: UploadProgress) => void, signal: AbortSignal,
): Promise<{ offset: number }> {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    let lastLoaded = 0, lastTs = performance.now();
    let rate = 0;

    xhr.open("PATCH", url, true);
    xhr.setRequestHeader("Authorization", `Bearer ${token}`);
    xhr.setRequestHeader("Content-Type", "application/octet-stream");
    xhr.setRequestHeader("Content-Range", contentRange);

    xhr.upload.onprogress = (e) => {
      const now = performance.now();
      const dt = (now - lastTs) / 1000;
      if (dt > 0.25) {                                  // 每 250ms 更新一次速度
        const inst = (e.loaded - lastLoaded) / dt;
        rate = rate === 0 ? inst : rate * 0.7 + inst * 0.3;   // ★ 指数滑动平均
        lastLoaded = e.loaded; lastTs = now;
      }
      onProgress({ loaded: e.loaded, total: e.total, rate });
    };

    xhr.onload = () => {
      if (xhr.status >= 200 && xhr.status < 300) {
        resolve(JSON.parse(xhr.responseText));
      } else if (xhr.status === 409) {
        // 服务端说 offset 不对：把正确 offset 带回去，让调用方重对齐
        const body = JSON.parse(xhr.responseText || "{}");
        reject(new OffsetMismatch(body.current ?? 0));
      } else {
        reject(new HttpError(xhr.status, xhr.responseText));
      }
    };
    xhr.onerror = () => reject(new NetworkError("upload network error"));
    xhr.ontimeout = () => reject(new NetworkError("upload timeout"));
    xhr.onabort = () => reject(new AbortError());

    signal.addEventListener("abort", () => xhr.abort(), { once: true });
    xhr.send(blob);
  });
}
```

**超时设置**：`xhr.timeout = 120_000`（2 分钟）。**为什么**：云带宽 5 Mbps 下 2 MB 分片约 3.2 秒，
120 秒留足 30 倍余量；无限等待会让"卡死"的上传永远占着队列。

**sha256 秒传**：一期**不在手机端算 sha256**。
理由：① 手机 JS 算 4 MB 文件的 sha256 需要 100–300 ms（`crypto.subtle.digest`），
批量 500 张就是 1–2 分钟，用户等不起；② 一期用"文件名 + 大小 + mtime"做初步判重已经够用
（`init` 时带上 `name/size/mtime`，服务端可查 `media` 表比对），
真正的 `sha256` 在**服务端 complete 时算**（见 §4.3.3 ④），秒传只对"服务端已算过 hash"的文件生效。
**二期优化**：若用户开启"完整去重"，再用 Worker 后台算 hash。

### 5.3 时间线虚拟滚动

#### 5.3.1 为什么这样设计

4900 张照片若一次性渲染，DOM 节点数 4900 × 3 层 = 15000 个，安卓中端机直接卡死。
**采纳方案：IntersectionObserver 懒加载 + 游标分页 + 按天分组**，不引入虚拟列表库。

**为什么不用 `vue-virtual-scroller`**：
① 照片是**等高网格**（3 列正方形），天然适合"按天分块"的分段渲染；
② 引入库要 +30 KB 且需要处理变高行；
③ 用"懒加载 + 卸载远端"就能达到 90% 的效果，实现量 1/5。

#### 5.3.2 分页与预取策略

| 项 | 值 | 说明 |
|---|---|---|
| 每页条数 | `limit=100` | 设计文档 §7.2 默认值 |
| 触发加载 | 最后一张**之前 30 张**进入视口 | 预取，避免用户滑到底等白屏 |
| 预取深度 | 提前加载**下一页** | 用户连续滑动时不中断 |
| 分组 | 按**本地日期**（`taken_at` 转本地时区）分天 | — |
| 游标 | `cursor = 上一页最后一条的 {taken_at, id}` | keyset 分页，见 §8.2 |
| 最大保留 | 保留最近 1500 条在内存，更早的卸载 DOM（数据留在 `Map<id, MediaItem>` 里） | 防内存膨胀 |

```typescript

    if (sentinel.value) io.observe(sentinel.value);
  });
  onUnmounted(() => io?.disconnect());

  return { sentinel };
}
```

```typescript
  state.loading = true;

      state.byId.set(it.id, it);
    }
    state.cursor = page.next_cursor;
    state.exhausted = page.next_cursor === null;
    rebuildDays();
  } finally {
    state.loading = false;
  }

  for (const it of state.items) {
    const key = localDateKey(it.taken_at);      // "2024-05-12"
    (groups.get(key) ?? groups.set(key, []).get(key)!).push(it);
  }
```

#### 5.4.3 内存管理 ★

**为什么必须限制同时解码的图片数量**：一张 4000×3000 的 JPEG 解码后是 `4000×3000×4 ≈ 48 MB`。
安卓 Chrome 的渲染进程内存上限约 300–500 MB（低端机更低）。
用户快速滑动浏览 10 张原图 = 480 MB → **必然 OOM 崩溃**。

**三层限制**：

| 层 | 限制 | 实现 |
|---|---|---|
| ① 同时挂载的 `<img>` 数量 | **最多 3 张**（当前 + 前后各 1） | `v-if` 卸载远端图片，只保留 URL 字符串 |
| ② 原图预取并发 | **最多 1 个** | 串行预取，且用 `AbortController` 取消上一个 |
| ③ 解码尺寸 | 预览图最大 1600，**原图仅按需** | 只有用户放大到 > 1.5× 才用原图 |

### 5.5 上传队列

#### 5.5.1 为什么这样设计

设计文档 §6.2 要求上传队列有"进度/速度/暂停/续传"。
手机上传是最容易被系统打断的场景（切后台、锁屏、来电），
因此**队列状态必须持久化**，否则切后台回来用户看到"什么都没了"。

#### 5.5.2 参数

| 参数 | 值 | 说明 |
|---|---|---|
| 并发度 | **2**（蜂窝）/ **3**（Wi-Fi） | 蜂窝下并发过高会让每个连接都慢；Wi-Fi 下 3 条能跑满 |
| 分片大小 | 由服务端 `init` 返回（2 MB / 8 MB） | §4.3.3 |
| 分片失败重试 | 3 次，退避 1s / 3s / 9s | 分片幂等，可安全重试 |
| 文件失败重试 | 2 次（整个文件重来，从 offset 续） | — |
| 队列持久化 | `IndexedDB` | 文件用 `Blob` 存，切后台不丢 |
| 进度更新频率 | 250 ms | 避免每帧触发 Vue 响应式更新 |
| 速度显示 | 指数滑动平均（α=0.3） | 抖动小，可读性好 |

#### 5.5.3 状态机

```typescript
interface UploadTask {
  id: string;                    // 本地 id（uuid）
  uploadId: string | null;       // 服务端会话 id（init 后才有）
  file: Blob;                    // 原始 File/Blob
  name: string;
  size: number;
  mtime: number;
  offset: number;                // 已成功写入服务端的字节数
  chunkSize: number;
  status: UploadStatus;
  retries: number;
  error?: string;
  rate: number;                  // 字节/秒
  startedAt: number;
}

async function runTask(task: UploadTask, signal: AbortSignal): Promise<void> {
  // ① init（幂等；若 uploadId 已存在则跳过）
  if (!task.uploadId) {
    const r = await api.post<InitResponse>("/api/uploads/init", {
      name: task.name, size: task.size, mtime: task.mtime,
    });
    if (r.exists) { task.status = "DEDUPED"; return; }
    task.uploadId = r.upload_id;
    task.chunkSize = r.chunk_size;
    task.offset = r.offset;                       // ★ 服务端可能已有部分数据
  } else {
    // ② 续传：先问服务端收到哪了（★ 以服务端为准，不信本地 offset）
    const r = await api.get<PatchResult>(`/api/uploads/${task.uploadId}`);
    task.offset = r.offset;
  }

  // ③ 循环发分片
  while (task.offset < task.size) {
    if (task.status === "PAUSED") return;
    const end = Math.min(task.offset + task.chunkSize, task.size);
    const blob = task.file.slice(task.offset, end);
    const range = `bytes ${task.offset}-${end - 1}/${task.size}`;
    try {
      const res = await uploadChunk(
        `${api.base}/api/uploads/${task.uploadId}`, token, blob, range,
        (p) => { task.rate = p.rate; }, signal);
      task.offset = res.offset;                   // ★ 以服务端返回为准
    } catch (e) {
      if (e instanceof OffsetMismatch) {          // 服务端说 offset 不对
        task.offset = e.current;                  // 重对齐后继续，不算失败
        continue;
      }
      throw e;
    }
  }

  // ④ complete
  task.status = "COMPLETING";
  const done = await api.post<CompleteResult>(
    `/api/uploads/${task.uploadId}/complete`, {}, { retry: 1 });
  task.status = done.deduped ? "DEDUPED" : "DONE";
  await persistQueue();
}
```

**进度与限速显示**：

```typescript
function overallProgress(): { percent: number; rateText: string; eta: number } {
  const total = tasks.reduce((s, t) => s + t.size, 0);
  const sent  = tasks.reduce((s, t) => s + t.offset, 0);
  const rate  = tasks.reduce((s, t) => (t.status === "UPLOADING" ? s + t.rate : s), 0);
  return {
    percent: total ? (sent / total) * 100 : 0,
    rateText: formatBytes(rate) + "/s",
    eta: rate > 0 ? (total - sent) / rate : Infinity,
  };
}
```

**为什么总速度是"各任务速度之和"而不是"总字节 / 总时间"**：
并发 3 条时后者会被"排队等待时间"拉低，显示的数字远低于用户感知的网速，让人以为很慢。

#### 5.5.5 wakeLock 防息屏

```typescript
// src/composables/useWakeLock.ts
let sentinel: WakeLockSentinel | null = null;

export async function acquireWakeLock(): Promise<void> {
  if (!("wakeLock" in navigator)) return;          // 桌面端/旧浏览器无此 API
  try {
    sentinel = await navigator.wakeLock.request("screen");
    sentinel.addEventListener("release", () => { sentinel = null; });
  } catch { /* 用户拒绝或页面不可见时静默失败 */ }
}

export function releaseWakeLock(): void {
  sentinel?.release().catch(() => {});
  sentinel = null;
}

// ★ 必须在页面重新可见时重新申请：切后台时浏览器会强制释放 wakeLock
document.addEventListener("visibilitychange", async () => {
  if (document.visibilityState === "visible"
      && uploadStore.hasActiveTasks()
      && !sentinel) {
    await acquireWakeLock();
  }
});
```

**申请时机**：队列从"空"变"非空"时申请；队列全部完成或用户暂停时释放。
**设计文档 §6.4 明确指出**：wakeLock 只在**安全上下文（HTTPS）**下可用——
这正是一期改用云桥接的收益之一。走局域网 HTTP 直连时 `wakeLock` 不可用，
此时降级为"提示用户不要锁屏"。

#### 5.5.6 切后台恢复

| 场景 | 行为 |
|---|---|
| 切后台 < 30 秒 | 上传继续进行（Chrome 允许短时后台） |
| 切后台 > 30 秒 | 浏览器冻结 JS → XHR 被挂起；回到前台后 `onerror`/`ontimeout` 触发 → 进入 `RETRY` |
| 页面被回收（内存压力） | 重新打开时从 IndexedDB 读队列，**全部 `UPLOADING` 状态重置为 `PENDING`**，重新走续传逻辑 |
| 网络断开（`offline` 事件） | 所有活跃任务立即暂停（`PAUSED`），不清空队列；`online` 时自动恢复 |

```typescript
// 页面加载时恢复队列

  const saved = await idbGetAll<UploadTask>("upload_queue");
  for (const t of saved) {
    // ★ 关键：任何"进行中"状态都不能信，一律回到 PENDING
    if (t.status === "UPLOADING" || t.status === "COMPLETING") t.status = "PENDING";
```

**为什么必须把 `UPLOADING` 重置为 `PENDING`**：页面被回收时无法知道最后一次分片是否成功落盘。
重置后走"先 `GET /uploads/{id}` 问 offset"的路径，**以服务端为准**，永远正确。

### 5.6 Service Worker 缓存策略

#### 5.6.1 为什么这样设计

设计文档 §6.4：*"缩略图永久缓存到手机本地，二次浏览几乎零流量"*。
这是 HTTPS 带来的最大红利，也是 §1.3"浏览 1000 张缩略图 ≤ 25 MB"指标能达成的前提
（首次 25 MB，之后接近 0）。

#### 5.6.2 分路策略

| 请求类型 | 匹配规则 | 策略 | 理由 |
|---|---|---|---|
| 缩略图 | `*/api/items/*/thumb*` | **Cache First + 永久** | 内容由 `(id, size)` 唯一决定，且源文件改动会换 ETag |
| 预览图 | `*/api/items/*/preview*` | **Cache First + LRU 上限 200 张** | 体积大（200 KB），需要限制 |
| 原图 | `*/api/items/*/raw*` | **不缓存**（除非用户点"离线保存"） | 4 MB × N 会瞬间吃光配额 |
| API 请求 | `*/api/*` 其他 | **Network Only** | 时间线/搜索必须实时 |
| 上传 | `PATCH */api/uploads/*` | **不拦截**（直接放行） | 非幂等，绝不能缓存 |
| 静态资源 | `/assets/*`、`/`、`/index.html` | Stale-While-Revalidate | 应用外壳要能离线打开 |
| 事件流 | `*/api/events` | **不拦截** | SSE 必须直连 |

```javascript
// public/sw.js
const THUMB_CACHE = "pb-thumbs-v1";
const PREVIEW_CACHE = "pb-previews-v1";
const SHELL_CACHE = "pb-shell-v1";
const PREVIEW_MAX = 200;
const TOTAL_QUOTA = 300 * 1024 * 1024;      // 300 MB 上限

self.addEventListener("install", (e) => {
  e.waitUntil(caches.open(SHELL_CACHE).then((c) => c.addAll(["/", "/index.html"])));
  self.skipWaiting();
});

self.addEventListener("activate", (e) => {
  e.waitUntil((async () => {
    // 清理旧版本缓存
    const keys = await caches.keys();
    await Promise.all(keys
      .filter((k) => !["pb-thumbs-v1", "pb-previews-v1", "pb-shell-v1"].includes(k))
      .map((k) => caches.delete(k)));
    await self.clients.claim();
  })());
});

self.addEventListener("fetch", (event) => {
  const url = new URL(event.request.url);

  // ① 不拦截：非 GET、上传、SSE
  if (event.request.method !== "GET") return;
  if (url.pathname.includes("/api/uploads/")) return;
  if (url.pathname.endsWith("/api/events")) return;

  // ② 缩略图：Cache First
  if (/\/api\/items\/\d+\/thumb/.test(url.pathname)) {
    event.respondWith(cacheFirst(event.request, THUMB_CACHE));
    return;
  }
  // ③ 预览图：Cache First + 数量上限
  if (/\/api\/items\/\d+\/preview/.test(url.pathname)) {
    event.respondWith(cacheFirst(event.request, PREVIEW_CACHE, PREVIEW_MAX));
    return;
  }
  // ④ 原图：不缓存
  if (/\/api\/items\/\d+\/raw/.test(url.pathname)) return;

  // ⑤ 其他 API：Network Only（离线时回明确的错误，而不是假数据）
  if (url.pathname.includes("/api/")) {
    event.respondWith(fetch(event.request));
    return;
  }
  // ⑥ 静态资源：Stale-While-Revalidate
  event.respondWith(staleWhileRevalidate(event.request, SHELL_CACHE));
});

async function cacheFirst(request, cacheName, maxEntries) {
  const cache = await caches.open(cacheName);
  const hit = await cache.match(request);
  if (hit) return hit;
  const res = await fetch(request);
  if (res.ok && res.status === 200) {
    // ★ 必须 clone：响应体只能读一次
    cache.put(request, res.clone());
    if (maxEntries) evictLRU(cache, maxEntries).catch(() => {});
  }
  return res;
}
```

#### 5.6.3 配额管理与清理

```javascript
async function evictLRU(cache, maxEntries) {
  const keys = await cache.keys();
  if (keys.length <= maxEntries) return;
  // 简单 FIFO（Cache API 的 keys() 顺序约等于插入顺序）
  const excess = keys.length - maxEntries;
  for (let i = 0; i < excess; i++) await cache.delete(keys[i]);
}

// 定期检查总占用（在 SW 的 activate 与每次缓存写入后抽查）
async function checkQuota() {
  if (navigator.storage?.estimate) {
    const { usage, quota } = await navigator.storage.estimate();
    if (usage > TOTAL_QUOTA) {
      const cache = await caches.open(PREVIEW_CACHE);
      const keys = await cache.keys();
      for (const k of keys.slice(0, Math.floor(keys.length / 2))) {
        await cache.delete(k);                 // 先清一半预览图
      }
    }
  }
}
```

| 项 | 值 | 说明 |
|---|---|---|
| 缩略图缓存 | 无上限（按 25 MB / 1000 张估算，1 万张 ≈ 250 MB） | 手机 128 GB 存储可接受 |
| 预览图缓存 | 200 张（约 40 MB） | LRU 淘汰 |
| 总配额软上限 | 300 MB | 超过则清一半预览图 |
| 用户手动清理 | "我的"页 → 缓存占用 → 清除 | 调 `caches.delete()` 全清 |

#### 5.7.1 用 Pinia 还是自写 reactive ★

| 维度 | Pinia | 自写 `reactive` |
|---|---|---|
| 体积 | +12 KB（gzip 后约 5 KB） | 0 |

③ 无插件生态需求（不需要持久化插件，因为 IndexedDB 逻辑要自己写）。

## 6. 错误处理与日志设计

### 6.1 统一错误码表 ★

#### 6.1.1 为什么这样设计

三端（云端 / 电脑端 / 手机端）都会产生错误。如果没有统一编码：
① 手机端只能靠 HTTP 状态码猜原因，文案只能写"操作失败"；
② 云端与电脑端的错误在手机端看起来一样，排障时无法区分是哪一段出的问题；
③ 日志里只能看到一句 `error: 500`，无法聚合统计。

**设计原则**：
1. **错误码是稳定的**，文案可改、码不可改（前端靠码做分支）。
2. **错误码分段**，一眼能看出责任方：`1xxx` 请求方错、`2xxx` 鉴权、`3xxx` 通路/设备、
   `4xxx` 媒体资源、`5xxx` 上传、`6xxx` 服务端内部。
3. **用户可见文案与内部详情分离**：`message` 给用户看（中文、无堆栈、无路径），
   `detail` 给开发看（仅写日志，**绝不返回给客户端**）。
4. **不泄漏绝对路径与系统信息**：所有面向客户端的错误消息中，路径一律用**相对库根的路径**。

#### 6.1.3 错误对象与映射

```python
# backend/app/errors.py
class AppError(Exception):
    """所有业务异常的基类。错误码是稳定契约，文案可以改。"""
    code: str = "internal"
    status: int = 500
    user_message: str = "服务器内部错误"
    retryable: bool = False

    def __init__(self, detail: str = "", *, extra: dict | None = None):
        super().__init__(detail)
        self.detail = detail          # ★ 只进日志，不进响应
        self.extra = extra or {}

    def to_payload(self) -> dict:
        return {"error": self.code, "message": self.user_message, **self.extra}

    def to_reply(self) -> "Reply":
        return json_reply(self.status, self.to_payload())


class BadRequest(AppError):
    code, status, user_message = "bad_request", 400, "请求参数有误"


class OffsetMismatch(AppError):
    """★ 唯一一个把内部状态返回给客户端的错误：客户端必须知道正确 offset 才能重对齐。"""
    code, status, user_message, retryable = "offset_mismatch", 409, "", True

    def __init__(self, current: int):
        super().__init__(f"offset mismatch, server at {current}", extra={"current": current})
```

| 异常类 | 码 | 状态 |
|---|---|---|
| `BadRequest` | `bad_request` | 400 |
| `PathDenied` | `path_denied` | 403 |
| `ReadonlyMode` | `readonly_mode` | 403 |
| `Unauthorized` | `unauthorized` | 401 |
| `MediaNotFound` | `media_not_found` | 404 |
| `FileMissing` | `file_missing` | 410 |
| `DiskFull` | `disk_full` | 507 |
| `OffsetMismatch(current)` | `offset_mismatch` | 409 |
| `Internal` | `internal` | 500 |

**映射规则（必须写在唯一一处）**：

```python
EXC_MAP: list[tuple[type[Exception], str, int, str, bool]] = [
    (SandboxError,             "path_denied",      403, "该路径不允许访问",         False),
    (ReadonlyError,            "readonly_mode",    403, "当前为只读模式，无法修改", False),
    (ArchiveError,             "archive_conflict", 500, "保存失败，请重试",         True),
    (sqlite3.OperationalError, "db_error",         500, "服务器内部错误",           True),
    (OSError,                  "internal",         500, "服务器内部错误",           True),
]


def to_app_error(e: BaseException) -> AppError:
    """把任意异常归一成 AppError。★ 未匹配的异常一律 6001，绝不把 str(e) 返回给客户端。"""
    if isinstance(e, AppError):
        return e
    for typ, code, status, msg, retry in EXC_MAP:
        if isinstance(e, typ):
            err = AppError(str(e))
            err.code, err.status, err.user_message, err.retryable = code, status, msg, retry
            return err
    return Internal(str(e))
```

**硬性要求**：响应体里的 `message` **禁止**出现以下内容（写测试断言）：

| 禁止出现 | 原因 |
|---|---|
| 绝对路径（`E:\`、`C:\`、`/home/`） | 泄漏服务器目录结构 |
| 异常类名与堆栈（`Traceback`、`File "..."`） | 泄漏实现细节，帮助攻击者 |
| SQL 片段（`SELECT`、`sqlite3.`） | 泄漏表结构 |
| 库内文件名 | 隐私 |
| Python 版本 / 库版本 | 指纹识别 |

### 6.2 三端日志规范

#### 6.2.1 通用要求

| 项 | 规定 |
|---|---|
| 格式 | 单行、结构化、UTF-8、`\n` 结尾（Windows 也**必须**用 `\n`，便于日志工具解析） |
| 时间 | **本地时间 + 时区偏移**（用户在自己电脑上看日志，UTC 反而难读） |
| 级别 | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL`，**禁止自造级别** |
| 敏感信息 | `token`、`agent_token`、配对码**只打前 4 位 + `***`** |
| 请求关联 | 每个请求分配 `rid`（8 位短 id），同一次请求的日志都带 `rid=` |
| 轮转 | 按大小轮转（见各端），保留有限份数，**绝不无限增长** |

**统一行格式（电脑端与云端）**：

```
2024-05-12 18:30:00.123 +08:00 INFO  [tunnel] rid=a3f9c1d2 hello_ack device=abc123 ver=0.3.0
```

```python
# backend/app/log.py
LOG_FORMAT = "%(asctime)s %(levelname)-7s [%(name)s] %(message)s"
DATE_FORMAT = "%Y-%m-%d %H:%M:%S"

def setup_logging(data_dir: Path, level: str = "INFO") -> None:
    """stdlib logging + RotatingFileHandler。
    为什么不引入 loguru/structlog：设计文档 §8.4 硬约束 1「不引入新依赖」。"""
    root = logging.getLogger()
    root.setLevel(level)
    fmt = logging.Formatter(LOG_FORMAT, DATE_FORMAT)

    fh = RotatingFileHandler(
        data_dir / "agent.log", maxBytes=10 * 1024 * 1024,
        backupCount=5, encoding="utf-8")          # ★ 必须显式 utf-8，否则中文日志乱码
    fh.setFormatter(fmt)
    root.addHandler(fh)

    if sys.stderr.isatty():                        # 只在有控制台时输出（打包后无控制台）
        sh = logging.StreamHandler(sys.stderr)
        sh.setFormatter(fmt)
        root.addHandler(sh)

    for noisy in ("uvicorn.access", "watchdog", "asyncio", "PIL"):   # 降噪
        logging.getLogger(noisy).setLevel(logging.WARNING)
```

| 设备注册表覆盖 | WARNING | 同一 `device_id` 从新 IP 连入（可能是重连，也可能是盗用） |
| 磁盘/内存告警 | CRITICAL | 1 核 1 GB 机器上尤其重要 |

**云端禁止记录**：请求体内容、任何图片字节、`agent_token`/`client_token` 明文。

#### 6.2.4 手机端日志

| 项 | 设计 |
|---|---|
| 生产环境 | **默认只记 `WARNING` 以上**，输出到 `console`（用户看不到） |
| 环形缓冲 | 内存里保留最近 200 条（`{ts, level, msg, ctx}`），"我的"页可导出 |
| 上报 | 一期**不上报**（无后端收集服务，也涉及隐私）；二期可加"发送诊断信息"（用户显式点击） |
| 级别 | `debug` 在 URL 带 `?debug=1` 时打开 |
| 禁止记录 | `token`、照片文件名（隐私）、EXIF 中的 GPS |

```typescript
// src/utils/log.ts
type Level = "debug" | "info" | "warn" | "error";
const LEVEL_ORDER: Record<Level, number> = { debug: 0, info: 1, warn: 2, error: 3 };
const RING_MAX = 200;
const ring: Array<{ ts: number; level: Level; msg: string; ctx?: unknown }> = [];
const minLevel: Level = new URLSearchParams(location.search).has("debug") ? "debug" : "warn";

export function log(level: Level, msg: string, ctx?: unknown): void {
  if (LEVEL_ORDER[level] < LEVEL_ORDER[minLevel]) return;
  ring.push({ ts: Date.now(), level, msg, ctx });
  if (ring.length > RING_MAX) ring.shift();
  const fn = level === "error" ? console.error : level === "warn" ? console.warn : console.log;
  fn(`[pb:${level}] ${msg}`, ctx ?? "");
}

export function exportLogs(): string {
  return ring.map((r) => `${new Date(r.ts).toISOString()} ${r.level.toUpperCase()} ${r.msg}`
    + (r.ctx ? ` ${JSON.stringify(r.ctx)}` : "")).join("\n");
}
```

### 6.3 用户可见错误 vs 内部错误

#### 6.3.1 分层原则

```
底层异常（OSError / sqlite3.Error / PIL.UnidentifiedImageError）
   │  ★ 只进日志，带完整堆栈
   ▼
AppError（有稳定 code + status + user_message）
   │  ★ code 与 status 进响应；detail 只进日志
   ▼
响应体 {"error": "<code>", "message": "<中文文案>", "extra?": {...}}
   │
   ▼
手机端 Toast（按 code 查本地文案表，可覆盖服务端文案）
```

**为什么手机端还要维护一份本地文案表**：① 服务端文案可能因版本不同而缺失；
② 前端可根据场景给出更精准的提示（例如上传页的 `offset_mismatch` 静默处理，详情页的则提示"重试"）；
③ 离线时也能给出提示。

#### 6.3.2 各端展示策略

| 场景 | 电脑端 | 云端 | 手机端 |
|---|---|---|---|
| 用户输入错误（1001/1102） | 表单红字提示 | 原样透传 | Toast |
| 鉴权失败（2xxx） | 弹"重新配对"对话框 | 401 透传 | 跳转配对页 |
| 通路问题（3xxx） | 托盘图标变灰 | 原样透传（含 `Retry-After`） | 顶部状态条变红/蓝 + Toast |

| 上传冲突（5003） | 不展示 | 透传 | **静默自动重对齐**（见 §5.5.4） |

**"静默"的判定标准**：如果一个错误有**确定的、无需用户决策的自动恢复动作**，
就不要弹给用户。`offset_mismatch` 是唯一这类错误。其他一律要让用户知道，
因为静默失败会让用户以为"上传成功了"。

### 6.4 崩溃与自愈

| 组件 | 崩溃表现 | 自愈策略 |
|---|---|---|
| 电脑端进程 | 服务消失，隧道断开 | 托盘菜单"退出"以外的崩溃由**外部守护**负责（一期不做自动重启，记入二期） |
| 单条 asyncio 任务 | `Task exception was never retrieved` | **所有** `create_task` 必须挂 `add_done_callback` 记日志，禁止裸 `create_task` |
| 缩略图 worker | 任务异常 | 捕获后走重试计数（§4.2.6），worker 本身**永不退出** |
| 索引任务 | 扫描中途抛异常 | `finally` 里清除 `_scanning` 标记 + 广播 `index_done{error}` |
| 云端隧道连接 | 断开 | 电脑端按指数退避重连（§2.7） |
| 云端进程重启 | 所有设备离线 | 设备按退避重连，注册表自然重建；**无需持久化隧道状态** |
| SQLite 锁 | `database is locked` | WAL + 单写连接（§7.1.4）从结构上避免；仍失败则重试 3 次 |

```python
def spawn(coro, *, name: str) -> asyncio.Task:
    """统一的任务创建入口。★ 全项目禁止直接 asyncio.create_task。"""
    t = asyncio.create_task(coro, name=name)

    def _done(task: asyncio.Task) -> None:
        if task.cancelled():
            return
        exc = task.exception()
        if exc is not None:
            log.error("task %s crashed", name, exc_info=exc)
    t.add_done_callback(_done)
    return t
```

## 7. 并发与异步设计

### 7.1 电脑端并发模型

#### 7.1.1 为什么这样设计

电脑端是一个 **asyncio 单事件循环 + 两个有界线程池**的进程。
**核心约束：事件循环上绝不能有超过 50 ms 的阻塞调用。**
一旦阻塞，隧道心跳（25 s）可能被延迟到超过 75 s 判定阈值，云端就会认为电脑离线，
用户看到"电脑离线"但电脑明明开着——这是最难排查的一类 bug。

#### 7.1.2 阻塞操作清单（必须丢线程池）★

| 操作 | 典型耗时 | 是否阻塞 | 处理 |
|---|---|---|---|
| `Image.open` + `_getexif()` | 5–200 ms | ✅ 阻塞 | **PILLOW_POOL** |
| 缩略图生成（`thumbnail` + WebP 编码） | 50–800 ms | ✅ 阻塞 | **PILLOW_POOL** |
| `os.walk` + `os.stat` | 1–50 ms | ✅ 阻塞 | 索引器**每 200 个文件 `await asyncio.sleep(0)`** |
| `sha256` 大文件（2 GB） | 3–8 s | ✅ 阻塞 | **IO_POOL**（分块 1 MB 读，可取消） |
| `send2trash` | 10–500 ms | ✅ 阻塞 | **IO_POOL** |
| SQLite 查询/写入 | < 1 ms（有索引） | ✅ 阻塞 | **专用写线程**，见 §7.1.4 |
| `os.replace` / `os.open` | < 1 ms | ⚠️ 轻微 | 直接在事件循环调用（原子、快） |
| `aiofiles` / `httpx` / `websockets` | 异步 | ❌ | 直接用 |

**两个线程池，职责隔离**：

```python
# 为什么分两个池：缩略图生成可能长时间占满池子，
# 若 EXIF 抽取与 sha256 共用同一个池，索引器会被缩略图饿死（排队等池子）。
PILLOW_POOL = ThreadPoolExecutor(max_workers=4, thread_name_prefix="pillow")
IO_POOL     = ThreadPoolExecutor(max_workers=4, thread_name_prefix="io")

async def run_pillow(fn, *args):
    return await asyncio.get_running_loop().run_in_executor(PILLOW_POOL, fn, *args)

async def run_io(fn, *args):
    return await asyncio.get_running_loop().run_in_executor(IO_POOL, fn, *args)
```

| 池 | 大小 | 用途 | 依据 |
|---|---|---|---|
| `PILLOW_POOL` | **4** | EXIF、缩略图 | `config.thumbs.workers=4`；4 个 Pillow 任务峰值约 4×60 MB |
| `IO_POOL` | **4** | sha256、send2trash、杂项 | 纯 IO，等待为主 |

**为什么池大小不是 `os.cpu_count()`**：设计文档 §1.3 要求"1 核 1 GB 可支撑"。
若按 CPU 数设置，1 核机器只有 1 个 worker，缩略图生成会成为瓶颈（首屏 2.5 s 达不到）。
固定 4 个 worker 在 1 核机器上靠**时间片轮转**仍能工作，只是慢一些；在多核机器上能跑满。

#### 7.1.3 信号量与队列上限

```python
thumb_queue: asyncio.Queue = asyncio.Queue(maxsize=2000)   # 防 4900 个协程堆积
upload_sem  = asyncio.Semaphore(3)                          # 防并发上传写爆磁盘
hash_sem    = asyncio.Semaphore(2)                          # 防 sha256 独占 IO 池
```

| 对象 | 上限 | 保护什么 |
|---|---|---|
| `thumb_queue` | 2000 条 | 内存（每条只是一个 tuple，2000 条约 200 KB） |
| `upload_sem` | 3 | 磁盘 IO 与临时空间（3 × 2 GB = 6 GB 上限） |
| `hash_sem` | 2 | IO 池不被 sha256 独占 |
| 单设备隧道并发 | 8 | 见 §7.2 |

#### 7.1.4 索引器与 API 的并发

**问题**：索引器正在批量写 500 条，同时手机端请求 `/api/timeline`，会不会读到不一致数据？

**答案：不会，因为 SQLite 的 WAL 提供了快照隔离。**

```
写连接 ──┬── BEGIN ── 写 500 条 ── COMMIT ──┬──
         │                                  │
读连接 ──┼────── 读（看到旧快照，一致） ────┼────── 读（看到新数据）
         │                                  │
         └── WAL 记录变更，读不阻塞写 ───────┘
```

| 角色 | 连接 | 隔离行为 |
|---|---|---|
| 索引器 / 上传 / 管理操作 | **唯一写连接**（单线程） | 事务 |
| API 读请求 | 每请求一个**只读连接** | WAL 快照，读到事务开始前的版本 |

**结论**：API 读请求**永远不会被索引器的写阻塞**（这是 WAL 相对 rollback journal 的最大优势），
且不会读到"写了一半"的状态。**这是必须写进代码注释的设计前提。**

### 7.2 云端并发模型

#### 7.2.1 多设备并发

云端是**单进程 asyncio**，每台电脑一个 `TunnelConnection`，每个手机客户端若干 HTTP 请求。

```
                    ┌──────────────────────────────────────┐
   手机 A ──┐       │           FastAPI (uvicorn)          │
   手机 B ──┼──────►│                                      │
   手机 C ──┘       │  ┌────────────┐  ┌────────────────┐  │
                    │  │ 限流中间件  │─►│ 路由 /d/{id}/** │  │
                    │  └────────────┘  └───────┬────────┘  │
                    │                          │           │
                    │                  ┌───────▼────────┐  │
                    │                  │ DeviceRegistry │  │
                    │                  │ id → Conn      │  │
                    │                  └───────┬────────┘  │
                    └──────────────────────────┼───────────┘
                                               │
              ┌────────────────────────────────┼───────────────────┐
              ▼                                ▼                   ▼
      ┌───────────────┐              ┌───────────────┐    ┌───────────────┐
      │ 电脑 1 隧道   │              │ 电脑 2 隧道   │    │ 电脑 3 隧道   │
      │ 并发上限 8    │              │ 并发上限 8    │    │ 并发上限 8    │
      └───────────────┘              └───────────────┘    └───────────────┘
```

| 层级 | 限制 | 目的 |
|---|---|---|
| 全局 | 无硬上限（由 1 核 1 GB 承载能力决定，约 50 并发连接） | 避免过度设计 |
| 单 client（`client_id`） | **120 req/s**（令牌桶，burst 60） | 设计文档 §7.2 |
| 单 client 上传 | **并发 ≤ 3** | 同上 |
| 单设备（`device_id`）隧道 | **并发 8 个 req_id** | 防止一个手机把电脑的 Pillow 池打满 |
| 单设备隧道超限 | **排队**（队列长度 32），队列满回 `3101 client_busy` | 优雅降级 |

```python
class DeviceConcurrency:
    """每设备的隧道并发控制。为什么必须限制：
    电脑端 Pillow 池只有 4 个 worker，若云端一次转发 50 个缩略图请求，
    这 50 个请求会在电脑端排队，每个都占着 req_id 与信用窗口，
    导致心跳帧都挤不出去 —— 表现为"云端认为电脑离线"。"""
    def __init__(self, limit: int = 8, queue_max: int = 32):
        self.sem = asyncio.Semaphore(limit)
        self.waiting = 0
        self.queue_max = queue_max

    @asynccontextmanager
    async def slot(self):
        if self.waiting >= self.queue_max:
            raise ClientBusy()
        self.waiting += 1
        try:
            async with self.sem:
                yield
        finally:
            self.waiting -= 1
```

**为什么并发上限是 8 而不是 4**：缩略图请求是"快请求"（命中缓存时 < 5 ms），
8 个并发能让快请求插队通过；而 4 个慢请求（首次生成）会占满 Pillow 池。
8 是"快慢混合"场景下的经验值，配置项 `relay.per_device_concurrency` 可调。

#### 7.2.2 带宽计数的并发安全

见 §3 的三层策略。**并发要点**：计数累加在**内存**里
（`dict` 的 `+=` 在单线程 asyncio 下是原子的，不需要锁），
每 30 s 由**唯一一个**后台任务 flush 到 DB。
这样高频请求路径上**没有任何 DB 写入**。

## 8. 性能优化设计

### 8.1 缩略图生成的 CPU 占用控制

#### 8.1.1 问题

首次索引 4900 张照片 = 4900 × 2（两级尺寸）≈ **9800 次图像解码 + 编码**。
按单张平均 120 ms（320 图 30 ms + 1600 图 90 ms）估算，总计约 **20 分钟的满负荷 CPU**。
若不加控制：① 风扇狂转，用户以为中毒；② 隧道心跳被饿死；
③ 用户同时浏览时卡顿。

#### 8.1.2 调度策略

| 策略 | 实现 | 效果 |
|---|---|---|
| **两级尺寸优先级分离** | 先生成 320，**立即**入队 1600（低优先级） | 首屏 2.5 s 目标只需 320 图 |
| **用户交互插队** | 用户点开大图时，该图的 1600 提到队首 | 交互优先 |
| **让出 CPU** | 每生成 1 张 `await asyncio.sleep(0.01)` | 事件循环有机会处理 IO |
| **交互期降速** | 最近 5 s 内有 API 请求 → 放慢到每张 `sleep(0.1)` | 浏览不卡 |
| **系统负载感知** | `psutil.cpu_percent()`（**二期**） | 避免过度设计 |

```python
class ThumbScheduler:
    """控制缩略图生成的节奏。"""
    INTERACTIVE_WINDOW = 5.0        # 秒：多久内有用户请求算"正在交互"
    IDLE_SLEEP = 0.01               # 空闲时每张之间的让出时间
    BUSY_SLEEP = 0.10               # 交互时放慢

    def __init__(self, engine: "ThumbEngine"):
        self.engine = engine
        self.last_request_at = 0.0

    def note_request(self) -> None:
        self.last_request_at = time.monotonic()

    async def _pace(self) -> None:
        if time.monotonic() - self.last_request_at < self.INTERACTIVE_WINDOW:
            await asyncio.sleep(self.BUSY_SLEEP)     # 用户在看照片 → 放慢
        else:
            await asyncio.sleep(self.IDLE_SLEEP)


PRIORITY_320, PRIORITY_1600 = 0, 1

async def on_indexed(media_id: int) -> None:
    """索引入库后：320 立刻做，1600 排队等空闲。"""
    await engine.queue.put((PRIORITY_320, next_seq(), media_id))

async def on_viewer_open(media_id: int) -> None:
    """用户点开大图：1600 插队到最前。"""
    await engine.queue.put((PRIORITY_1600, next_seq(), media_id, URGENT))
```

用 `asyncio.PriorityQueue` 实现：元素为 `(priority, seq, media_id)`，
`seq` 是单调递增计数器，保证**同优先级内 FIFO**（否则同优先级的图顺序随机，用户会看到缩略图乱序出现）。

### 8.2 时间线查询的索引利用 ★

#### 8.2.1 为什么 keyset 分页比 OFFSET 快

**OFFSET 分页的问题**：`LIMIT 100 OFFSET 4800` 要求 SQLite **扫描并丢弃前 4800 行**，
即使有索引也要走 4800 次 B-tree 定位。翻到第 49 页时，每页都要重复这个成本。

**keyset（游标）分页**：用"上一页最后一条的排序键"作为起点，**直接定位**到 B-tree 对应位置，
跳过前面所有行。成本与页码**无关**，恒定。

```sql
-- ❌ OFFSET 分页：翻到第 49 页时，前 4800 行被扫描后丢弃
SELECT id, taken_at, file_name, width, height
FROM media
WHERE missing = 0
ORDER BY taken_at DESC, id DESC
LIMIT 100 OFFSET 4800;

-- ✅ keyset 分页：直接定位，与页码无关
SELECT id, taken_at, file_name, width, height
FROM media
WHERE missing = 0
  AND (taken_at < :cursor_taken_at
       OR (taken_at = :cursor_taken_at AND id < :cursor_id))
ORDER BY taken_at DESC, id DESC
LIMIT 100;
```

**索引设计**（对应设计文档 §5.5）：

```sql
CREATE INDEX idx_media_timeline ON media(taken_at DESC, id DESC);
```

**为什么索引列顺序是 `(taken_at DESC, id DESC)`**：
SQLite 可以反向扫描索引，所以 `(taken_at, id)` 也能服务 `ORDER BY taken_at DESC, id DESC`。
**但显式声明 `DESC` 更保险**：它让 `EXPLAIN QUERY PLAN` 输出确定的
`SEARCH media USING INDEX idx_media_timeline`，且与查询排序方向完全一致，无需 SQLite 做方向推断。

**为什么必须有 `id` 作为第二列**：`taken_at` **不唯一**（连拍、同一秒多张）。
只用 `taken_at` 做游标会**丢数据或重复数据**：同一 `taken_at` 的 100 张里，
第 101 张的 `taken_at` 与第 100 张相同，`taken_at < cursor` 会**跳过它**。
加 `id` 构成**全序**，游标才正确。

#### 8.2.2 必须验证的执行计划


#### 8.2.3 对比（量级估算，待实测校准）

在 4900 行、`taken_at` 无重复的合成数据集上：

| 页码 | OFFSET 分页（估算） | keyset 分页（估算） | 说明 |
|---|---|---|---|
| 第 1 页（前 100 条） | ≈ 0.3 ms | ≈ 0.3 ms | 两者都只读 100 行 |
| 第 10 页（OFFSET 900） | ≈ 1.2 ms | ≈ 0.3 ms | OFFSET 多扫 900 行索引项 |
| 第 49 页（OFFSET 4800） | ≈ 5 ms | ≈ 0.3 ms | OFFSET 多扫 4800 行 |
| 5 万行时第 500 页 | ≈ 50 ms | ≈ 0.3 ms | 差距随数据量线性放大 |

> **数据说明**：上表按"索引项顺序扫描约 1 μs/行"推算，是**量级估算**而非实测。
> 关键结论是**趋势**：OFFSET 是 O(offset)，keyset 是 O(limit)。
> C3 里程碑需用 `timeit` 在真实库上实测并回填本节。

**另一个必须注意的点**：OFFSET 分页在**并发插入/删除**时会**错行**
（第 2 页可能重复第 1 页的最后一条，或漏掉一条），而 keyset 分页天然免疫。
这在"用户一边浏览一边上传"的场景下是真实问题。

### 8.3 数据库查询的 N+1 问题规避

#### 8.3.1 典型 N+1 场景

```python
# ❌ N+1：100 张照片触发 101 次查询
items = await db.query("SELECT id, root_id, rel_path FROM media LIMIT 100")
for it in items:
    root = await db.query("SELECT path FROM roots WHERE id=?", it.root_id)   # ← 每次一条
    it.url = f"/api/items/{it.id}/thumb"
```

**在 SQLite 上 N+1 的代价**：每次查询即使 < 1 ms，101 次也是 100 ms 额外延迟；
更重要的是**每次都要走一次 asyncio + 线程池调度**，实际开销远大于查询本身。

#### 8.3.2 规避手段

| 手段 | 适用 | 实现 |
|---|---|---|
| **JOIN 一次取全** | 关联表小（`roots` 只有几个） | `SELECT m.*, r.path FROM media m JOIN roots r ON r.id=m.root_id` |
| **批量 IN 查询** | 关联表大 | 先取 id 列表，`WHERE media_id IN (?,?,...)` 一次查回，内存里 group |
| **内存缓存** | 极少变动的表 | `roots` 表**全量缓存在内存**（启动加载，变更刷新） |
| **派生字段直接存** | 需要计算的值 | `media.thumb_state` 直接存，避免每次查文件系统 |

**`roots` 表的内存缓存（必须实现）**：

```python
class RootCache:
    """roots 表只有几个根目录，全量放内存。为什么：
    每次请求都要用 root_id 换 path（沙箱需要），N+1 就发生在这里。
    缓存后是 dict 查找，零查询。"""
    def __init__(self) -> None:
        self._by_id: dict[int, dict] = {}
        self._lock = asyncio.Lock()

    async def load(self) -> None:
        rows = await db.query("SELECT id, path, mode, label FROM roots WHERE enabled=1")
        self._by_id = {r["id"]: dict(r) for r in rows}

    def get(self, root_id: int) -> dict:
        try:
            return self._by_id[root_id]
        except KeyError:
            raise MediaNotFound(f"unknown root {root_id}")

    async def invalidate(self) -> None:
        async with self._lock:
            await self.load()

roots = RootCache()
```

**必须的代码审查检查项**：任何 `for` 循环体内出现 `await db.` 的代码都要被质疑。
CI 加一条静态检查：`grep -n -A3 "^\s*for " backend/app/**/*.py | grep "await db\."` 应为空。

|---|---|---|

| HTML（含关键 CSS） | 100 ms | 500 ms |

1. **JS 体积不得超 60 KB gzip**（每次新增依赖都要核算）；

```python
from __future__ import annotations

class FrameType(enum.IntEnum):
    """帧类型常量。值一旦发布不得更改（协议兼容性）。"""
    REQ_HEAD = 0x01      # 请求头（JSON payload）
    REQ_BODY = 0x02      # 请求体分片（二进制）
    REQ_END  = 0x03      # 请求体结束
    RES_HEAD = 0x04      # 响应头（JSON payload）
    RES_BODY = 0x05      # 响应体分片（二进制）
    RES_END  = 0x06      # 响应体结束
    ERROR    = 0x07      # 错误（JSON payload）
    CANCEL   = 0x08      # 取消某个 req_id
    PING     = 0x09      # 心跳
    PONG     = 0x0A      # 心跳应答
    CREDIT   = 0x0B      # 流控信用回补
    NOTIFY   = 0x0C      # 单向通知（req_id 无会话语义）


# req_id 高 2 位预留：bit31 = 加密（二期 E2E），bit30 = 压缩（预留）
F_ENC        = 0x80000000
F_COMPRESSED = 0x40000000
REQ_ID_MASK  = 0x3FFFFFFF
MAX_FRAME    = 65536                    # HELLO_ACK.max_frame

HEARTBEAT_SEC  = 25                     # HELLO_ACK.heartbeat_sec

class Frame:
    type: FrameType
    req_id: int                    # 已与 REQ_ID_MASK 运算，不含 flags
    flags: int = 0                 # 高 2 位（F_ENC / F_COMPRESSED）
    payload: bytes = b""

    @property
    def json(self) -> dict[str, Any]:
        """把 payload 解析为 JSON。仅对 *_HEAD / ERROR / NOTIFY 有效。"""
        return json.loads(self.payload.decode("utf-8")) if self.payload else {}

    heartbeat_sec: int = HEARTBEAT_SEC
    max_frame: int = MAX_FRAME
    credit_window: int = DEFAULT_CREDIT


@dataclass(slots=True)

    """REQ_HEAD 的 payload。"""
    method: str
    path: str
    query: dict[str, str] = field(default_factory=dict)
    headers: dict[str, str] = field(default_factory=dict)
    client_id: str = ""
    client_name: str = ""
    body_len: int | None = None        # 已知长度时给出，便于电脑端预判
    enc: str | None = None             # ★ 二期 E2E：加密算法标识（一期恒为 None）
```

### 9.3 数据结构一致性校验（必须实现）

**为什么需要**：§9.1 的 Python 结构与 §9.2 的 TS 结构手工维护，极易漂移
（后端加了一个字段，前端不知道）。漂移会导致"接口看起来正常但字段是 `undefined`"的隐蔽 bug。

**方案（一期，零依赖）**：后端从 `MediaItem` dataclass **生成**一份 JSON Schema，
前端用同一份 Schema 做**类型断言测试**。

```python
# backend/tools/export_schema.py —— CI 里跑，产出 frontend/src/api/schema.json
import dataclasses, json, sys

def dataclass_to_schema(cls) -> dict:
    props, required = {}, []
    for f in dataclasses.fields(cls):
        t = f.type
        props[f.name] = {"type": _json_type(t)}
        if f.default is dataclasses.MISSING and f.default_factory is dataclasses.MISSING:
            required.append(f.name)
    return {"type": "object", "properties": props, "required": required}
```

```typescript
// frontend/tests/schema.spec.ts —— 断言 TS interface 与后端 Schema 字段集合一致
import schema from "../src/api/schema.json";
import type { MediaItem } from "../src/api/types";

it("MediaItem 字段与后端一致", () => {
  const backendKeys = new Set(Object.keys(schema.MediaItem.properties));
  // 用 satisfies 让 TS 编译期就发现多/少字段
  const sample = {} as MediaItem;
  const frontendKeys = new Set(Object.keys(sample));
  expect([...backendKeys].difference(frontendKeys)).toEqual([]);
  expect([...frontendKeys].difference(backendKeys)).toEqual([]);
});
```

**CI 门禁**：`export_schema.py` 产出的 `schema.json` 若与仓库中的不一致，CI 直接失败。
这样任何后端字段变更都**强制**前端同步（对应 00 文档硬约束 5"改表必须给迁移"的同类要求）。

设计文档（v0.3）给出的是架构决策，以下条目是本文档**为实现而补充的、设计文档未明确规定的**细节。

| # | 补充项 | 所在章节 | 理由 |
|---|---|---|---|
| 1 | 帧头增加 **4 字节长度前缀**（`type + len + req_id + payload`） | §2.4 | 设计文档只写了 `type + req_id + payload`，未定义**分帧方式**。TCP 是字节流，没有长度前缀就无法区分粘包/半包 |
| 2 | `req_id` **高 2 位预留 flags**（`F_ENC` / `F_COMPRESSED`），有效位 30 位 | §2.2 | 设计文档说"帧头预留 flags 位"（二期 E2E），但未说明放在哪里。放在 `req_id` 高位可在不改变帧头长度的前提下扩展 |
| 3 | 流控**死锁防护**：`CREDIT_DEADLOCK_TIMEOUT=30s` / `CONN_DEADLOCK_TIMEOUT=60s` | §2.6 | 设计文档未回答"对端一直不回 CREDIT 怎么办"。若只按信用窗口暂停，一旦对端 bug 就永久挂死 |
| 4 | 上传**只支持顺序追加**，乱序回 `409 offset_mismatch + current` | §4.3.3 | 设计文档未明确分片是顺序还是随机。选顺序追加是因为"文件长度 = 已收字节数"，续传无需额外位图状态，永不与 DB 不一致 |
| 5 | 上传临时区**必须与目标同卷**（`<库根>/.photobridge_tmp/`） | §4.3.2 | 设计文档未指定临时区位置。若放 `data/`（H 盘）而库在 E 盘，`os.replace` 跨卷会失败，退化为非原子的复制+删除 |
