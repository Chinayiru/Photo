# 12 · 部署核查记录（Windows 本机 + ECS 入口）

> **版本**：v1.0 ｜ **核查日期**：2026-11-26 ｜ **触发来源**：2026-11-24 渗透测试报告 P1「核查 Windows 实际部署」
> **结论**：管理面（`/panel/**`）的回环门禁在代码与测试上都成立；**但本机在"公共网络"配置下有一条对任意来源、任意端口放行 `photobridge.exe` 的防火墙规则**，以及 `data/` 目录对本机全体已认证用户可写。两条都需要在提权的 PowerShell 里修，本记录给出逐条命令。

## 2. 现状

### 2.1 服务配置与监听

`data/config.json` 的 `server` 段：

```json
{"host": "0.0.0.0", "port": 8799, "transport": "cloud_tunnel", "allow_lan": true}
```

- `host=0.0.0.0` + `allow_lan=true` 是**设计如此**：局域网直连（`/api/pair`、`/api/timeline` 等）需要手机在同一个 Wi-Fi 下能连上。
- 核查当时 **8799 未处于监听状态**（托盘程序没在跑）；本机实际监听只有 DSH 的 `127.0.0.1:58553` 和一个 `0.0.0.0:80/443` 的第三方进程。⇒ "规则开着但服务没开"是当前的真实暴露面，服务一启动，暴露面立刻变成"规则允许的范围"。

### 2.2 运行账户

托盘程序以**登录用户**身份运行，不是服务、不是 SYSTEM、不是管理员。这是正确的选择：读照片库只需要用户自己的权限，出问题也不会牵连系统。

### 2.3 启动方式

`Get-ScheduledTask` 全表里**没有** PhotoBridge / cloudflared 相关任务；本机只有豆包、OneDrive、NVIDIA、WPS 等厂商任务。⇒ 中继与 cloudflared 不在这台 Windows 上随计划任务启动，要么跑在 ECS 上，要么是手工启动的。**本机能被自动拉起的只有托盘程序本身**（开机自启项），这一点和"服务化部署"不是一回事，不影响安全结论，但影响"重启后是否可用"的运维判断。

### 2.4 公网入口实测

对 `<ECS 公网地址>` 的 5 个端口做 TCP 连接测试：**只有 22 开放**，`80`/`443`/`8799`/`8080` 全部拒绝。

- 说明对外的 HTTPS 不是靠 ECS 自己监听 443，而是 cloudflared 反向隧道（域名形如 `https://<随机词>.trycloudflare.com`）。
- `22` 对全网开放，是本次核查发现的第二个收口点（见 §5 F3）。

## 3. 发现

### 3.0 一键收口脚本

本节 F1、F2 两条都可以用仓库里的 `scripts/harden_exposure.ps1` 一次做完（幂等、可预演）：

```powershell
# 预览要改什么（不需要管理员）
pwsh -NoProfile -File scripts/harden_exposure.ps1 -DryRun

# 真正执行（在「以管理员身份运行」的 PowerShell 里）
pwsh -NoProfile -File scripts/harden_exposure.ps1
```

脚本做的事：按「程序路径」精确找出所有放行 `photobridge.exe` 的入站规则并删掉 Public 配置下的宽放行 → 建一条 Public 的显式 **Block** 规则（顺带压掉"下次弹窗又被点允许"的复发路径）→ 建"仅 Private/Domain、仅 8799、仅本地子网"的放行规则 → 收紧 `data/` 的 ACL（当前用户 + SYSTEM + Administrators，其余全清）→ 复核并打印结果。**不动** Tailscale 自己的规则。

下文的命令保留作为"脚本做了什么"的逐条说明，便于核对与手工复现。

### F1（高）公共网络配置下，`photobridge.exe` 的任意端口对任意来源放行

两条 `DisplayName = photobridge` 的入站规则，逐字段展开后是：

| Profile | Direction | Action | Protocol | LocalPort | RemoteAddress | Program |
|---|---|---|---|---|---|---|
| Public | Inbound | Allow | TCP | **Any** | **Any** | `H:\远程照片\dist\photobridge\photobridge.exe` |
| Public | Inbound | Allow | UDP | **Any** | **Any** | 同上 |
| Domain,Private | Inbound | Allow | TCP | 8799 | Any | Any（`PhotoBridge 8799 (Tailscale/Private)`） |

**为什么是问题**：公共网络（咖啡厅 Wi-Fi、机场）下 Windows 应用 Public 配置，于是这两条规则生效 —— 该 exe 监听**任何端口**都对**任何来源**可达。当前 `/panel/**` 有回环门禁（§4），所以不是"管理面板被公网打开"，而是"整台机器的这个程序被放到公共网络上"，且一旦以后新增一个没做门禁的监听端口，这道防火墙不会拦。这与"公网只能到达预期入口"的验收标准不符。

**修法**（提权 PowerShell，管理员）：

```powershell
# 1) 先看清楚：两条 Public 通配规则的确切名字（DisplayName 可能带后缀）
Get-NetFirewallRule -DisplayName 'photobridge' | Format-Table Name,DisplayName,Profile,Direction,Action

# 2) 删掉 Public/TCP 与 Public/UDP 两条通配规则（按上一步输出的 Name 精确删）
Remove-NetFirewallRule -Name '<第 1 步输出的 Name>'

# 3) 改成"只在专用网络、只放 8799、只对本子网"
New-NetFirewallRule -DisplayName 'PhotoBridge 8799 (Private, LAN only)' `
  -Direction Inbound -Action Allow -Protocol TCP -Profile Private `
  -LocalPort 8799 -RemoteAddress LocalSubnet `
  -Program 'H:\远程照片\dist\photobridge\photobridge.exe'

# 4) 复核：Public 配置下不应再有任何放行 photobridge.exe 的规则
Get-NetFirewallRule -Direction Inbound -Action Allow |
  Where-Object Profile -match 'Public' |
  Get-NetFirewallApplicationFilter |
  Where-Object Program -match 'photobridge' |
  Format-Table Program,InstanceID
```

**为什么不直接删成"全禁"**：Tailscale / 局域网直连是正常路径，删掉 8799 的专用网络规则会让"同一个 Wi-Fi 下直连"失效；收口目标是"公共网络不放行、专用网络只放这一个端口、只对本子网"。

### F2（中）`data/` 目录对本机全体已认证用户可写

`Get-Acl data` 的实际 ACE（节选）：

```
NT AUTHORITY\Authenticated Users  Modify, Synchronize  Allow
BUILTIN\Users                     ReadAndExecute       Allow
```

`data/` 里有 `photobridge.db`（含 `devices.token_hash`）、`config.json`（含云端凭据）、`audit.log`。含义是：**这台机器上任何一个登录用户都能改数据库、改配置、改审计日志**。单人自用机器上风险有限，但"配置与凭据可被同机其他账户改写"不符合最小权限。

**修法**（提权 PowerShell，把当前登录用户换成实际账户名）：

```powershell
$data = 'H:\远程照片\data'
icacls $data /inheritance:r
icacls $data /grant:r "$env:USERNAME:(OI)(CI)F" 'SYSTEM:(OI)(CI)F' 'Administrators:(OI)(CI)F'
icacls $data   # 复核：不再出现 Authenticated Users / Users 的写权限
```

注意：托盘程序与 pytest 都以当前用户运行，上面这条不会影响它们；如果以后改成"以服务身份运行"，需要把服务账户加进去。

### F3（中，服务端）ECS 的 22 对全网开放

`Test-NetConnection` 显示 22 开放、80/443/8799/8080 关闭。SSH 对全网开放，等于把暴力破解面交给互联网；至少应限制来源，或只保留密钥登录 + fail2ban。

**修法**（在 ECS 安全组里做，不在本机）：

- 安全组入方向：22 的来源改成你的固定出口 IP / 跳板机，而不是 `0.0.0.0/0`；
- `sshd_config`：`PasswordAuthentication no`、`PermitRootLogin no`；
- 复核手段：`ss -lntp` 确认只监听预期端口，`journalctl -u ssh` 或 `/var/log/auth.log` 确认没有异常爆破。

> 这一条超出本机核查能动手的范围（无凭据），记录在此是为了让"公网入口"这件事有完整闭环，而不是留一个"查不到就不写"的空白。

## 4. 管理面回环门禁的验证

`/panel/**` 是"本机管理操作"（生成配对码、看设备列表、看审计），设计上只允许回环访问。代码位置：

- `backend/app/handlers/auth.py:316`、`:338`、`:377` —— 三个 panel handler 各自 `if not is_loopback(ctx): raise ...`；
- `backend/app/auth.py:941 def is_loopback(ctx)` —— 判定实现；
- `backend/app/netguard.py:40` —— 记着 F11 的历史教训：`is_loopback("")` 曾返回 `True`，导致空 `client_ip` 被当成回环、`/panel` 静默放行。现在的实现要求"非空且是回环地址"。

自动化验证：`backend/tests/test_p1_pages.py`（页面与 `/panel` 路径）、`backend/tests/test_security_20261026.py`（含 F11 回归用例）在 2026-11-26 的全量运行中通过。

⇒ **这一项符合验收标准**："远端无法执行本机管理操作"在代码与测试两层都成立；F1 修掉之后，防火墙层也不会再把这个程序整体暴露到公共网络。
