## 1. 为什么要有这份文档

这个项目由**单人 + AI 协作**完成，代码会在"AI 写 → 你验收 → AI 改"的循环里反复迭代。
没有统一规范，会出现三个具体问题：

| 问题 | 后果 | 规范怎么解决 |
|---|---|---|
| AI 每次换一种写法 | 代码风格漂移，读起来像多人拼凑 | §3 风格规范固定下来 |
| 安全约束靠"记得" | 某次改动引入 `os.remove`，照片被误删 | §7 硬规则 + §8 自动检查 |
| 改动无记录 | 出问题不知道谁改了什么、为什么 | §6 提交与变更记录规范 |

**核心原则：把"约定"变成"可检查的规则"。** 凡是能写成 linter 规则的，就不靠人记。

- 以 `shared/protocol.py` 为唯一协议实现（云端与电脑端均导入该模块）
- 修改后必须同步到 `backend/app/protocol.py`
- 用脚本校验两份文件一致（CI 或提交前手工跑）：


## 3. Python 编码规范

### 3.1 基础约定

| 项 | 规定 |
|---|---|
| 语言版本 | **Python 3.12**（不使用 3.13+ 特性，因为目标机器可能只装 3.12） |
| 格式化 | **Ruff format**（行宽 100） |
| Lint | **Ruff**（规则集：`E,F,W,I,N,UP,B,A,C4,SIM,RUF`） |
| 类型检查 | **mypy --strict**（至少对 `sandbox.py`、`protocol.py`、`uploads.py` 严格） |
| 类型注解 | **所有公开函数必须标注**参数与返回值 |
| 文档字符串 | 公开函数用 Google 风格 docstring，说明"做什么 + 为什么" |
| 导入顺序 | 标准库 → 第三方 → 本项目（Ruff `I` 规则自动排序） |

### 3.2 命名

```python
# 变量与函数：snake_case
upload_session_id = "abc"
def resolve_path(root_cfg, rel_path, need): ...

# 类：PascalCase
class TunnelConnection: ...
class UploadSession: ...

# 常量：UPPER_SNAKE_CASE
MAX_FRAME_SIZE = 65536
CREDIT_WINDOW = 8 * 1024 * 1024

# 私有：单下划线前缀
def _compute_sha256(path): ...

# 协议帧类型常量（十六进制，与协议文档一致）
MSG_REQ_HEAD = 0x01
MSG_REQ_BODY = 0x02
MSG_RES_HEAD = 0x04
```

**禁止**：单字符变量名（循环变量 `i`/`j` 除外）；拼音命名（`tupian_lujing` ❌）；缩写歧义（`usr_lib_path` 可以，`ulp` ❌）。

### 3.3 类型注解

```python
# ✅ 正确：参数与返回值都标注
def resolve(root_cfg: RootConfig, rel_path: str, need: Literal["read", "write"]) -> Path:
    ...

async def forward_request(req_id: int, req: Request) -> Response:
    ...

# ❌ 错误：缺返回值
def resolve(root_cfg, rel_path, need):
    ...

# ✅ 用 TypedDict / dataclass 表达结构化数据
class Frame(TypedDict):
    type: int
    req_id: int
    payload: bytes

@dataclass(frozen=True)
class MediaItem:
    id: int
    rel_path: str
    taken_at: float
    ...
```

**禁止**：`Any` 滥用（除非确实无法表达，且要写注释说明原因）；`# type: ignore` 不写原因。

### 3.4 异步与并发

这是本项目最容易出错的地方，单独强调。

```python
# ✅ 正确：Pillow 是阻塞的，必须丢到线程池
async def generate_thumb(media_id: int, size: int) -> bytes:
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(THUMB_POOL, _generate_sync, media_id, size)

# ❌ 错误：在协程里直接调用阻塞的 Pillow，会卡死整个事件循环
async def generate_thumb(media_id: int, size: int) -> bytes:
    return _generate_sync(media_id, size)   # 阻塞事件循环！
```

**必须遵守**：
1. **所有阻塞 I/O 与 CPU 密集操作必须走 `run_in_executor`**：Pillow 解码/编码、hashlib 大文件哈希、EXIF 解析
2. 线程池大小固定（缩略图 4 个 worker，哈希 2 个），**不允许**用默认的 `ThreadPoolExecutor`（默认 = CPU 核数 × 5，会把内存吃光）
3. 文件写入用 `aiofiles` 或 `run_in_executor`，不用同步 `open().write()`
4. **禁止 `time.sleep()`**，用 `await asyncio.sleep()`
5. 数据库操作：SQLite 是同步的，短查询可接受同步调用；长事务必须走线程池

### 3.5 错误处理

```python
# ✅ 正确：捕获具体异常，带上下文，能恢复的恢复，不能恢复的往上抛
try:
    thumb_bytes = await generate_thumb(media_id, 320)
except UnidentifiedImageError as exc:
    logger.warning("缩略图生成失败：无法识别的图片 media_id=%s path=%s", media_id, rel_path)
    await mark_thumb_failed(media_id)
    raise ThumbGenerationError(f"媒体 {media_id} 无法解码") from exc

# ❌ 错误：裸 except 吞掉一切
try:
    thumb_bytes = await generate_thumb(media_id, 320)
except:            # 连 KeyboardInterrupt 都吞了
    pass           # 出问题完全不知道
```

**规则**：
1. **禁止裸 `except:`**，至少要 `except Exception:`
2. 捕获后必须**记录日志**（含关键上下文：media_id、rel_path、req_id）
3. 用 `raise ... from exc` 保留异常链
4. 自定义异常继承自项目基类 `PhotoBridgeError`，便于统一处理
5. **不允许**用异常做正常流程控制

### 3.6 日志

```python
import logging

logger = logging.getLogger(__name__)

# ✅ 正确：用惰性格式化（%s），不是 f-string
logger.info("索引完成：扫描 %d 个文件，新增 %d 条", scanned, added)

# ❌ 错误：f-string 会无条件求值，即使日志级别不输出
logger.info(f"索引完成：扫描 {scanned} 个文件，新增 {added} 条")
```

**日志级别约定**：

| 级别 | 用途 | 示例 |
|---|---|---|
| `DEBUG` | 开发排查细节 | 帧收发、SQL 语句、缩略图缓存命中 |
| `INFO` | 正常关键事件 | 服务启动、索引完成、上传成功、隧道连接 |
| `WARNING` | 可恢复的异常 | 缩略图生成失败、EXIF 缺失、重连尝试 |
| `ERROR` | 影响功能的错误 | 隧道断开、上传校验失败、数据库错误 |
| `CRITICAL` | 服务不可用 | 库目录不存在、端口被占用 |

**绝对禁止记入日志**：
- `agent_token`、`client_token`、密码、`SECRET_KEY`
- 完整的请求体（可能含照片内容）
- 你的邮箱等个人信息

```python
# ✅ 令牌只记前 8 位用于排查
logger.info("设备注册 device_id=%s token_prefix=%s", device_id, token[:8])

# ❌ 绝不允许
logger.info("agent_token=%s", agent_token)
```

## 4. TypeScript / Vue 编码规范

### 4.1 基础约定

| 项 | 规定 |
|---|---|
| TypeScript | **strict 模式**，禁止 `any`（用 `unknown` + 类型守卫） |
| 格式化 | **Prettier**（行宽 100，单引号，无分号由 Prettier 统一） |
| Lint | **ESLint** + `@typescript-eslint` + `eslint-plugin-vue` |
| Vue | **组合式 API + `<script setup>`**，不用选项式 API |
| 状态管理 | Pinia（理由见 §4.4） |

### 4.2 命名

```typescript
// 组件：PascalCase
// Timeline.vue, StatusBar.vue

// 变量与函数：camelCase
const currentDeviceId = ref<string | null>(null)
function switchToLan(): Promise<boolean> { ... }

// 常量：UPPER_SNAKE_CASE
const LAN_PROBE_TIMEOUT_MS = 1500
const CHUNK_SIZE_CLOUD = 2 * 1024 * 1024

// 类型与接口：PascalCase（不加 I 前缀）
interface MediaItem { id: number; takenAt: number }
type TransportMode = 'lan' | 'cloud' | 'offline'

// 事件：kebab-case（模板中）
// <Timeline @item-selected="onSelect" />
```

### 4.3 类型安全

```typescript
// ✅ 正确：API 响应用 interface 定义，不用 any
interface TimelineResponse {
  items: MediaItem[]
  nextCursor: string | null
  hasMore: boolean
}

// ❌ 错误：any 会让类型检查失效
const data: any = await res.json()

// ✅ 正确：外部数据用 unknown + 校验
function isTimelineResponse(v: unknown): v is TimelineResponse { ... }
```

**接口类型必须与 [04-接口设计文档](04-接口设计文档.md) 保持一致**，字段名用 camelCase（后端返回 snake_case 时在前端转换层统一处理）。

### 4.4 状态管理选型说明

**选 Pinia，不用自写 reactive**。理由：
1. 双通路状态（当前走直连/云端/离线）需要在多个组件间共享且频繁切换，Pinia 的 devtools 能直接看到状态变化
2. Pinia 支持模块化（`useTransportStore`、`useUploadStore`、`useMediaStore`），职责清晰
3. 体积小（约 1.5 KB），不违反"不用重型库"的原则

**不选 Vuex**：官方已推荐 Pinia，Vuex 处于维护模式。

### 4.5 安全相关的硬规则（前端）

```vue
<!-- ❌ 绝对禁止：v-html 会引入 XSS -->
<div v-html="photoDescription"></div>

<!-- ✅ 正确：Vue 默认转义 -->
<div>{{ photoDescription }}</div>
```

```typescript
// ❌ 禁止：把 token 拼进 URL（会进服务器日志、浏览器历史）
const url = `/api/timeline?token=${token}`

// ✅ 正确：放 header
const res = await fetch(url, { headers: { Authorization: `Bearer ${token}` } })
```

## 5. 数据库与 SQL 规范

### 5.1 硬规则

```python
# ❌ 绝对禁止：字符串拼 SQL（SQL 注入）
sql = f"SELECT * FROM media WHERE rel_path = '{user_input}'"
cur.execute(sql)

# ✅ 正确：参数化查询
cur.execute("SELECT * FROM media WHERE rel_path = ?", (user_input,))
```

**规则**：
1. **所有 SQL 必须参数化**，禁止 f-string / `%` / `.format()` 拼接
2. 表名、字段名用 `snake_case`
3. 每个表必须有 `PRIMARY KEY`
4. 时间统一用 **Unix 时间戳（REAL）**，不用字符串日期
5. 布尔值用 `INTEGER`（0/1），SQLite 无原生布尔
6. 改表必须写迁移脚本（`migrations/NNN_描述.sql`），**禁止删库重建**

### 5.2 索引规范

```sql
-- ✅ 复合索引的列顺序：等值条件在前，范围/排序在后
CREATE INDEX idx_media_timeline ON media(taken_at DESC, id DESC);

-- ✅ 唯一约束用 UNIQUE 而非应用层检查
CREATE UNIQUE INDEX idx_media_root_path ON media(root_id, rel_path);
```

**规则**：新增查询前先 `EXPLAIN QUERY PLAN` 确认走索引；不允许全表扫描出现在时间线、搜索等热路径。

### 5.3 事务

```python
# ✅ 批量入库：500 条一批 + 单事务
with conn:                       # 自动 commit / rollback
    conn.executemany("INSERT INTO media (...) VALUES (...)", batch)

# ❌ 错误：每条一个事务，4952 条 = 4952 次 fsync
for item in items:
    conn.execute("INSERT INTO media (...) VALUES (...)", item)
    conn.commit()
```

#### 6.2.1 换行符：改文件前先想清楚用什么工具（踩过）

**规则**：**不要用会重写换行符的工具改仓库里的文本文件。**

仓库里混着两种换行符且这是既成事实：19 个文件是 CRLF（历史遗留，`git show HEAD:<文件>` 里就是 CRLF），其余是 LF。混着不致命，但如果**某个工具把整个文件的换行符换掉了**，后果是：

- `git diff` 显示整个文件被重写（实测一次 `docs/07` 是 **+3425 / -3425**）；
- 而 `git diff --ignore-all-space` 是**空**的 —— 即 0 行语义改动；
- `git blame` 对该文件全部失效，`git log -S` 找不到真实改动；
- review 时不可能从 6840 行 diff 里挑出真正的 18 行。

**危险工具**：PowerShell 的 `Set-Content` / `Out-File` / `-replace` 管道回写（把 LF 全变成 CRLF）。

**安全做法**：

```powershell
# ❌ 会把整个文件的换行符改成 CRLF
(Get-Content f.md) -replace 'a','b' | Set-Content f.md

# ✅ 用 Python 按二进制读写，换行符原样保留
python -c "p=r'f.md'; b=open(p,'rb').read(); open(p,'wb').write(b.replace(b'a',b'b',1))"
```

或者用 `edit` 这类**只替换指定字符串、不触碰其余字节**的工具。

**兜底**：`backend/tests/test_repo_hygiene.py` 把当前 19 个 CRLF 文件钉成基线，`HEAD` 里是 LF 而工作区变成 CRLF 的文件会被测试点名（实测重演那次事故，它精确报出 `docs/07-测试计划与用例.md  CRLF=3425`）。

**没做的事，以及为什么**：

- **不把现有 CRLF 文件一次性转成 LF**：那是一个 1.4 万行的纯换行提交，会把 19 个源文件的 `git blame` 全部作废 —— 修一个可读性问题却制造更大的可读性问题。它们会在各自下次被真正修改时自然转成 LF。
- **不加 `.gitattributes`**：试过。加了 `eol=lf` 之后，那 19 个文件会**永远**显示为 `M`（Git 每次比对都认为工作区是 CRLF、索引里该是 LF），除非先提交那 1.4 万行规范化 —— 等于把"一次性噪音"换成了"持续噪音"。

## 7. 安全编码硬规则（不可违反）

> 这一节是整个规范中**唯一没有例外**的部分。违反任何一条都视为严重缺陷。

### 7.1 文件访问

| # | 规则 | 违反示例 | 正确写法 |
|---|---|---|---|
| S1 | **所有文件访问必须过 `sandbox.resolve()`** | `open(root / user_path)` | `p = sandbox.resolve(root_cfg, user_path, "read"); open(p)` |
| S2 | **禁止 `os.unlink` / `os.remove` / `shutil.rmtree`** | `os.remove(p)` | `send2trash(p)` |
| S3 | **禁止覆盖已有文件** | `shutil.move(tmp, target)` | 先检查存在性，冲突则加 `_1` |
| S4 | **必须原子落盘** | 直接写目标路径 | 写临时区 → 校验 → `os.replace()` |
| S5 | **拒绝符号链接与重解析点** | 直接 `resolve()` | 逐段检查 `is_symlink()` / reparse point |

```python
# ✅ 唯一允许的文件访问模式
def read_media(root_cfg: RootConfig, rel_path: str) -> bytes:
    path = sandbox.resolve(root_cfg, rel_path, need="read")   # 必须第一步
    with open(path, "rb") as f:
        return f.read()
```

## 8. 自动化检查（把规则变成工具）

### 8.1 自定义检查脚本

**实际落地的是 `scripts/check_lint.py`**（AST 实现，20 条规则一一对应
[06 §10](06-安全设计文档.md)），提交前跑：

```bash
.venv/Scripts/python.exe scripts/check_lint.py            # 全部，0 违规才 exit 0
.venv/Scripts/python.exe scripts/check_lint.py --rule=2   # 单条
.venv/Scripts/python.exe scripts/check_lint.py --json     # 机读
```

#### 为什么这里原本的 `scripts/check_rules.py` 没有按原样实现

本节早前给了一份 30 行的正则版检查脚本（`RULES = [(规则编号, 正则, 说明,
适用目录), ...]`），要求"创建 `scripts/check_rules.py`"。**那份清单本身
是错的**，照抄会立刻失败：

```python
# 原文的第 1 条
("S2", r"\bos\.unlink\b|\bos\.remove\b|\bshutil\.rmtree\b",
 "禁止删除文件：必须用 send2trash 进回收站", ["backend/app", "cloud/relay"]),
```

`backend/app` 里有 **9 处**合法的 `os.unlink`，全部针对临时文件/缓存/半成品
（清理写权限探测文件、清临时目录、删半成品缩略图、跨卷复制校验通过后删源……）。
这条规则一跑就红，而它对"用户照片有没有被真删"这个真实问题**什么都说明不了** ——
用户照片的删除走的是 `handlers/browse.py` 的 `delete_items` → `_trash_one` →
`send2trash`。

同理，原文第 4 条 `("S14", r"execute\s*\(\s*f[\"']", "禁止 f-string 拼 SQL")`
会把 4 处**只拼 `?` 占位符**的批量 `IN (VALUES ...)` 判成注入。

#### 三条硬要求（踩过才知道）

1. **用 AST，不用正则。** 正则分不清 `os.unlink(临时文件)` 与
   `os.unlink(用户照片)`，分不清 `f"... IN ({placeholders})"`（拼占位符）
   与 `f"... WHERE name = '{name}'"`（拼值），也分不清"注释里提到 `token=`
   是在解释为什么不这么做"与"代码里真的拼了一个带令牌的 URL"。
2. **每条判据都必须能抓到注入的坏样本。** `backend/tests/test_check_lint.py`
   对 20 条各注入一个已知坏样本、断言它**恰好报出那一行**。只断言"真实仓库
   干净"的检查器和 grep 没有区别 —— 它会一直通过，直到某天有人把实现删了。
3. **解析出 0 个目标时直接判失败。** 规则 20 要解析路由表；项目用的是
   `r.add("GET", path, handler)` 而不是 FastAPI 的 `r.get(path)`，第一版按后者
   解析出 0 条，规则静默"通过"。**空判据比没有判据更坏**，因为它让人以为
   检查过了。

> 完整审计过程与 134 处误报的逐条修正见
> [11 Q-024](11-风险登记册与决策记录.md)。

## 11. 常见反模式（本项目特别容易犯的）

| 反模式 | 为什么危险 | 正确做法 |
|---|---|---|
| 在协程里直接调 Pillow | 卡死整个事件循环，所有请求超时 | `run_in_executor` |
| 用扩展名判断文件类型 | 改名的恶意文件能绕过 | 魔术字节校验 |
| 用 `shutil.move` 落盘 | 覆盖同名文件 = 照片丢失 | 检查存在性 + `os.replace` |
| 直接 `open(root / user_input)` | 路径穿越 = 任意文件读写 | `sandbox.resolve()` |
| 每条记录一个事务 | 4952 条 = 4952 次 fsync，慢几十倍 | `executemany` + 单事务 |
| 用 OFFSET 分页 | 深翻页性能崩溃 | 游标分页 |
| 整体缓冲大响应 | 1 GB VPS 内存爆炸 | 流式转发 + credit 流控 |
| 一次性解码所有缩略图 | 安卓浏览器 OOM 崩溃 | 限制并发解码数 |
| 用 f-string 打日志 | 即使不输出也求值，热路径拖慢 | `%s` 惰性格式化 |
| 把 token 放 URL | 进日志、进历史，泄露 | 放 header |
| 改了 `protocol.py` 只改一边 | 隧道静默故障，极难排查 | 两份同步 + diff 校验 |
| "先做着看"加功能 | 范围蔓延，单人项目翻车主因 | 走 §10.1 的变更流程 |

## 12. 规范的自检

这份规范本身也需要维护：

- 如果某条规则**从未被违反**，说明它可能没必要 → 考虑删除，减少认知负担
- 如果某条规则**反复被违反**，说明它不够自动化 → 考虑写成 linter 规则
- 如果发现新的坑，**加一条规则**，而不是口头提醒（口头提醒下次还会犯）
- 每完成一个里程碑，回顾一次本文件，把"事后才想到的"补进去
