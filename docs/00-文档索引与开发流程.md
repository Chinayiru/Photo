## 2. 开发流程（本项目的裁剪版瀑布 + 迭代）

### 2.1 阶段划分

```
① 需求分析 ──► ② 概要设计 ──► ③ 详细设计 ──► ④ 编码实现 ──► ⑤ 测试验证 ──► ⑥ 部署交付 ──► ⑦ 运维迭代
   (01)          (02)           (03/04/05/06)     (按 09)        (07)           (08)          (11)
     │             │                │                │             │              │             │
     └─ 已完成 ────┴─ 已完成 ───────┴─ 已完成 ───────┴─ 已完成 ──┴─ 已完成 ─────┴─ 已完成 ────┘
                                                       (L1–L7)       (自动化)       (exe 已产出)
```

**为什么用"瀑布骨架 + 迭代填充"**：
- 骨架（阶段顺序）用瀑布，因为这是单人项目、需求明确、没有频繁变更压力
- 填充（每个阶段内部）用迭代，因为 L1→L7 每个里程碑都是一次"编码→测试→验收"的小循环
- **不采用敏捷/Scrum**：单人项目，站会、燃尽图都是纯开销

### 2.2 每个里程碑的"完成定义"（Definition of Done）

一个阶段**只有同时满足以下 6 条才算完成**，否则不进入下一阶段：

| # | 检查项 | 判定方式 |
|---|---|---|
| 1 | 代码写完且能跑通 | 按 [07-测试计划](07-测试计划与用例.md) 的验收用例手工/自动跑过 |
| 2 | 该阶段的**验收标准**全部满足 | 逐条对照 [01-需求规格说明书](01-需求规格说明书.md) 的对应条目 |
| 3 | 涉及接口的，[04](04-接口设计文档.md) 已同步更新 | 文档与代码字段一致 |
| 4 | 涉及表结构的，[05](05-数据库设计文档.md) 已同步更新 | 版本化迁移逻辑与 `schema_version` 记录已同步 |
| 5 | 测试用例有对应记录 | 关键路径有自动化测试（pytest / vitest） |
| 6 | 无未记录的"临时绕过" | 临时方案必须写进 [11-风险登记册](11-风险登记册与决策记录.md) |

### 2.3 里程碑与文档的对应关系

> **里程碑编号已从 C1-C7 改为 L1-L7。** 原 C1-C7 是"云端优先"的排法（C1 就要做云 Relay、
> C3 就要买 VPS 与域名）；**2026 年架构调整为"局域网优先、远程留接口"**后，
> 云相关部分整体移到二期 P1，里程碑按"本机就能验证"的顺序重排。
> 对照关系：原 C1（云 Relay + 隧道）→ **二期 P1**；原 C2（索引器 + 缩略图 + 浏览 API）
> → 拆成 **L2 + L3**；原 C3（手机端网页）→ **L4**；原 C4（上传 + 归档）→ **L5**；
> 原 C5（局域网直连 + 双通路）→ **并入 L3**（局域网直连不再是"加速项"而是主通路）；
> 原 C6（打包 + 托盘）→ **L6**；原 C7（测试 + 压测 + 加固）→ **L7**。

### 2.4 版本号与变更管理

- **文档版本**：`vX.Y`，X 为结构性变更（增删章节），Y 为内容修正
- **代码版本**：`v0.1.0` 起步，语义化版本；每个里程碑打一个 tag（`v0.1.0-l1`、`v0.1.0-l2`…）
- **接口版本**：URL 里带 `/api/`，暂不做多版本；破坏性变更必须同时改 [04](04-接口设计文档.md) 并记录到 [11](11-风险登记册与决策记录.md)
- **数据库版本**：以 `schema_version` 表和 `backend/app/db.py` 中的版本化迁移逻辑为准；禁止通过删库重建升级。

## 3. 协作约定（人 + AI）

这个项目由**你（决策 + 验收）** 和 **AI（设计与编码）** 协作完成，因此需要明确分工边界。

### 3.1 职责划分

| 事项 | 谁决定 | 说明 |
|---|---|---|
| 需求与范围变更 | **你** | 加功能/砍功能必须你点头 |
| 架构与技术选型 | AI 提方案，**你确认** | 有多个合理方案时给对比表 |
| 关键参数（路径、配额、阈值） | AI 提议，**你确认** | 如库目录、上传上限、保留策略 |
| 编码实现 | AI | 按 [03](03-详细设计说明书.md)/[04](04-接口设计文档.md) 执行 |
| 是否满足验收标准 | **你** | AI 自测通过 ≠ 验收通过 |
| 购买 VPS / 域名 | **你** | AI 只给建议与部署脚本 |

### 3.2 每轮交互的推荐格式

```
你：提出目标 / 回答问题 / 反馈验收结果
AI：1) 复述理解  2) 给方案（含取舍）  3) 问必要的确认  4) 执行  5) 自测结果  6) 下一步建议
```

### 3.3 AI 执行时的硬约束（不可违反）

1. **不擅自扩大范围** —— 一期只做图片，不碰视频、不引入 ffmpeg
2. **不擅自安装依赖** —— 新增依赖须先说明理由
3. **不删你的文件** —— 任何删除操作只进回收站，且需你确认
4. **不把密钥写进代码** —— 令牌、密码一律走配置文件或环境变量
5. **改表必须给迁移脚本** —— 不允许"删库重建"
6. **写完必须自测** —— 不允许"应该能跑"就交付

## 4. 关键路径与开工顺序

```
L1 ──► L2 ──► L3 ──► L4 ──► L5 ──► L7
                             │        ▲
                             └── L6 ──┘

（二期 P1：云 Relay + 隧道，接在 L3 的传输抽象之上）
```

- **一期全部可在本机完成，关键路径上没有"必须先花钱"的环节**
  —— 局域网直连不需要 VPS、不需要域名、不需要备案
- **L3 是"技术可行性验证点"**：做完 L3 就能确认"电脑当存储 + 手机浏览器访问"这条路线成立
- **L5 与 L6 可以互换顺序**（打包不依赖上传功能）；**L4 必须先于 L5**
  （上传界面前端依赖配对与时间线的状态管理）
- **P1 依赖 L3 的 `transports/base.py` 抽象**：业务代码已经写成协议无关的
  `Ctx`/`Reply` 中间表示，接隧道时只需新增一个适配器，业务代码零改动
