### 1.2 工期估算说明

估算方法沿用原文：**乐观值 / 悲观值三点估算**，取 `(乐观 + 4×最可能 + 悲观) / 6`。

| 里程碑 | 乐观 | 最可能 | 悲观 | 期望值 | 文档中采用 | 实际状态 |
|---|---|---|---|---|---|---|
| L1 地基（配置/沙箱/DB/协议/中间表示） | 1 | 1.3 | 2.2 | **1.4** | 1.5 天 | ✅ 已完成 |
| L2 索引器 + EXIF + 缩略图 | 1 | 1.2 | 2 | **1.3** | 1.5 天 | ✅ 已完成 |
| L3 浏览 API + 传输层 + 局域网服务 | 1 | 1.5 | 2.5 | **1.6** | 1.5–2 天 | ✅ 已完成 |
| L4 手机端网页 | 2 | 2.5 | 4 | **2.7** | 2–3 天 | ✅ 已完成 |
| L5 分片上传 + 归档 | 2 | 2.5 | 4 | **2.7** | 2–3 天 | ✅ 已完成 |
| L6 打包 + 托盘 + 自启 | 1.2 | 1.6 | 2.5 | **1.7** | 1.5–2 天 | ✅ 已完成 |
| L7 测试 + 压测 + 加固 | 0.8 | 1.2 | 2 | **1.3** | 1–1.5 天 | 🔄 进行中 |
| **一期合计** | | | | **12.7 天** | **10–14 天** | |
| P1 云 Relay + 隧道接入（二期） | 2 | 2.5 | 4 | **2.7** | 2–3 天 | ⬜ 未开始 |

> **原计划里最贵的部分被推走了**：原 C1（云 Relay + 多路复用 + 流控）期望值 2.7 天，
> 是原文档明确写下的"**唯一有真正技术难度的地方**"，悲观值 4 天、超期即触发架构复审。
> 改写后它整体变成 P1，一期不再被它阻塞；而它的协议部分（原 C1-2、C1-3）已经以
> `shared/protocol.py` 的形式在 L1 完成，不需要再算进 P1 的工期。
>
> **一期期望值 12.7 天 vs 原计划 15.2 天，差 2.5 天**，来源是三项被移出一期的估算：
> ① 原 C1 的云端实现部分（约 1.9 天，协议部分留下）；
> ② 原 C6-5 云端部署脚本（0.4 天）；
> ③ 原 C7-2/3/4 协议测试 / 断线重连压测 / 2GB 隧道内存验证（约 0.8 天），
> 扣除这三项（3.1 天）后再补回为局域网通路新增的工作量（约 0.6 天，主要是 L3-7 与配对鉴权）。
> **功能范围没有缩减**，移出的全部是"有云才有"的工作。
>
> 为什么 L1/L2/L3 的期望值（合计 4.3 天）明显低于原 C1+C2+C5 的 5.9 天：
> 这三块本身包含原 C2 的全部内容（沙箱 / DB / EXIF / 缩略图 / 索引器 / 浏览 API / 本地服务），
> 只是去掉了原 C1 的云端实现与原 C5 的云端侧改造；而局域网 HTTP 服务端本来就比
> "HTTP + 隧道双通路"更简单——**这是"局域网优先"在估算上的直接体现，不是估算放水**。

### 1.3 缓冲与风险预留

- **不单独留缓冲**，用"悲观值"本身作为缓冲（沿用原文原则）。
- 一期的悲观余量现在集中在 **L4（手机端网页）**——它是唯一无法在本机闭环验证的环节
  （真机、浏览器差异、非安全上下文限制都只能实测）。
- **熔断条款随 C1 一起移到二期**：P1 超过 4 天隧道仍未打通 → 触发架构复审
  （见 [11-风险登记册](11-风险登记册与决策记录.md) R-001）。

#### 缺陷记录：关机时缩略图 worker 永不回收（L7-6）

**怎么发现的**：`scripts/verify_lan_e2e.py` 跑真实库时，功能断言全绿，但末尾报
`FAIL 服务优雅退出`，标准错误刷出 4 条
`Task was destroyed but it is pending!`（`thumb-0`..`thumb-3`）。

**机制（三层叠加）**：
1. `server._shutdown` 用 `asyncio.wait_for(st.thumbs.stop(drain=True), timeout=20.0)`
   **从外面掐超时**；
2. `asyncio.wait_for` 超时会 **cancel 这个协程**；
3. 而 `thumbs.stop()` 把回收写在 `await self.queue.join()` **之后且没有
   `try/finally`** —— 取消让回收整段跳过；同时 `self._running` 已置 `False`，
   于是**第二次 `stop()` 直接 early-return**（`if not self._running: return`），
   worker 与线程池**永远不会被回收**。

**用户可见后果**：托盘退出看起来"卡住了"，用户只能去任务管理器强杀进程，
而强杀会留下 WAL。

**走过的一次弯路**：第一版修法用 `try/finally: await asyncio.shield(...)`。
`shield` **不解决问题** —— `wait_for` 超时后 shield 的内层任务继续跑，但调用方
已走完 `_shutdown` 并让 `asyncio.run` 关闭事件循环，那个还在跑的任务照样被销毁。
**唯一可靠的做法是不让取消发生**：把超时长在函数内部（`drain_timeout` 参数），
超时只停止等待，回收在同一协程里走完。

**修法**：`ThumbEngine.stop(*, drain=False, drain_timeout=None)` 把回收放进
`finally: await self._teardown()`；`_teardown()` 幂等（靠独立的 `_stopped` 标志，
与 `_running` 分开），**先清空队列并平衡 `task_done()`**（worker 被取消后没人再调
`task_done()`，未平衡的计数会让后续任何 `queue.join()` **永久挂起**，表现是
"第二次关机卡死"），再 cancel worker、`gather(return_exceptions=True)`、
`self._pool.shutdown(wait=False, cancel_futures=True)`。`server._shutdown` 改为
`await st.thumbs.stop(drain=True, drain_timeout=20.0)`。

**复现证据**（探针把 `_generate_one` 换成永久阻塞，用外部 `wait_for(0.3)` 复现真实路径）：
```
BUGGY form:  workers after external cancel: 2   _stopped: False   queue size: 3   LEAKED worker tasks: 2
FIXED form:  workers after external cancel: 0   _stopped: True    queue size: 0   LEAKED worker tasks: 0
```

#### 缺陷记录：`--config` 在首次运行时被整个丢掉（L7-6 附带）

**这是"事故 2"的另一半。** 事故 2 修好了 `data_dir` 不跟 `--config` 走的问题，
但 `serve()` 里判定首次运行的那一行仍然是**无参**调用：

```python
if is_first_run():                       # ← 只看全局 CONFIG_PATH
    bootstrap_default_root()             # ← 也用全局 load()/get()
    cfg = get_config()                   # ← 把调用方传进来的 cfg 整个丢掉
```

于是 `--config H:/tmp/x/cfg.json` 指向一份已写好的配置时，程序仍去看默认的
`data/config.json`；默认配置不存在（或 roots 为空）时判定"首次运行"，
随后用**自动探测出来的**配置覆盖掉调用方那份。

**实测后果**：`--config` 指向一个只有 1 张图的临时库，程序却去索引了自动探测到的
真实照片库 `D:\Photos`，并在那份库上 `marked 2000 rows missing`。
用户以为在用 A 配置，实际跑的是 B。

**修法**：三个函数都接受可选的 `cfg` 并尊重它 ——
`is_first_run(cfg)` 有 cfg 时只看 `cfg.roots`；`bootstrap_default_root(cfg)`
就地改 `cfg.raw`、写到**它自己的路径**、就地返回它（并清 `cfg._roots` 缓存，
否则 `cfg.roots` 还是改之前的空列表）；`serve()` 改为
`if is_first_run(cfg): cfg = bootstrap_default_root(cfg)`。

**回归用例（3 条，均在 buggy 代码下实测失败）**：
- `test_is_first_run_honours_given_config`
- `test_bootstrap_writes_to_given_config_not_default`
- `test_serve_does_not_discard_passed_config`（★ AST 检查，禁掉
  `cfg = get_config()` 形状的覆盖赋值）

**同类教训**：本仓库已经栽过三次"检查代码用文本匹配被自己绊倒"
（`check_docs.py` 的正则字面量、`test_server_shutdown_passes_internal_drain_timeout`
的注释、以及本条）。**检查代码结构就用 AST。**

#### 缺陷记录：新克隆的仓库没有前端，`GET /` 返回 404（L7-6 附带）

`frontend/dist/` 被 `.gitignore` 排除（构建产物不入库），所以
`git clone` 之后按 README 直接启动，后端与 API 全部正常，**只有手机打开 `/`
得到 `404 {"error":{"code":"E1004",...}}`**。

**为什么值得记**：这个失败模式很容易被误判成"程序坏了"，而真正的原因只是
少跑了一次构建。后端日志里其实有明确的一行
`未找到前端构建产物（…\frontend\dist），根路径不提供界面`，但用户不一定去看日志。

**修法（文档而非代码）**：README 的"从源码跑"步骤里把

不构建时的具体表现、日志里的那行提示、以及"exe 不需要这一步"。
（**没有**把 dist 提交进仓库：那是构建产物，入库会让每次前端改动都产生巨大 diff，
而且很容易忘记重新构建、提交了一份过期的 dist。）

#### 缺陷记录：测试自身的 Windows 文件占用竞态（L7-6 附带）

全库跑约每 8~10 次出现 1 次
`PermissionError: [WinError 32] 另一个程序正在使用此文件`，
失败在 `test_server.py` 的 `(env.library / row["rel_path"]).unlink()`。

**根因**：`env.library` 里的文件同时被**后台缩略图线程**读取 —— 索引器刚把文件
入队，worker 可能正拿着它生成缩略图（Pillow 打开文件期间 Windows 不允许删除）。
单跑该用例 8 次全过，是典型的并发时序问题，**不是产品缺陷**。

**修法**：新增 `_unlink_settled(path, *, tries=40, delay=0.05)`，`FileNotFoundError`
直接返回（目标已达成）、`PermissionError` 退避重试，耗尽才 `AssertionError`。
两处 `unlink()` 调用点（`test_missing_file_degrades_gracefully`、
`test_missing_file_is_flagged_after_rescan`）都改为调用它。修复后**连续 5 次全库
运行 exit 0**。

#### 缺陷记录：审计日志被实现成三份，且互不一致（L7-8）

**怎么发现的**：做 L7-8「审计日志验证」时，先查真实库的 `audit_log` 表与
`data/audit.log` 文件，发现**同一个动作在两处的数量对不上**：

```
audit_log 表  56 行，全部是 pair
data/audit.log   pair 16 + rescan 2 + delete 1
```

删除与重扫**从未进过索引表**。

**根因**：[02-概要设计](02-概要设计说明书.md) 与 [03-详细设计](03-详细设计说明书.md)
都规定审计日志的唯一实现是 `backend/app/audit.py`，但**这个文件从未被创建**，
写入逻辑被复制成了三份：`handlers/auth.py` 的 `_audit()`、`handlers/browse.py`
的同名函数、`uploads.py` 的 `_audit()`。三份的差异：

| 行为 | `auth._audit` | `browse._audit` | `uploads._audit` |
|---|---|---|---|
| 写 `audit_log` 表 | ✅ | ❌ | ✅ |
| `flush()` + `os.fsync()` | ❌ | ❌ | ✅ |
| `client_id` 落列 | ❌（塞进了 `rel_path`） | ❌ | ❌ |
| 设备名列 | 设备名 | 设备名 | **空串** |

**为什么一直没暴露**：三份实现都用 `except Exception` 把写表失败吞掉（只记 DEBUG）。
"某条记录文件里有、表里没有"完全静默，没有任何报错。

**修法**：新建 `backend/app/audit.py` 作为唯一入口（`record()` / `read_entries()` /
`format_line()` / `parse_line()` / `safe_field()` / 9 个 `ACTION_*` 常量），三处调用点
全部改为调它，删掉两个本地 `_audit`。`record()` 的顺序固定为**先写文件（`O_APPEND`
+ `fsync`）再写表**，文件是主记录、表是索引。

**新增 27 条回归用例**（`backend/tests/test_audit.py`），其中两条做了"退回旧实现"
的验证：

- 把 `record()` 改成只写文件不写表 → **8 条失败**
- 去掉 `os.fsync(fd)` → **1 条失败**（`test_record_actually_fsyncs_to_disk`）

**一条被自己实验推翻的论断（值得记下来）**：我最初把"不 fsync 则进程被强杀会丢
记录"写进了 docstring 与测试。实测把它推翻了 —— `with open(...,"a")` 退出时会关闭
文件，把缓冲区交给内核，进程被强杀时记录**确实幸存**：

```
OLD with-block       exit=7  log_size=  45  survives=True
OLD never-closed     exit=7  log_size=   0  survives=False
NEW os.write+fsync   exit=7  log_size=  45  survives=True
```

fsync 真正防的是**断电 / 系统崩溃**，而那无法在单测里模拟。因此该用例改名为
`test_record_durable_across_abrupt_exit` 并在 docstring 里写明**它证明不了必须
fsync**；"确实调了 fsync"只由 monkeypatch 那条保证。

**遗留局限**：`upload_sessions` 表没有 `client_id` / `device_name` 列，因此**上传
这条审计线索无法回答"哪台手机传的"**。要补得做 schema 迁移，已记在代码注释与
[07-测试计划](07-测试计划与用例.md) §4.7。

  100 KB/s（12 MB，100% 完整）、`0.1 MB/s`（12 MB 经真 uvicorn 全链路，
  `12582912 / 12582912` 完整，云端 RSS 增量 0.0 MB）、以及"消费者停 40 秒"
  这种极端停顿。**这一项曾抓到真缺陷** —— 慢读会在 `CREDIT_WINDOW`（8 MB）
  处被静默截断、HTTP 仍是 200，见 [11] ISSUE-022。未做的是 10 KB/s 量级的
  长时间（小时级）挂测。

**风险**：P1 是二期唯一有真正技术难度的阶段。若超 4 天，停下来复审方案（熔断条款见 §1.3）。

## 9. 与原计划的偏差说明

> 本节回答四个问题：**为什么改**、**改了什么**、**成本与风险怎么变**、**二期还接得上吗**。

### 9.1 为什么改：用户明确要求"先做局域网，给远程连接留接口"

需求原话（用户提出）：**"先做局域网连接，给远程连接留接口"**。

这个要求的实质是把项目的**交付顺序**倒过来：

| 维度 | 原计划（云端优先） | 改写后（局域网优先） |
|---|---|---|
| 第一个能用的版本 | 需要云 + 域名 + 备案流程才能给手机看 | 手机连同一 Wi-Fi 即可 |
| 前置成本 | VPS + 域名，且要在 C3 前就位 | **¥0** |
| 架构验证时机 | 验证"云桥接路线是否成立"（有技术风险） | 验证"照片库 + 浏览 API 是否成立"（无外部依赖） |
| 失败模式 | 隧道踩坑 → 整个项目停摆（原 R-001，🔴 高） | 局域网先跑通，二期再解决外网 |

三条理由（按重要性排序）：

1. **省钱**：一期不需要 VPS、不需要域名、不需要备案，直接归零。
2. **先跑起来**：局域网通路能让"手机看照片"这件事在**没有服务器**的前提下先成立，
   用户当天就能用上；而云端方案要先买机器、配 DNS、部署、签证书才能看到第一张照片。
3. **验证架构**：项目的技术风险集中在"索引 4915 张照片是否够快、缩略图是否够小、浏览 API 是否够顺"，
   而这三件事**与传输通路无关**。先在局域网把业务层验证透，二期接入隧道时
   就只剩"隧道本身"一个变量——这是把不确定性拆开、逐个消灭。

### 9.2 改了什么：里程碑顺序与编号映射

**新顺序**：`L1 地基 → L2 索引与缩略图 → L3 浏览 API 与局域网服务 → L4 手机端网页
→ L5 上传与归档 → L6 打包与托盘 → L7 测试与验收 →（二期）P1 云端隧道 → P2 视频 → P3 E2E 加密`

与原顺序的逐项映射：

| 原编号 | 原内容 | 现归属 | 说明 |
|---|---|---|---|
| C1 | 云 Relay 骨架 + 隧道协议 | **拆成两半** | 协议部分（原 C1-2/C1-3）→ **L1-5/L1-6**；云端实现（C1-1、C1-4~C1-10）→ **P1-1~P1-3、P1-6、P1-7** |
| C2 | 索引器 + 缩略图 + 浏览 API | 拆成 L1 + L2 + L3 | 沙箱/DB → L1；EXIF/缩略图/索引器 → L2；浏览 API/本地服务 → L3 |
| C3 | 手机端网页 | **L4** | 内容基本不变，但删掉"部署到 VPS / 4G 实测"，改为"同 Wi-Fi 实测" |
| C4 | 分片上传 + 归档 | **L5** | 内容不变 |
| C5 | 局域网直连加速 + 双通路 | **升格 + 拆分** | 局域网 HTTP 服务端 → **L3-1/L3-2（一期主干）**；"双通路状态机" → **P1-8/P1-9** |
| C6 | 打包 + 托盘 + 部署 + 向导 | **拆分** | 电脑端打包/托盘/向导/自启 → **L6**；云端部署脚本 → **P1-10** |
| C7 | 测试 + 压测 + 加固 | **拆分** | 安全/集成/冒烟 → **L7**；协议测试/断线重连压测/2GB 隧道内存 → **P1-11** |

**两个最重要的位移**：

- **C1（云 Relay）从"第一个里程碑"变成"二期 P1"**。它原来是根节点、是关键路径的第一环，
  现在是二期开头。相应地，原文档里"C1 超 4 天触发架构复审"的熔断条款也一起移到 P1。
- **C5（局域网直连）从"加速优化"变成"一期主干"**。原文档写它是"可并行或延后"的
  "非关键路径"项（1 天）；改写后局域网 HTTP 服务成为 **L3 的骨干**，
  手机端所有功能都跑在它上面，它不可延后、不可省略。

### 9.5 风险影响

**被完全绕开的风险**：

- **R-001「云桥接技术路线不成立」**（原文档评为 🔴 高，是风险表里唯一"可能让项目无法交付"的一条）：
  改写后一期根本不走云，**这条风险在一期被完全绕开**——它推迟到 P1 才可能发生，
  而届时一期已经是一个可用的产品。这就是"先做局域网"最大的风险收益：
  **把"项目能不能成"与"隧道能不能通"解耦**。
- 连带绕开的还有：R-006（隧道内存撑爆小 VPS）、R-009（国内机房 ICP 备案）、
  R-010（云宕机/到期/跑路）、R-011（运营商 NAT 拦 WebSocket）、R-015（配对码被爆破）、
  R-024（成本超预算）——这些全部是"有云才有"的风险，在一期不适用。

**新增的风险**：

| 编号（建议登记） | 风险 | 等级 | 触发条件 | 应对 |
|---|---|---|---|---|
| **R-030** | **局域网 HTTP 是非安全上下文，PWA 能力受限**：Service Worker 离线缓存、完整 PWA 添加到主屏幕、`navigator.wakeLock` 三条不可用 | 🟡 中 | 手机用 `http://192.168.x.x:8787` 访问 | ① 如实告知，不承诺离线能力；② 上传续传改为**依赖服务端持久化 offset**，不依赖 `wakeLock`；③ `<input capture>` 相机直拍不受影响，核心功能完整；④ 二期上 HTTPS 后这三条自动恢复 |
| **R-031** | **电脑局域网 IP 变动导致手机需重新配对** | 🟢 低 | 路由器 DHCP 重新分配地址；电脑换网 | ① 文档引导做 DHCP 保留（§4.3 第 11 项）；② 首次向导与托盘显示当前访问地址；③ 配对信息可清除后重配 |

> 相比原风险表里"云服务器被入侵可看到明文照片"（R-003，🔴 高），这是一个明显更小的暴露面。

### 9.6 架构是否仍支持二期：三个保证零改动接入的机制

**结论：是的，二期接入云端隧道时，业务代码（handler）零改动。** 依据是三条已经落地的机制：

**① 传输层是可插拔适配器**

- `backend/app/transports/base.py` 定义 `ServerTransport` 协议——把 `Router` 暴露给手机的统一接口；
- `backend/app/transports/local_http.py` 是一期的局域网实现（uvicorn + Range）；
- 二期只需**再写一个适配器** `backend/app/transports/cloud_tunnel.py`：
  把隧道帧还原成 `Ctx`，调用**同一个 Router**，再把 `Reply` 编回帧。
- `backend/app/config.py` 里已经留好开关：`server.transport = "local_http"`，
  注释明确写着"二期加 `relay` 时只需在 `transports/` 注册新适配器"。

**② 全程序唯一路由表**

- `backend/app/routers/__init__.py` 的 `build_router()` 是**唯一**的路由表构造入口。
  两个传输层都调用它，因此**不可能出现"局域网能访问、云端 404"**——
  路由不存在两套，路径语义也不存在两份实现。
- 这一点也体现在原设计里：手机端只知道两个不同的**基址**，路径部分完全相同。

**③ 业务处理函数不依赖 starlette**

- `backend/app/handlers/**` 全目录**不 import starlette**，只接受 `Ctx` 返回 `Reply`
  （文件头注释写明："二期云端隧道复用的正是这些"）。
- 因此从 HTTP 请求到隧道帧的切换，对 handler 是透明的——它看到的数据结构始终是 `Ctx`。

**二期接入的工作量因此收敛为**：写云端 relay + 写一个传输适配器 + 前端加双通路探测。
**业务逻辑（浏览、搜索、上传、归档、缩略图、鉴权）一行不用改。**

> 补充一条一期就已经做对的事：**`shared/protocol.py` 是云端与电脑端共享的同一份物理文件**。
> 二期不会出现"两端各写一份帧编解码"，帧格式不存在漂移的窗口期。
> 该文件一期只被单元测试引用，不进入任何运行时路径，所以"一期不接云端"与"协议已完成"并不矛盾。

### 9.7 一句话总结

**原计划把"最难、最贵、最不可控"的一环（云隧道 + VPS）放在最前面；
改写后把它放到最后，并且让它在被做之前，产品已经可用。**
功能范围没有任何缩减，只是交付顺序从"自外向内"改成"自内向外"。
