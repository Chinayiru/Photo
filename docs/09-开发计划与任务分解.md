## 1. 计划总览

### 1.1 一期总工期

| 项 | 值 |
|---|---|
| 里程碑数 | 7（C1–C7） |
| 总工期 | **12–16 个工作日** |
| 工作模式 | 单人 + AI 协作，非线性（AI 可并行产出） |
| 关键路径 | C1 → C2 → C3 → C4 → C6 → C7 |
| 可并行项 | C5（局域网加速）可与 C4 并行或延后 |
| 阻塞项 | C3 起需要 **VPS + 域名**（C1–C2 完全不需要） |

### 1.2 工期估算说明

估算方法：**乐观值 / 悲观值三点估算**，取 `(乐观 + 4×最可能 + 悲观) / 6`。

| 里程碑 | 乐观 | 最可能 | 悲观 | 期望值 | 文档中采用 |
|---|---|---|---|---|---|
| C1 云 Relay + 隧道协议 | 2 | 2.5 | 4 | **2.7** | 2–3 天 |
| C2 索引器 + 缩略图 + 浏览 API | 1.5 | 2 | 3 | **2.1** | 2 天 |
| C3 手机端网页 | 2 | 2.5 | 4 | **2.7** | 2–3 天 |
| C4 分片上传 + 归档 | 2 | 2.5 | 4 | **2.7** | 2–3 天 |
| C5 局域网直连加速 | 0.5 | 1 | 2 | **1.1** | 1 天 |
| C6 打包 + 部署 + 向导 | 1.5 | 2 | 3 | **2.1** | 2 天 |
| C7 测试 + 压测 + 加固 | 1.5 | 1.5 | 3 | **1.8** | 1–2 天 |
| **合计** | | | | **15.2 天** | **12–16 天** |

> **悲观值为什么这么高**：隧道协议（多路复用 + 流控 + 断线重连）是本项目唯一有真正技术难度的地方，
> 一旦踩坑（如 WebSocket 半包处理、asyncio 与 Pillow 阻塞冲突），返工 1–2 天是常态。

### 1.3 缓冲与风险预留

- **不单独留缓冲**，而是用"悲观值"本身作为缓冲（12–16 天区间的上界 16 天已含约 1 天缓冲）
- 如果 C1 超出 4 天仍未打通隧道 → **触发架构复审**（见 [11-风险登记册](11-风险登记册与决策记录.md) 的"技术路线不成立"风险）

## 2. 里程碑任务分解

### C1 · 云 Relay 骨架 + 隧道协议（2–3 天）

**目标**：本机同时跑"云"和"电脑端"，验证隧道能通、多路复用与流控正确。

| 任务 | 内容 | 产出文件 | 预估 | 依赖 |
|---|---|---|---|---|
| C1-1 | 项目骨架搭建：目录结构、依赖清单、配置加载 | `cloud/relay/*.py`、`requirements.txt` | 0.3 天 | — |
| C1-2 | **帧编解码器**：encode/decode + 流式 FrameParser（处理粘包/半包） | `protocol.py` | 0.5 天 | C1-1 |
| C1-3 | 帧编解码单元测试（含粘包、半包、截断、非法 type） | `tests/test_protocol.py` | 0.3 天 | C1-2 |
| C1-4 | 云端 WebSocket 入口 `/agent/ws` + 设备注册表（内存 map） | `tunnel.py` | 0.5 天 | C1-2 |
| C1-5 | **多路复用器**：req_id 分配、pending 表、超时清理 | `tunnel.py` | 0.5 天 | C1-4 |
| C1-6 | **流控 credit 机制** + 死锁防护 | `tunnel.py` | 0.4 天 | C1-5 |
| C1-7 | 电脑端隧道客户端 + 指数退避重连 + 心跳 | `backend/app/tunnel.py` | 0.5 天 | C1-2 |
| C1-8 | 请求转发路径 `/d/{device_id}/**` + 流式转发 | `relay/main.py` | 0.5 天 | C1-5 |
| C1-9 | 账号、设备注册、配对码 API | `auth.py`、`devices.py`、`pairing.py` | 0.5 天 | C1-1 |
| C1-10 | 回显测试：`curl` 能通过云打到电脑 | 测试脚本 | 0.2 天 | C1-8 |

**验收标准（DoD）**：
- [ ] 本机启动"云"和"电脑端"，`curl http://localhost:8000/d/{dev}/api/system/ping` 返回电脑端的响应
- [ ] 单条隧道上 10 个并发请求互不干扰（多路复用生效）
- [ ] 传输 100 MB 数据时，云端进程内存增量 **< 50 MB**（流控生效）
- [ ] 杀掉电脑端进程后重启，隧道 60 秒内自动恢复
- [ ] 帧编解码单元测试全部通过，覆盖率 ≥ 90%

**风险**：C1 是唯一有真正技术难度的阶段。若超 4 天，停下来复审方案。

## 6. 里程碑检查点（Go / No-Go 决策）

| 检查点 | 时机 | 判断 | 不通过怎么办 |
|---|---|---|---|
| **G1** | C1 完成后 | 隧道能通、多路复用与流控正确？ | 若 C1 超 4 天，复审隧道方案（考虑现成方案 frp/Tailscale） |
| **G2** | C2 完成后 | **架构成立吗？**本机能看到照片墙？ | 若不成立，重新评估架构（可能退回局域网方案或改用现成网盘同步） |
| **G3** | C3 完成后 | 手机 4G 能看照片？首屏 ≤2.5s？ | 若太慢，优化缩略图或升级 VPS 带宽 |
| **G4** | C4 完成后 | 上传可靠？断点续传生效？不覆盖文件？ | 若上传不可靠，重做上传协议（这是数据安全底线，必须过） |
| **G5** | C7 完成后 | 全部验收用例通过？ | 延期修复，不带着严重缺陷交付 |

> **G2 是最重要的检查点**：它决定这个项目要不要继续做下去。

## 8. 计划的调整机制

1. **每完成一个里程碑**，更新本文件的进度跟踪表，并复核后续估算
2. **估算偏差 > 50%** 时，必须分析原因并记录到 [11-风险登记册](11-风险登记册与决策记录.md)
3. **范围变更**（想加功能）必须走：提出 → 评估影响 → 决定是否插入 → 更新 [01-需求规格](01-需求规格说明书.md) 与本文件
4. **不允许**"先做着看"式的隐性范围蔓延——这是单人项目最容易翻车的地方
